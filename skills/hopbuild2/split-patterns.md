# split-patterns（hopbuild2 分拆知识库）

> `split-node.md`/`split-structure.md` 的 doc-ref 被引文件（节标题是切片锚,不可改名）——分拆判定与成文的判据全在此,spec 只留编排骨架。权威=docs/design/hopbuild2.md（^anc-build-split-patterns 等）,本文件是注入投影,冲突以设计为准。

## HOP 全局认知（目标语言与产物是什么）

**NL skill**（自然语言 skill）是你的输入：一份用散文写的任务操作文档——它描述一件事怎么做（先做什么、注意什么、什么样算做好）,通常给 LLM 或人读着照办。散文的问题是纪律靠读者自觉：步骤可以被跳过、审核可以被忽略、重试全凭记性。

**HopSpec** 是你的目标语言：把任务写成**编号步骤树**的规约（markdown 形态）,每个步骤一行 `N. [类型] 一句话描述`,可嵌套子步骤（`N.M.`）。**HopJIT 引擎**逐步执行这份规约——不是人读着办,而是引擎按树逐步驱动,所以纪律由引擎强制而非靠记忆。你的工作就是把前者翻译成后者。

**结构化编程范式**：HopSpec 整体遵循结构化编程——步骤树只允许**顺序**（平铺步骤）、**分支**（branch/case）、**循环**（loop,体内可 break/continue）、**调用**（call）四种控制结构,没有 goto,不允许跳转到任意步骤。执行流只能顺着树走、进容器、出容器——这保证任何一份 spec 的执行路径都能从文本直接读出来。

一份完整 HopSpec 长这样（骨架认知——注意其中的 subtask 探索范式,这是 HopSpec 独有的核心结构;细则见片段语法速查）：

```markdown
# Spec: 标题
Id: spec-id
Goal: 一句话目标
Inputs:
- name: type  # 一句话说明
Outputs:
- name: type  # 一句话说明
## Steps
1. [reason] 一句话任务描述
  - ← 输入变量
  + → 输出变量: type  # 首现标类型 + 一句话说明
  > 执行说明
2. [subtask retry=3] 干一段活、验收达标后提交（探索-验收-提交事务）
  + → 交付物: type  # 本段活的产出
  2.1. [act] 探索段：干活（可安全重做）
    - ← 输入变量
    + → 交付物: type  # 产出
  2.2. [check final] 验收门：判交付物达标与否
    - ← 交付物
    + → ok: bool  # 判定槽
    + → fail_note: text  # 说明槽（不达标的缺口）
  2.3. [commit] 提交段：不可逆动作（发送/落盘）,只在验收通过后执行
    - ← 交付物
    + → done_mark: line  # 提交回执
    > ```hop_python
    > write(path: "deliver.md", content: 交付物)
    > done_mark = "已交付"
    > ```
```

（commit 应当带 hop_python body——发送什么、写到哪在生成期定死,执行期零裁量;参数复杂就前置步骤备好,body 只做最后一调。）

上例第 2 步就是 **subtask 探索范式**（探索 act/reason → 验收 check → 提交 commit,同一事务内）,两条引擎语义支撑它：

- **验收不过自动重跑**：check 判 false 时引擎带着 fail_note 重跑整个 subtask（最多 retry 次）——重试语义引擎自带,不用手写循环;commit 排在 check final 之后,验收不过的轮次走不到它;
- **提交后不再重试**：commit 一旦被执行,所处 subtask 便停止 retry（再失败直接判败,不重跑）——引擎自动避免不可逆动作重复提交,作者不用写任何防重逻辑。

- **步骤类型面**：`reason`（LLM 分析判断）/ `act`（确定性执行:取数/计算/落盘,可安全重做）/ `commit`（不可逆动作:发送/支付/删除）/ `check`（验收判定,固定产出一个 bool 判定值+一个 text 说明）/ `confirm`（人工审批）/ `ask`（向人收集数据）——这六种是**可执行叶子**;`subtask`（一段活的事务容器,可带 retry=N 失败重跑）/ `branch`+`case`（条件分流）/ `loop`（遍历列表）——这三族是**结构容器**;`call`（调用另一份 spec,如函数调用）/ `exit`（当场结束返回）。
- **数据流经声明传递**：每步用 `- ← 变量名` 声明消费哪些上游产出,用 `+ → 变量名: 类型  # 说明` 声明产出什么——引擎按声明喂数据、按声明收产出,没声明的变量步骤看不见。
- **两类步骤的执行面**：LLM 步（reason/check 等）由引擎组装上下文调 LLM;机械步（act/commit/check 带 `hop_python` 代码 body 的）由引擎**直接执行代码,零 LLM**——纯机械动作写成 body 就把不确定性彻底赶出执行期。
- **你产出的 fragment 去哪**：你交付的步骤片段会被机械拼装进一份完整 spec,最终由引擎执行——所以片段必须是合法 HopSpec 语法（有机械 validate 把关）,且语义要与原文等价（有语义 check 把关）。

## 附属文件二分（多文件保真必读）

**alignment-notes.md 在场恒判流程性（跨轮口径传承）**：skill 目录下若有 alignment-notes.md,它是上轮构建时作者在对齐门拍定的修订口径（一条一款带日期与意见原话）——恒判流程性并入构建基准,生成头部契约时当先验对照。错过它=人拍过的板本轮重新犯（实撞:同语料两轮构建,作者拍定五件口径三件复犯——历史审批不自动适用整条丢失/重试口径复抄弱句/防火墙禁令缩水挂角）。

成熟的自然语言 skill 普遍是多文件目录形态：本体文件只做路由与骨架,流程细节、判据清单、数据表住在 references/ 与 scripts/ 里。对这类输入,只翻本体不读引用,产物的把关面就只有本体摘要的粒度——被引文件里的逐阶段门禁全部蒸发（实撞:28 个附属文件共 500KB 的部署 skill,五个阶段收成一条自由执行步,每阶段的退出门禁一个都没落）。

**二分判据一句话**：这段内容错过会导致纪律失守（门禁跳过/闸门蒸发/顺序乱）的是**流程性**,只影响执行细节对错的是**参考性**。

- **流程性**（执行序列、退出门禁、确认闸这类内容）：整件并入构建基准,其中的门禁句/闸门句后续按纪律句翻成显式 check/confirm。**并入基准≠展开进产物**——要拎出来的只是把关句,阶段的操作细节仍留在被引文件里由产物步骤"读它再干";
- **参考性**（数据表/故障库/原始 YAML/脚本用法说明这类查询式内容）：不并入基准,产物步骤写"读 <包内相对路径>"按需取用——硬翻参考性内容进步骤,违"不用一次拆太细"的粒度原则;
- **混合**（同一文件两种成分并存——主体是参考性字段表,尾部却有一节退出门禁）：按其中最严内容处置,整件并入基准;参考性主体在产物里仍按路径按需读,两不冲突;
- **未引用**（本体没提到但同目录存在的附属,如宿主 agent 的配置件）：不进翻译不进包,记台账呈终审由人裁——它可能是给别的消费者的,翻译者无权替裁;
- **可执行脚本**（scripts/ 下的 .py/.sh/.js）恒参考性：产物步骤按路径调用它,不把代码翻进 spec。脚本的**用法说明**若含门禁句（"退出码非零必须停"）,那段话是流程性——又一例定性对象是内容不是文件。

**方法论类语料**（本体教"怎么做"而没有现成执行流程,"错过会不会导致纪律失守"无从判）：先依 frontmatter 的 quick_start/使用说明立出任务面（如"把方法论应用到具体需求产出方案"）并记研判点台账,二分才有基准——这类语料全程无问人闸门/交付动作是语料本性不是翻丢。

## 节点两型与判定序（你在做什么）

**你的任务**：把一个 **NL 节点**分拆成 **hop node**。NL 节点=一段自然语言任务描述,语义在散文里,引擎无法强制;hop node=HopSpec 步骤,类型已定、输入输出已声明,纪律由引擎强制。整个构建过程就是一棵树上的 NL 节点逐个被消解成 hop node。

**方法是判定序**：对一个 NL 节点,按固定顺序逐个判定它能按哪种结构拆——**顺序 → 分支 → 循环**。每个判定只回答一个问题,首个命中就生效、当场分拆返回;三判全不中即叶子,按内容三档分型落定为探索-核验-提交三件套（含不可逆剥 commit/含闸门剥 ask/其余探索+核验成对——有界浅拆:不做单步认领判定,每个叶子天然带把关;结构判仅前两迭代生效,第 3 迭代起直接落叶）。

**分拆是自上而下逐层收敛的——你只是树上的一层**：每一层只回答"本层分几块、每块是什么",块内细节留给递归（loop 里对每个占位 call 判定器,下层自然摊开）。**不要就地深挖任何一块的内部**——那是抢下层的活,而且你的注意力花在第一块的细节上,后面的块就会被挤出窗口整块丢失（真机实撞:三条计划在手,骨架步扎进第一条写了 9 个具体步骤,第二、三条整段没了,语义关打回重来一轮）。大节点的正确骨架往往薄得出奇——三条计划就是三行占位,这不是偷懒,这正是本层的全部职责。

**未尽原子的落型按内容分,不是一律一种**（落错型会吞工具面或蒸发闸门）：含不可逆动作→探索范式三件套且 commit 剥出单列（[act free] 不得承载提交语义）;含交互闸门→ask/confirm 剥出保留、其余落 [act free];工具与推理混杂→单步 [act free];纯推理→[reason];**做法取决于前序运行时产出、写 spec 时定不了的整段活→[subtask free]**（到步展开——只声明输入/交付契约,children 空,执行到步引擎带运行时数据索计划;展开物强制含 check 禁 commit。与 [act free] 分工:act free=单步执行自由,subtask free=整段规划自由）。反例（实撞）：把"评审执行"（含并行发射 Agent、验证报告、异常处理）落成一句 [reason]——reason 无工具面,执行期什么也干不了。

判定时的共同纪律：

- **"明确"是硬门槛**：判定拿不准就是 false,落到下一个判定,不硬拆——错误的结构化是负资产,诚实的自然语言步骤是合法交付;
- **false 无代价**：你只是判定序的一环,判 false 不是失败——后面还有判定接手,最终未尽原子也是合法交付档。勉强判 true 才有代价;
- **真切分才算命中**：分拆方案必须让范围真变小——至少两个子节点,或单子节点但已当场定型。方案里只剩一个 NL 子节点、范围又和本节点差不多大=零进展（递归会对同一段落无限重拆）,判 false;
- **拆分粒度四条硬规则**（三向互补：1、2 防"切香肠"——横向切太碎,真机实撞:一条 4 行的原文被逐层各切两半,每层都算真切分,5 层只消化一句话,撞递归深度上限 16 实例全灭;3 防"就地深挖"——单层内扎太深,真机实撞:20K 大节点三条计划,骨架步扎进第一条展开 9 步,后两条整段丢失;4 防"纵向过深"——跨层累积拆过头,产物步骤号一路排到四五段,读者跟不动嵌套）：
  1. **一次拆分不超过 5 个子节点**,且在这个范围内**尽可能当场拆到位**——子节点能定型的直接写成步骤,不要切成两半留 NL 等下一层再切;留 NL 占位只给真装不下的大块;
  2. **一个节点能用少于 800 字说清楚的,不再主动拆**——当场把全部子步骤写成成品（探索范式的 act-check-commit 三段这种纪律性拆分照常做,它产生的是定型步骤不是 NL 占位）;实在定型不了的部分直接以自然语言描述落步骤（未尽原子）,不留占位递归。递归一层的成本是固定的（判定+骨架+三检,分钟级）——小节点再递归一层,成本比直接写完它还高;
  3. **大节点骨架只搭框架**：分拆方案多于一条、或某块内容自身就是大段（阶段级/章级）时,骨架里每块恰好落一行——一行定型步骤,或一行 NL 占位;**禁止就地展开任何一块的内部细节**（展开是递归层的活——你多写的每一步都在挤别的块的注意力,还和下层重复干活）。规则 1 的"尽可能当场拆到位"只适用于小块收尾,不适用于大块起步——小的写完别拆,大的搭框架别挖,判据以块的体量为准不赌手感;
  4. **产物嵌套深度不超过 max_depth 层（缺省 3）**：深度按产物里的步骤号段数计——`3` 是 1 层、`3.2` 是 2 层、`3.2.1` 是 3 层,容器与叶子同算。每个分拆节点带着自己的绝对层深（depth,根=1）干活:骨架某行的绝对深度=depth+该行步骤号段数-1,超上限的行会被 split-structure 1.3 深度闸机械打回。到了上限层就当场定型或落自然语言步骤,不再留 NL 占位递归。与前三条的关系:1、2 管横向（一层切几块/小节点别拆）,3 管单层内（大块别就地挖）,本条管纵向累积（层层各自合法也可能叠出五层深的产物）——三向互补;规则 2 的"<800 字禁再拆"在本条之下独立生效,两条闸各拦各的;
- **语义等价**：分拆前后业务语义不变,不添不漏;原文没给的判据/阈值不算缺陷——按最合理推演暂定并记研判点台账,不臆造不打回;
- **header_final 是对齐后的契约,盖过原文**：原文里有、但 header 的 goal/outputs/tools_available 已明确不含的能力（作者在对齐门裁掉的,如"产物不做 PDF 导出"）,**不翻译进产物**——判定与切分时跳过该段,记 log_notes 一条"原文含 X,已按对齐契约裁剪"。原文切片会原样传到每一层,只忠实原文不看契约,被裁掉的能力会在深层节点重新长出来（实撞:对齐门删了 puppeteer 与导出模式,第 3 层子节点按原文又拆出 export_pdf 分支）;
- **reason 步没有工具**：它不能自己读文件、调接口——分析所需的材料必须全部由 `- ←` 输入变量和注入的知识喂进来;需要取数就在它前面加一个 act 步;**成文时对每个 reason 步自查一遍输入面**：描述说"通读/分析/对照 X",输入里就必须有承载 X 内容的变量——只接了路径变量（doc_path）没接内容变量（doc_content）,执行期它拿着一个文件名什么也读不了（实撞:步骤描述"通读待评审文档做五问梳理",输入仅 ← doc_path,内容变量前步已产出却没接进来——整步空转,终检打回）。同理,前序步骤产出的计划/清单类变量,后续消费它的步骤必须真把它接进 `- ←`——产而不用的变量是断链信号（实撞:第 1 段产 round_plan 轮次计划,第 2 段发射步没接它,"分轮"语义整个蒸发）;
- **reason 的输入输出注意大小**：它的全部输入变量和产出都要装进一次 LLM 调用的上下文窗口——不要让一个 reason 吃全文级大变量再产全文级大产出（超窗即截断或失败）。料太大就先拆:前置步骤切片/摘要,reason 只吃它真正要分析的那部分;产出太大同理,分段产出或只产结论与要点;
- **细则章三选一落点,名词提及不算引用**：识别到**定义/判据/模板类段落**（特征:分档定义表、带阈值的公式、评估标准清单、prompt 模板、字段格式规约）时,处置恒三选一——**a) 短判据阈值**（一两句装得下的）**全文内联**进消费步骤的描述或执行说明;**b) 成章细则**（表格、多条定义、整段模板）**抽成产物 spec 的内容章节**（非关键字 `##` 节——引擎对产物 spec 的内容章节全程恒定供给,执行者每一步都读得到,机制权威=核心规范"内容章节:写进文件的就是要供给的";注意它与到步 doc-ref 的差别:内容章节是全程供给,外置文件+doc-ref 才是到步注入——细则是产物自己的知识,选内容章节保产物自包含分发）,消费步骤的说明里点名"按《节名》的判据";**c) 本层装不下的大段**留占位行号（归属形式=并入消费它的条目的行号段,与切段规矩既有措辞同）。**禁止形态=名词串**：把细则压成消费步描述里的一串名词提及。反例（真实实撞）:产物步骤描述写"设计汇聚分析员职能（报告质量三评估标准与低质量降权 0.3、…严重度锚点 1-5、优先级公式 P0-P1-P2、对焦策略）"——而原文有五档判定标准全文与公式阈值（"严重度 4 且 ≥3 个审查员独立指出=P0"）。错误后果:产物独立执行时执行者只见 spec 不见原文,"严重度 4"与"3"的分界等于不存在,优先级判定必然瞎判——名词在、定义失,这些名词等于空气（名词提及不算落点,判据的定义必须能在产物里读出来）。与下方"流程与材料"段的关系:那段管材料"不丢也不拆",本条管"引用怎么落才算不丢";

**流程与材料**（判定前先分清原文里哪些内容参与分拆）：原文内容分两种。**流程**是要执行的动作序列——它规定接下来做什么、按什么先后、产出什么,分拆的对象只有它。**材料**是被动作使用的内容,自己不是动作——规格、示例、模板、清单、背景说明都属此类。分拆时材料**不丢也不拆**：随所属流程步骤的执行说明引用（如"按第X章规范生成"）,执行期整段供给执行者。把材料结构化成步骤树是负资产——参考手册层层是清单、层层可再拆,只会发散不会收敛,产物里也没人"执行"一个色板表。引用的落点形态见上方共同纪律《细则章三选一落点》条——"引用"不等于提个名词,细则的定义内容必须经三选一之一真实落进产物。

实例：

1. "读取文档,分析特征,生成评审报告"——三个动作,流程;
2. "色板如下：主色 #003BFF、副色 #00B7FF…"——被"生成"动作使用的规格,材料;
3. "最佳实践：内容先用 Markdown 写清楚;生成后用浏览器打开预览验证"——前半句是给作者的建议（材料）,后半句藏着一个真验收动作（流程,该切出来做 check）。同一段落两种成分并存时,只把动作切出来。

## 二轮展开（expand 场景）

mixed 产物二轮进构建器时,你（split-node）收到的 `node_source` 是 source.md 的**行号段切片,不是全文**——行号仍是全局号（切片保留 L 前缀,与首轮深层节点收到切片的形态完全一致）。切片范围外的原文引用不扩范围:确需提及范围外内容时按研判点台账记一条,不把范围外的行拉进本节点的翻译面。其余判定序与首轮完全一致——二轮没有任何特殊判定规则,四判、粒度规则、语义等价照旧。

## subtask 探索范式（步骤定型与事务形态）

**subtask 探索范式**是 HopSpec 组织"一段活"的核心形态：把一段活写成 **探索 → 验收 → 提交** 三段,套进一个 `[subtask retry=K]` 事务容器——探索段干活（可重做）,验收段判达标（不达标引擎自动重跑整段）,提交段做不可逆动作（只在验收通过后执行,执行过就不再重试）。步骤定型（每个动作落什么类型）和事务形态（这些步骤怎么组装）是同一件事的两半,本章一起讲。

### 步骤定型：动作落什么类型

- 试错/计算/取数/落盘中间产物 → `act`（可逆,可安全重做;纯机械的带 hop_python body,拆不开的复杂任务标 `[act free]`）;
- 分析/判断/决策 → `reason`（动脑的步骤。它没有工具,不能自己读文件取数——需要的材料必须全部由 `- ←` 输入变量喂进来,缺料就前置一个 act 步先取数）;
- 验证/确保 → `check`（验收判定步。固定产出两个变量:一个 bool 判过没过、一个 text 说明没过在哪——判 false 时引擎自动重跑所在容器,所以它必须放在 subtask 或 case 里）;
- **不可逆动作**（发送/支付/写生产/删除）→ `commit`;
- 人工审批放行 → `confirm`;问人要数据 → `ask`;
- act 与 reason 的分工：**尽可能把推理放进 reason,只把工具操作和外部影响留给 act**——分析、判断、生成内容都归 reason（纯推理本就允许一定的不确定性）;act 只做确定性的取放与计算（带 body,零推理）。工具调用与推理搅在一起、调用时机要看情况定的,才迫不得已保留在 `[act free]` 里——这是兜底形态不是常规选项。

**commit 的判据看原文与约束,不看动词表面**：

- header 约束或原文说"不可修改/撤不回/不可撤销"的动作一律落 commit——写成 act 的后果:它所在容器重试时不可逆动作被重复执行（引擎只对 commit 类型设防重放机制）;
- **交付物写盘（若有）恒 commit**：原文含"保存/写入/发送/落盘"类交付动作的,一律落 commit——覆盖用户文件撤不回（中间产物落涂鸦区才用 act）;
- **原文没有写盘动作,就不要自己加一个**：交付物已经在头部 Outputs 里声明了,执行结束时引擎会把它作为结果返回——不需要写文件也能交付。原文没提"保存/落盘"却加一个写盘步骤,属于杜撰业务步骤,语义审查会打回。

### 事务形态：三段一个 subtask

```
N. [subtask retry=K] <这段活的目标>
  + → <交付变量>: <type>  # 交付物
  N.1. [act/reason] <干活>          ← 探索段（可多步:取数/加工/分析,均可安全重做）
    + → <交付变量>: <type>  # 产出
  N.2. [check final] <验收判据>     ← 验收门（判据来自原文的"必须/确保/达标"句）
    - ← <交付变量>
    + → ok: bool  # 判定槽
    + → note: text  # 说明槽（不过时的缺口——引擎注入重跑轮定向修正）
  N.3. [commit] <提交动作>          ← 提交段（原文有不可逆动作才有本段;没有就到 N.2 为止）
    - ← <交付变量>
```

两条引擎语义支撑：

- **验收不过自动重跑**：check 判 false,引擎带着 note 重跑整个 subtask（最多 retry 次）——重试语义引擎自带,不用手写循环;commit 排在 check final 之后,验收不过的轮次走不到它;
- **提交后不再重试**：commit 一旦执行,所处 subtask 停止 retry（再失败直接判败,不重跑）——引擎自动防重复提交,作者零防重逻辑。

使用要点：

- **识别信号**："核对并确保…"、"验证…后再…"、"质量达标才…"、"不对就重做"——产出+达标要求成对出现的段落;"重复直到/最多 N 次"也是本范式（不是 loop——loop 没有事务语义）;
- **原文没写验收也要补**：含 commit 的段落,其前必须有针对交付物的 check（验收将要提交的东西本身——发送清单前 check 的是清单）,补了记台账——三段序补全不算添业务步骤;真要人拍板的用 confirm;
- **返工语义 retry 自带,check 后不写返工分支**：check false 那一刻引擎已经在重跑整段了——`[check]` 后再接 `[branch]`+`[case(not ok)] 返工…` 是死分支（false 路径根本走不到 branch）,还与 retry 双轨。原文说"不对就返工/重做"→ 落成的就是 retry=K 本身,唯一要写的是 check 的验收判据;
- **接线纪律**：`<交付变量>` 就是该节点对父层承诺的输出——套范式不改变节点的对外 I/O 契约。

反例（每条都是真机踩过的坑）：

- ❌ loop max=N 包一段 + branch 判"是否通过"手搭重试——丢引擎事务语义;
- ❌ check 塞进探索段中间——验收钉在探索之后;
- ❌ 交付变量只在 check 里出现——验收对象须是真产出;
- ❌ check 后接 `[case(not ok)]` 返工分支——死分支,返工归 retry;
- ❌ check 独居 subtask（干活步在事务外）——retry 重跑的只有 check 自己,对同一产物反复判到耗尽,修复回路不存在;"验证并修复 X"=把生成 X 的步骤与 check 同套一个 subtask;生成事务里已有 check final 的,不再包第二道"验证 subtask"重复判同一对象;
- ❌ subtask 头声明的交付变量无子步骤同名产出——只声明没人赋值,运行期恒空。

### 交互闸门与其它定型细则

- **交互闸门**：原文中"执行到这里必须停下来等真人表态才能继续"的点。表态分两种——**给值**（人提供或修正数据）落 `ask`,**放行**（人批准或否决既定方案）落 `confirm`。交互闸门是原文作者刻意设的控制点,**必须逐个落成 ask/confirm 步骤**,落成 reason 就是把"问人"偷换成"机器替人答"——语义蒸发里最重的一种（忠实关必打回）。识别时注意原文的间接写法,实例：①"把数据给店主过目确认,目标可当场改"——直白闸门,ask;②"用 AskUserQuestion 确认风险点与评审模式"——借工具名指代问人,照样是闸门,ask（工具名是原文语境的实现细节,产物里落 ask 步骤即可,不引用该工具名）;③"人工确认模式下,对焦决策须逐条经用户确认后才记录"——模式条款里藏的闸门,confirm;④"分析文档特征,确定定位类型"——纯分析没有人参与,reason,不是闸门（不要把所有"确认/确定"字面都当闸门——主语是执行者自己的判断就是 reason）;
- **require_human 修饰（ask/confirm 通用）**：交互对象是真人、不许 LLM 代答 → 加 `require_human`（原文语境是给真人用的 skill 就加,如 `[ask present_inputs=data require_human] 与用户确认数据`、`[confirm require_human] 请人批准部署清单`）;
- **present_inputs 修饰（ask 专属——confirm 不收,写上即属性总闸 parse 拒〔实撞:构建产物给 confirm 带它,重试七次才过〕）**：原文要求"给人过目/呈给用户看后再定"→ ask 步加 `present_inputs=<要呈的变量>`（引擎强制呈全才能答——不加则驱动方可缩略,人没看清就拍板;多变量逗号紧连**不带空格**:`present_inputs=data,target`——带空格即属性解析炸）;**present_inputs 里的每个变量必须同时声明进该步的 `- ←` 输入**——呈现给人的值是从输入取的,没 ← 声明引擎手里无值可呈,校验 P14 必拒（实撞:兜底成文写 `[ask present_inputs=doc_type_proposal]` 但 ← 没引它,三轮同败同一条 P14——呈现的往往是"本步要人确认的新值",直觉上想不到要先 ← 引入,所以专门立此条:先 ←,再呈）。**confirm 要呈材料给人看不用这个属性**——confirm 停驻时引擎把它 `- ←` 声明的输入值完整呈给人（超长自动走文件卸载）,把要呈的内容声明成输入即可（大材料前置机械 act 读入文本变量再 ← 引入——"备料/提交分离"节的呈清单人批形态就是这个写法）;
- **ask 是"呈现+收值"一体的单步**：原文"把 X 给人过目确认（可当场改）"就是一个 ask——present_inputs 呈 X,产出=确认（或修改）后的值,不拆成"展示步+确认步"复合序（呈现是 ask 的自带面,不是独立动作）;
- **完成检查点一律翻成 check**：原文"完成检查点：…未完成→不得进入下一步"这类字样,是流程闸门——必须落成 check 步骤（产出 ok 判定位,判 false 时靠所在 subtask 的重试语义阻断后续）。把它写成 reason "产出检查记录"是丢闸门：记录没有判定位、也阻断不了控制流,后续步骤照走,"不得进入"成了空话（忠实关必打回。真机实撞:同一份原文两个节点,一个正确落 check final、另一个降级成 reason 被打回——这不是难点是漂移,照本条直译即可）;
- **一步一动作数的是执行动作,不是产出个数**：一次推理给多个结论（"判断达标没有,并给两三条建议"）是**一个 reason 步多个 `+ →` 产出**——判断与建议出自同一次对照分析,拆开反而断料;
- **"当场可定型"判据**（判定步给 split_plan 标类型时用,与叶子分型判据同款从紧）：一步一动作、描述一两句装得下、无内部交互闸门,才许当场标类型。**阶段级段落必标 NL 留占位**——段落内含多个规定子步骤、或含问人/审批闸门、或含并行发射+验证+汇聚这类复合序,标成单个 act/reason 就是把一章压成一行（语义蒸发,忠实关必打回）;标 NL 交给递归,子层自然摊开。

## 微判定把关（目标执行档核验弱档的把关形态）

target_profile 指向核验弱档模型（能力档案 check_judge 为单点核验档）时,判定对象多于约 4 项的把关不写单个大 check——拆三段,把协调工作全部从 LLM 手里拿走,LLM 只出原子事实：

```
N. [act] 机械归组
  - ← <判定对象清单>, <对照基准>
  + → <作业单>: [<作业单元类型>]  # 每单元一件:对象+该对象的对照材料
  > hop_python body 按机械键（行号/编号/类别）把判定对象分组——建框架归程序,零 LLM。

N+1. [loop for-each job in <作业单>, collect <单元结论> into <结论清单>] 逐单元微判定
  N+1.1. [subtask parallel] 判定单个单元
    N+1.1.1. [reason] 单元封闭判定
      - ← job
      + → <单元结论>: <结论类型>  # 自含单元 id（并行乱序靠 id 归位）
      > 只回答一个封闭问题（yes/no + 缺口内容）。判定对象内含多个并列断言时,
      > 用显式核销:先逐条列出断言,每条写"断言 → 覆盖它的条目或'无'",再给结论
      > ——隐式的整体比对在多断言并列时会失焦漏判。禁止评价之外的任何内容。

N+2. [check final] 机械汇总验收
  - ← <结论清单>, <作业单>
  + → ok: bool
  + → note: text
  > hop_python body:全单元通过才 true,缺口清单机械拼装——汇总与门槛归程序,
  > 判官摇摆无处发生。可加假阴性兜底:结论报"缺 X"而 X（归一化后）逐字就在该
  > 单元对照材料里,是机器可裁决的自相矛盾,机械改判不算缺口。
```

三条要点：**小题粒度从紧**（一次一个原子问题;"一行一题"在一行多断言时仍失焦——细到一断言一题,或小题内强制显式核销）;**判定确定性归引擎**（建框架=归组 body、遍历完整性=循环结构、门槛=汇总 body——LLM 换不了框架也摇不了门槛）;**收敛形态自证**（健康的微判定失败恒收敛到具体可修的判据缺口,不是摇摆烧尽）。真机范本=examples/hop-fact-check.qwen3.8-27b.md 的 2.4/2.5/2.6 与 LineJob/LineVerdict 类型对。概念权威=概念层《HopSpec V3扩展-模型变速箱适配》适配方法 1。

## 分支与循环判据

一个完整的分支形态先看全貌（原文"如果工单是退款类,核算金额生成退款单;是投诉类,起草安抚回复;其他转人工"）：

```
1. [reason] 判定工单类型与处理要点
  - ← ticket
  + → ticket_kind: enum(refund, complaint, other)  # 工单类型
2. [branch] 按工单类型分流处理
  + → result: yaml  # 处置结果（统一接口——各 case 同名赋值,下游只认这一个名字）
  2.1. [case(ticket_kind == "refund")] 退款处理
    2.1.1. [reason] 核算应退金额并生成退款单
      - ← ticket
      + → result: yaml  # 退款单
  2.2. [case(ticket_kind == "complaint")] 投诉处理
    2.2.1. [reason] 起草安抚回复
      - ← ticket
      + → result: yaml  # 回复文案
  2.3. [case(else)] 其他转人工
    2.3.1. [act] 组装转人工工单
      - ← ticket
      + → result: yaml  # 转人工记录
      > ```hop_python
      > result = {"action": "escalate", "ticket": ticket}
      > ```
```

要点都在例中：条件是纯表达式（enum 成员裸写）;需要动脑的判断前置成 reason 产出 ticket_kind,branch 按产出分流;三个 case 给同一个 `result` 赋值（统一接口）;else 兜底不穷尽的路径。

**分支（branch+case）命中条件一句话：原文存在互斥的多条路径,就是 branch**。"如果…就…否则…"是分支;"方式一…方式二…"并列可选是分支;"生成新文档 / 修改已有文档"多种任务模式也是分支——**并列多选一就是分支,判定期不问条件现不现成**。

**条件怎么取值是成文期的事,三种技法按序试**：①条件已是现成变量/输入 → case 直接写纯表达式;②模式差异体现在输入形态上（"修改模式才有 existing_doc"）→ 条件即输入判空 `[case(existing_doc)]`/`[case(else)]`,header inputs 收齐模式所需输入（可选输入允许空值）;③前两者都不通 → 先 `[ask]` 收一个 enum 模式值,branch 按它分流（问人取值正是 ask 的本职——"要问人才知道走哪条"恰恰说明这是 ask+branch,不是"不可判"）;要动脑分析才能判的条件 → 前置 reason 产出判定值再分流。case 条件本身仍须纯表达式（比较/and/or/not/字段访问/判空裸真值,禁工具禁裁量）——这是对**写出来的条件**的形态要求,不是对**判定命中**的门槛。有的路径确实不该进产物——比如原文写了"也可以纯手工操作"这种完全不经过引擎的用法。这种路径可以不翻译,但**必须在 log_notes 里写一条"某某路径没有翻译进产物,原因是什么",让作者在终审时看到并决定接不接受**。不许自己悄悄判 false 把它吞掉——作者看不到的裁剪等于没发生过,出了问题没人知道是哪一步丢的。

**循环的判定一句话：重复的模式都是循环,全部纳入 loop 分拆**。（"做X并核验,不合格才重做"的失败重试形态不用在这里操心——判定序里顺序判在前,它已经被切成干活段+验收段收编走了,轮到循环判时见到的重复都是真循环。）两种成文形态：

- **逐条处理（loop for-each）**：有一批同类条目、每条走同一套处理。列表在两处找——原文语义（"每封邮件/逐个文件"）,或 **header inputs 的 `[T]` 列表型输入**：原文说"按 X 生成/处理各部分"而 X 声明为列表型（如 `content_outline: [yaml]` 每页一条）时,"逐项"语义已在输入契约里,判定只扫原文找"每个/逐个"字样会漏掉它（实撞:ppt 大纲逐页生成被判"无现成列表来源"）;
- **重复推进（loop max=N + break）**：流程本身要求做多轮,直到某个条件满足或到轮数上限——"分轮评审直到无新发现""持续监控直到风险降级或满 5 轮""迭代改进最多三轮"。骨架形态:`[loop max=N] 描述` + 体内干活步骤 + `[check]` 判继续条件 + 条件满足支路 `[break]`。轮数上限原文没给就按最合理推演暂定并记 log_notes。



成文规矩：

- **case 是容器,必有子步**（空 case 即 validate S5 error）——命中后要做的动作哪怕只是"把本项计入汇总"也要写成一个子步;**没有动作的路径就不写 case**（branch 未命中自然静默跳过,空 `[case(else)]` 不是兜底是 error）;
- 每个 case=原文一个条件路径;条件不穷尽且下游需要统一接口值时补 `[case(else)]` 给缺省赋值并记台账（else 同样必有子步）;
- 分支公共的前置取数上提为 branch 前的顺序步骤,不复制进各 case;
- 下游要消费分支产出 → branch 头声明统一接口 `+ →`,各 case 同名赋值;
- 判空只用裸真值 `x` 或 `len(x) == 0`（❌ `x != ""`——null 时误入非空分支）。

**条件收集（循环内过滤汇总）标准形**——"每项判定,命中的才计入清单"：判定 reason + branch,命中 case 里一个 act 把本项赋给 collect 单项变量;**未命中轮该槽收 null**（引擎哨兵语义）,循环后一个 act body 滤空得命中清单：

```
1. [loop for-each email in unread_emails, collect judged into judged_list] 逐封判定紧急性
  + → judged_list: [yaml]  # 逐轮槽值列表（未命中轮为 null）
  1.1. [reason] 判断本封是否紧急
    - ← email
    + → is_urgent: bool  # 判定
  1.2. [branch] 紧急的计入汇总
    1.2.1. [case(is_urgent)] 计入
      1.2.1.1. [act] 收集本项
        - ← email
        + → judged: yaml  # collect 单项槽（命中才赋值）
2. [act] 滤出命中项
  - ← judged_list
  + → urgent_emails: [yaml]  # 紧急邮件列表
  > ```hop_python
  > urgent_emails = [x for x in judged_list if x]
  > ```
```

**循环（loop for-each）命中条件**："每个/逐个/遍历所有"且**条目可枚举**（列表存在或可由前置取数步产出）。成文规矩：

- 遍历列表须 `[T]` 型;来源不明先补取数步骤;
- 限定词（"所有/未处理的/本周的"）落到**列表来源**,不落体内自行过滤;
- 体内产出要汇总 → `collect <单项> into <列表>` 两个名字两个变量;循环体只写单项份内事,跨项汇总归收齐后的串行步骤。

## hop_python 降格判据

**可降**：节点动作是纯机械计算/取放/判定——读写文件、拼接、字段提取、比阈值、判空、调已声明工具,零推理零裁量。**不可降**：含分析判断/生成措辞/语义裁量（reason 恒不降——动脑步无 body）。

写 body 的规矩：

- 可调面三部分：白名单内置函数（len/split/strip/str/…与 Python 同名）+ **引擎内置文件工具组（read/write/edit_file/search_file/exists/move 等十一件,恒可用——文件读写复制这类活写 body 就靠它,全表见"hop_python 文法速查"）** + header_final.tools_available 已声明工具;
- 中间产物路径一律 `work_zone_path("名")` 取引擎涂鸦区绝对路径——**不写相对 `work_zone/…`**（会落到用户工作区且父目录缺失即炸）;
- 禁循环语句（列表推导 `[expr for x in xs]` 可用）;禁未定义名;
- check 也可以带 body 做纯机械判定——直接给两个输出变量赋值：`ok = <条件>` 和 `note = "" if ok else "<不达标说明>"`;
- **body 必须给每个 `+ →` 赋值**：声明四个产出就赋四个（漏赋的产出运行期为空,下游断料）——body 装不下就少声明或不带 body;
- **语义等价终审**：body 每一行对得上原文动作,无添漏——写完对读一遍,不等价就撤销降格（诚实的 NL 步骤好过错误的 body）;
- **禁假 body（值来源必须真实）**：body 里每个输出变量的值必须来自真实计算（对输入变量的运算）或真实工具调用——**把任务描述赋成字符串字面量、凑一个假状态对象,都是假 body**。反例（实撞,比 NL 占位更恶劣——占位诚实说"没做",假 body 谎称"做了",假数据直接流给下游）：

```hop_python
# ❌ 假 body:步骤声称调 WebSearch,body 却只是把任务描述赋给输出——零工具零推理,产出假数据
industry_findings = "行业实践对标结果（需WebSearch搜索至少2个关键词）"
# ❌ 假 body:凑一个假状态对象冒充"已发射"
reviewer_reports = {"status": "launched", "plan": round_plan}
```

  判据一句话：**遮住步骤描述只看 body,它真的做了那件事吗?** 做不到（工具时机/次数要看现场）就不要 body——落 `[act free]` 承认现状,这正是 free 档存在的意义。

## 骨架成文纪律（占位/编号/裸片段直出）

**多路径 skill 的 Outputs 拿每条完成路径反验（hopissues/0084 实撞——Outputs 变量只在 branch 一臂产出,validate 全绿,用户跑另一臂运行时完备闸 failed;引擎已补条件产出静态 warn 第三档,翻译教学是前手闸）**：按条件路由、不同分支交付不同产物的 skill,默认拆 call 子 spec、各交付链自带本路径 Outputs;共享顶层 Outputs 只收每条完成路径都真产出的变量——头部定稿前逐条完成路径走一遍问"这条路走完,Outputs 每个变量都有值吗",答不上的变量下放子 spec 或在缺产出路径补赋值。

**输入材料的形状不可臆测（hopissues/0086 实撞——原文说输入是"a profile list",翻译字面理解成文件顶层是 JSON 列表并声明 `[yaml]`;真实文件顶层是对象 `{schema_version, entities:[…]}`,运行时对象赋列表类型确定性 SCHEMA_MISMATCH,run 死在读取步）**：翻译带结构化输入文件（JSON/YAML/CSV）的 skill 时,解析步骤的类型声明按**真实材料**顶层形状定——包里带样例文件就读一眼（顶层对象还是列表、字段名叫什么）;无样例不硬声明,在读取步说明里写明形状假设、留给对齐门确认。原文的描述性措辞（"一份清单"）说的是业务语义不是文件顶层结构——列表语义完全可能装在对象的某个字段里。

**数值/阈值/枚举/分支条件禁改写禁软化（整卷审计实锤:原文「80%/90% 资源阈值」在产物软化成「达标」;控制面副本门禁原文分集群 3/单点 1 两支,产物只留集群支——单点场景照此门禁必误判）**：原文里的数字（百分比/份数/版本号/时间量/枚举值）与按条件分支的取值,翻译时原样进产物——产物文字装不下就原文附注（如「阈值见原文 L 行号」）;把数值改写成定性形容词（「达标」「足够」）或丢掉条件分支,都是保真缺陷,合理关数值对账子面会抓。

- **裸步骤序列直出**：值首字符即 `1`,不加 ``` 围栏、不加键前缀（如 `skeleton:`）、不写前言后语——下游机械验证与拼装按裸片段消费,任何包裹都是污染;
- **编号相对从 1 起**：片段是子树,顶层步骤号恒为 `1.`、`2.`、`3.`——**不沿父层骨架的号续编**（parent_context 里看到 `3.2` 不等于你从 `3.2.1` 写起;写 `1.1` 起头=解析拒"parent 不存在"）;全文编号由拼装工具按树位置机械重刷,你不管全局号;
- **"待展开——"是机器识别的占位标记,不是描述风格**——先立定义再讲格式：整棵体系里这个前缀只有一个含义"**此步没写完,等递归来展开**"。机械关按它计数（小节点带它=直接拒）、拼装按它定位、终检按它扫残留。**定型步骤（IO 声明齐、描述完整、可直接执行）禁止带此前缀**——带了就被机器当占位处理,小节点必拒、大节点白多递归一层（实撞:152 字小节点的骨架首步实为成品〔IO 齐全〕却带着"待展开——"前缀,机械关按占位拒,LLM 认为自己写的就是成品,双方对"什么算占位"判据不一致,六轮各说各话烧尽降档）。**父层骨架里的"待展开"行是父层的占位、不是措辞范本**——你的任务恰恰是把它变成不带该前缀的成品;
- **占位叶子标准形**：`N. [reason] 待展开——<任务描述> ⟦范围: L<起>-L<止>⟧`——拆不完的子节点留占位,**范围标记内嵌在占位行尾,值是原文行号段**（原文每行行首都有 `L<数字>:` 全局行号,标记写该占位对应原文的哪些行,如 `⟦范围: L120-L185⟧`;逻辑块不连续时允许多段,用 ` + ` 连接:`⟦范围: L120-L185 + L310-L312⟧`;单独一行写 `L42-L42`）。行号从你面前的 node_source 行首直接读,不要数、不要猜——写错行号段会被机械对账当场打回（漏行/越界都拦）。任务描述写**一句明确范围的概括**,不逐条抄原文动作——动作清单完整躺在行号段所指的原文里,子层按行号拿到的是逐字保真切片,你抄一遍是冗余且会把描述膨胀成小型全文。**不需要另行维护登记清单**——占位清单由后续机械步从骨架扫描提取（步骤号/描述/范围都从占位行上机械切出）,你只需把占位行本身写对这一件事;**下游要消费占位产出的,占位行下一行声明 `+ →`**——该声明是子节点的交付契约（递归展开的子片段必须以同名产出收尾,换名=拼装后下游引用断链）;
- **交付契约优先**：任务描述注明"必须以这些名字交付"的,片段的最终产出步骤必须用那些名字（不自行起名——名字是父层接线的另一半）;
- **片段不写收尾 [exit]**：spec 执行到步骤序列末尾自然结束,交付变量在容器头 `+ →` 声明即返回——片段顶层补一个 `[exit] 返回…` 是冗余,拼装后与父层收尾双份;`[exit]` 只用于 case 内提前返回（"若X直接结束"语义）;
- **不给整个流程套大事务壳**：subtask 只包"产出+达标"段（探索范式的事务语义——check 不过重跑那一段）;把全流程包进一个 `[subtask retry=N]` 是冗余嵌套（任何一环出错整个流程从头重跑,交互步也重问——顶层平铺就是主干形态）;
- **子片段只覆盖本节点范围**：父层骨架已有的步骤（验收/存档/返回）不在子片段里重写——sub_source 只含本子节点那段原文,照它成文;越范围重写=拼装后步骤双份;
- **变量选真名**：上游变量从 parent_context 的可用变量清单里选,清单外的名字不许引（header_final.inputs 除外）——凭任务描述造名=跨节点断链;
- **内置类型名是全局保留字,不得作变量名**：`prompt`/`text`/`yaml`/`line`/`markdown`/`bool`/`int`/`float`/`number` 这些类型词不能用来命名变量——`+ → prompt: text` 必被机械核拒（V2:类型词与变量在部分语法位同槽,静默错读）。要装提示词内容就叫 `prompt_text`/`agent_prompt`,装正文就叫 `body_text`——名字里带类型词没问题,整个名字恰好是类型词才违规（实撞:审查员模板节点声明 `+ → prompt: text`,V2 拒后改名重过,白烧一轮）;
- **交付变量是产出不是输入**：头部 Outputs 里声明的交付变量（最终要交付的名字）,在步骤里用 `+ →` 产出它,**不要写进 `- ←`**——它还没被造出来,当输入引用必报"未定义变量"（真机实撞:深层骨架把顶层交付名写进 ←,三轮重试同错耗尽）;
- **parent_context 双侧同一格式**（产出侧组装=消费侧解读）：第一段=本层骨架全文;第二段=可用变量清单,按行 `名字: 类型  # 说明`（本层各步 `+ →` 全列,含 header_final.inputs）——组装 sub_context 时照此格式,子调用才解读得动;
- **新输出必带说明**：每个 `+ →` 首现带 `# 一句话说明`——名字+说明是写给后继执行 LLM 的接口文档;
- **带 body 的步骤,body 必须给每个 `+ →` 赋值**（声明两个产出就赋两行;装不下就把多余产出挪成独立步骤——漏赋的产出运行期为空,下游断料）;
- **每步 `- ←` 只吃它真消费的变量**（步骤"解析 X"就 ← X 的来源变量——接错料执行 LLM 对着无关输入干活,产出必跑偏）;
- **列表型输出没有内容时,交付空列表 `[]`,绝不交付 null**。声明为 `[line]`/`[yaml]` 的产出（如 log_notes）,本轮恰好没有条目是常态——这时输出 `"log_notes": []`,不是 `"log_notes": null`,也不是省略该字段。引擎把 null 和缺字段都判作"声明的输出未产出",整步作废重来（真机实撞:骨架步因两个列表输出连交三轮 null,算子级重试全部烧尽,整步失败——内容全对,就败在空值形态上）。

## hop_python 文法速查（写 body 必读）

hop_python 是 act/commit/check 步骤 body 的语言——受限 Python 子集,引擎直接解释执行,**执行期零 LLM**。本节是它的完整能力面：能做什么、能调什么、什么活该写 body。

### 能做四类事（白名单即能力边界）

1. **基础运算**：算术 `+ - * / % // **`、字符串拼接、比较 `== != < >`、布尔 `and/or/not`、成员测试 `in`、字段取 `obj.field`、下标（含负数）、切片 `seq[start:stop]`（端点可省可负，钳位宽容；无步长形态，反转用 `reversed`）、字面量构造 `[1, x]` / `{"k": v}`、f-string `f"共{n}条"`;
2. **白名单调用**：内置纯函数（下节全表）+ 工具（再下节）——白名单外的任何调用都非法;
3. **赋值**：局部变量与 `+ →` 输出——**body 必须给每个 `+ →` 赋值**（声明四个产出就赋四个,漏赋的产出运行期为空,下游断料;body 装不下就少声明或不带 body）;
4. **确定性分支**：`if cond:`/`elif`/`else:`（Python 同款缩进块）与条件表达式 `x = a if c else b`——只是算个值的分支塌进 body,影响后续步骤走向的分叉才升 branch。

### 内置纯函数（全量,与 Python 同名同义,一律裸名调用）

- **字符串**：`split(s, sep)` / `join(xs, sep)` / `strip(s)` / `lower(s)` / `upper(s)` / `replace(s, old, new)` / `startswith(s, p)` / `endswith(s, p)` / `strip_fence(s, key?)`（剥 markdown 代码围栏取正文;第二参 key 可选——给出且剥壳后首行恰为 `key:`/`key: |` 时连键前缀与其引入的缩进一并剥,LLM 产出带 `draft_fragment: |` 这类自标记键前缀时用双参形态）;
- **列表与聚合**：`len(x)` / `count(xs)` / `sorted(xs)` / `reversed(xs)` / `range(n)` / `any(xs)` / `all(xs)` / `sum(xs)` / `min(...)` / `max(...)`;
- **字典**：`keys(d)` / `values(d)` / `get(d, k, 默认值?)`;
- **数值与转换**：`int(x)` / `float(x)` / `str(x)` / `bool(x)` / `round(x, n?)` / `abs(x)`;
- **解析与路径**：`parse_json(s)`（JSON 文本转结构,配合 LLM 产出的文本解析）/ `work_zone_path("文件名")`（引擎涂鸦区绝对路径,中间产物一律放这——**不写相对路径 `work_zone/…`**,会落到用户工作区且父目录缺失即炸）/ `now()` / `today()`。**workspace 持久路径一律相对写法,不以 `/` 开头**——原文里 `/名字/` 式的"库根"记号（如 `/DocReviewers/领域/`）翻译时去掉前导斜杠写 `DocReviewers/领域/`：以 `/` 开头是系统绝对路径,工具面直接拒（实撞:构建产物照抄原文 21 处 `/DocReviewers/...`,首次真机 makedirs 一击即拒）。

### subprocess.run（命令行调用——原文里的 shell 命令翻译到这,别落 free 别漏译）

原文写了"跑 `git diff`""执行 `npx vitest run`"这类**确定的命令行**时,body 里直接用 `subprocess.run` 翻译——它是内置（hop_python 唯一的 `x.y(...)` 形态名）,不需要 tools_available 声明。命令确定却落 `[act free]` 是降档（free 是"签名写不出来"的兜底,命令行的签名明明写得出来）;整个跳过不译是漏译。

```hop_python
# ✅ 命令与参数一个列表,一个参数一个元素;结果是结构体,字段名同 Python
r = subprocess.run(["git", "diff", "--stat"])
ok = r.returncode == 0
hits = r.stdout
```

四条硬边界（写错即拒,不静默）：

- **禁整串命令行**：`subprocess.run("git diff")` 会找一个叫 "git diff" 的命令,必失败——拆成列表;
- **禁 `shell=True` / `check=True`**：shell 走私进来白名单管控全失;HopSpec 无异常机制,失败是值,returncode 的处置写 check 步或分支;
- **只认 `input=` / `timeout=` / `cwd=` 三个具名参数**（timeout 单位秒缺省 60,cwd 缺省本实例 work_zone）;管道 `a | b` 翻成逐段调用——上一段的 `.stdout` 显式喂给下一段的 `input=`;
- **命令名必须在宿主 sandbox 的命令白名单（`runtime.available`）里**,名单空=此能力关死。翻译时不用核名单（那是运行环境的事）,但产物说明里要如实写清依赖哪些命令。

三条翻译期纪律（引擎不拦——漏了是静默错,比上面四条更难被发现）：

- **依赖的命令名写进产物 Config 段的 `requires_commands:` 键**（hopissues/0090）：引擎启动时拿这个声明与宿主白名单对账,缺配置在进任何步骤之前就拦下并指路;但键本身漏写引擎不拦（键缺席零比对——存量 spec 零破坏的另一面）,漏写=用户退回运行期撞墙,所以写键是翻译纪律不是引擎强制。

- **原文 `source <文件>` 注环境变量的套路必须显化断桥**（hopissues/0090 P4）：subprocess.run 不传环境变量,原文靠 `source env.sh` 灌变量给后续命令的,直接照搬=子进程读空值、失败发生在下游脚本深处。翻译时在产物部署前提说明里显化"某某命令运行期依赖该文件的文件态注入"并列出变量名,桥接约定（命令自读该文件,或宿主部署时保证注入）与用户对齐。
- **原文的祈使命令句是步骤不是散文**（hopissues/0091 实撞:对称同模板一对 stage 只译一边,发布链整挂）："先执行 xxx timer init""写完执行 xxx timer finalize"这类祈使句,argv 完整写得出来就必须译成 subprocess.run 调用步——下游脚本硬消费其副作用的（读它写的文件/字段）漏译=功能蒸发。原文有同模板成对段落时,译完并排对偶核:同一模板位置的命令调用要么都译出要么都不译,只出现在一边的回原文核实。

**宿主命令类不可逆动作的完整模板**（原文的 SSH 擦盘/集群 reset/发布部署这类"跑命令且撤不回"的动作——不可逆语义与命令行载体叠加时的定型）：前置 act 备好参数 → `[check final]` 验收将要提交的东西 → `[commit]` body 里 `subprocess.run` 命令序列**生成期定死**——**逐拍判 returncode**（每跑完一条命令就检查它的 returncode,非零就停下并把失败写进产出值;不检查的话前面失败后面照跑,产出谎报成功）,失败路径写进产出值（如 `"push_failed:" + str(r.returncode)`）——终态可见不静默;依赖的命令名如实写进产物的部署前提说明。**生成期命令序列定不死**（哪台机器、跑什么要看现场）→ 走下方「备料/提交分离」形态+记研判点台账——命令定不死 ≠ commit 步写不出:裁量前移到备料与人批,commit body 仍然静态定死（读人批清单逐条执行）。free 不得承载提交语义的红线不变:能剥出确定命令的部分仍直接剥进 commit。**外部脚本的退出码语义先核再依赖**：best-effort 设计的脚本一切路径都退 0（凭据缺失/HTTP 失败全被记成功）,依赖 returncode 判成败前先看脚本的退出码语义,恒退 0 的改按 stdout 标志判（实撞:webhook 通知脚本恒 exit 0,产物按退出码判 sent/failed,唯一输出必失真）。

**备料/提交分离（命令定不死时的正形）**：不可逆动作的具体命令要看现场（哪台机器/哪些盘/删什么留什么）时,不把整摊活裸落一个 [act free] 再用散文嘱咐「须由 commit 承载」——那样的产物真跑到不可逆处必被引擎拦死（运行期到步展开禁 commit,散文里的提交语义没有任何步骤能合法执行它;实撞:沙箱部署语料的铲除路线整条锁死）。正形三步,裁量全部发生在前两步：

1. `[act free]` **只读发现与备料**——探索现场,生成精确执行清单文件（哪台机器/什么命令/什么顺序/保留项,具体到可机械执行）与证据,写 work_zone;交付 `manifest_path: line`（**大产物走文件不走变量**——清单/证据这类体量件恒落盘,变量只传路径,与修错步 draft_path 同轴）;
2. **呈清单人批两步**：先一个机械 act 读清单入文本变量（`manifest_text = read(path: manifest_path)`——confirm 呈现材料的正道是把内容声明成输入:confirm 停驻时引擎把它 `- ←` 的输入值完整呈给人,超长自动走文件卸载;`present_inputs` 属性是 ask 专属,confirm 不收）,再 `[confirm]` 消费 manifest_text 请人批——原文里「对精确清单明确授权」这类句子翻译时直接落这一步,语义天然同构;
3. `[commit]` **按人批清单执行**——body 生成期定死为代码,清单是人批过的**数据**——执行期零裁量。**执行形态按清单条目数是否生成期已知分两种**（hop_python 没有循环语句,写不出"对动态长度清单逐条 run"）：条目数与形态生成期已知（如恒三条:停服务/删目录/清账）→ 逐条 `subprocess.run` 逐拍判 returncode;**条目数看现场**（备料时才知道删几台机器几块盘）→ 备料步把清单直接落成**可执行脚本**（如 manifest.sh,每行一条命令,`set -e` 逐条失败即停）,confirm 呈脚本内容人批,commit body **消费批过的文本本体而非只拿路径**（`- ← manifest_text`,body 先 `write(path: work_zone_path("approved.sh"), content: manifest_text)` 再 `subprocess.run(["bash", ...])` 执行刚写的这份——执行物即人批内容,"清单是人批过的数据"是血缘事实不是修辞,批完到执行之间盘上原文件被外部改动的窗口整个消失）,判整体退出码——单调执行不是偷懒是文法内的正形。两种形态失败都写进产出值（模板 D 的三件纪律全部适用）。

要点：备料步只探索不提交（act free 里只读发现/staging/清单生成,运行期展开全程 act/check 合法零障碍）;提交半边静态在骨架上（confirm+commit 构建期写死、经终审门人审）。反例对照：把三步压成一个 [act free]+说明里写「删除前须经用户授权、由 commit 承载」=提交语义落散文,引擎强制面为零,mixed 产物该路线结构性跑不通。

**门禁证据分离（降档范围含门禁句时的正形）**：降档进未尽原子的范围里含门禁句（「必须 X 才能 Y」——判定一个前置条件,动作句台账的门禁语汇行就是底册）时,不把门禁整个埋进原子的散文说明——那样门禁从引擎强制的把关步退化成执行者自觉,产物的把关面直接空掉（实撞:整卷 480KB 运维产物,原文约 8 组硬门禁〔逐阶段退出门禁/铲除 17 项验收/PLAY RECAP failed=0〕全落散文,成品 [check] 步数为 0——执行者想跳哪条门禁都没有任何东西拦）。正形两件：

1. **原子契约要求产出结构化门禁证据**——未尽原子的交付物里加一个证据变量（或 work_zone 证据文件+路径变量,体量大恒走文件）,形态:每项检查一条记录（检查名/判定 PASS 或 FAIL/证据路径）——原子内部怎么查、查哪些命令,仍是运行期展开的自由;
2. **骨架补显式 `[check]` 步消费证据判定**——读证据,有 FAIL 或应查项缺席即判 false（引擎强制打回原子重跑）,全 PASS 才放行后继。门禁**判定**由此回到引擎强制,门禁**执行细节**仍留在原子里后延——渐进降档照常,只是把关面不再随降档蒸发。

与「备料/提交分离」同范围叠用（范围既含门禁句又含不可逆动作时）：原子先备料再自查产证据 → 骨架 check 消费证据 → confirm 呈清单人批 → commit 执行——check 站在 confirm/commit 之前,恰是引擎 P8 结构（commit 前必站 check final 或 confirm）的自然形态。

**交互式命令的三分处置（原文的命令会中途停下来问人时）**：原文操作命令有的会中途提问（比如 `kubeadm reset` 问"确认吗？输 y"）。按交互的性质分三种，逐种处置：

1. **机械确认**（命令问的是"确认执行吗"，答案在起跑前就定了）→ 备料脚本里用命令的非交互参数（--force / --yes），没有这类参数的用 expect 预喂应答。为什么可以这样：人的决定已经在 commit 前面的 confirm 停点做过了（人看过并批准了备料脚本），命令自己再问一次是重复上闩，预喂应答是如实反映"确认已经发生"，不是绕开安全；
2. **中途真决策**（决策需要的信息要命令跑到一半才出现——"发现 3 个分区，擦哪个？"）→ 把命令序在决策点拆成两段：前半段做成探索步，把现场信息取出来；中间放 ask 停点请人拍板；后半段做成 commit，拿人的答案当参数执行。不要想着给命令内部开交互通道——ask/confirm 停点就是引擎现成的交互机制，拆开命令序交互就自然回到停点；
3. **原子命令拆不开、中途又真要人判断**（前两种都套不上）→ 目前没有实撞案例。真遇到时如实呈报给用户，不要硬编。

❌ 反例：把 `kubeadm reset` 原样塞进 commit body，运行时命令停在"确认吗？"上等 stdin，subprocess.run 没有应答通道，整步挂死。
✅ 正例：备料脚本里写 `kubeadm reset --force`，脚本全文经 confirm 呈人批过，commit 执行批过的脚本。

**结构性设计意图被简化时必须呈报（对齐门必报项）**：原文对执行结构有设计的（分几轮、什么顺序、后面的做法依赖前面的产出），产物做了简化就必须在对齐门明说，请用户批方向——用户批了才算数。这与"数值禁软化""定义禁名词化""动作禁蒸发"是同一条原则：原文的设计意图不许静默降级。

❌ 反例：原文写"审查员分 2-3 轮上，每轮 1-3 个，后轮根据前轮发现调整重点"，产物直接落成一批全并发+排序记录——结构意图静默丢失，用户从头到尾不知道（doc-review 语料实撞）。
✅ 正例：产物同样落单批并发，但对齐门呈报里写明"原文此处是多轮渐进派发，我简化成了单批并发，理由是各轮执行体同构且轮间只传排序信息——请批方向"；用户不批就外套轮次循环保住原文结构。

### body 里调工具（文件操作就靠这个——"受限子集"不等于做不了文件 IO）

工具用**命名参数**裸名调用：`content = read(path: src_path)`。可调面两部分：

1. **引擎内置文件工具组,恒可用**（不依赖 tools_available 声明,引擎自带兜底）：

| 工具 | 调用形 | 干什么 |
|---|---|---|
| `read` | `c = read(path: p)` 或 `seg = read(path: p, start_line: 10, end_line: 20)` | 读文件返回内容——不带行号参数=全文;带 start_line/end_line 只取那一段（行号 1 起,end 越界自动截到文件尾;工单带 L 行号引用时直接按号取段,不整读） |
| `search_file` | `hits = parse_json(search_file(path: p, pattern: "关键词"))` | 单文件子串搜索,返回命中清单 JSON 文本 `[{line, text}]`（行号 1 起;纯子串不是正则;零命中=空列表不报错）——按关键词定位行号后配 read 行号段取段;edit_file 动手前也可用它自证 old_text 唯一性（命中数即匹配数） |
| `write` | `write(path: p, content: c)` | 写文件（新建或覆盖） |
| `create` | `create(path: p, content: c)` | 排他新建——已存在即失败（并发抢占哨兵用） |
| `append` | `append(path: p, content: c)` | 追加（不存在则创建） |
| `edit_file` | `edit_file(path: p, old_text: o, new_text: n)` | 局部精确替换（old_text 恰匹配一处才替换,零/多匹配报错——改几行不整文件重写）。三种编辑同一原语:替换=改后文本;删除=new_text 空串;插入=old_text 取插入点锚文本、new_text=锚文本+新内容 |
| `exists` | `r = parse_json(exists(path: p))` 后用 `r.exists` | 探测,返回 JSON 文本 `{exists, kind}`——**必须 parse_json 再取 .exists 当条件**;裸值是非空字符串恒真,`read if exists(...) else` 这种写法首轮必炸 ENOENT（实撞）。parse_json 幂等:回传链已解析成对象也照样安全通过 |
| `listdir` | `xs = parse_json(listdir(path: p))` 后按列表用 | 列目录,返回 JSON 文本 `[{name, kind}]`——**同 exists,须 parse_json 再用** |
| `makedirs` | `makedirs(path: p)` | 建目录含中间层,已存在即成功 |
| `move` | `move(from: a, to: b)` | 移动/改名 |
| `remove` | `remove(path: p)` | 删文件（不存在即失败） |

2. **header_final.tools_available 里已声明的外部工具**——同款命名参数调用。标 `requires_commit` 的不可逆工具（发送/支付/写生产库）只有 commit body 能调,act 里调用即拒。

**写域分域（引擎强制,2026-08-28；静态检 B9 2026-09-01 加）**：act 和 check 步骤的 body 只能写 **work_zone**（路径用 `work_zone_path("文件名")` 取——中间产物、草稿、台账都放这里）,写 workspace 其他位置引擎直接拒（WORK_ZONE_ONLY）;**commit 步骤才能写 workspace 任意位置**（交付物落盘,目标路径用相对写法不带前导斜杠）。翻译时的落点判据：这次写盘是中间过程还是最终交付？中间过程 → act 步 + work_zone_path;最终交付 → commit 步 + 真实目标路径。**目录创建也是写盘**——makedirs 持久目录同归 commit（act 步只做只读探测,建目录挪到消费它的 commit body 里 makedirs 幂等先建再写,实撞:act 步建领域目录树被写域闸整步拒）。validate 期就会拦:act/check body 里写盘工具的 path 是字面路径形态直接报 B9 error,不用等真机。

常用组合示例——**复制文件 = read + write 两调**（没有单个 copy 函数;示例是交付写盘,所以在 [commit] 步——act 步同款操作要写 `work_zone_path(...)` 路径）：

```hop_python
tpl = read(path: "ppt-html-template.html")
write(path: target_path, content: tpl)
```

**读-改-写**（如按大纲改 `<title>` 这类文本替换;同上,写真实目标路径的版本属 [commit] 步）：

```hop_python
tpl = read(path: "ppt-html-template.html")
tpl2 = replace(tpl, "<title>演示</title>", "<title>" + page_title + "</title>")
write(path: target_path, content: tpl2)
```

**往共享索引/清单文件写入,禁裸 write 全量覆盖**：原文语义是"更新/登记/追加条目"的文件（总索引、清单、台账——跨次运行持久,别的运行也会写它）,body 用 `append`,或先 `read` 旧内容再拼接后 `write`（读-改-写）;直接 `write` 只装本次内容=把此前所有条目抹掉（实撞:原文明写"每次新增模板后**更新**总索引",body 却 `write(path: DocTree.md, content: 只含本领域的清单)`——第二个领域跑完,第一个领域的索引整段消失）。判别口诀:原文动词是"更新/维护/登记"而文件可能已存在 → append 或读-改-写;原文语义是"生成/输出"一次性交付物 → 裸 write 才对。

### 什么活写 body、什么落 free、什么归 reason（三选一判据）

| 情形 | 落型 | 例 |
|---|---|---|
| 确定性操作,签名写得出来：文件读写/复制/文本替换/拼接/字段提取/按固定参数调已声明工具 | `[act]` + hop_python body（执行期零 LLM） | "复制模板并改标题" → read + replace + write 三行 body |
| 要用哪些工具、什么时机调,得看现场情况才能定 | `[act free]`（兜底档,不带 body） | "在仓库里找到相关配置并修正引用"——找哪些文件需要探索 |
| 纯推理：分析/判断/生成内容,不碰工具不碰外部 | `[reason]` | 从素材归纳评审要点 |

**body 的适用场景**：首轮构建里 body 只出现在 commit 步（不可逆动作必带 body,B7 红线）与骨架单行赋值;叶子探索半边首轮恒 [act free] 不写 body——body 写作归定向优化轮(expand 下钻时按需精化)。本节 body 文法知识服务这两个场景与定向优化轮。（不做"先试 body 再考虑 free"的单步认领判定——60 字节点复制模板实撞的教训:该场景在定向优化轮写 body,首轮粗粒度不烧这个轮次。）

**写 body 时"能写"不等于"硬凑"**（定向优化轮与 commit 场景适用）——判据是"签名写得出来"（工具名/参数/次数在生成期就能定死）,不是"能不能让语法关过"。写不出真签名就老实落 free：**用字面量假赋值凑出来的 body 是假 body**（见上方禁假 body 条）,它能骗过语法关,但产出的是假数据——判据始终是同一条：**body 必须真做那件事**。

### 与真 Python 的差异（负面清单,写错即 parse error）

- **无方法调用**：`strip(s)` 非 `s.strip()`;`split(text, "\n")` 非 `text.split("\n")`;列表追加用拼接 `xs = xs + [item]` 非 `xs.append(item)`;
- **一语句一行,禁跨行**：dict/列表/调用都写在一行内（`stats = {"total": t, "best": b}`——Python 习惯的多行 dict 字面量/多行实参直接 parse error）;**无多重赋值**（`a = b = expr` 拆两行）;
- **禁 for/while 循环语句**（循环升 loop 步骤）;**列表推导可用**：`[i.name for i in xs]` 与带滤 `[x for x in xs if cond]`（纯映射过滤,嵌套深度≤2——外层过滤+内层聚合谓词合法,如 `[x for x in xs if any([startswith(x, g) for g in gs])]`,三层以上升 loop 步骤;体内可调工具——如 `[read(path: p) for p in files]` 逐件读,但要留意失败面:任一件调用炸整步炸,大批量或可疑路径先探测再读）;
- **对象字面量键**：固定键名加引号 `{"k": v}`;裸名键=变量引用（未定义会被静态拦）;
- **判空只用裸真值** `if xs:` 或 `len(xs) == 0`（❌ `x != ""`——null 时误判;❌ `bool(a and b)` 对字符串判在场——bool() 对非空字符串恒 true 判不了空,hopissues/0087 实撞 preflight 确定性失败）;判文件在场用 `parse_json(exists(path: a)).exists`——字符串"空不空"用裸真值问,文件"在不在"用 exists 问。

## HopSpec 片段语法速查（骨架成文必读）

**中文关键词对照**（hop_env_language="zh" 时骨架用中文关键词——中英恒等价,AST 恒英文;权威表在语法参考 §12）：段头 `目标/约束/类型/输入/输出/工具/配置/步骤`,`标识:`≡`Id:`;步骤类型 `推理=reason 探索=act 检查=check 确认=confirm 询问=ask 提交=commit 调用=call 分支=branch 条件=case 子任务=subtask 循环=loop 结束=exit 失败兜底=on fail`;属性 `重试=retry 上限=max 终检=final 并行=parallel 开放=free 自适应=adaptive 可上升=escalatable 必须真人确认=require_human`;子句 `遍历 x 于 xs`≡`for-each x in xs`,`收集 r 入 rs`≡`collect r into rs`;统配 `[条件(其他)]`≡`[case(else)]`。

步骤行与节点体格式：

```
N. [类型 修饰] 一句话任务描述
  - ← var                        # 输入:只写变量名
  + → var: type  # 一句话说明    # 输出:首现必标类型+说明
  - 工具: 工具名  # 本步用它做什么   # 工具授权:仅 [act free] 步需要,见下条
  > 执行说明
```

**Tools 段声明与环境注册面的 init 对账**：产物 spec 的 Tools 段声明的每个工具,起跑时引擎会对环境注册面逐个对账——**声明了环境里没有注册的工具,run 当场以 INIT_FAILED 拒载**（error 级,报文点名"注册后再跑,或从 Tools 段移除",不是跑到用它那步才失败）。这正是头部契约把拿不准的工具标"待确认"呈人裁定的意义：翻译期只管把原文真实依赖的外部服务如实登记,部署期用户按报文注册或删减——产物说明里如实写清依赖哪些外部工具,让部署方零意外。

**工具授权行（`- 工具:`）——[act free] 步用外部工具时必写**：引擎对无 body 的 act 步按节点声明下发工具面——tools_available 里的外部工具（web_search/发送类这些），[act free] 步不写 `- 工具: 工具名  # 意图` 这一行，执行期该工具就**不在这一步的可用工具面里**，执行 LLM 会因为没有工具而合规空转（不报错、静默产出空结果——业务面最难发现的失效形态）。三条边界：每行恰好一个工具名（两个工具写两行）；只有 [act free] 需要写（带 body 的 act 在 body 里直接调用、不经声明下发；reason 没有工具面，写了会被 validate 拒）；引擎内置文件十一件（read/write/edit_file/search_file 等）零声明恒可用，不用写。位置在 `- ←`/`+ →` 之后、`> 执行说明` 之前。

**call 步骤（调子 spec/工具）与参数映射的拆平规矩**：形态 `N. [call 子specId(子参数名: 父变量名, ...) parallel?] 描述`——括号里是输入映射（左边=子 spec Inputs 声明的参数名,右边=父层变量名或字面量;同名可写裸名）,`+ →` 行是输出映射（`父变量: 子输出名`,同名写裸名）。**映射右侧只认整名变量与字面量——对象字段路径（`item.x`）不进映射**：引擎按整名查父变量,`item.reviewer_prompt` 不是变量名,查不到会被静默跳过,子实例拿 undefined 起跑（validate 期 V12 直接报 error 指路本条）。循环里逐项调子 spec 时,先在循环体内用一个带 body 的 act 步拆平字段,再 call 用平变量：

```
27. [loop for-each item in launch_items, collect receipt into receipts] 逐个派发
  - ← launch_items, doc_text
  + → receipts: [line]
  27.1. [act] 拆本轮材料为平变量
    - ← item
    + → cur_prompt: text  # 指令
    + → cur_dir: line  # 目录
    > ```hop_python
    > cur_prompt = get(item, "reviewer_prompt", "")
    > cur_dir = get(item, "report_dir", "")
    > ```
  27.2. [call reviewer-worker(reviewer_prompt: cur_prompt, review_material: doc_text, report_dir: cur_dir) parallel] 子实例
    + → receipt: report_receipt
```

**callee 位插值形态（晚绑定）**：形态 `N. [call {变量或字段}(映射) parallel?] 描述`——callee 位写花括号插值（如 `[call {job.analyzer_spec}(problem: cur_kind) parallel]`），执行期把表达式求值成 spec Id 再走与静态 Id 完全相同的调用链路。何时用的判据：**生成期能枚举的恒用静态 Id**（正例：固定三份分析 spec 就写三个 call 步骤，每个 callee 写死）；只有"连调哪个子 spec 都要现场定"才用插值（正例：探索步跑完才知道每类问题该配哪份 analyzer——前序步骤产清单、每项含 callee 标识字段，for-each 逐项 call `{item.analyzer_spec}`）。反例与后果：生成期明明能枚举、却图省事写成插值把选择推迟到运行期——validate 期查不了 callee 是否存在、拼错要到执行期才炸，静态可核性白丢。

带机械 body 的 act/commit/check,body 恒为 `> ` 引用行内的 hop_python 围栏（别的写法如 `> hop_python: |` 都不是 body,会被当散文执行说明）：

```
N. [act] 描述
  - ← x
  + → y: text  # 说明
  > ```hop_python
  > y = strip(x)
  > ```
```


### 类型位与修饰

步骤类型共 14 种：reason/act/commit/check/confirm/ask/call（可执行步）+ subtask/loop/branch/case/break/continue/exit（结构步）。修饰跟在类型后面,空格分隔：

- `retry=N`——只有 subtask 和 case 能带（它们是事务边界,失败整块重跑）。loop 不能带 retry;
- `final`——只有 check 能带,含义见下面"check 与 check final"条;
- `require_human`——只有 confirm 和 ask 能带,含义是"必须真人应答,驱动侧不得代答";
- `present_inputs=<变量,变量>`——**只有 ask 能带**（confirm 带它=属性总闸 parse 拒）,含义是"列出的输入变量必须完整呈给人才能作答";列出的每个变量必须同时在该步 `- ←` 声明。confirm 呈材料的写法是把材料声明成 ← 输入,不用此属性;
- `free`——只有 act 能带,写作 `[act free]`：工具操作与推理搅在一起拆不开的自由任务档。free 步不带 body（它的本质就是"写不出确定签名"）。

### check 的输出：一个 bool 判定槽 + 一个 text 说明槽（名字自己起）

check 步骤必须恰好声明两个输出：**一个 bool 型**（判定槽——装"过/不过"）和**一个说明槽**（装"为什么不过/打回清单"——**缺省用 text**;引擎也接受 yaml 型说明槽,那是给结构化缺口上报的高级形态,普通产物用 text 即可）。**槽位看的是类型不是名字**——名字按语义自己起,`types_ok`/`types_note`、`sensible_ok`/`sensible_note`、`ok`/`note` 都合法;正因为按类型定位,改槽名不影响引擎行为,这是设计不是漏检。

正例（名字带语义前缀,推荐——多个 check 的输出互不撞名）：

```
3. [check] 核类型声明合法
  - ← header_text
  + → types_ok: bool  # 判定槽:类型面是否全过
  + → types_note: text  # 说明槽:不过时逐条列问题
```

反例与后果：声明三个输出、或两个都是 text、或漏了说明槽——validate 当场报 P11 error"must declare exactly two outputs: one bool + one text"。**不是**"名字必须叫 ok/note"——那是本速查旧版教错的地方,名字随便起,类型对就行。

### check 与 check final：中途验收 vs 收尾验收

- 裸 `[check]`＝容器**中途**的阶段性验收,后面可以接任何步骤;
- `[check final]`＝容器**收尾**验收——它之后只允许出现 commit/exit/另一个 check final/on fail 块,再接普通步骤（reason/act/ask…）validate 报 C7 error。语义:final 宣告"探索结束,下面只许提交或退出",把探索段和提交段隔开;
- 一个 subtask 通常一个 check final 压轴;commit 前面必须有它（retry 容器里没有把关就 commit,validate 报 P8）。

反例与后果：`[check final]` 后面接了一个 `[act] 继续加工` → C7 error,"final 之后不得再有普通步骤"——要么把加工挪到 final 之前,要么那个 check 本来就不该标 final。

### 高频 validate 规则（写错长什么样）

这些代号会出现在 validate 报错里,每条配"写错的样子",对着改：

- **V1（变量来源）**：每个 `- ← x` 的 x 必须来自某个前序步骤的 `+ →` 或文件头 Inputs。写错的样子:步骤引用了 `- ← doc_content`,但前面没有任何步骤产出过 doc_content、Inputs 里也没有——多半是变量名打错了（前面产的叫 `doc_text`）,或者真忘了加读取步骤;
- **S5（容器必有子步）**：subtask/loop/branch/case 下面必须有缩进的子步骤。写错的样子:`[case(else)] 无需处理` 单独一行没有子步——没有动作的路径就不写 case,branch 未命中自然静默跳过;
- **C6（check 必须在容器内）**：check 不能平铺在顶层,必须在某个 subtask 或 case 里面。写错的样子:顶层直接 `3. [check] 验收`——把它和它守的那几步一起包进一个 subtask;
- **C7（final 收尾）**：见上条"check 与 check final";
- **P8（commit 前须把关）**：带 retry 的容器里,commit 前面必须有 check——否则重试时不可逆动作会被重复执行。写错的样子:`[subtask retry=2]` 里直接 act→commit 两步,没有 check 夹在中间;
- **P11（check 双槽）**：见上条"check 的输出"。

### loop for-each 与 case 条件

- `[loop for-each item in list_var, collect unit into result_list] 描述`——list_var 必须是 `[T]` 列表型;collect 子句两个名字是两个变量：unit 是循环体每轮产出的单项（体内步骤 `+ →` 声明它）,result_list 是收集成的列表（在 **loop 头**的 `+ →` 声明,类型 `[T]`）。写错的样子:collect 的列表在体内声明、或 unit 忘了在体内产出——validate 报 V10;
- `[case(条件表达式)] 描述`——条件是 hop_python 纯表达式（比较/and/or/not/字段访问）,禁工具调用禁赋值。统配 `[case(else)]` 必须放最后。

### 类型面与文件头行格式

- 可用类型：`bool`/`int`/`float`/`line`（单行文本——路径、名字、一句话;number 已除名,数字只有 int/float）/`text`（多行文本）/`markdown`/`yaml`（结构化数据——对象、列表套对象,不是文本）/`[T]`（列表,如 `[line]`/`[yaml]`）/`enum(a,b,c)`（枚举,答案只能是列出的值之一）/`line(非空)`（带非空约束的单行文本——该槽产出必须非空,空串被引擎打回;必须有值的槽才标,业务上可缺的槽用裸 `line` 并在 # 注释写明缺席约定,如「无 → 空串」）。**不自造具名复合类型**（如 `ReviewReport`）——结构化数据一律用 yaml 或 [yaml];
- 文件头 Inputs/Outputs 每行格式 `- 名字: 类型  # 一句话说明`——说明前必须有 `#`。写错的样子:`- doc_path: line 待评审文档路径`（漏 `#`）——"待评审文档路径"被当成类型的一部分,声明失效,引用它的步骤全文 V1 报错。
