## HopSpec 全局知识（语言形状与语义）

**HopSpec** = 把任务流程写成结构化规约的语言;**hopskill** = 用 HopSpec 写成的 skill。翻译后纪律由 **HopJIT 引擎结构化强制**：引擎驱动游标保证遍历不漏（for-each）、check final 是跳不过的验收门、confirm 让引擎暂停等真人、不可逆操作隔离在 commit 且前序必有把关。你翻出的每一行都会被引擎逐步执行——**写的不是文档,是程序**。

一份 HopSpec 的完整形状：

```markdown
# Spec: <标题>
Id: <kebab-case-id>              # 可选,供 call 引用
Goal: <一句话业务目标>
Constraints:                     # 可选,硬约束（常映射为 check final）
- <约束>
Types:                           # 可选,复用复合类型（PascalCase）
- <TypeName>:  # 一句话说明
  - <field>: <type>  # 一句话说明
Inputs:                          # 可选,任务的业务输入
- <name>: <type>  # 一句话说明
Outputs:                         # 可选,交付物契约（exit 必须全部交付）
- <name>: <type>  # 一句话说明

## Steps
N. [Step类型 修饰] 一句话任务描述
  - ← var                        # 输入:只写变量名（类型在源头已声明）
  + → var: type  # 一句话说明    # 输出:首现必标类型+说明
  > 执行说明（角色视角/方法论/约束;可挂 [[知识文件#章节]] doc-ref 注入）
```

**Steps 是结构化编程**——同 Python:只有**顺序**（编号依次执行）、**循环**（loop）、**分支**（branch+case）三种控制结构,加分层编号（`3.1.` 是 `3.` 的子步）表达嵌套,没有 goto 没有跳转。整个流程的形状看缩进与编号就能读出来。

**头部是契约,Steps 是路径**：头部回答"这是个什么任务"（目标/业务输入/承诺的交付物/硬约束）;Steps 每步一个类型——谁动脑（reason）谁动手（act 可逆探索/commit 不可逆提交）谁把关（check 机器核验/confirm 人审）谁问人（ask 收数据/对齐意图）谁委托（call 调另一 spec）谁组织（subtask 事务边界/loop 遍历/branch+case 分支）,加 break/continue/exit 流控。**这就是全部合法步骤类型**——选型细则见「step 类型选型」节,以该节为准,不得凭本句以外的记忆增删类型。

**数据流**：变量经 `- ←`（取）与 `+ →`（放）在步骤间流动,引擎管变量存储。每个 `←` 必须能追到前序某个 `→` 或 Inputs——数据不许凭空出现。

**变量语义与 Python 一致**——就按 Python 函数级作用域理解,零新概念：一份 spec 的一次执行 = 一次函数调用 = 一个扁平命名空间;subtask/loop/branch/case 是控制流块不是作用域——同 Python 的 `for`/`if` 块,块内赋值写的就是函数命名空间里那一个变量,嵌套多少层容器都不变。**同名 = 同一个变量**,不存在『深层写产生局部副本』。

**🔴 新定义变量的 `# 说明` 必选**：每个 `+ →` 首现输出、每个 Inputs/Outputs 声明、Types 的类型名与每个字段,都必须带 `# 一句话说明`,讲清含义/意图。**命名与说明是写给后继执行 LLM 的接口文档**——变量是跨步通信的唯一通道,后继步骤理解一份数据的全部依据就是名字+说明：名字 snake_case、意义明确,避免单个词、避免望名生义;说明救的是下游步骤的判断,不是排版（『# 周营业额,含税』vs『# 金额』）。

**类型**（`+ →` 首现与 Inputs/Outputs/Types 的类型位）：
- 基础值 `bool` / `int` / `float`;
- 文本按用途细分：`line`（单行短文本,路径/标题）/ `text`（多行自由文本）/ `markdown`（结构化文档）;
- `yaml` = **结构化数据**（对象/列表,不是文本）——类型声明的意义是"下游按结构消费它"：这个变量进了变量空间就是对象/列表,body 里直接字段下钻、零手动 parse（怎么消费见「hop_python 小语言」节）。执行期产出怎么格式化是引擎的事（引擎在每步的输出约束里现场教执行 LLM）,翻译者只负责**把类型声明对**——结构化数据错声明成 text,下游就会把它当字符串处置,这才是要防的错;
- **输入材料的形状不可臆测**（hopissues/0086 实撞——原文说输入是"a profile list",翻译器字面理解成"文件顶层是 JSON 列表"、把读取步声明成 `[yaml]`;真实文件顶层是对象 `{schema_version, note, entities:[…]}`,运行时 parse_json 的对象结果赋给列表类型,确定性 SCHEMA_MISMATCH,整个 run 死在读取步）：翻译带结构化输入文件（JSON/YAML/CSV）的 skill 时,解析步骤的类型声明必须按**真实材料**的顶层形状定——skill 包里带样例文件就打开读一眼（顶层是对象还是列表、要取的字段叫什么）;没有样例时不许硬声明,在读取步的说明里写明形状假设并请用户在对齐环节确认。原文的描述性措辞（"一份清单""a list of profiles"）说的是**业务语义**不是**文件顶层结构**——列表语义完全可能装在对象的某个字段里;
- `[T]` 列表——for-each 遍历的对象必须是 `[T]`;
- `enum(v1, v2, …)` 有限值枚举——供 case 条件裸字比较（`risk == high`）;逗号后带不带空格均可（引擎归一为规范形入库）;
- **Types 自定义复合**：文档头 `Types:` 区定义（PascalCase 名+逐字段）,步骤里按名引用、字段点号下钻：

```markdown
Types:
- TicketFinding:  # 单个工单的审查结论
  - ticket_id: line  # 工单编号
  - severity: enum(high, medium, low)  # 严重度
## Steps
1. [reason] 审查工单
  + → finding: TicketFinding  # 本工单的审查结论
2. [branch] 按严重度分流
  2.1. [case(finding.severity == high)] 高危路径
  …
```

**失败与重试**：步骤失败挂结构上,retry 是 subtask/case 独有的**事务边界属性**（普通步骤与 loop 都没有）。**subtask/case 天然内置 retry,缺省 3**——不写 `retry=N` 也会整组重跑 3 次,写了是改次数不是开开关。由此推出 commit 在 retry 容器里的纪律：**commit 前序必须有足够的 check/check final 把关**（『探索→验收→提交』同容器是正统事务形态——重跑发生在验收不过时,那时 commit 还没执行;把关缺位=盲执行不可逆操作,规则 P8 拦）;**commit 执行后所在容器退火**（引擎语义:commit 一旦 done,它的全部祖先容器不再能 retry——之后的失败直接如实上报,引擎不制造 commit 重放。所以 commit 之后的收尾步要稳,那里失败没有重试兜底）;**commit 自身尽可能幂等**（按业务键 upsert 而非无条件 insert——退火管『引擎不重放』,幂等管『崩溃重放不加害』,双保险）。另外别对确定性失败依赖缺省重试（缺凭证/参数错重跑几次都一样,见 retry 反思步）。整组重跑=容器内全部子步从头再走;check 的失败说明（text 槽）由引擎组装成**修正指令区块**注入重跑轮全部子步（打回来源点名+上一轮产出作修改基准+意见原文+累计意见史——确切形态见「失败反馈怎么流转」节）,定向修正非盲重试。retry 耗尽=容器作为一个整体 fail,继续找外层事务边界,顶层无人接住即实例终止。这就是为什么关键验收要放 `subtask + check final`：验收不过就带反馈重跑,过了才放行。

**"重试直到通过"恒写 `subtask retry + check final`,不要自己搭循环**。原文出现"最多试 N 次""不通过就重做""修到达标"时,正确形态就是上面这一种：`[subtask retry=N]` 容器 + 尾部 `[check final]`——检查不过引擎自动整组重跑并注入失败说明,全部机制（次数上限/反馈注入/耗尽升级）引擎自带。用 `loop max=N` 包一段再加 `branch` 判"是否通过"来手搭重试,是最常见的误译：loop 没有事务语义（不整组重跑、无失败注入、check 也不能放 loop 里〔C6 拦〕）,手搭版本比 retry 容器多一倍结构还丢失全部引擎保障。

## 附属文件二分（多文件 skill 第 2 步判据）

多文件 skill（本体只做路由、细节住 references/、scripts/）的附属文件逐个定性,二分判据：**这段内容错过会导致纪律失守（门禁跳过/闸门蒸发/顺序乱）的是流程性,只影响执行细节对错的是参考性**。流程性读进来供翻译消费,参考性登记路径按需读。细则五条：

- **定性对象是内容不是文件**——混合文件（主体是参考性字段表、尾部有一节门禁约束）按其中最严内容处置：整读、门禁句照拎,参考性主体仍留文件按需读;
- **方法论/模式库类语料先立任务面再二分**——"教怎么做"的 skill 本体没有现成执行流程,"错过会不会纪律失守"无从判：先依 frontmatter 的 quick_start/使用说明立出任务面（如"把方法论应用到具体需求产出方案"）记台账,二分才有基准;这类语料全程无 ask/confirm/commit 多半是语料本性（纯知识、非交互、不真执行）不是翻丢,如实写为预期;
- **不在任务面执行路径上的附属文件**不进翻译也不进打包清单,登记台账呈终审由人裁随不随包——含两形态:本体压根没引用的（宿主 agent 配置件）;被引用但引用目的不是执行的（上游作者的自测材料、创作日志——引用它的是说明文字不是执行动作）;
- **参考性文件里的零星门禁短句**（如故障排查文件尾部两条"先在副本上测"）：与已拎门禁语义重叠的并入既有 check 判据不另立步骤,独立不重叠的照拎——处置与粒度记台账。**先分"门禁还是心法"**（同是文件尾部清单,性质可能不同）：有明确"过/不过"判定语义与放行后果的是门禁（拎 check）;"遇到 X 时可以试试 Y"的经验心法是参考知识（留文件 doc-ref 或进 reason 描述,不硬造 check）。**门禁再分"执行时点在不在本任务内"**：门禁的判定动作发生在本任务生命周期内的（"方案出来后核对八项"）照拎成执行期 check;执行时点在任务结束之后的（"上线后要监控回滚窗口""迁移完成后一周内观察慢查询"）**转位为交付物内容要求**——写进产出物的验收判据（"方案里必须含上线后监控项清单"）而不是硬造一个本任务执行不到的 check;
- 哪个文件拿不准归哪类,就把文件名和疑问记进研判点台账,先按更严的一类（流程性）处置继续翻,终审时由作者裁定。

## 多文件与粒度细则（第 4 步硬纪律的完整表述与反例）

翻译中的硬纪律（违反=翻译错误,非风格问题）：

- **交付写盘归 commit**："保存为 xxx/写入文件/发送"这类交付动作必须是 [commit] 步骤且前面有针对交付物的 [check]——act free 不得承载提交语义;往共享索引/清单文件写入用 append 或读-改-写,禁裸覆盖。**"写进真实项目/外部目录"是同一条的高发变体**（TDD 类语料实撞:原文"把测试写进项目的测试目录、把实现写进源码目录"翻成 act free,真跑时首次写盘即被写域闸拒——act 的写域只有 work_zone 涂鸦区,free 不放大权限）：正确形态=act free 在 work_zone 里起草,交付级落盘由 commit 步承载（写域=workspace）;项目目录在 workspace 外的,commit body 走 subprocess.run 命令通道并记部署前提;
- **交互闸门保留**：原文的 AskUserQuestion/人工确认必须落成 ask/confirm 步骤——闸门落成别的类型等于把"问人"偷换成"机器替人答";
- **reason 步没有工具**：描述说"通读/分析 X",输入就必须接 X 的内容变量——只接路径变量执行期空转;前步产出的计划类变量后步必须真消费,产而不用即断链;
- **check 判官零工具面,判料必须经 ← 喂入**（deep-validate 连抓四处的高发病:判据写"读分片文件抽验""核实证据路径真实存在"——判官纯判定不动手,没有 read 没有 exists,按字面执行只能如实拒判,retry 烧尽死在最后的门禁上）：check 要核的材料,要么前置步骤读好经 ← 传入,要么核验下沉 check body（exists/read 引擎直执零 LLM）,要么判据措辞改为对已喂入材料的判定（"清单每行有路径字段且落在约定目录下"——不写"真实存在"）。判据里出现"读/打开/核实存在"这类动手动词,就是这条被违反的信号;
- **对齐后的契约盖过原文**：用户在对齐门裁掉的能力（删掉的工具、砍掉的模式）不翻进产物——原文里还有也不翻,记台账"原文含 X 已按对齐契约裁剪";
- **粒度跟随原文自然结构,不为"结构化"硬拆细**：细节住引用文件的,步骤写"读 <包内相对路径>再执行"是合法形态——拆太细执行慢、构造贵。但**粒度粗不豁免把关**：流程性引用文件里的**门禁句/闸门句必须拎出来翻成显式 [check]/[confirm] 步骤**——操作细节可以留在文件里让执行者读,"过没过门禁"的判定必须由引擎强制。只翻本体不拎门禁,产物的把关面就只剩本体摘要粒度,引擎强制名存实亡。门禁句附带补救动作的复合句（"发现系统性错误后重跑同类全部记录"）：判定半边拎成 check,补救半边优先落 retry 容器回路;容器粒度粗于原文动作粒度时如实记台账,不硬造步骤也不静默丢弃;
- **动作不许蒸发**（粗粒度下最高发的失真形态,逐个自查）：confirm/check 闸门**之后**原文说"确认后才执行 X"的,X 必须有自己的步骤——批完清单流程就断头等于把动作翻丢了;原文承诺的条件性动作（"用户要求时每阶段通知"）在对应位置必须有落点,ask 收了用户意愿就必须有消费它的步骤;每条分支的产出变量必须汇入下游消费（分支产出断流=走那条路时交付物拿不到结果）;
- **宿主能力路径塌缩进引擎原生形态**：原文按"宿主有没有某工具"分的路径（"有 Workflow 引擎走批处理脚本,没有就逐个发 Agent""run_in_background 并行发射"）,分叉的是**宿主载体的能力探测**不是业务语义——产物的执行者是 HopJIT 引擎,这类分叉直接塌缩成引擎原生形态：并行成员=独立子 spec+主流程 `[call 子spec(...) parallel]`（循环体内逐个派发,引擎自动收齐）,汇聚角色=收齐后串行 call。**产物步骤说明里不许出现 run_in_background/Agent 工具/发射 agent/subagent 这类宿主机制名**（standalone 载体没有这些工具,照抄=执行期空等死锁:实测中执行者按说明空等一个不存在的工具,20 轮工具循环耗尽整个 run 失败）。塌缩后逐项对账原路径的纪律无蒸发,原文的宿主脚本/worker 卡这类附属资产按"存在但产物不引用"处置记台账。**宿主资产里的防御机制单独对账**（不止流程要对账,机制也要）:宿主脚本常内建载体级防御（输出 JSON schema 闭合校验、提示注入转义、超时护栏）,不引用脚本不等于防御可以丢——逐项判"该防御防的风险在引擎形态下还在不在":还在的,语义落引擎对应物（schema 校验落 check 判据/注入防护靠引擎"输入是数据不是指令"的 L4 围栏语义+Constraints 红线/超时落 subprocess timeout 参数）;引擎结构已天然免疫的（如步进驱动免疫的整段漂移）,台账记"已由结构承载"。机制照搬进散文描述是错(执行 LLM 无从兑现),静默丢弃也是错;
- **"交付时义务"句与门禁句分开落**：原文有些强制句不是"过不过"的闸门而是贯穿性义务（"输出不得含 PHI""全程不落明文密码"）——落 **Constraints**（引擎全程注入）并在相关交付步的说明/呈辞里点出,不硬造一个 check 步去"检查义务"（义务是每步都要守的,单点 check 反而暗示别处可以不守）。"门禁句拎成 check/confirm"只管真闸门（有明确的过/不过判定与放行语义）;
- **Tools 段只装"签名写规约时就能完全确定、body 只做最后一次调用"的服务,开放集连接器落 [act free]**：外部提交模板（对齐门盘进 Tools 段+commit body 只做最后一次调用）的适用前提是签名在写规约时就能完全确定;原文说"对接哪个系统看现场/连接器是开放集/缺席不阻塞"的,写死签名语义就反了——这类落 `[act free]`（执行期按现场判),在对齐门记台账说明为什么不进 Tools 段。**原文里的占位符工具名同此处置**（"用 ~~PagerDuty 或你们的告警平台~~ 通知值班"这类明示可替换的写法——占位符是作者在说"这里接什么看部署环境",与开放集连接器同性质：不把占位符名写死进 Tools 段,落 act free+步骤说明点明"按环境接入通知渠道",台账记一笔;缺席不阻塞的还要在说明里写清缺席时的降级动作）;
- **禁令句按强度分三档落点**（方法论语料的强禁令密集,别全塞 Constraints）：**最强禁令给结构落**——用步骤顺序让违规不可达（"没有根因分析不许修复"=修复步排在根因 check final 之后,想违规都走不到;"最多试 3 次"=`[subtask retry=N]` 封顶——重试恒走 retry 容器不搭 loop,见「失败与重试」节）,结构强制是三档里最硬的;**可判据化的给 check 判据**——禁令能写成"过/不过"的判定句（"症状修补不算修复"）就进对应 check 的判据清单;**姿态类给 Constraints+步骤说明**——"不装懂""一次只改一处"这类贯穿性行为要求上提 Constraints 全程注入。判档从上往下试:能结构落的不降到判据,能判据化的不降到散文——散文纪律换个地方住,强制就名存实亡;
- **上游生态指针不译入**：原文引用生态里其他 skill 的指针（"参见 superpowers:test-driven-development"这类跨包引用）照译必悬空——不译入,该指针背后的纪律若有本包内落点（既有 check/步骤已承载）就点明承载处,没有就记台账呈裁;指针闭合关会兜住漏网的;
- **方法论语料里"功能被引擎结构替代"的节可不译**：抗压话术、执行纪律自查表这类内容,存在意义是"散文纪律时代靠执行者自我约束"——翻译后同一约束已由引擎结构承载（loop 封顶/阶段门/呈人闸）的,整节不译并记台账"原文 X 节功能已由步骤 Y 结构替代";仍有判据价值的部分（如 Red Flags 清单）保留为 doc-ref 判据注入。哪些替代哪些保留是方法论语料的固有裁量点,逐节记台账呈终审;
- **编号脚本族先核有无独立调用入口,进程内注册遍历的不拆 spec 层 loop**（实例:d01~d15 检测器族看着是"逐个跑"的静态清单遍历,实读代码发现检测器是模块导出形态无独立 CLI,遍历由 registry.js 进程内自动发现承载,原文也只调一条总入口命令）：遍历纪律已被**下层确定性代码**结构承载的,spec 层一步 act+subprocess.run 调总入口即忠实——硬拆 loop 反而是杜撰流程且可能绕过原文的闸门逻辑。判据:逐个脚本看有没有被原文逐个调用（有独立入口且原文逐个调=真遍历落 for-each;进程内注册统一入口=下层已承载,不拆）,判断过程记台账;
- **横切动作抽成子 spec,各落点一行 call**（"每阶段完成发通知"×5 阶段=60 行几乎逐字相同的样板,漏一处即保真缺陷）：原文要求"每个阶段/每处 X 之后都做同一件事"（发通知/记进度/上报状态）,把这件事抽成独立小 spec——输入=各落点不同的那几个参数（阶段名/文案）,内部 commit 带 body+on fail 兜底,**全部步骤带 body 引擎直执零 LLM**（子实例开销只是建目录记状态账,毫秒级,不必担心"杀鸡用牛刀"）;各落点一行 `[call 子spec(phase_name: "P-0", ...)]` 完事。60 行样板变 5 行调用,改通知逻辑只改一处。自查判据不变:横切动作逐落点核对不漏（抽了子 spec 漏写某处 call,和漏抄样板一样是蒸发）。**抽不抽的边界看省不省样板,不看重不重复**：body 只有一两行的重复步骤（如三个阶段各跑一次同一条测试命令）保留原样各写各的——抽成子 spec 后每处落点还是一行 call,行数没省,反倒多一个文件多一层跳转,且这类步骤往往动作相同而语义不同（确认失败/确认通过,check 判据各异）;成段成组的重复（动作连带把关/兜底一起重复,照抄十几行）才抽。**抽了子 spec 就必须把子 spec 文件随产物交付**——引擎的 call 按 spec_id 同目录寻址（`[call extract-batch(...)]` 找的是主 spec 同目录的 `extract-batch.md`）,写了 call 而子 spec 文件不在交付里,执行到 call 步直接 ENOENT,与悬空指针同性质但更隐蔽（call 是步骤标注不是路径引用,合理关的指针闭合核字面上抓不到它——交付前逐个 call 步核同目录有同名 .md,workflow 脚本/worker 角色说明都不是引擎能 init 的 callee,实撞:产物 call 了只存在于 workflows/ 脚本形态的流程,ENOENT）;
- **多轮派发的依赖只在轮次之间,翻成外层轮次 loop+轮内并行**：原文说"分 2-3 轮派审查员、每轮 1-3 个、后轮根据前轮发现差异化设计"时,先把依赖关系理清——**跨轮依赖是合法业务语义**（第二轮看第一轮的发现设计新角色）,**同轮成员必须互相独立**（同批并行发出的成员不可能依赖彼此还没产出的东西——原文若写了同批内依赖,那是原文自身不自洽,记台账呈裁）。正确形态语言里现成:外层 `[loop max=N]` 轮次串行（体内先一个 reason 步"按已有发现设计本轮成员",再轮内 for-each+call parallel 派发）,轮间依赖经变量自然流动。**不要降级成单批全并发**——那会把跨轮差异化这个合法语义丢掉;也不要反过来把同轮成员串行化——同轮独立并行是原文本意。**"差异化"的边界**：后轮的差异化=在既定成员的审查指令上**附加前序发现增补**（角色五要素不动）,不现场发明超出设计清单的新角色——现场造角色会让"成员设计"这个把关点失去意义;原文若明写"按发现新增角色",按原文翻并记台账。

**展开一个节点时**：该节点对应的原文范围是工作边界,已定的上层骨架不重拆不越位;引用上游变量只用已声明的真名（凭任务描述造名=跨节点断链）。某一步内含循环/分支/复合逻辑时先记下待展开,轮到那一层再自然展开——宁可多展开一轮,不一口吐完整棵树。**反馈回路两级**：单节点自查不过,当场重写该节点;自检关/终审不过,按问题清单定向修正涉事节点后重过各关——意见含具体指向就只动所指,不整树重来。

## step 类型选型

（文件骨架/节点体/类型系统见「HopSpec 全局知识」——本节只管**读原文选步骤类型**。）

**叶子步选型**（读原文按动词认）：
+ 分析/判断→`reason`（唯一动脑步。**减法：判断若是确定性计算——核等式/比阈值/对账差值/核数量,判据能写成算式——不进 reason**,用 act/check 带 hop_python body 让引擎算:LLM 判等式会漂移,引擎算零漂移。reason 只装真需要语义理解的判断）
+ 计算/提取/跑脚本→`act`（必无不可逆副作用、可安全重跑;**等式核验/对账/差值计算这类可写成算式的'检查'也是计算**——act 或 check 带 body 机械算产出 gap,别按'检查'字面翻成 reason;拆不开的复杂任务标 `[act free]`——执行者可推理可用工具的自由任务档）
+ 做法取决于前序运行时产出、写 spec 时定不了的整段活→`[subtask free]`（到步展开:只声明输入/交付契约,children 空,执行到步引擎带运行时数据索计划;展开物强制含 check 禁 commit。与 [act free] 分工:act free=单步执行自由,subtask free=整段规划自由）
+ 发送/支付/删除/写生产→`commit`（前序须有把关闸门：confirm 人审/足够 check/环境预授权；retry 容器内合法且是正统形态——『探索→验收→提交』,把关必须在其前〔P8〕;自身尽可能幂等,按业务键 upsert 重放不加害）
+ 验证/确保→`check`（固定输出 bool+text，必在 subtask/case 内；`check final` 必在容器末尾、adaptive 不可跳）
+ 让用户审批→`confirm`（driver 不得替答，reject 全局中止）
+ 问用户要数据、对齐意图→`ask`（`present_inputs` 呈交依据）
+ 调另一流程→`call`（结构化逻辑标准写法 `[call id(子参数: 父变量, 同名裸名)] 描述`——机读全入方括号；**输出收取写法**：call 行下方 `+ → 父变量名: 子spec输出名  # 说明`——冒号左=落进父变量空间的名字,**右边是子 spec 的 Outputs 变量名,不是类型**（与普通输出行 `+ → 名: 类型` 形态一模一样,位置语义却不同——call 行下这个位置写成类型是高发笔误,validate 会因映射不到子 Outputs 报错）。loop 体内的 `[call ... parallel]` **同样要写这行**,且冒号左边的名字就用循环头 collect 点名的单项变量名——收取行给单项变量供值,引擎再逐轮把它聚进 collect 列表(S16/V10 会核"collect 点名的变量有人供给",漏写收取行即 error);不需要的是额外的聚合步骤,收齐由引擎做）

**容器/控制流**（对标 Python：subtask≈带重试的代码块、loop≈for/while、branch+case≈if/elif/else、break/continue/exit 同名同义）：

+ `subtask`——一组有共同边界的步骤+**事务单元**：整组要么走完、要么带反馈整组重跑。`retry=N` 定重跑次数（缺省 3）,`adaptive` 允许失败后重规划步骤（交付契约与 check final 不可改）。关键验收的正统形态就是 `subtask + 尾部 check final`;
+ `loop`——`max=N` 条件循环 / `for-each x in xs, collect r into rs` 列表遍历。loop 自身无 retry（失败单元是单次迭代）,单次迭代要事务性时体内嵌 `[subtask retry=N]`;
+ `branch` + `case`——同层互斥的多条路径。branch 是分流器,**case 是"带准入条件的 subtask"**：除了"条件命中才激活",它的一切能力与 subtask 相同（可 `retry=N`/`adaptive`、体内可放 check/check final、可标 parallel）。写法与规矩：
  - 标准写法 `[case(条件)] 人读描述`——条件是 hop_python 纯表达式（比较/`and/or/not`/算术/字段下钻 `x.y`/`x == None` 探空/`a if c else b`;禁工具调用禁赋值）;
  - **判空只用裸真值 `x` 或 `len(x) == 0`**（对 null/空串/空列表一体安全;❌ `x != ""`——字段为 null 时 `None != ""` 为 True 误入非空分支）;
  - 兜底写 `[case(else)]` 且必在最后;各 case 按声明顺序判条件,第一个命中的执行;
  - **case 自身是容器,不能直接带 body**——哪怕这条分支只做一句机械置值,也要在 case 下立一个 [act] 子步来承载那句 body（case 行直接挂 body 会撞 S5 裸容器与 P4 死代码两条 error）;
  - **下游要消费分支产出时,branch 头声明 `+ →` 统一接口,各 case 用同名 `+ →` 填充**——外层只见 branch 的那个名字,走哪条路都拿得到值（漏了统一接口=走某条路时下游断流）;
+ `break`/`continue`——同 Python,只能在 loop 内;可带目标循环步骤号从内层直接作用外层（`[break 1]` 跳出循环 1,缺省作用最近祖先循环）;
+ `exit`——结束整个 spec,`+ →` 标记交付变量（Outputs 非空时必须全部交付）。

**并发（parallel 属性）**：`parallel` 是**属性不是步骤类型**,可标三种宿主——`subtask` / `call` / `case`,其余步骤标了是文法错误。语义统一：执行到标注步骤即**异步派出**、主线不等它继续走,**所在容器结束前引擎收齐全部派出的活**（容器边界=收齐点）。三形态各一个可抄样例：

**形态一·循环并发**（最常用——一批同类条目并发处理）。单项 `result` 与列表 `results` 两个名字分开声明,引擎按 collect 收齐；**循环头不可标 parallel**（并发是体内步骤的性质）：

```markdown
3. [loop for-each doc in doc_list, collect review into reviews] 逐文档并发审查
  + → reviews: [yaml]  # 全部审查结论（引擎收齐）
  3.1. [subtask parallel] 审查一份文档
    - ← doc
    + → review: yaml  # 本文档的审查结论
    3.1.1. [act free] 读取并审查 doc
      - ← doc
      + → review: yaml
```

**形态二·兄弟并发**（互不相同的几段活同时干——不硬塞进 for-each）。各自具名输出,父容器结束前收齐：

```markdown
2. [subtask] 并发取三路材料
  + → merged: yaml  # 三路汇合结果
  2.1. [subtask parallel] 抓行业报告
    + → industry_notes: yaml  # 行业面材料
  2.2. [subtask parallel] 抓财务数据
    + → finance_notes: yaml  # 财务面材料
  2.3. [reason] 汇合三路（本步不标 parallel——要等前两路收齐才能做,引擎在容器边界收齐后执行）
    - ← industry_notes, finance_notes
    + → merged: yaml
```

**形态三·call 并发**（把独立子 spec 作为子实例并发跑——原文"发 N 个 agent"的正确翻法）。call 步照常写输出收取行,收取名用 collect 点名的单项变量（下例 verdict）——引擎逐轮把它聚进 collect 列表,不需要额外的聚合步骤：

```markdown
4. [loop for-each角色 in reviewer_roles, collect verdict into verdicts] 逐角色并发评审
  + → verdicts: [yaml]  # 各角色判词
  4.1. [call reviewer-worker(role: 角色, material: draft) parallel] 派一个评审子实例
    + → verdict: report  # 收取子 spec 的 report 输出为本轮 verdict
```

**parallel 标注步骤输出禁累加器**（派出去的活无共享空间——`+ → x = 初值` 累加式在并发下是文法错误 S13;汇聚只有收集列表一种语义,reduce 在收齐后的串行步做）。**部分失败=列表变短**：某个并发活失败不拖垮主线,它的元素缺席（不是 null 占位）,收齐后列表短一截——要"全成功才继续"就在收齐后加 check 核数量。

## 高频验证规则（生成后自查，避免 validate error）

**负向探针要选 error 级破坏**（把 check final 改 act 只出 warning,探针白跑一趟）：探针的目的是证明"零 error 是查过不是空转",破坏形态必须选 validate 会报 **error** 的——最稳的几种:输入变量名改坏（V1）/ body 引用未声明变量（B4）/删 commit body（B7）/删 check 的一个输出槽（P11）。P15（doc-ref 指坏）现行引擎口径：文件在场而**章节/键未匹配恒报 error**（R10 实测,教学旧文写"只 warn"已过时）——P15 可以做探针,把章节名改坏即 error 级;文件本身找不到的形态才可能按运行期核降 warn,拿不准就换 V1/B4。改 warning 级形态（步骤类型换个还合法的/retry 数改 0）证明不了报错通道。恒用副本操作,核完删副本原件复验。

> 加粗编号是 `hopjit validate` 报错里的规则码（全 49 条里最常撞的一批）——报错带码,按码来这查怎么改。按主题分组：

**变量与数据链**
- **V1** 步骤 `←` 输入必来自前序 `→` 输出或 `Inputs:` 声明，不能凭空引用。
- **V2** 同名 = 同一变量——再次 `+ → x`（裸名或同型）是合法再赋值，**同名异型才是 error**（扁平命名空间，无块级作用域）。
- **V2 保留字**：语言关键词和内置类型名都不能作变量名。最容易撞的是自然变量名 `outputs`/`inputs`/`steps`/`config`/`goal`/`check`/`in`/`max`/`final`——它们全是段头词/步骤词/属性词。**翻译取名时给变量带上限定词**（`output_files`/`check_result`/`max_retries`）就天然避开；类型名（`text`/`yaml`/`line` 等）同禁。撞闸的报错会列出完整清单。**保留字只禁作变量名——作内置函数调用照常合法**：body 里写 `min(50, len(x))`、`max(a, b)` 都没问题（min/max 在内置纯函数白名单里），别把"禁作变量名"误读成全面禁用。

**循环与并发**
- **V8** for-each 的 listVar 声明必须是列表型 `[T]`。
- **V10** collect 的单项名须有 child 产出（T 型）、列表名须循环头声明（[T] 且元素型匹配）。
- **collect 子句里不写类型**：`collect result into results` 后面**不带** `: [yaml]`——类型声明归循环头的 `+ → results: [yaml]` 行（❌ `collect result into results: [yaml]` 会把 `: [yaml]` 切成未知属性 parse error）。
- **S13** parallel 标注步骤禁带 `= 初值` 的累加器输出。

**输出与类型**
- **B8** `yaml`/`[T]` 声明的输出禁在 body 里赋标量字面量（`cur = ""` 对 `+ → cur: yaml` 是 error）——结构化声明的空态写 `{}` 或 `[]`。

**结构与容器**
- **S5** 容器步骤（subtask/loop/branch/case）必须至少有一个子步骤——动作不能写在容器行自身,下沉为子步。
- **P11** `check` 输出恰两槽：一个 bool 裁决 + 一个 text 说明,多一个都是 error。

**核验结构**
- **C6** `check` 必在 subtask/case 容器内。
- **C7** `check final` 必在容器**末尾**。

**交付完备**
- **P10** Outputs 每个声明输出必须有产出点（某步 `+ →`、call 输出映射或 exit）——声明了没人产出是 error；运行期声明输出未赋值（如 branch 走了不产出的分支）整个 run 判 failed——分支型产出让每个 case 都给统一接口变量赋值。
- **exit** Outputs 声明变量必须全部交付（bare exit = 隐式交付全部）。**hop_python body 只许出现在 act/commit/check 三型步骤**——流控步（exit/break/continue）与容器步（subtask/loop/branch/case）带围栏都是死代码,validate 拦（P4）;计算一律放 [act] 步:收尾计算放前置 act 后 exit 裸交付,容器内计算下沉为容器的 [act] 子步。

**知识与写法提示**
- **P15** doc-ref `[[文档路径#章节名]]` 的文件与章节必须真实存在（路径按 spec 同目录解析——裸文件名与**包内子目录相对路径**〔`references/rules.md#节`〕都合法,知识文档随 spec 走；禁 `..` 跨目录——跨目录引用依赖启动目录,换环境即断）。**目标是 YAML 文件（`.yaml`/`.yml`）时锚点写键名**：`[[references/faults.yaml#teardown_procedure]]`（全文档找首个同名键）或 `[[references/faults.yaml#外层键.内层键]]`（点路径精确定位,限逐层直接子级不许跳级）——切出该键及子树连同其上方紧邻注释块注入,P15 静态校验同样罩住（键名写错即 error）。原始规则表存 YAML 的 skill 语料（故障知识库/检测器注册表）不必再整文件注入或降级散文指路。
- **B6**（info 提示,非阻断）act body / case 条件里 `!= ""` / `== ""` 判空会被提示 null-unsafe——按上文改裸真值 `if x:` 或 `len(x) == 0` 即消。

生成完跑 `node <CLI> validate <spec>` 核验零 error。零 error 只覆盖静态文法面——**运行期假设（步骤说明教的动作 × 执行模式能力面）要 deep-validate 查**：交付前例行跑 `scripts/deep-validate/deep-validate.md`（params={spec_path: 产物, exec_mode: 目标模式}），风险报告随交付呈用户，建议性不阻断（SKILL.md 第 7 步已定例行化,此处是两道核验的分工提醒：validate 管"写得合法",deep-validate 管"跑得起来"）。

## 失败反馈怎么流转（引擎语义,你不建通道）

错误信息的流转全部是**引擎语义**——翻译时不需要为它建任何变量通道,你只负责把 check 的 `text` 槽写好。三条通道各管一段：

**① 容器内重跑（最常用）——修正指令自动注入**。完整闭环四拍：

1. **check 判 false** → 引擎读它的 `text` 槽（固定双槽签名里那个说明槽——失败原因就写在这）,记入所在 subtask/case 的失败记录,容器触发重跑（retry 预算内）;
2. **重跑轮注入** → 容器内**每个**重跑子步（reason/act 都算）的上下文尾部多出一个"修正指令"区块,形如一张修订工单——打回来源点名（哪个 check、核验看了哪些输入）+ 上一轮产出全文（作修改基准）+ 打回意见原文 + 此前各轮已被打回过的意见（保持落实,不许改好又改回去）+ 行动框架（逐条落实/意见与执行说明冲突时以核验要求为准/交付前自查逐条能指出改在哪）;
3. **执行者定向修正** → 重跑步的 LLM 拿着基准和意见照着改——非机械盲跑;
4. **变量自然保留** → 上一轮已产出的变量值跨重跑保留（fail 不清值空间）,上轮半成品是修复素材;要每轮干净起点的变量,作者显式 `= Null` 初值。

一个具体例子（翻译时你写下左边,执行期引擎兑现右边）：

```markdown
5. [subtask retry=2] 起草并验收摘要
  5.1. [act free] 写摘要初稿
    - ← source_text
    + → summary: markdown  # 摘要
  5.2. [check final] 验收:三个论点全覆盖且每点有原文行号
    - ← summary, source_text
    + → ok: bool  # 判定
    + → note: text  # 失败说明——写具体!这是重跑工单的正文
```

执行期 5.2 判 false 且 note 写"论点二'成本反转'未覆盖;论点三有覆盖但缺原文行号"→ 引擎自动重跑 5.1,那一轮 5.1 的执行 LLM 会在上下文尾部看到修正指令区块：被 5.2 打回、上一轮的 summary 全文（基准）、上面那句意见原文、"逐条落实"的行动框架——它据此定向补论点二、给论点三加行号,而不是从零重写。**你全程没为这条通道写任何变量或步骤**——只把 5.2 的 note 写具体了。

**② 按错误换路——adaptive 升级阶梯**。同因反复失败不该同构盲重跑：容器标 `adaptive` 后,重跑仍失败时引擎带着**完整失败历史**重规划容器内步骤（交付契约与 check final 不可改）。"按错误种类走不同修复路径"归这里——不要在 spec 里手写错误分类分支去模拟它。

**③ 跨容器上浮——FailRecord**。retry 预算耗尽,容器作为整体 fail,**完整失败记录**（每轮原因/第几次/哪步）随失败上浮交外层事务边界或最终 caller。外层要知道"里面怎么失败的"靠这个——容器还在自救时外层看不到中间失败,这正是事务边界的封装语义。

**on fail 兜底块——先给可照抄的写法**（R10 两路实测都卡在"讲了语义没给形"：一路烧完查证预算靠 validate 探针试出正形，一路被迫绕道 loop+branch 承载同语义。写法就是一个容器行，与 subtask 平级缩进挂在所属容器内，编号照排）：

```markdown
3. [subtask retry=2] 诊断并修复
  + → resolution: yaml  # 处置结论
  3.1. [act free] 诊断
    + → findings: yaml
  3.2. [check final] 验收:根因确认且修复通过
    - ← findings
    + → ok: bool  # 判定
    + → note: text  # 缺口
  3.9. [on fail] 三轮不收敛的兜底
    3.9.1. [act free] 把已收集的证据打包成诊断包,引用此前失败情况写明卡在哪
      - ← findings
      + → resolution: yaml  # 降级交付:诊断包路径与未决原因
```

要点三个：容器行写 `[on fail]`（写成裸 `on fail:` 行会被判不合本段文法忽略掉，连锁报错）；块内步骤照常编号、照常 `+ →` 给容器供值（降级交付物走这里）；它只在所属容器 retry 耗尽时激活，正常路径零参与。

**on fail 的两条引擎语义**（写"失败后清理/降级交付/上报"时要知道的账）：

- **兜底步自身选什么类型**：转述失败原因、写登记记录这类要引用注入失败上下文的兜底步,选 `[act free]`——非确定性内容写不出确定 body,标 free 承认现状（实测写 [act] 无 body 撞 B7 warn 后才改,教学此前没说）;纯机械清理（删临时目录/复位状态）照常 [act]+body;发通知按提交句判（通知服务在 Tools 段就 commit+body 或 call 通知子 spec）;

- **接住语义**：兜底块正常走完,容器**按完成收场**,失败不再向父层传播,主线继续往下走;兜底块内的 `+ →` 照常给容器供值（降级交付物走这里）。所以"失败也要发通知然后继续"落 on fail 是对的;而"失败就整个停下"的语义**不要加 on fail**——加了反而把失败吞掉变成继续;
- **兜底步看得见失败原因**：执行到 on fail 里的步骤时,上下文里有一段"此前失败情况"——哪步失败、第几轮、失败原因文本（check 的判词原文在场）,由引擎自动注入,不需要建变量通道去搬。兜底步要"把失败原因写进通知/诊断包"的,直接在步骤描述里要求即可（如"通知正文引用此前失败情况中的原因,如实转述"）。

**④ act free 步撞到现场异常——执行者自报,引擎接管**。act free 步执行期撞到环境问题（输入路径不存在、命令找不到、外部服务连不上）时,引擎有结构化出口：执行者交一个单键自报 `{tool_failure: "哪件工具怎么失败、对本步产出什么影响"}`,引擎判定后按失败处置——所在容器有 retry 就带故障说明整组重跑（瞬时故障重试即愈）,耗尽就随完整失败记录上浮（reason 步同享此通道;缺信息另有 lack_of_info 通道,仅 reason——两者不混:工具坏了报 tool_failure,材料里没有报 lack_of_info）。**对翻译的含义**：act free 的步骤描述**不需要写死异常处置逻辑**（"如果路径不存在则如何如何"的分支不用造）——通道是引擎语义,执行者如实自报即可;描述里把正常路径的预期写清就够,顶多加一句"环境异常如实上报,不编造产出"。

**由此推出 check 的写作纪律（翻译核验句时最值得花笔墨的地方）**：前三条通道的信息源头都是 check 的 `text` 槽——**失败说明写得越具体（缺什么/错在哪一条/期望是什么）,重跑修正越准、重规划依据越足、上浮诊断越清**;只写"不合格"三个字,三条通道全变盲的。

❌ **不要为错误信息建变量通道**（外部 init 一个 `last_err` + check 回填 + 重跑步 `←` 读——三步样板在模拟引擎已内置的 ①,同一信息注入两遍还多三步噪声;错误分类分支在模拟 ②;把内层失败泄给外层变量在破坏 ③ 的封装）。

## HopSop 流程草稿记法

翻译先打**HopSop 草稿**（大纲,纯 Markdown——控制流先定形,细节后升格）。记法词汇与你要产出的 HopSpec 关键词同一词族——草稿→升格词汇零换挡,这正是对偶的意义：

- 多层数字序号表达层级与顺序：`1` / `1.1` / `1.2.1`,子节点缩进 2 空格;
- 容器节点（仅四种可拥有子节点）：`[subtask]` 一组有共同边界的子节点;`[loop]` 子节点构成循环体;`[branch]` 子节点必须全是 `[case(…)]`;`[case(命中条件)]` 等同 subtask、直接挂该分支的步骤,兜底写 `[case(else)]` 且只能放最后。**容器行必挂至少一个子步**——容器行自身只承载结构与条件,动作写在子步行（case 里的"提取并追加"也要下沉成子步,不塞进 case 摘要行;暂不展开的容器挂一行占位子步 `[reason] 待展开——<任务描述>`）——validate 的 S5 拦裸容器;
- 普通步骤：无标记,一句话描述一个动作;
- **量级硬线：一层草稿超 ~30 行必须拆层留占位,不许硬写**——超线时把复合段收敛为容器行+占位叶子,本层只立骨架（宁可多一层递归,不可单层大输出——大输出易顶满预算,已产出内容全丢;机械核会拦"超线且零占位"）;
- 流控节点（与容器同用中括号标注）：`[continue <循环序号>]` / `[break <循环序号>]` / `[exit]`;
- **输入/输出可选标注**：节点行下缩进 `input:` / `output:` 行（英文词与草稿词族一致;值=自然语言名称,不写类型）——过程每步的 I/O 客观存在,草稿可省略但升格时 `←`/`→` 必须补全;
- **只表达控制流与可选 I/O**——不写类型、步骤类型（那些是升格为 HopSpec 时的事）。

草稿→HopSpec 升格（词汇同名直通）：`[subtask]`→subtask、`[loop]`→loop for-each（补 for-each 子句与 collect）、`[branch]`+`[case(…)]`→branch+case、流控三词同名、普通步骤按动词选叶子类型（见「step 类型选型」）。

## 执行时每步能看到什么（写步骤的自足性判据）

你翻出的每一步将来被执行时,执行 LLM 的**全部视野**由引擎按六层组装（权威:核心规范 Prompt 组装——层号照录,写步骤时逐层想"我引用的东西在哪层"）：

| 层 | 内容 | 对翻译的含义 |
|---|---|---|
| **L1** Spec 契约+骨架 | Goal/Constraints/Types（字段级定义）/Outputs + 静态步骤树（每步**只有编号/类型/摘要行与控制流属性**） | 摘要行是每步在全局地图上的唯一名片——一句话要说清这步干什么;别步的 `>` 描述与 body **不在骨架里** |
| **L2** 知识 | doc-ref `[[文档#章节]]` 精确切片 + `@knowledge` 检索(可选) | 大段判据靠它进视野——描述里引"评分规则"就得 doc-ref 引到那节 |
| **L3** 执行链 | 从根到本步的容器结构+**已完成步骤的产出值**+loop 迭代计数+branch 命中 case。依赖驱动树状:输入依赖节点全文、每层最近 ~5 个同级全文,更早的压缩成单行 | 已完成产出可见,但**深处/久远的会被压缩**——关键数据别指望 L3 捎带,走 `←` 显式声明（L4 全文注入不压缩） |
| **L4** 步骤输入 | `- ←` 声明变量的**实际值** | 本步依赖数据的正道——要用就声明,没声明的变量值不可见 |
| **L5** 步骤指令 | 摘要行 + `>` 描述全文 | 你写的任务描述,执行时逐字在场 |
| **L6** 输出约束 | `+ →` 声明的名/类型/`#` 说明 | 执行 LLM 按它产出——类型与 `#` 说明写不清,产出就歪 |

**retry 重跑时额外多一个"修正指令"区块**（垫在上下文尾部）：重跑轮里容器内**全部**子步都会看到——打回来源点名+上一轮产出（修改基准）+打回意见原文+累计意见史+行动框架。完整闭环四拍、具体例子与 check text 槽写作纪律见「失败反馈怎么流转」节。

**看不到的**：其他步骤的 `>` 描述细节与 body（骨架只有摘要行）、未经 `- ←` 声明的变量值（L3 可能压缩,唯 L4 可靠）、翻译时的原文（原文不随产物走）、你翻译时脑中的任何隐含背景。

**由此推出步骤自足性判据（合理性检查的核心）**：每步的 摘要行+`>` 描述+`←` 输入+注入知识 必须**自足**——描述里引用的每样东西,执行 LLM 都能在上述六层里拿到。反例:描述说『按前面分析的口径处理』（『前面分析』的细节在别步的 `>` 里,L1 骨架只有摘要行——口径要么经 `←` 变量传〔L4〕,要么写进本步描述〔L5〕或知识注入〔L2〕）;描述说『参照原文第三节』（原文不随产物走——需要的内容翻译时写进描述或抽成知识文档 doc-ref 引）。

## 展开层参考六面（按节点类型取用的细则）

> **宪法七条在 SKILL.md**（核心中的核心,正文随流程在场——权威在设计 docs/design/hopbuild.md「首要原则」章,SKILL 是投影位,本节不复述）。下列六面是**展开层参考**——展开到哪类节点取用哪面,不是顶层关卡判据。

**1. 事务步骤怎么写对（写 subtask/commit 时取用）**：试错段全部可逆、中间产物入引擎 work_zone 涂鸦区（body 里 `work_zone_path("名")` 取绝对路径——不写相对 `work_zone/…`,那会落到用户工作区）,不可逆动作不得混入探索段;check 验收（机器可验）/confirm（人审,仅原文真要人拍板）,验收在提交之前,核验不得跳过或降级为 reason 散文;不可逆动作隔离在 commit、前序把关闸门已放行（confirm/足够 check/环境预授权三选一）、自身按业务键幂等重放不加害。

**2. 每步的信息供给怎么配平（写 I/O 与 doc-ref 时取用）**：每个消费方拿到的信息恰好够用,不多也不少——
- **步骤自足**：每步的 摘要行+描述+`←`输入+注入知识 必须自足;判自足的前提是懂执行链视野机制（见「执行时每步能看到什么」节——写 I/O 与写描述必先懂它,不懂视野机制的自足判断=盲判）;
- **I/O 恰如其分**：Inputs=任务的业务输入（不漏不添;CLI 路径/状态目录/当前时间等执行设施不进——步骤描述直接说『用执行环境的 X』）;Outputs=原文承诺的交付物（不漏不添;草稿/中间清单等中间产物不进——工作台不摆进交付箱）;
- **注入不多不少**：每步只注该步需要的判据切片,无判据的机械步零注入;
- **缓存亲和**：判据外置知识件走 doc-ref（内联进各步描述=缓存不了还重复付费）;同类步骤共用同一知识切片;spec 级恒需知识上提 Constraints 全局注入。判据：执行时逐字节重复出现的内容必须有单一来源。

**3. 输出量级与结构怎么控（写 `+ →` 输出声明时取用）**：结构就简,量级控制——首选单值/平面字段,嵌套结构易崩塌,判定输出 enum 化;单步输出受控（>~30 条结构化条目必拆或分段落盘）;要大结构拆步或"reason 平面字段→act body 机械组装"（组装是确定性代码,不是 LLM 格式赌运气）。

**4. 问人步骤怎么设（写 ask/confirm 时取用）**：注意力经济,形式高效,信息充分必要——能推断的别问（default 给足）、必须问的一次问清、暂停点只留业务上真需要人拍板的;一个 ask=一个可独立作答的决策（合并=打包拍板,拆碎=碎问）;present_inputs 呈交依据完整不缩略不让人盲拍;**该人研判的不得给 default 溜过**（『视情况/酌情』等裁量语义处新立 ask/confirm 不算擅自加——记研判点台账呈终审;真擅自加=原文通篇无裁量语义纯凭感觉添人审）。产物是给非程序员用户的：问题措辞/呈现/输出说明零行话。

**5. 全树结构自查（合理关与终审前取用）**：
- **循环任务明确识别**：原文每个"对每一个/逐个/遍历"一个不漏——**静态判据清单同属遍历**（原文列编号清单"检查以下 N 类:1)…N)"且逐类同构动作,数量写死也是遍历——这形态不含"每一个/逐个"字眼最易漏认,分解打草稿时就要认出画成 `[loop]` 或留核验闭环）。识别是原则,保障策略可选（for-each 结构保障/生成-核验-迭代闭环二选一,须真有闭环）。**禁止**翻成 act body `for` 循环或 reason"逐个分析"（遍历完整性交回 LLM 记忆）;
- **整体结构合法**：数据链每个 `←` 追溯得到且类型匹配、validate 零 error、工具引用都在声明的工具面内;
- **retry 迭代闭环**：每个 retry 容器答得出"重跑凭什么会变好"（带反馈重跑/adaptive 换路/确定性失败不 retry 直接上报）——答不出的裸 retry 是缺陷。

**6. 语义与命名自查（合理关与终审前取用）**：
- **忠实翻译**：只做结构化映射,不擅自增删业务步骤（核心观点归原 skill 作者）;某面无真实触发如实记录不强造;原文意图不清记档呈终审不臆断;行为映射可核（每步可追到原文出处——草稿行尾括注即载体）;
- **命名与说明明确合理**：变量名/类型名防望名生义;新定义变量与 Types 字段的 `#` 说明必选——名字+说明是写给后继执行 LLM 的接口文档。

## 四类纪律句怎么翻

> 原文四类纪律句（遍历/核验/研判/提交）各给：**识别信号**（自然语言原文里怎么认出它）→ **生成模板**（翻成什么 HopSpec 结构）→ **反例**（翻错长什么样）。概念层权威锚点在每节标注。

### 遍历句：循环遍历不漏 → for-each 容器

**概念层**：`^anc-step-parallel`（`HopSpec V3核心规范.md`）。引擎按列表驱动逐项执行、体内标注 parallel 的步骤异步派发（渐进并发）、**容器结束前引擎收齐全部派出的活**、`collect` 子句声明的单项输出由引擎收进列表——遍历完整性由引擎收齐语义保证，不靠 LLM 记着"还有几个没处理"。

**识别信号**（自然语言原文里）：
- "对每一个 X…"、"逐个处理"、"遍历所有…"、"针对列表中每项…"、"批量地对每个…"
- 隐式循环：原文说"处理这些文件/模块/记录"且数量运行时才定。
- **静态判据清单**（最易漏认的形态）：原文列了编号清单"检查以下 N 类：1)… 2)… 9)…"且逐类做同构动作（扫描/判定/收集）——数量写死在原文里也是遍历。翻法：前置 act body 构造 N 元素判据列表（每项含类名+判据说明）,for-each 逐类驱动;或大面生成+核验步逐类点名核完整性（须真闭环）。❌ 单个 reason 步 instruction 里散文枚举 N 类="LLM 记住别漏"——原文越强调"积极搜索/头号来源"的类别越容易被凑数带过。

**生成模板**：
```markdown
5. [loop for-each item in items, collect result into results] 逐项处理（体内步骤标 parallel 即并发）
  + → results: [text]            # collect 子句的列表端（容器头声明类型）

  5.1. [subtask retry=2] 处理单项
    - ← item
    + → result: text             # collect 子句的单项端（每轮产出，引擎轮末收进列表）
    > 对单个 item 做处理…
```
关键：**取放成镜像**——`for-each <单项> in <列表>` 取的一端、`collect <单项> into <列表>` 放的一端，单项与列表是**两个名字两个变量**；**循环体只写一个 child**（引擎按列表驱动）；`item` 在 child 及后代可作输入引用；列表变量先由前序步骤产出 `[T]` 类型。

**标不标 parallel（并行判据）**：child 标 `parallel` = 各迭代异步派出并发跑,不标 = 逐项串行。判据看**迭代间有没有依赖**：
- **各项自包含**（每片独立标注/每个文件独立分析——本项处理不需要看别项的结果）→ 标 parallel,并发是白拿的加速;
- **迭代间有序**（本轮要跟已处理项比对去重/累进状态/后项依赖前项结论）→ **不标**,串行是语义需要不是保守;
- 原文的措辞常给信号："各自独立/互不相关/分别处理"→并发;"逐个比对/依次累加/在前面基础上"→串行。
- 并发 child 的输出走 collect 收齐,**收齐后的列表顺序=派发顺序**（与完成先后无关）;跨项的汇总/去重/reduce 放收齐后的串行步做（体内没有共享空间）。

**反例（翻错）**：
- ❌ 翻成 `[act] 循环处理所有项` 并在 hop_python body 里写 `for item in items:` —— act body **禁止循环**，且把遍历塞进一步 = LLM 执行期可能漏项，正是要消除的失效。
- ❌ 翻成 `[reason] 逐个分析每项` **且无核验闭环**——遍历完整性交回 LLM 记忆,无任何屏障。两种情况下非 for-each 合法（原则是『不漏』,for-each 只是保障策略之一——设计策略章「遍历保障两策略」）：①**嵌套内层**（外层已 for-each,内层第一版留任务描述——渐进策略『一次只拆一层』,用户点名才拆到位）;②**生成-核验-迭代**（大面生成+后续核验步查完整性+缺口反馈补——须真有核验闭环,无核验的大面生成=裸赌不算此策略）。最外层遍历若两者都不占,必须 for-each。
- ❌ for-each 下写多个不同 child 模板 —— 只允许一个（引擎按列表驱动）。多种互不相同的并发分支各自 `[subtask parallel]` 兄弟并列，或用 branch。

**单步产出规模上限（不要一口吃个胖子）**：设计 spec 时，凡一个 reason/check 步骤要对**大量条目**逐一产出结果（判定清单、审计结果、逐项报告），必须掂量单步输出规模——LLM 单次超大输出（几十条 × 每条几行 yaml ≈ 上万 token）极易死在产出阶段且已产出内容全丢。两种结构化解法（优先前者）：
- **切小 for-each 的元素粒度**：让每个 child 只管 ~20-30 条（前序步骤把大列表切段成 `[[T]]`，for-each 遍历段而非条目）——引擎级并行 + 每 child 输出天然有界；
- **步骤内分段落盘**：单步确实要处理大清单时，`>` 指令里明确"逐段判定、每段完成立即 append 追加到涂鸦区分段文件（路径经 `work_zone_path()` 或上游变量取,不写相对 `work_zone/…`）、全部段落盘后读回组装最终输出"——中断后可从分段文件续，不重做。
判据：预估单步输出 > ~30 条结构化条目就必须用上述之一，禁止指望执行 LLM 一口气产完。

### 核验句与研判句：核验不跳 → check；真人拍板 → confirm/ask

**核心是核验**：人审只是核验的一种形式，视需求决定。审核有两种，自然语言原文里常混在一起说"审核/把关/确认"，翻译时**必须分辨**——机器能核验的用 check，原文真要人拍板的才用 confirm：

#### 核验句：产出核验 → check / check final

**概念层**：`^anc-step-check`。check 验证产出是否达标，固定输出 `bool + text`；失败触发容器 retry。**`check final`** 位于全部探索性步骤之后（其后只允许 commit/exit 提交性收尾）、**不可被 adaptive 改写或跳过**——是 Constraints 的可执行化身，最强的"验收不能跳"保证。

**识别信号**："验证…是否达标"、"检查…对不对"、"确保满足约束"、"质量达标才…"、自然语言原文的 Constraints 里每条硬约束。

**生成模板**（关键验收）：
```markdown
3. [subtask retry=2] 执行并验证
  + → summary: text
  3.1. [act] 执行操作
    - ← input
    + → output: yaml
    > …
  3.2. [check final] 验证 output 满足约束        # 必在探索步骤之后（其后只可 commit/exit）
    - ← output, threshold
    + → ok: bool                 # 判定槽
    + → note: text               # 说明槽（未达标时的缺口）
    > 检查 output 是否达标，输出 true/false。
```
Constraints 里每条可执行的硬约束，都应对应一个 check（关键的用 check final）。

**check 步只做判定,不要顺手加工数据**：check 步的输出固定是两个——一个 bool（过没过）加一个 text（说明）,多一个都不合法。不要在 check 步里顺手做别的事,比如把草稿变量赋值成正式变量、整理拼装产出内容——这些是它前面那个步骤的活,塞进 check 步会因为输出超出两个、步骤干了判定之外的事而引出一串 warning。想表达"验收通过了才算定稿"：让前面的步骤直接产出定稿变量,check 步只对这个变量判过不过——检查不过容器会整组重跑,重跑后变量自然被新值覆盖,"没过的版本不会流出去"这个效果引擎已经保证了,不需要你在 check 里再做一次赋值。

**原文要求"出错就整个停下"时,不加重试不加兜底就是正确翻译**：有的原文写"发现任何一处不符,立即停止整个流程,不许手工修补继续往下走"——它要的效果就是检查一旦不过,后面的步骤全都不再执行,整次执行以失败告终、把失败原因报出来。这个效果用 `[subtask retry=0]` 加尾部 check final 就能忠实表达：retry=0 表示检查不过也不重试,又没有 on fail 兜底块,所以这个容器一失败,失败就一路向外传,没有任何步骤接住它,整次执行就停了——这正是原文要的。validate 看到"没有重试也没有兜底"会出一条 P6 warning 提醒你,这只是提醒不是错误：在研判点台账记一句"原文要求出错就停,所以刻意不加重试和兜底"留档即可,不要为了消掉这条提醒硬加 on fail。（on fail 兜底块是给"失败之后还有事要做"的场景用的——比如清理现场、改交付一个降级版本、向人上报;原文没有这些要求就不要硬造。）

**纯机械判定写成 body（零 LLM）**：判定是确定性计算时（判空/比阈值/核数组长度/查子串），check 直接带 hop_python body 让引擎算，不烧 LLM 且判定零漂移：
```markdown
3.2. [check] 合法关：结果非空
  - ← output
  + → ok: bool     # 判定槽
  + → note: text   # 说明槽
  > ```hop_python
  > ok = len(output) > 0
  > note = "" if ok else "output 为空——上游未产出"
  > ```
```
语义面核验（"内容质量够不够"这类要判断的）不带 body，照旧 LLM 判——两种产出方式走同一判定路径（bool false → 容器 retry）。

**先分辨核验语义再落模板——合法 false 是什么**：
- **不达标（闸门核验）**：false = 产物有缺陷该重做（格式错/漏字段/约束违反）——上方模板正解：判定不过 → verdict false → 容器 retry 带反馈修正；
- **是数据（忠实性核验）**：false = 业务上合法的不利判定，**本身就是要交付的输出**（对账不平的 gap、核不清的存疑项、待人裁的 HOLD）——check 核的不是"判定是否为 true"而是"**判定已如实记录**"（pass/fail 已落输出槽 + fail 时缺口/说明已随值 surface），核验点满足即 verdict true。识别信号：原文说"不平就**列出来**别硬轧平"、"pass/fail 连同差异一起报"、"标记出来交人审/待定夺"——判定的两个取值都要**进报告**，不阻断流程。

```markdown
  3.2. [check final] 核验对账判定已如实记录
    - ← foot_check, foot_note
    + → recorded_ok: bool        # 判定槽：pass/fail 已落值 + fail 时 gap 已写进 foot_note
    + → why: text                # 说明槽
    > 核验 foot_check 已置 pass/fail 且 fail 时 foot_note 含缺口说明——判定本身是交付数据,两个取值都合法。
```

❌ 报告类任务把"must foot（必须轧平）"翻成 `foot_ok == true` 闸门——合法的不平（gap 本该进报告）触发 retry 耗尽,run abort 丢掉其余全部账户。判据一句话：**这个 false 该出现在最终报告里吗？该 → 忠实性核验；不该 → 闸门。**

❌ **逐项核验结论用 `[check]` 收集**——循环体里"逐项核对,把未通过项记入清单"写成 `[check]`：check false 会触发所在容器重试/失败,**不会继续走到"写入清单"那步——未通过项永远进不了清单**,下游"依未通过项修订"不可达。正解：逐项判定用 `[reason]`/`[act]` 产出判定值（pass/fail 都是数据）,收齐后再用 check 核"每项都有结论"（忠实性核验形态）。

#### 研判句：人来把关 → confirm/ask（仅当原文真要人拍板或含裁量语义）

**概念层**：`^anc-step-confirm` + `^anc-exec-hitl-presentation`。confirm = paused 介入点，driver **必须**问外部决策者、**不得替答**；`require_human: true` 时必须真人；**reject 全局中止**（后续步骤全 skipped、终态 failed）——所以放在 commit 前的 confirm 是"拒绝即停、不可逆操作绝不发生"的硬闸门。

**识别信号**："让用户确认"、"人工审批"、"等待批准"、"需要授权"、"经同意后再…"。**注意**：原文只说"验证/检查/确保"没有点名要人 → 用 check，不要擅自升级成 confirm（把机器核验降级成打扰人）。**但『视情况/酌情/根据实际』等人裁量语义处例外**——那是原文隐含的研判点,新立 ask/confirm 不算擅自加（研判点台账记档,终审呈作者终裁）;裁量语义与核验语义的区分：前者无客观判据（人偏好/权衡）,后者有(格式/阈值/规则)。

**生成模板（confirm——审批闸门,输出恒 bool）**：
```markdown
6. [confirm require_human] 请批准执行修复
  - ← fix_plan                   # 给决策者看的依据
  + → approved: bool             # approve→true；reject→全局中止
  > 展示 fix_plan，请决策者批准是否执行。
```
`require_human` 修饰：涉及不可逆/高风险 → 加（强制真人）；一般确认 → 可省（允许上层 agent 代答，但默认倾向问人）。

**生成模板（ask——收数据/收裁量,输出是业务值）**：
```markdown
3. [ask present_inputs=draft_summary] 询问负责人细节偏好
  - ← draft_summary              # 呈交依据（present_inputs 引用的变量必须在 ← 声明——问人要给人看依据,依据变量不声明执行时拿不到）
  + → detail_preference: text    # 负责人的偏好回答（业务值,不是 approve）
  > 呈现 draft_summary，请负责人给出细节详略偏好；有默认倾向时给 default 供直接采用。
```
ask 与 confirm 的分辨：要的是**数据/偏好/裁量**（回答进业务流）→ ask；要的是**批不批**（bool 闸门）→ confirm。

**反例（翻错）**：
- ❌ 人工审批翻成 `[reason] 判断是否该批准` —— reason 是 LLM 自己推理，**架空了外部决策者**，违反 CITL 语义。审批必须 confirm。
- ❌ 产出核验翻成 `[act] 检查质量` 且不放容器 —— 孤立 check 违反 c6；且 act 无 retry 兜底，达标失败无法重试。
- ❌ 关键验收用普通 check（非 final）放 subtask 中间 —— 可能被 adaptive 跳过。硬约束验收用 **check final** 钉在探索段末（其后只做提交性收尾）。
- ❌ 原文"最多试 N 次/不通过就重做"翻成 `loop max=N` + `branch` 判是否通过的手搭重试 —— loop 无事务语义（不整组重跑、无失败注入、check 进不了 loop〔C6〕），正确形态恒为 `[subtask retry=N]` + 尾部 `[check final]`（引擎自带次数上限/反馈注入/耗尽升级）。
- ❌ 自然语言原文里明明说"确保 X"却在 spec 里没有任何 check —— 约束丢失，翻译不忠实。

---

**check 判据遇"材料本来就缺"的口径——缺口来自输入就放行、缺口来自执行就打回**：验收标准要求的信息在输入材料里本来就没有（如"每行动项有负责人"但用户材料没提负责人）→ 占位符+显式标注"输入未提供"**可以过**,打回只会逼执行 LLM 编造;但必须在最终交付物里显式列"待补事项"清单,不许把占位埋正文蒙混。执行者没去找、没去做导致的缺 → **照打回**。落法:check 判据写成显式两分（"每行有负责人,或标注了'输入未提供'并进待补清单"）,不给执行者自行扩大占位适用面的空间;缺口属输入还是属执行,check 的 note 里写明溯源。

**ask 的两个高频写法**：

- **present_inputs 支持多变量**——逗号列出 `present_inputs=quality_report,proposals`（parser 专门保护属性值内逗号不切碎）,不必为呈多样材料先加一步机械拼接;列出的每个变量必须在本步 `- ←` 声明（V11 精确判）;
- **收决策值的输出就是普通 enum 输出**——`+ → decision: enum(approve, skip)  # 用户裁决`,下游 branch 按 `decision == approve` 分流。样例：

```markdown
6. [ask require_human present_inputs=quality_report,proposals] 请审阅报告与修改提议,批准或跳过
  - ← quality_report, proposals
  + → decision: enum(approve, skip)  # 用户裁决:approve=执行修改,skip=只交付报告
```

**"否决后应续行"的审批场景用 ask 收 enum,不用 confirm**：confirm 的 reject 语义是**全局中止**（整个 run 终止,已产出的其他交付物一并作废）;原文的审批若是"不批就走另一条路/不批只影响这一段"（不批更新但报告照交付/不批豁免则回主流程按正常纪律走）,用 confirm 就把"合法的否决路径"变成了"整体失败"。这类场景落 `[ask]` 收 `enum(approve, skip)` + branch 分流——approve 臂做被批的事,else 臂走否决后的正当续行。confirm 只留给"不批=整件事就不该继续"的真中止语义（发布前终审/不可逆大动作的最后闸）。

### 提交句：提交把关 → act（可逆）vs commit（不可逆）

**概念层**：`^anc-step-act` vs `^anc-step-commit`。act **必无不可逆副作用、可安全重做**；commit 有不可逆副作用、**不可重试、需幂等**，且**能执行到 commit 说明授权/放行已在前序完成**——概念层原文：「前置 confirm 步骤 **或** 环境预授权」。即 commit 要的是**前序有把关闸门**，不是硬绑 confirm。把关闸门三选一：**confirm**（人来批）／**足够的 check**（验证放行条件已满足，如"质量达标才落库"）／**环境预授权**（能跑到即已授权，无需额外步）。试错/探索阶段的所有操作都应是 act（可反复重跑不留后果），不可逆动作隔离到 commit。

**识别信号**（不可逆 → commit）：
- "发送邮件/消息"、"支付/扣款"、"写入生产数据库"、"删除文件"、"提交 git"、"调用写语义的外部 API"、"发布"。
- 判据：**这个操作做完能不能安全地再做一遍 / 撤销？** 不能 → commit。

**生成模板 A（人审把关：confirm + commit）**——需人拍板放行时：
```markdown
7. [confirm require_human] 批准发送
  - ← draft
  + → approved: bool
  > 展示 draft，请批准是否发送。

8. [commit] 发送邮件
  - ← draft, approved
  + → sent: line
  > 不可逆操作（发送后不可撤回，前序 confirm 已放行）：调用邮件工具发送 draft。
  > 幂等设计：按 message_id 去重，避免重复发送。
```

**生成模板 B（验证把关：check + commit）**——放行条件可自动验证时（无需人）：
```markdown
5. [subtask retry=2] 校验后落库
  5.1. [check final] 校验记录满足入库约束
    - ← record
    + → valid: bool
    + → valid_note: text
    > 检查 record 满足入库约束（必填齐全、无冲突键），输出 true/false。
5b. [commit] 写入生产库
  - ← record, valid
  > 不可逆操作（前序 check 已验证放行条件）：valid 为 true 时按业务键 upsert record（幂等）。
```
> 环境预授权场景则无需前序步——能执行到 commit 即已授权（如 CLI 已登录态下的 git commit）。

**生成模板 C（外部提交：声明工具 + commit）**——提交动作是"写数据库/发消息/调外部导入服务"这类**没有内置函数签名**的外部动作时。commit 必带 body（验证规则 B7），而 body 里只能调内置文件十一件和 **Tools 段声明过的工具**——所以这类提交的正形是三拍：①对齐门把这个外部服务盘进 Tools 段（它就是"真正的外部服务"的典型成员）；②前置步骤把参数备成变量；③commit body 只做最后一次调用（参数全部来自前置步骤备好的变量,body 里没有任何现场判断）：

```markdown
Tools:
- db_import(package_dir) -> import_note: line  # 数据库导入服务（授权方提供,按记录稳定 ID upsert 幂等）

…
6. [act] 备齐导入参数
  - ← knowledge_package
  + → package_dir: line  # 知识包目录路径
  > 把知识包落到固定目录,路径存入 package_dir。

7. [commit] 执行数据库导入
  - ← package_dir, auth_ok
  + → import_note: line
  > 不可逆操作（写生产数据库,前序 check 已核验授权完备）：调用声明过的工具做最后一次提交,参数全部来自前置步骤备好的变量。
  > ```hop_python
  > import_note = db_import(package_dir: package_dir)
  > ```
```

❌ **反例：body 里现场发明宿主语言形态**——把 Python 的 `try/except`、`with open(...)`、方法调用链 `s.strip().split()` 这类写法照搬进 body（hop_python 没有异常捕获、没有上下文管理器；字段链上的**方法调用**被禁——字段取 `obj.field` 是合法的，禁的是 `obj.method()`）。注意两个曾被本反例误伤的合法形态：`subprocess.run(命令列表, cwd: 目录)` 是引擎认字面的内置特例（带具名参数专项拦，见 subprocess 节），`result.returncode` 是合法字段取（本文 returncode 检查纪律节正教它）——本反例拦的是这两者之外的宿主形态发明。危险在于部分未知名字 validate 在 act/check 步只 warn 不拦（B2 视为外部工具;commit 步未声明的会 error 拒载——0089 批升档），真跑执行期才炸。写不出合法签名=这个外部服务还没进 Tools 段，回对齐门补声明，不要在 body 里编。

**生成模板 D（宿主命令类不可逆动作：subprocess.run + commit + 命令白名单）**——提交动作是"SSH 到目标机执行脚本/擦盘重装/跑部署命令"这类**本质是一串 bash 命令**的现场操作时。这类动作不进 Tools 段（它不是外部服务是命令行），正门是引擎内置的 `subprocess.run`——签名恒定（命令与参数装进 argv 列表），命令名须在项目配置 hopjit.yaml 的 `commands:` 白名单里（研发阶段可在白名单放宽口先跑起来,生产收敛为具名清单——配置项就是开关）。三拍：

1. 现场裁量的部分（探测目标机、按现场选参数）**前置 act 步备成变量**——commit body 不做判断只做执行；
2. commit body 用 `subprocess.run` 写下完整的命令序列（写规约时就确定,执行时照跑）,**每跑完一条命令就检查它的 returncode,非零就停下**——不检查的话前面的命令失败了后面的照跑,产出会谎报成功;失败要写进产出值,不许静默；
3. **部署前提随交付写明，命令依赖双落点**：产物用到的命令名逐个列出——写进产物 Config 段的 `requires_commands:` 键（引擎启动时自动对账宿主白名单，缺配置在进步骤之前就拦下带指路，比运行期撞墙早得多也好修得多）+散文指引用户加进 hopjit.yaml `commands:` 白名单——研发阶段可宽口（直接放行 `bash`/`ssh`，一切现场命令经它跑，先跑起来）；生产收敛为逐个具名命令（把 bash/ssh 从名单撤下），管控从"全开"收到"点名"，spec 里的 requires_commands 声明与步骤一字不改只动宿主配置。

```markdown
7. [commit] 在目标机执行铲除脚本
  - ← target_host, teardown_approved
  + → teardown_result: yaml  # 执行结果(含退出码,失败如实在场)
  > 不可逆操作（前序 confirm 已放行）。命令序列写规约时已完全确定,执行时照跑,不需要任何现场判断:
  > ```hop_python
  > r = subprocess.run(["ssh", target_host, "bash /opt/deploy/teardown.sh"], timeout: 1800)
  > teardown_result = {"returncode": r.returncode, "note": "ok" if r.returncode == 0 else "failed:" + r.stderr}
  > ```
```

**环境变量注入的写法**（原文常见 `export VAR=... && node ...` 形态,而 subprocess.run 签名无 env 形参）：用 `env` 命令前缀 `subprocess.run(["env", "VAR=value", "node", "script.js"], ...)`——此时 argv[0] 是 `env`,白名单要把 `env` 和真命令（node）都加上,部署前提清单里两个都列并注明为什么。这是当前的绕行正形;若语料频繁撞此形态,引擎补 env 形参是候选(记台账呈引擎侧)。

**文件态环境注入必须显化**（hopissues/0090 P4 实撞:一整条发布链因此挂掉）：原文是 bash 流程时常见 `source env.sh` 把一批阶段变量灌给后续命令（`source env.sh && designer-ctl gate ...`——被调脚本从环境变量里读这些值）。hop 的 subprocess.run 不传环境变量（设计纪律:外部状态以文件为载体传子进程,保重放确定性）,直接照搬调用就是断桥——子进程读到的全是空值,而且失败发生在下游脚本深处,离病根很远（实撞:gate 命令读不到阶段变量→不写发布凭证→计时收口报"凭证缺失"→发布链整条挂,宿主顺着报错查了一整条链才回溯到 `source` 在翻译时蒸发了）。翻译时两件必做：①识别"`source <文件>` 注变量供后续命令消费"套路,在产物的部署前提清单里显化一条"某某命令运行期依赖 <文件> 的文件态注入",把它注入的变量名列出来;②给出桥接约定——与用户对齐"被调命令自读该文件"（改命令入口自举读取,最彻底）,做不到就在步骤说明里写明该文件是命令的运行期配置、宿主部署时必须保证命令进程能读到这些值。静默照搬 = 把断桥留给宿主真跑撞。

**中间产物落点恒用 work_zone_path()**（hopissues/0090 P5 实撞）：原文 bash 套路"子进程把中间产物写到某个目录,后续步骤再读回"搬进 hop 时,落点必须对齐涂鸦区——`out_path = work_zone_path("名字")` 生成路径,子进程经参数（如 `--output <out_path>`）写它,后续 `read(path: out_path)` 读回。照抄原文的绝对路径落点（如 `env.checklist_dir + "/..."`）,子进程写得进去（命令通道不受文件沙箱管）,但内置 read 读不回来——绝对路径禁令只豁免涂鸦区,读回那步必死且反复 retry（写成功读失败,现象离病根隔一步,很难一眼看出是落点问题）。判据一句话：凡是"这一步写、后面步骤读"的中间文件,路径一律 work_zone_path() 生成;只有要交付给用户的最终产物才落 workspace 相对路径。

**外部脚本的退出码语义先核后用**（实撞:通知脚本是 best-effort 设计——凭据缺失/HTTP 失败/网络异常一切路径都 exit(0),spec 按"退出码非零记失败"判定,结果一切失败都被记成已发送,唯一产出必失真）：body 依赖 subprocess.run 的 returncode 判成败时,先读一眼被调脚本的退出码语义（grep sys.exit / exit 即可）——恒退 0 的 best-effort 脚本,改从 stdout 的成功标志判（如"推送成功"字样）,或在台账记"脚本退出码不可判成败"呈裁;语料脚本的行为不擅自改,判定通道选对即可。

**写死还是留活的判据**：问"写这份规约的时候,命令序列能不能完整确定"——命令/参数/顺序都不依赖执行现场才知道的信息 → **写死进 body**（写死是白赚的确定性）;要先探测现场状态才知道跑什么、或按上一拍输出决定下一拍 → **留活落 `[act free]`**（act free 本来就是给尝试性执行的合法形态,不是降档）,但留活的不可逆动作前面必须有闸门（confirm 人审或 check）看住,并记台账说明为什么定不死。**高频场景直接给指导**:同类留活场景在语料里反复出现时（如"SSH 到目标机按现场排障"）,把该场景的作业要点写进步骤说明或抽知识文档 doc-ref——留活不等于零指导,说明写得越具体执行期漂移越小。

**原文的祈使命令句是步骤,不是可略过的散文**（hopissues/0091 实撞:同模板一对 stage 只译了一边）：原文 prompt 里"阶段开始前先执行 `xxx timer init`""写完执行 `xxx timer finalize`"这类祈使句,必须译成 act/commit 步里的 subprocess.run 调用,不许当成叮嘱性散文略过——尤其当下游脚本硬消费它的副作用时（实撞形态:发布脚本读 timer init 写的凭证字段,缺了直接报错退出;收口脚本不被调,任务状态永远停在进行中、通知不发）。两个判据：①句式是"执行某命令"且 argv 完整写得出来 → 它就是一个步骤,漏译=功能蒸发;②拿不准某句祈使是不是硬依赖,查下游有没有谁消费它的产物（grep 它写的文件/字段被谁读）——有消费者的祈使句漏译,失败会发生在离病根很远的下游,宿主排障代价极高。

试错/中间产物用 act：
```markdown
4. [act] 生成候选草稿                # 可反复重跑，不留外部后果
  - ← input
  + → draft: text
  > 生成草稿，纯产出无副作用。
```

**反例（翻错）**：
- ❌ 把"发送/写库/删除"翻成 `[act]` —— act 契约是"可安全重做"，不可逆操作放 act = 崩溃重跑会重复扣款/重复发送。
- ❌ commit 前**无任何前序把关**（既无 confirm、也无验证 check、也非环境预授权）—— 不可逆操作无把关直接执行，违反"试错不 commit"精神。（有 confirm **或** 足够 check **或** 环境预授权，任一即可，不必都要 confirm。）
- ❌ retry 容器内 commit 前无任何把关步骤（confirm/check 均无，或把关跟在 commit 后面）——把关必须在提交之前；"act 探索 → check final 验收 → commit 提交"同容器是合法且正统的事务形态（验收不过 retry 重跑探索段，commit 只在通过后执行）。
- ❌ 试错/探索步骤用 commit —— 试错就该可反复重来，用 act；commit 只留给"最终真的要落地"的那一下。

### 四类纪律句串起来的典型形态

一个"遍历 + 审核 + 落地"流程翻完通常长这样：
```
loop for-each … + 体内 subtask parallel（traverse 遍历所有项，引擎保证不漏）
  └ subtask
      ├ act（试错/生成，可逆）
      └ check final（verify 产出核验，不可跳）
confirm require_human（hitl 人工把关）
commit（commit 不可逆落地，前序有把关闸门：confirm / 足够 check / 环境预授权）
```
翻译完对照原 skill 文本 自查：**每个遍历都成了 for-each（traverse）？每个核验都落在 check（verify）、原文真要人拍板处才有 confirm/ask（hitl）？每个不可逆操作都成了 commit 且前序有把关闸门（任一即可）？** 逐落点 yes 才算忠实——与草稿行尾标记逐一对上。

## hop_python 小语言（body 与 case 条件的完整语言面）

**body 的物理形态先说死**（裸围栏不解析——实测有执行者两个 spec 的 body 全部顶格裸写,B7 报"没有 body"而不是"围栏形态不对",排障只能靠对照范本）：body 必须住在步骤的 `>` 说明行内,围栏的每一行都带 `> ` 挂行前缀。顶格写围栏（行首没有 `> `）,parser 不把它认作该步的 body——步骤等于无 body,撞 B7。模板里的写法就是唯一合法形态,照抄别改造。

hop_python 是 HopSpec 内嵌的确定性小语言——**Python 语法的一个受限子集**：能按 Python 直觉写的都按 Python 写,凡有出入的下面逐条列全。它出现在两处：act/commit/check 步骤的 ` ```hop_python ` 围栏 body（引擎直接执行,零 LLM）;case 步骤的条件表达式（同一语言,只许纯表达式）。

**心智模型**：body = 一段跑在 spec 变量空间里的 Python 脚本——`←` 声明的变量进来就是活的结构化值（yaml 型=对象/列表、[T]=列表）,直接消费零手动 parse;body 里的赋值就是给 spec 变量赋值,`+ →` 声明的输出变量在 body 里赋过值即交付。

### 与 Python 一致的部分（按直觉写即可）

- 赋值/算术/比较/逻辑（`and/or/not`）/字符串拼接;
- **字段访问与下钻**：`contract.inputs` 点号、`vr["errors"]` 下标,混用下钻 `plan.steps[0].name` 均可;
- **列表推导**：`[i.name for i in contract.inputs]`、带滤 `[x for x in xs if x.ok]`（嵌套深度≤2——外层过滤+内层聚合谓词合法,三层以上升 loop 步骤）;
- **条件语句与条件表达式**：`if cond:` / `elif` / `else:` 缩进块、`x = a if c else b`——确定性分支直接写 body,不必升 branch 步骤（branch/case 留给"影响后续步骤走向"的分叉;只是算个值的分支塌进 body 更省结构）;
- **裸真值判空**：`if xs:` 对 null/空串/空列表/空对象一体安全——判空恒用它或 `len(xs) == 0`,❌ `x != ""`（null 时 `None != ""` 为 True 误判非空）;
- `in` 成员测试：`"子串" in 文本` 是字符串包含、`x in 列表` 是元素测试、`"k" in 对象` 是键测试——**与 Python 同义,所以拿对象做"子串匹配"恒 False**（`'"errors":[]' in vr` 的 vr 是对象,这是键测试不是子串搜索——判对象内容用字段访问 `len(vr["errors"]) == 0`）。

### 与 Python 不同的部分（逐条,写错即 parse error 或运行期炸）

1. **禁 for/while 循环语句**——重复处理升为 HopSpec `loop` 步骤（列表推导不算循环语句,可用）;
2. **无方法调用**——一律裸名函数：`strip(s)` 非 `s.strip()`、`split(s, ",")` 非 `s.split(",")`;列表追加用拼接 `xs = xs + [item]` 非 `xs.append(item)`;
3. **每条语句单行写完**——body 按行解析,列表/对象字面量不许跨行（跨行的 `[{...},\n {...}]` 报"] 未闭合"）;长清单逐行拼接：先 `xs = [第一项]` 再 `xs = xs + [第二项]`;
4. **对象字面量固定键名必须加引号**——`{"k": v}`;裸名键 `{k: v}` 是"变量 k 的值作键名",k 未定义被静态拦;
5. **函数与工具调用用命名参数**——`write(path: p, content: c)` 冒号形态（Python 是 `=`）;
6. **禁 LLM 判断**——body 里没有"语义判断"这回事,需要语义裁量的活不进 body（那是 reason/act free 的事）。
7. **判空禁用 bool() 对字符串的隐式强转**（hopissues/0087 实撞——fraud-detection 产物写 `inputs_present = bool(a and b and c)` 对路径字符串判在场,引擎 preflight 确定性失败）：bool() 对非空字符串恒返回 true,拿它判"输入是否为空"判不出任何东西。正确写法两种——**判空用裸真值**（`if a:` 进非空分支;多个就 `if a and b and c:`;要显式布尔值就 `len(a) == 0` 判空——与上文"判空只用裸真值"同一条正形:`a != ""` 不要用,字段为 null 时 `None != ""` 为 True 误入非空分支,且引擎 B6 lint 会点名它）;判文件在场用探测工具 `parse_json(exists(path: a)).exists`。一句话记忆:字符串的"空不空"用裸真值问,文件的"在不在"用 exists 问,bool() 两个都答不了。

### 可调用的三类函数

**① 内置纯函数**（恒可用零声明——白名单全集,权威=引擎 act-builtins）：`len/count/min/max/sum/abs/round/int/float/str/bool`、`lower/upper/strip/split/join/replace/startswith/endswith`、`keys/values/get`、`sorted/reversed/range/any/all`、`strip_fence`（剥代码围栏）、`parse_json`、`now/today`（取时的唯一正门,重放安全）、`work_zone_path`（取涂鸦区绝对路径）。

**② 内置文件十一件**（恒可用零声明,有副作用故只在 body 不在 case 条件）：`read(path:, start_line?:, end_line?:)/write(path:, content:)/append(path:, content:)/edit_file(path:, old_text:, new_text:)/search_file(path:, pattern:)/exists(path:)/listdir(path:)/create/makedirs(path:)/move/remove`。read 带行号参数只取那一段（1 起,end 越界截尾）;search_file 单文件子串搜索返回命中行清单 JSON 文本（行号 1 起,零命中空列表——同 exists 须 parse_json 再用）。**exists/listdir 返回 JSON 文本不是结构值**——`parse_json(exists(path: p)).exists` 包裹后取字段,裸取下标是在字符串上取下标运行期炸（工具速查表逐件标注了哪些返回 JSON 文本）。**解开后的字段名**:listdir 条目是 `{name, type}`（type 取值 file/dir——判文件用 `e.type == "file"`）;exists 返回 `{exists, type}`。字段名不要凭感觉猜——实撞:凭直觉写了不存在的字段名,缺键取 None 恒假,过滤结果恒空,真机产出必坏而 validate 全绿;路径按 workspace 相对解析,绝对路径被沙箱拒（唯一豁免:work_zone_path() 取的涂鸦区路径）。**要读 workspace 外的绝对路径时**（如用户给的输出目录/系统位置文件）：内置 read 没有这个能力,正门是 `subprocess.run(["cat", 绝对路径])`（cat 进 commands 白名单,列入部署前提清单）——这不是绕行是设计边界:内置文件件的沙箱语义就是"workspace 内+涂鸦区",越界读写显性走命令通道让白名单管控;写侧同理（workspace 外写盘走命令通道且必须在 commit 步）。

**③ 外部命令与声明工具**：跑命令行的唯一正门是 **`subprocess.run(argv, input?, timeout?, cwd?)`**——写法同 Python（argv=命令与参数一个列表,不经 shell 零注入面）,返回 `{stdout, stderr, returncode}` 结构值,**命令名必须在项目 sandbox.runtime.available 白名单内**（名单外运行期拒;这是显性化管控的设计本意——不要教产物用宿主 Bash 绕）;命令失败不炸步,`returncode` 是返回结构里的一个值——每跑完一条命令就检查它,非零按失败处置并写进产出。Tools 段声明过的外部工具按签名调用（`db_import(package_dir: d)`）。这三类之外的名字一律不可调——validate 的 B2 对未知名字分步骤类型处置:act/check 步 warn"运行期对照清单"不拦;**commit 步且 Tools 段未声明的直接 error 拒载**（不可逆步不接受野函数名,0089 实撞升档）,写不出合法调用=该能力没进 Tools 段,回对齐门补声明,不在 body 里编。

### 样例（三类调用各一瞥）

```markdown
1. [act] 统计并落盘
  - ← raw_data
  + → profile: yaml  # 字段统计概览
  + → saved_path: line  # 落盘路径
  > 无推理计算：统计缺失率,结果写入涂鸦区。
  > ```hop_python
  > total = len(raw_data)
  > bad = [r for r in raw_data if not r.value]
  > rate = round(len(bad) / total, 4) if total else 0
  > profile = {"total": total, "missing": len(bad), "rate": rate}
  > saved_path = work_zone_path("profile.json")
  > written = write(path: saved_path, content: str(profile))
  > ```

2. [check] 核验仓库状态干净
  - ← saved_path
  + → repo_ok: bool  # 判定
  + → repo_note: text  # 说明
  > 机械判定:git status 零输出为净。
  > ```hop_python
  > st = subprocess.run(["git", "status", "--porcelain"], cwd: ".")
  > repo_ok = st.returncode == 0 and len(strip(st.stdout)) == 0
  > repo_note = "" if repo_ok else "工作区不净或命令失败(rc=" + str(st.returncode) + "):" + st.stdout
  > ```
```

无 body 时按 `>` 自然语言描述执行（执行 LLM 用宿主工具,那是另一个执行面——本节语言规则只管 body 与 case 条件）。

## 知识抽取与 doc-ref（大段判据外置）

**问题**：内容丰富的自然语言 skill 常在某步塞大段**判据知识**——评分规则、FLAG 清单、分类标准、方法论、报告模板。若原样全塞进 spec 步骤的 `>`，spec 会臃肿（编排骨架被判据淹没）、且判据无法复用。

**知识按作用范围分两层供给**：

- **章节性知识随节点展开**——只在某几步用到的判据（某步的评分规则、某步的 FLAG 清单），抽成 knowledge 文档章节、在消费它的步骤 `>` 里 doc-ref 引用——引擎执行到那步才注入，**不过度占据全局注意力上下文**（全程注入=每一步的执行 LLM 都被无关判据挤占注意力）；
- **全局性知识不能遗失，作为 spec 的全局知识供给**——贯穿全程的东西（原文的总原则、全程红线、跨步共用的口径）不能只挂在某一步上：红线句上提 **Constraints**（引擎全程注入每一步）；大段的全局方法论放 knowledge 文档后在 **spec 级 doc-ref** 引用（头部引用=全程在场，区别于步骤级的到步注入）。判断一条知识归哪层：只有一两步消费→章节性随步注入；每步都可能要对着它判断→全局供给。**两层都不许丢**——章节性知识忘了 doc-ref=那步执行时判据缺席（合规空转），全局性知识只挂某一步=其余步骤红线失守；
- **全局知识里提到章节性内容时，简要描述、留到具体步骤再展开**——全局供给的方法论为了连贯和完整，常要提到某个只在特定步骤才用的细节（如总流程里说"第三阶段按评分规则打分"）：全局层写一句话简述保住上下文连贯（"按评分规则打分，规则细节在打分步注入"），细节全文留在章节性知识里由那一步 doc-ref 展开——不在全局层复制细节全文（复制=全程占上下文+两处真值必漂移），也不因为细节在别处就把全局层的这句提及删掉（删了全局方法论就断脉络）。

**做法**：把大段判据抽成**陪伴 knowledge 文档**，spec 步骤的 `>` 用 doc-ref `[[knowledge文件#章节名]]` 引用，**引擎运行期自动切片注入**该步 agent 上下文（小节内联，超阈值转 `$file` 指针）——spec 只留编排骨架，判据沉于知识文档、引用即注入。

**何时抽**（判据）：某个 act/reason/check 步的 `>` 满足任一 → 抽：
- 承载**可复用判定规则**（如"应 FLAG / 不应 FLAG"清单、严重度分类标准、评分区间）；
- 大段**方法论/执行协议**（分几步、读哪些文件、±行号范围）；
- **报告/输出格式模板**（章节结构、统计表格式）；
- 纯经验：`>` 超过约 5-6 行且非"这一步具体做什么"的一次性指令。

**🔴 目录约束（硬）**：knowledge 文档必须与 spec **同置目标 skill 目录**，doc-ref 用目录内相对引用（裸文件名或包内子目录路径如 `references/xx.md`）——引擎按 spec 所在目录解析,skill 目录从哪启动都命中。**禁引用 skill 目录外文件**——禁 `..`,跨目录引用依赖启动目录、换环境即断。hopskill + knowledge 是自包含可分发单元。

**怎么抽**：
1. 建陪伴文档 `<spec-id>-knowledge.md`（**与 spec 同一 skill 目录**），按判据主题分 `## 章节`（章节名即 doc-ref 锚点，须真实存在——validate p15 会校验）。遵循渐进展开：一个章节一个自足判据块。
2. spec 步骤 `>` 里保留**一句话意图** + doc-ref 引用：
   ```markdown
   6. [reason] 审计 mock 质量
     - ← mock_patterns
     + → mock_audit: yaml
     > 对每个 mock 按注入的判据判定应否 FLAG，产出审计结果。引擎已自动注入（doc-ref）：
     > [[test-coverage-audit-knowledge#mock FLAG 判据]]
   ```
3. Constraints 里也可引用（如"判据权威见 `[[…-knowledge#…]]`，禁止自创判据"）。

**不抽的**：一次性的"这一步具体干什么"（如"用 Write 把 X 写入 Y"）留 `>` 即可，别为抽而抽。
