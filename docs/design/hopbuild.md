## 一个 hopspec skill 的构成【说明】 ^anc-build-anatomy

一个 hopspec skill（pack 产物）由三类构件组成，**各有各的读者，内容互不越界**：

| 构件 | 文件 | 读者 | 装什么 |
|---|---|---|---|
| **壳**（薄包装） | SKILL.md | 触发它的 agent（对话侧） | 触发说明/参数引导/执行委托/交付四段——把用户带进执行再把结果交出来，自己不含流程与判据 |
| **spec**（流程权威） | spec.md | HopJIT 引擎 | 步骤编排+I/O 契约+介入点——纪律由引擎强制的那部分 |
| **知识件** | *-knowledge.md / *-primer.md | 引擎（doc-ref 按步/按 spec 级切片注入执行 LLM） | 判据/规则/全局导览——执行到才需要的内容，谁也不整读 |

三类构件的边界就是各纪律的来源（见「构件纪律」章）。越界的通病一句话：**把内容放到不该读它的读者面前**。

## 首要原则 ^anc-build-first-principles

hopspec构建的七条原则：

0. **内容忠实**：不能丢失或篡改原始 skill 的**意图和知识**——
   - **知识完备性**：原文的判据/规则/模板一份不丢,进步骤、进 Constraints 或进知识文档随包,总之要在产物里。落点按作用范围分两层（2026-09-05 作者定）：**章节性知识随节点展开**——只在某几步用的判据抽 knowledge 章节、消费步 doc-ref 到步注入,不过度占据全局注意力上下文;**全局性知识不能遗失,作为 spec 的全局知识供给**——全程红线上提 Constraints（引擎全程注入）、全局方法论走 spec 级 doc-ref,只挂某一步=其余步骤失守;**全局知识里提到章节性内容的,出于连贯性和完整性简要描述,留到具体步骤再展开**（全局层一句话简述保脉络,细节全文归章节性知识由消费步 doc-ref 展开——不复制细节全文进全局层,也不删全局层的提及句）;
   - **流程忠实性**：承诺的动作/门禁/依赖一个不许蒸发,不擅自增删业务步骤;
   - 粒度可以粗但语义必须全;
   - **原文本来就没写的判据或阈值,缺了不算翻译缺陷**——正确做法:先按最合理的理解填一个暂定值,把"这里原文没给、暂定了什么、为什么"记进研判点台账,由作者终审拍板;不因原文缺这个卡住不翻,也不在检查关把它当错误打回（实撞:mini/branch 合理关反复打回『紧急判据缺失』直至 replan 耗尽,而原文本来就没给判据）;
1. **明确易懂**：产物的行文、布局要说人话——**人和 LLM 都一遍读懂**——
   - 步骤说明、变量说明、判据都用完整的话写清楚——不用缩略语,不用只有写的人自己才懂的简称和代号,不用压缩断句的文言腔;判断标准=没跟过翻译过程的读者一遍能读懂;
   - **布局方便阅读**：分立的事项分条列,不挤成一坨长段;一个段落只装一个主题,判据/清单/前提逐条一行;
   - 结构一眼能讲出"为什么这样拆"——讲不出的嵌套不如留任务描述待下层展开;
   - **关键行为必须用"必须"等强化语气确保**：门禁/禁令/红线句翻译时保留原文的强度——"必须/不得/禁止"弱化成"建议/尽量"就是篡改语义（执行 LLM 对弱语气的服从不稳定）;
2. **分离范式**：**subtask{ act（探索）→ check（核验）→ retry（不过带反馈整组重跑）→ check final（验收）→ commit（提交）}**,确保探索与提交分离——
   - **act 探索工作在 work_zone 内实施**：试错段可逆、中间产物全入涂鸦区不碰正式位置;
   - 核验在提交之前,不过就 retry 重跑直到验收放行;
   - 不可逆动作隔离在 commit 且前序有把关;
3. **渐进展开**：一次不用拆得过细——
   - **每次构建,在上一次基础上把主要问题点的结构拆出来即可**：首版立顺序骨架,后续轮次对着上一版的问题点定向拆,不整树重来;
   - **用好 `[act free]` / `[subtask free]`**：拆不清的段落以自由步/到步展开诚实落定,是合法形态不是欠账——比硬拆错强;
   - 单层量级受控（量级硬线不变——渐进生成不要一次太多）;
4. **渐进输出**：尽量不要整篇整篇地输入输出——
   - 产物文件落 work_zone 后,后续修订用 **edit_file 局部精确替换**等文件编辑工具改点不重写全文（LLM 整文重写=改三处赌全文不漂移,局部替换=只动要动的;引擎内置 edit_file 2026-09-05 已落地,与 read/write 同属恒可用文件工具面）;
   - **调整 spec 步骤树用树编辑工具**（insert_node/replace_node/replace_children）：按步骤号落位/替换/换 children,编号机械重刷不手工改号,序号一致性由工具保证非 LLM 手工;
   - 大产物分段落盘,不经变量通道整篇搬运;
5. **逐步优化**：复杂循环、并行化在逐步优化时再考虑——**"循环不漏"不再要求一次做到**——
   - 循环形态的识别与精化（"对每一个/逐个"与静态判据清单形态,精化成 for-each 或生成-核验闭环）、嵌套遍历拆内层、互不依赖段落并行化,全归首版骨架跑通后的优化步骤;
   - 首版把重复语义如实落住即可,串行跑对先于并发提效;
   - 判据:首版交付"主结构对+把关在场+可跑",优化轮交付"遍历完备+并发提效+注入精准";
6. **工具核验**：交付的 hopspec 文件必须通过两道工具检查,缺一不算交付完成——
   - **validate**（静态文法零 error）——管"写得合法";
   - **deep-validate**（运行期假设体检——步骤说明教的动作 × 执行模式能力面,风险报告随交付呈用户）——管"跑得起来"。

七条之外的细节知识不用预读——翻到哪类步骤,查 primer 对应节。

## 多文件 skill 的翻译与交付（自包含契约）【契约：作者定 2026-09-04,hopissues/0069 首发语料实锤后立】 ^anc-build-multifile-fidelity

成熟的自然语言 skill 普遍是**多文件目录形态**：SKILL.md 本体只做路由与骨架，流程细节、判据清单、数据表住在 references/ 与 scripts/ 里（渐进披露写法——0069 首发语料 sandbox-platform-deploy-630 即此形态：本体 8.7KB，28 个附属文件共 500KB）。对这类输入，翻译与交付各有一条硬约束：

**翻译面——引用文件分两类，处置不同**：

- **流程性引用**（被引文件装的是执行序列、退出门禁、确认闸这类"错过会导致纪律失守"的内容，如 workflows.md 的逐阶段门禁）：翻译时**必须把被引文件读进来**，其中的门禁句/闸门句按四类纪律句翻成显式 check/confirm——只翻本体不读引用，产物的把关面就只有本体摘要的粒度，"引擎强制"名存实亡（实锤：hopbuild2 产物全新部署五阶段收成一条 act free，逐阶段门禁蒸发——构建全程只读了 skill_path 一个文件）。**读进来≠展开进来**：阶段的操作细节仍可留在被引文件里由步骤"读它再干"（粒度大原则），要拎出来的只是**把关句**——门禁翻成 check 步骤，细节留文件，两不冲突；
- **参考性引用**（数据表/故障库/原始 YAML/脚本用法说明这类查询式内容）：不翻进 spec，产物步骤写"读 <包内相对路径>"按需取用——硬翻参考性内容进步骤=违"不用一次拆太细"的粒度大原则。

分类判据一句话：**这段内容错过会导致纪律失守（门禁跳过/闸门蒸发/顺序乱）的是流程性，只影响执行细节对错的是参考性**。定性对象是**内容不是文件**——混合文件（主体是参考性字段表、尾部却有一节退出门禁）按其中最严内容处置：整读、门禁句照拎，参考性主体仍留文件按需读（首跑验证实撞：knowledge-schema.md 主体字段表+尾部一致性约束节即此形态）。**方法论/模式库类语料先立任务面再二分**（多语料验证实撞：database-migration 这类"教怎么做"的 skill 本体没有现成执行流程，"错过会不会导致纪律失守"无从判——先依 frontmatter 的 quick_start/使用说明立出任务面〔如"把方法论应用到具体需求产出方案"〕并记台账，二分才有基准；这类语料全程无 ask/confirm/commit 是语料本性不是翻丢，实测报告写为预期）。拿不准的记研判点台账呈终审。

两个边角的处置（首跑验证实撞后补）：**门禁+补救动作的复合句**（"抽查发现系统性错误后重跑同类全部记录"）——判定半边照拎成 check，补救半边优先落 retry 容器回路（check 不过带反馈整组重跑）；容器粒度粗于原文动作粒度时如实记台账，不硬造步骤也不静默丢弃。**存在但本体未引用的附属文件**（如宿主 agent 的配置件）——不进翻译也不进 --assets 清单，登记台账呈终审由人裁随不随包（它可能是给别的消费者的，翻译者无权替裁）。

**交付面——产物必须自包含**：spec 步骤正文引用的每个包内路径，交付目录里必须真有那个文件——原文的 scripts/、references/ 等附属资产**随产物同目录交付**（产物落原 skill 目录时天然满足——附属文件本来就在；产物另立目录或 pack 分发时必须把被引资产一并带走）。**交付写盘遇同名旧文件先备份再覆盖**：目标位置已有旧版 spec.md/source.md 时,先 `cp` 出带时间戳的 `.bak` 副本留原目录再写入,交付告知点明备份文件名——旧版可能被用户改过或正被引用,直接覆盖等于替用户销毁其资产。**悬空指针是保真缺陷不是风格问题**（实锤：hopbuild v1 产物只交 spec/SKILL/source 三件，14 处"读 references/x"全悬空——执行者按指针取流程真身时两手空空，流程随依赖一起丢失）。合理关增设**指针闭合核**：扫产物步骤正文里的包内路径引用，逐个对照交付清单，悬空即不过。

**与既有原则的关系**：本契约是「忠于原始语义」（首要原则 1）在多文件输入上的具体化——原文的"承诺"不只在本体里，被引文件里的门禁与闸门同样是原文语义，丢了同样是失真；「探索-核验-提交分离」（首要原则 2）在此的兑现形态就是流程性引用里的门禁句必须落成引擎强制的 check，不许收进 act free 的散文里。

## 构建原则（六面参考——2026-08-20 降位:不再作为顶层关卡判据,作为展开层与终审的参考面）【决策：作者六面定形 2026-08-16;降位 2026-08-20】 ^anc-build-principles

**六面是理想产物的属性描述**，供展开层按节点类型取用、终审时人参考；**顶层关卡不按六面全量拦**（关卡判据=首要原则四条）。知识件/primer 是注入投影（冲突以本章为准）。

**1. 探索-核验-提交三段式（事务面）**：任务的正统事务形态，每段正向构造与禁令一体——
- **工作区探索**：试错段全部可逆，中间产物入 work_zone 沙盒；不可逆动作不得混入探索段；
- **核验迭代**：check 验收（机器可验）/confirm（人审，仅原文真要人拍板），不过带反馈重跑——验收在提交之前；核验不得跳过或降级为 reason 散文；
- **（尽量）幂等提交**：不可逆动作隔离在 commit、前序把关闸门已放行（confirm/足够 check/环境预授权三选一）、自身按业务键幂等重放不加害。

**2. 知识与信息自洽（信息面）**：每个消费方拿到的信息恰好够用，**不多也不少**——
- **步骤自足**：每步的 摘要行+描述+`←`输入+注入知识 必须自足（描述引用的每样东西都在执行 LLM 视野内）——**判自足的前提是懂执行链上下文机制**（执行 LLM 每步看到什么/看不到什么：全局骨架只有摘要行、别步描述细节与 body 不可见、未经 `←` 声明的变量值不可见、翻译时原文不随产物走），此机制本身是翻译各环节的必须知识（primer『执行时每步能看到什么』节承载，写 I/O 与写描述的步骤必注入——不懂视野机制的自足判断=盲判）；
- **I/O 恰如其分**：Inputs=任务的业务输入（不漏不添；执行设施不进），Outputs=原文承诺的交付物（不漏不添，中间产物不进）；
- **注入不多不少**：每步只注该步需要的判据切片，无判据的机械步零注入（对产物 spec 与 hopbuild 自身注入图同适用）；
- **缓存亲和**：产物 spec 的执行是同 run 内几十次独立 LLM 调用，跨步不变的内容（头部契约/骨架/spec 级知识）引擎按稳定前缀缓存（prompt 组装分层与 cache_control 归引擎——见 [[prompt-assembler]]），**翻译侧的责任是别把稳定面写脏**：判据外置进知识件走 doc-ref（内联进各步 `>` 描述=每步独有文本,缓存不了还重复付费）；同类步骤共用同一知识切片（十个循环体步骤引同一节=一份缓存,各自内联=十份全价）；spec 级恒需知识上提 Constraints 全局注入,别在每步重引。判据：**执行时逐字节重复出现的内容必须有单一来源**——这与"注入不多不少"同根（重复注入既是浪费也是缓存杀手）。

**3. LLM 输出（输出面）**：**结构就简，量级控制**——
- 结构就简：首选单值/平面字段，嵌套结构易崩塌；判定输出 enum 化；
- 量级控制：单步输出受控（>~30 条结构化条目必拆或分段落盘）；要大结构拆步或"reason 平面字段→act body 机械组装"。

**4. HITL 沟通（人机面）**：**注意力经济，形式高效沟通，信息充分必要**——
- 注意力经济：能推断的别问（default 给足）、必须问的一次问清、暂停点只留业务上真需要人拍板的；
- 形式高效：一个 ask=一个可独立作答的决策（合并=打包拍板，拆碎=碎问）；
- 信息充分必要：呈交依据完整（present_inputs 硬约束，不缩略不让人盲拍）；**该人研判的不得给 default 溜过**（裁量语义处新立 ask/confirm，忠实门终裁）。

**5. 结构完备（结构面）**：
- **循环任务明确识别**：重复性任务一个不漏——识别是原则，保障策略可选（for-each 结构保障 / 生成-核验-迭代，见策略章）；静态判据清单（编号清单逐类同构动作,数量写死）同属遍历——识别面含运行时列表与静态清单两形态（0025）；
- **整体结构合法**：数据链每个 `←` 追溯得到且类型匹配、validate 零 error、工具引用都在声明的工具面内；
- **retry 迭代闭环**：每个 retry 容器答得出"重跑凭什么会变好"（带反馈重跑/adaptive 换路/确定性失败不 retry 直接上报）——答不出的裸 retry 是缺陷。

**6. 语义完备（语义面——产物承载的语义必须完备：对源忠实不失真，表达明确不歧义）**：
- **忠实翻译**：只做结构化映射，不擅自增删业务步骤（核心观点归原 skill 作者）；某面无真实触发如实记录不强造；原文意图不清问作者不臆断；行为映射可核（每步可追到原文出处——草稿行尾括注即其载体）；

## 构建策略（过程的选择——缺省姿态，按情况可调）【决策：作者历轮定形】 ^anc-build-strategies

**策略=达成原则的过程选择**，是缺省而非铁律——用户点名或实跑反馈可调，检查关不拿策略当原则拦：

- **档位分路**（简单/复杂两策略分开）：
	- **简单任务=能一眼看清、直接做规划的**（轻档:根节点单轮直达叶子）;
	- **复杂任务=需要遵循步骤来分解执行做规划的**（重档:一次一层逐轮下钻——即渐进展开:第一版只做结构最小集〔拆循环/落核验/隔离不可逆〕,细分支/并行/知识外置留后续迭代;**循环一次只拆一层**,嵌套遍历只拆最外层、内层留任务描述——**用户点名『内层也要不漏』即一次拆到位**,策略让位于用户要求的典型例。量级判据:步骤量级≈原文段落量级,膨胀超 ~2 倍反省）。同一展开循环机器,粒度与实测组数不同。档位头部事务评估、呈审可改（作者点名即改档）;
	- **档位是节点属性,不是全局单值**（递归展开的粒度控制面）：任务级初始档只决定**根节点**的档与实测组数;下钻产生的每个子节点入队时各带自己的档——重档节点拆一层后,一眼看清的子节点标 light 入队（下轮直达叶子,递归自然收敛）,仍复杂的标 heavy（继续一次一层）。没有节点档=所有轮次共用一档,下钻永不收敛只能拆到底;
	- **自动升档（按节点）**：某节点的单轮规划 2 次 retry 内不成功=该节点『一眼看清』的前提证伪,第 3 次尝试起该节点转 heavy 只拆一层（升档只升当前节点,不牵连队列中其他节点;降档不自动,只升不降——重档节点为子节点标 light 是入队评估非降档）。
- **遍历保障两策略**（『不漏』是原则,for-each 只是策略之一——**本条是「简单直接生成/复杂按步骤生成」二分在条目粒度的特例**,与档位分路同一谱系:任务级分简单/复杂,条目级同样分）：
	- **生成-核验-迭代**=简单形态直接生成——先大面上生成,再核验步查完整性、缺口反馈迭代补（条目边界模糊/生成式产出/一眼可尽的批量,结构化循环反而僵硬——对应任务级的轻档直译）;
	- **结构保障**=复杂形态按步骤生成——loop for-each 引擎驱动游标结构性不漏（条目可枚举、逐项处理独立、批量大到一眼看不尽——对应任务级的重档分解）。
	- 两策略都合法达成宪法支柱『循环遍历不漏』（结构面·循环任务识别条）,选型按条目形态;核验路必须有真核验闭环（无核验的大面生成=裸赌,不算本策略）;**静态判据清单同属遍历**（0025:原文编号清单'检查以下 N 类'逐类同构动作——数量写死也是遍历,识别信号原只列运行时列表形态,9 类公式检查被翻成单 reason 散文枚举零闭环;primer 遍历句识别信号补第三条:前置 act 构造判据列表 for-each 驱动,或大面生成+逐类点名核验）;
	- **升档同构**：核验-迭代补了几轮仍有缺口=一眼可尽的前提证伪,改写 for-each（与任务级 2 次 retry 自动升重档同一规则）。
- **重档过程机制**（复杂任务按步骤生成的具体组织——轻档下退化为单轮平凡形态:一个节点、一轮落盘、结构与 I/O 一次做完）：
	- **关注点分步**：结构→I/O 与 ask 面→retry 面→执行细节，每步一个关注点——并做哪个都做不透（单轮作业三段的分工依据）;
	- **中间表示=HopSop 草稿**（详见专章）：分解段先出大纲不直写 spec 嵌套结构（两档同用记法,重档逐层各出一份、轻档全任务一份）;
		- **逐节点落盘**：展开循环每轮把本节点展开结果并入 work_zone 草稿——断点可续、重跑只补问题节点（轻档单轮即单次写盘）。

## 构件纪律（壳/spec/知识件各自的内容边界）【契约】 ^anc-build-discipline

- **壳**：四段式（触发/参数引导/执行委托/交付——参数段对齐 Inputs、交付段对齐 Outputs，两头不悬空）；参数表只列用户真有信息的参数（agent 自供的探测值不列）；**禁披露内部件**（不罗列知识件/注入机制/spec 内部结构——引擎自动注入，写出来=诱导预读后手工执行判据，绕开引擎强制）；@trace note 只写定位句。壳层契约权威（适用一切 pack 产物）在 [[hop-cli#^anc-cli-pack-shell]]，本节是 hopbuild 实例。
- **spec**：I/O 按信息面原则（知识与信息自洽）；参数面三关判归属（该不该存在→真需传递→用户填 vs agent 自供）——执行环境本就持有的信息不进 Inputs（实撞：cli_path 三级退场）。
- **知识件**：判据单一注入源，壳与 spec 正文不复制其内容（复制=第二真值必漂移）。
- **行文形态（全构件通用,2026-08-28 作者定——与 hopbuild2 行文原则/CLAUDE.md 说人话铁律同源）**：壳、spec 步骤说明、知识件的一切行文**用完整的话写清楚——不用缩略语,不用只有写的人自己才懂的简称和代号**,判据=没跟过构建过程的读者（含 LLM 执行者）一遍读懂。特别强调 LLM 受众：产物 spec 的最终读者是执行 LLM——它对压缩表述的理解比人更容易出错且非常不稳定,人读不懂会反问,LLM 不会反问、按猜的理解直接执行且不出声（实撞:步骤说明的缩写判据被执行 LLM 猜错,带错误理解跑完全程零报警）。翻译时原文里的口语简称也要展开——"按老规矩处理"这类原文表述,翻进 spec 前先向用户问清"老规矩"是什么再写全。

## 翻译流水线：迭代构建循环【决策】 ^anc-build-pipeline

**总纲**：**目标·约束 → 步骤 → I/O → 细节 → review → 迭代**的构建循环。构建策略章定"怎么选路"（简单/复杂档位、遍历两策略、重档过程机制——定义权威在彼处，本章引用不复制）；本章定"流程怎么走"。hopbuild 自身即构建循环的自应用。

**结构**（spec 步骤序）：

- **① 头部契约核查**（单事务：生成→呈审→修订闭环，对齐门 check final 放行）：
	- goal/约束/Inputs/Outputs/可用工具面
	- **档位评估**（策略章判据）一并生成呈审——档位是用户在对齐门可改的策略项；
- **② 递归展开构建循环**
	- 外层构建循环是 adaptive 事务，retry=6——终审意见轮与各关重跑共享，给作者多轮修订余地
	- **全段中途零 ask**：人机面注意力经济策略--人触点恒两处=①对齐门与本段末终审——对齐门管方向、终审管终裁，中途不要碎问；
	- 构建循环内实质性新增决策点记研判点台账、随终审一并呈裁——呈裁义务来自『该人研判的不得溜过』，延迟呈裁来自注意力经济，两条合成『记档后置』而非『当场问』：
  - **构建节点生成段**：call expand-node(root) 递归展开（展开器=独立可 call spec,单轮作业四拍+复合子步骤子 call 递归+edit_spec_tree 拼装——见下方「生成环机器」）。**中间产物一律落引擎 work_zone 涂鸦区**（`work_zone_path()` 取真身,2026-08-20 实撞改定——原 spec 写 `work_zone/…` 相对路径,解析到 workspace 根下裸目录:既污染用户工作区〔根残留 ignore 过一次〕又没进引擎隔离区;LLM 工具循环时代靠 LLM 遇 ENOENT 自调 makedirs 糊住,步骤 2 body 化后引擎直执零适应性,缺口裸露三例秒败。body 步经 `work_zone_path("<名>")` 取绝对路径;LLM 步经 `work_zone_root` 变量〔步骤 3 body 产出〕拿位置——两执行面同一真身）。**研判点台账是跨实例共享通道**（expand-node 递归子实例 append、主流程 5.7 read——各实例引擎 work_zone 互不相同）：主实例 `work_zone_path("judgement-log.md")` 绝对路径经 call 参数（expand-node 新增 Input `judgement_log`）逐层透传,全树共写一份（写侧工具对 work_zone 绝对路径放行,见 [[tools#^anc-exec-work-zone]]）。事务面『探索段产物入沙盒』;草稿文件退役:递归形态片段经 call 输出直接回传拼装,不再逐轮落盘草稿；
  - **整体关**（review 链前半，机器关）：
	  - validate 结构合法
	  - 语义合理（判据注入，不空口判——审 validate 查不了、单轮又不够全局的语义面：步骤自足全文过一遍〔抓跨节点隐式指代〕/retry 闭环逐容器/结构从简；量级仅参考且以本轮任务范围为准——迭代轮次的合理增长不算膨胀。数据链与类型归 validate 关，产物 ask 面归补 I/O 段+终审台账，不重查）
	  - 实测（构造案例〔组数按档位：轻单组/重按分支多组〕→ 逐组 init+首步核证 → 报告 → 实测关。
		  - 测试深度当前只做探证——init 便宜不烧执行 LLM；真起全程子实例的深度实测，等探证实证不足再升）；
  - **终审收口**（review 链后半，人关）：
	  - **审阅走文件**——备料步把审阅包（spec 全文+研判点台账+实测报告）**就地汇集**成 work_zone 单一审阅文件（中间产物已恒居 work_zone——生成段 I/O 约定；盘上引用汇编，不经变量搬运大内容），ask 呈**审阅纲要**（各件要点计数+结论+文件路径，present_inputs 呈纲要即全量——量级几十 K 的载荷内联终端=把人淹在滚屏里，注意力经济反面；
	  - 人按路径打开文件审，意见原话回填）+ **意见闸 check final**（机械闸非二次审查——忠实审查本体是 ask 的真人;引擎重跑回路由 check final fail 驱动,判 ask 产出故必在其后。「忠实门」=终审 ask+意见闸的合称）——意见空放行；
	  - 意见非空回填 iter_feedback 重跑（清单定向入队问题节点，不重展开合格部分）；意见指向头部契约=超本事务范围，如实 fail 人重发起；
	  - 作者要中止=run 层中止；
- **③ 提交**：commit 写盘（把关在前：终审真人已审+忠实门放行）→ exit。


**生成环机器**（上面结构段 ② 生成段的定义展开——「单轮作业」定一轮怎么做，「递归展开」定轮与轮怎么递归。由原则与策略推演，每则标注推导源，源变则随变）：

1. **单轮作业**（←事务面『探索-核验-提交三段式』×策略章『关注点分步』：一个节点的展开就是一个小事务——先构造〔分解与补 I/O 两个关注点分立〕后核验，不过不出；对一个节点做一遍，三段依次）：
   - **SOP 分解**：把节点的任务描述对回原文范围。本段只定控制流与任务描述，不写 I/O 不写细节——控制流是骨骼，先立骨骼再长肉：
	   - 用且只用三种控制结构改写成 HopSop 骨架——重复语义（"每个/逐个/依次"）落 `[loop]`，条件语义（"如果/视…而定/分情况"）落 `[branch]`+`[case(…)]`，有共同边界或事务性的一组动作落 `[subtask]`，其余为顺序普通步骤；
	   - 同时做结构化附带：探索/核验/提交三段分离（试错段后置核验、不可逆动作单列）。
   - **补 I/O 与细节（约束先行，简单直出）**——约束与细节的关系如同原则/策略之于产物：约束是该节点的恒定要求，细节是满足约束的具体构造。简单/复杂二分在此再现（任务级分档、条目级分遍历策略、节点级分本条——同一规则第三个粒度）：
	   - **简单节点直出**：一眼能写对的，I/O 与细节一次成文；
	   - **复杂节点约束先行**：一次想不清细节的（多输入交织/输出结构有选择/失败路径不明），先把**该节点的约束**定下来。细节基于这些约束构造。约束想不清=节点还太大，该回分解段再拆（升档同构）。**约束=该节点上一切先于细节可定、且钉住细节自由度的要求**——下面是常见类别（开放清单非穷举：原文对该节点的特定"必须/不可"、顺序依赖、时限/资源要求等，凡属先于细节可定的都梳理进来）：
		   - **I/O 契约**（最容易先想清，先写定）：数据从哪来给谁用，不依赖细节反过来钉住细节——`←` 输入（判据：这就是在决定该步执行视野——执行要用的信息一个不能漏）、`→` 输出（判据：名字+类型+`#` 说明齐全的接口文档纪律；输出受控、结构从简、判定 enum 化）；
		   - **原文要求**：原文对该节点范围的一切约束性表达逐条摘出——显式的「必须/不可」只是最好认的；还有**条件性要求**（「如果…就…」「仅当」）、**顺序与前置**（「先…再…」「…之后才」）、**范围限定**（「只处理…」「不含…」）、**质量与程度**（「至少/不超过/优先」）、**隐含在动词里的**（「核对」含比对基准、「确认」含人或凭据）。头部 Constraints 管全局，节点级的落在这——它们后面要落成 check、case 条件或写进 `>` 描述，先摘出来才不会在细节里被顺手丢掉；
		   - **动作性质**：可逆性（定 act 还是 commit）、用什么工具做（在 tools_available 面内）、重放安不安全（幂等要求）；
		   - **失败语义**：retry 值得吗、失败该报什么、部分完成算什么（继续/回滚/如实报）。
	   - **细节构造的内容与判据**（两路同用；复杂路的 I/O 已在约束环定好，此处只做剩余）：
		   - 定步骤类型（按动词：分析判断→reason／计算执行→act／验证→check／人审→confirm／要数据→ask／不可逆→commit）
		   - 写 `>` 执行说明（判据：自足性——描述引用的每样东西都在该步视野内）
		   - act/commit 纯机械时配 hop_python body
		   - 事务容器定 retry 值（判据：答得出『重跑凭什么变好』——retry 该不该有已在失败语义约束里定）；
   - **结构与语义核查**（本节点验收关，不过带反馈重跑本轮）：
	   - 结构面机械项交 validate_spec 内置工具——in-process 直验裸片段（工具契约 [[tools/spec-tree-tools#^anc-exec-builtin-validate-tool]]:与引擎同版本零环境依赖,内容直传不落盘;片段语义同 [[hop-cli#^anc-cli-validate-response]] 片段条款,known_vars 注入上层已知变量入 V1 来源）,`←` 可追溯/类型匹配/容器合法全是 validate 规则,LLM 空口判既浪费又不可靠;工具没法判的结构（无谓嵌套/单步输出受控）核查步补核；
	   - 语义面核忠实——节点任务范围覆盖无遗漏且**对回原文**（核查步视野必须含原文——骨架回声〔把正在执行的构建流程自身步骤当翻译对象输出〕在此拦）、工具引用都在声明面内、描述不引用视野外信息。结构面管"数据链不断"，语义面管"翻译不失真"——两面都过本轮才算完；
2. **递归展开=call 自递归**（2026-08-19 作者改判 v4.0.0——原工作清单队列形态退役。改判理由：队列=手工重建递归运行时,清单格式约定/游标 body/档位尾段解析/编号换算全是它的设施成本,历轮实撞〔格式漂移/判据死链/5.2b 静默吞〕全出自这套设施;而『定向重跑』『进度可见』两条队列优势经推演证伪——递归形态对问题子树再 call 一次即定向重跑,树编号即进度。队列形态对生成 LLM 编程能力挑战大、spec 可读性差〔解释 work_items 花 primer 一整节=设计味道不对的信号〕）：
	- **展开器独立成可 call spec**（`expand-node.md`,与主 spec 同目录——DirSpecProvider 同目录寻址）：输入=node_task（本节点任务描述）+ parent_context（父骨架片段+可用变量清单——**调用栈天然传递父上下文**,队列形态丢上下文靠手工补的病根消除）+ skill_content + header_final;输出=fragment（本子树**完整展开**的 spec 片段,编号相对从 1 起）;
	- **单轮作业原样保留**（分解→升格→片段 validate→核查——四拍是展开的原子工序,与形态无关）;分解发现仍复合的子步骤 → **逐个 `call expand-node(子任务, 本层骨架为 parent_context)`**——递归就在这一步;子片段回来后 **edit_spec_tree 拼进本层骨架**（replace_children 替换占位叶子,编号机械重刷——序号一致性由工具保证非 LLM 手工）;
	- **简单任务=递归的天然退化**——根节点一层拆完全是叶子,零子 call,一次调用返回完整 spec（不再需要显式档位分叉 branch:『一眼看清就直达叶子,看不清就拆一层递归』是展开器内的自然判断,task_weight 只保留为实测组数依据）;
	- **深度与并发**：max_call_depth=10 覆盖重档 4-5 层实际需求;互不依赖的兄弟子树可 `call expand-node(...) parallel` 并发展开（队列形态做不到的白得能力,首版先串行,并发留观察）;
	- **占位形态沿用**（容器行+`[reason] 待展开——<任务描述>` 占位叶子——S5 约束不变,子 call 返回后由 edit_spec_tree 替换）;
	- **量级线是分解步硬判据**（2026-08-20 作者拍板『同意,应该有 check 核验』——重档实录:flash 对 1.8KB 复合题选择一层硬写全树不留占位,正文+thinking 顶满 65536 三轮 OUTPUT_TRUNCATED;『一眼看不清才拆』的判断弱模型不执行,量级线从合理关事后审〔仅提示〕前移为分解步事前拆〕）：**本层 node_sop 预估步骤数超 ~30 行必须拆层留占位,不许硬写**——超线的复合段收敛为容器行+占位叶子入 sub_tasks;1.4 单轮核查加机械核（**check body 数 node_sop 步骤行数,超线且 sub_tasks 空=硬写违规当场拒**——量级判据机械可查,不靠 LLM 自律）。

**失败语义**（全部由容器/call 结构承载，不造跨容器跳转）：

- 单轮核查失败 → 回填 node_feedback，展开器内子事务 retry 本轮定向修正（节点内问题不出本层）；
- 子 call 失败 → 按 call 语义上浮本层（CalleeFailure）——本层事务 retry 重调该子树（定向重跑=对问题子树再 call 一次）；
- 整体关失败 / 终审意见 → 回填 iter_feedback，大循环事务 retry：按反馈重 call 受影响子树（意见含节点路径即定向）；
- retry 耗尽 → fail 上浮外层 adaptive 重规划（交付契约与各验收关不可改）。

## 中间表示=HopSop 草稿【决策：作者定 2026-08-16】 ^anc-build-hopsop-draft

结构段的中间产物用什么格式承载——定 HopSop 大纲，不用自定义嵌套 Types：

- **是什么**：SOP 分解段的产出（hopsop_draft）是一份 HopSop 大纲——text 纯文本，数字编号+`[subtask]`/`[loop]`/`[branch]`+`[case(…)]` 节点行；头部契约另走平面 yaml（header_final），两者分开承载；
- **为什么不用嵌套 Types**：中间产物用自定义嵌套结构=逼 LLM 每步输出赌格式（嵌套越深错误率越高），违自家输出面原则『结构就简』；HopSop 大纲是 LLM 的自然输出形态；
- **记法词汇用英文版**：与 spec 所用 HopSpec 关键词同一词族（对偶表见概念层 HopSop §五）——升格时 `[subtask]`→subtask、`[loop]`→loop、`[branch]`+`[case]`→branch+case 同名直通，词汇零换挡；
- **复合类型不在草稿立**：延迟到细节升格时就地立 Types——草稿只管控制流；
- **取舍**：放弃中间产物的机械可核性（大纲是散文不是 AST——但升格后的片段立刻过 validate,机械核在下一环补上），换每步 LLM 输出都是自然形态。

**忠实关（自检层的忠实性检查）**：终审忠实门是人审兜底,不能让首要原则第 0 条只靠人审——自检阶段必须有翻译者自己的忠实性对读关,置于合法关之后、合理关之前（先保文法合法,再保内容不丢,再审结构合理）。作业形态：拿 source.md 原文逐段对读产物,每段核两问——**完备性**（这段的判据/规则/模板/阈值在产物哪里?合法落点四处:步骤正文/Constraints/随包知识文档/研判点台账——台账记"不译入及理由"也算有落点,四处全无=知识丢失）;**忠实性**（落进产物的表述语义变没变?三个高发变味形态:强度弱化/范围收窄/条件偷换）。产出=可审计的对读结论（对读段数/补落数/纠偏数入实测报告）,不是印象式自评。

**合法关的 warning 表态纪律**：合法关判据=零 error **加 warning 逐条表态**——每条 warning 要么修掉、要么在研判点台账记一句为什么留（P6 失败即停/B2 外部工具运行期对账这类正当 warn 就是一句话）。不许静默路过（实抓:R6 sandbox 两条 B7 形态欠账在七班接力+多轮自检里零人表态,不是判了可留,是没人看——同轮其他路对各自 P6 warn 都主动记了台账,说明缺的是硬性条款不是能力）。

**deep-validate 关的必走与缓办口径**：宪法 6 两道工具核验缺一不算交付,deep-validate 不是例行装饰——实测它抓的部署缺口（命令白名单缺席/绝对路径输入/act free 写域越界/判官零工具面）全部是"validate 全绿但真机必死"的形态,恰是它的设计定位。**正式交付必跑**;**验证跑可缓办但必申报**——报告里固定一行"deep-validate:未跑（验证跑不起引擎 run）,收编时必补",静默蒸发即流程缺陷（实抓:两轮验证跑六路里五路只字未提,只一路如实申报）。批量场景用 dv-batch（scripts/deep-validate/dv-batch.md,spec_paths 列表一次体检,七件约 3-6 分钟实测）。

**明确易懂关（自检层的宪法 1 检查）**：首要原则第 1 条同样不能只靠终审人审——自检阶段补一道明确易懂关,置于合理关之后、实测关之前。检查姿态与忠实关恰好相反：**忠实关拿原文对读,明确易懂关不看原文只读产物**——坐进"没跟过翻译过程、第一次拿到这份 spec"的读者座位,通读产物全文核四面：①**行文**——步骤说明/变量说明/判据是不是完整的话,说人话不写文言文：有没有缩略语、自造简称、只有翻译过程里才有含义的代号（执行 LLM 没跟过翻译过程,这类词到它手里就是噪声或误导）;有没有压缩断句、四字块连缀的文言腔（"料须经喂齐""不过即回"这类——每个都要展开成完整的句子,LLM 对压缩表述的理解比人更不稳定,且它不会反问、按猜的理解直接执行）;②**布局**——分立事项分条列了吗,有没有多件事挤成一坨长段（判据/清单/前提逐条一行,长段落里藏三个判据=执行 LLM 漏读其二;段落只装一个主题,超了就拆条目或拆段）;③**变量接口**——每个变量的名字+`#` 说明能不能让下游步骤不猜就懂（装的是路径还是内容、文本还是结构）;④**强语气在场**——门禁/禁令/红线句读起来仍是"必须/不得"的强度（忠实关核的是"与原文比有没有弱化",本关核的是"产物自身读起来够不够硬"——两关一个对源一个对己,不重复）。产出同样要可审计：通读一遍,改写了几处、改了哪类,入实测报告。NL 形态忠实关/明确易懂关落 v1 SKILL 第 5 步;引擎强制形态由 hopbuild2 批次落位（欠账随 0072 卡第⑦项）。
