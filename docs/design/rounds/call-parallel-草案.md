## 一、统一概念：parallel = 步骤级异步派发属性

### 1a. 定义

翻转后（parallel = callee 并发性质申报：自包含/无共享写/可安全多实例），申报的执行语义**全局统一为一条**：

> **主线执行到标注 parallel 的步骤（subtask 或 call）→ 派出去跑，不等它完，主线继续推进下一兄弟/下一迭代；容器要收工时，必须先把本容器里派出去的活全部等完收好（收齐）。**

没有"静态并行组"和"渐进派发"两种机制——只有一种：**主线串行推进 × 标注步骤派出去跑 × 容器边界收齐**。并发从"容器的形态"变成"步骤的性质"，caller 侧零调度语义。

**并发名额不进 spec，走 hop 系统配置，缺省 5，且主线自己也算一路**（✅ 作者拍板 2026-08-10）：配置 N = 主线 1 路 + 同时最多 N−1 个在跑的活；配成 1 = 名额全被主线占着、一个活也派不出，parallel 标注全部退化为主线同步执行——**全串行调试口子由此天然成立，不需要任何附加机制**。落点沿用现有 `ResourceLimits.max_concurrent_workers ?? 5`，统一模型下即全局名额池的同一配置项，零新配置（注释口径改为"含主线的总并发路数"）。

### 1b. 三个规范形态（同一模型的实例）

```
[loop for-each x in xs, collect r into rs]     ── 形态一：循环体整体异步
  1.1 [subtask parallel] 处理一项               ← 每迭代派出一个，渐进并发
      + → r

[subtask] 汇总                                  ── 形态二：兄弟混排
  2.1 [subtask a parallel]   ← 派出去跑，主线继续
  2.2 [subtask b parallel]   ← 派出去跑（a 也还在跑）
  2.3 [subtask c]            ← 主线自己同步做（a、b 照常在跑）
  2.4 [subtask d parallel]   ← 派出去跑
                              ← 容器边界：等 a/b/d 全部跑完收好，容器才 completed

[loop for-each ch in chs, collect built into results]  ── 形态三：流水线（原 call parallel 需求）
  3.1 [act] OCR/钉版/确认     ← 主线串行，有序依赖
  3.2 [call construct(src: confirmed) parallel]  ← 派出构建，下一章生产与本章构建重叠
      + → built
```

**形态二的关键读法**：c 未标注 ≠ c 要等 a、b——主线做 c 的时候 a、b 照常在跑。并发安全由被派出方的申报保证（a、b 申报了自包含 → 跟谁同时跑都安全），主线步骤是主线本身、无须申报。未标注只意味着"c 自己不被派出去"（主线停在 c 做完它，才轮到派 d）。

### 1c. 现有形态归约（旧机制是新模型的退化特例）

| 现有形态 | 归约为 |
|---|---|
| 静态 parallel 组（`[subtask parallel]` + children）| 兄弟全标注的形态二——主线一路派完没有同步步骤，边界收齐，效果=同时启动全部 join |
| `loop for-each ... parallel`（静态批 fan-out）| 形态一——体标注、渐进派发；列表已知时引擎可仍走批量 fan-out 作为**执行策略优化**，语义等价（顺序模拟等价性是 exec-engine 决策 4 既有基石，同一论证覆盖"批量 vs 渐进"） |
| TODO 的 call parallel | 形态三——call 标注出现在循环体内，与形态一同构（派发单位从 subtask 换成 call，子实例机制本就同构） |

即：**翻转不是措辞重读，是执行模型统一**——原两条并行通道（静态组、for-each fan-out）收编为统一模型的特例。✅ 作者拍板（2026-08-10）：**旧通道退役、`loop ... parallel` 循环头属性废除**——旧形态归约进新模型后不留双轨；存量 spec 机械迁移（循环头 parallel 去掉、体内步骤加标注，裸步骤序列循环体包一层 subtask 正好显式化派发单位）。列表已知时的批量 fan-out 若保留，只能作为引擎内部执行策略优化，语义面单一口径。

### 1d. 数据面：无 Future 原则，输出只经容器边界

统一模型下数据规则一条：**parallel 步骤的输出，在同一容器里的后续步骤不许直接用**（值可能还没回来；S12 泛化为此禁令，静态拦），只经容器边界导出：

- loop：collect 子句收列表（单项端=parallel 步骤的 `+ →`，零新文法）；
- subtask 容器：`+ →` 声明输出在收尾等待完成后按既有容器输出提升规则收取；
- 容器内真要用它的输出？把两者包进同一个子 subtask（依赖显式化为串行结构）。允许容器内直接用=允许在半路等某一个结果=变相把 Future 凭据交给作者。

这保持了结构化并发的既定取舍（凭据不暴露、无 await 单个、无 cancel），并让 S12 从"校验容器声明合法"变为"校验容器内没有人引用还没跑完的输出"——检查逻辑同源（变量流图跨项边），方向调整。

## 二、收齐（gather）：机制与时机（核心，泛化到一切容器）

### 2a. 收齐 = 容器完成条件的扩展，非新步骤非新状态

> 任何容器的完成条件：主线走完（兄弟序列走完/迭代耗尽/break）**∧ 本容器派出去的活全部跑完收好**。

引擎侧零新状态机形态："children 未全终态则容器未完"本就是不变量，等待的位置天然存在。真正的改动只有一处：**推进条件放宽**（parallel 步骤派出去了就算"主线可以继续"），完成条件不动。**"派出去"与"算完成"解耦，是整个模型在引擎侧的全部本质**——三个形态共用这一处解耦。

### 2b. 时机裁决：在哪里等？（三候选，**作者已定 A**，2026-08-10）

- **A. 容器边界（✅ 作者拍板）**：主线走完，就地等所有在跑的活收完；
- B. 首次消费点：谁用列表，就在谁那里才开始等。**拒绝**——看似能多重叠一段（循环后不相干的步骤可以先跑），但破坏三条根基：①容器整体性（容器标了 completed，里面的活还在跑）；②失败归属（容器完了之后某个活失败了，账记给谁——容器已终态不可翻案）；③HITL 归属（还没跑完的活要问人，介入请求却挂在一个"已完成"的容器下面）。结构化并发的要义正是拿这点边缘并发余量换作用域封闭性；
- C. 显式 gather 步骤（作者写一行"在这收"）：**拒绝**——作者手里没有凭据（不暴露是既定取舍）；收在哪、收什么，引擎自己都知道，新文法纯冗余。

### 2c. 随到随收贯穿全程，收尾等待只在边界

- **随到随收（reap）**：哪个活跑完了，当场收——成功的取输出、失败的记 FailRecord，**名额立刻腾出来**。这是贯穿主线全程的连续动作：不当场收，名额转不起来，流水线就死了；
- **收尾等待（drain）**：主线走完后，等剩下在跑的活一个个收完。这才是作者感知到的"等"——容器显示"还在跑"直到全部收好。
- 即：**收齐 = 全程随到随收 + 边界一次收尾等待**。随到随收是引擎内部动作，作者只看见收尾等待。
- **满了等名额，是收尾等待的对偶**：派发时名额满了，主线就停在派发点等——和收尾等待是同一个"等哪个活先跑完"的机制，只是一个等到出空名额就走，一个等到全部收完才走。全模型只有这两个等待位置（容器内不许用输出的禁令保证了没有第三个）。

### 2d. 边界情形定形

- **break/提前退出**：=「后面不派了」，照常收尾等待（结果还是要的，等完收好——正常路径不杀活）；
- **主线步骤失败时，在跑的活怎么办**（✅ **作者拍板 2026-08-10：全部杀死，不留幻影**）：主线失败 → 引擎立即终止全部在跑的活，容器 settle 为 failed。理由：失败了结果就没人要了，让活继续跑只会留下"容器已败、里面还有东西在动"的幻影状态——普通人的心智模型就是"失败=停"，降低认知难度优先。被杀的活记 killed 终态（不算 failed、不产出结果，崩溃恢复时不复活）。
  - **与「不做 cancel」既定取舍的关系**：不冲突，边界收窄——不做的是**作者面的 cancel**（spec 里没有撤销语法，凭据仍不暴露）；杀活是**引擎失败路径的内部清场动作**，作者无感。break 是正常路径照旧不杀，只有失败路径杀；
  - 连带代价（正式设计须落）：引擎要有终止子实例的手段——独立模式=进程内中止信号；复用模式=子实例是 driver 起的外部会话，引擎只能记 killed 并把"该杀谁"交给 driver 协议执行，杀不干净时靠 killed 记账保证语义面无幻影（账面终态，即便外部进程苟活也不再被收割）；
- **在跑的活失败**：按容器导出形态定——loop+collect：不贡献元素、列表变短（既有唯一例外语义原样泛化）；subtask 容器具名输出：收完后容器 fail（函数级，FailRecord 加壳）——部分失败例外仍只属于集合语义，不扩散；
- **在跑的活要问人（paused/HITL）**：冒泡不变（confirm 全局直达/ask 逐层自治）；收尾等待把它也等上（等人无限期，无超时哲学）；"等人时把名额让出来"是 P1 优化，不改收齐语义——收尾等的是跑完，不管占不占名额；
- **几个活同时要问人**：统一模型下必然出现（形态二 a、b 同时 paused）——放宽现有"一次只有一个 paused"假设是概念级必需，非实现细节；
- **嵌套**：各容器管各的账、各自收齐；内层容器整体也可标注 parallel（它对外就是一个步骤）——容器的树状嵌套即结构化并发的 TaskGroup 树。

## 三、支撑概念的关键技术可行性

（收链凭据：engine.ts/engine-traverse.ts/dispatcher.ts/parser.ts/validator.ts 实读；`^anc-exec-parallel-batch` / `^anc-exec-parallel-fanout-advisor` / `^anc-exec-call-recursion` / `^anc-exec-pause-persist` 等）

1. **单一机制统摄成立**：在跑的活的记账+名额+随到随收/收尾等待，一套机制覆盖三形态。基建全现成——子实例双目录同构（calls/ 与 parallel/ 一行切换）、滑动窗口补位/原子防重/流式派发日志（fanoutSchedule + dispatched + recordParallelDispatch 本就是连续派发形态）、终态判定（isChildTerminal）、失败加壳通道。**既有静态 fan-out 通道（collectParallelBatch→批量→单点 join）语义上是新模型特例**，迁移可分步：新通道先并行存在，旧通道形态归约后退役或留作批量优化；
2. **"派出去"与"算完成"解耦，改动确实局部**：两个条件同在推进枢纽函数（propagateCompletion/dfsNextStep），放宽一类判定即可。⚠️ 该函数有实撞史（parallel loop 无限重跑），且统一模型下它要同时服务三形态——**这是第一风险点**，回归矩阵必须覆盖混排/嵌套/三形态交叉；
3. **收齐所需两个信息引擎确有，且崩溃恢复后可重建**：「主线走完没有」=推进单点逻辑；「还有哪些活在跑」=子实例状态独立落盘+记账进 StateFile（随既有原子写与 load 恢复通道）——容器封闭性承诺在崩溃面前不破，概念级必需已有载体；
4. **两模式都能落**：独立模式=进程内异步等待（泳道池先例）；复用模式引擎没有进程可等，"等哪个活先跑完"外化为对 driver 的介入形态（fanoutSchedule wait 响应先例现成）——模型不绑并发原语，符合 exec-engine 决策 4 既有口径；v1 期间 driver 手工代行已验证形态三语义（hopkb 实撞）；
5. **文法近零增量**：`[subtask parallel]` 现成；`[call <Id>(...) parallel]` 有一处 parser 硬拦截（平衡扫描要求 `)` 紧贴 `]`，括号后属性无通道）小改可通；S12 泛化为容器内消费禁令，扫描逻辑同源。附带核实：TODO 所引 validator info"未声明但判定独立"**文档有文、代码未实现**（已标 v1 偏差）——翻转论据不受影响，但该 info 在统一模型下语义也变了（"判定独立，可考虑让 callee 申报"）。

**可行性结论：统一模型成立，且比窄版（只给 call 加修饰）更省**——不是在两条既有并行通道旁再加第三条，而是一套机制收编全部形态；唯一新机制仍是"派出去与算完成解耦"这一处放宽。风险集中在推进枢纽函数改造（第 2 点⚠️）与旧通道迁移的过渡期共存管理。
