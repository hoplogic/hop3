## 为什么要这个工具【决策】

run 一旦 completed，产物 spec 就成了孤儿——发现缺陷时的选项只剩两条烂路：**整树重跑**（0036 实撞：35KB 语料重建 5.6 小时/390 万 tokens，只为改两处步骤说明），或**人肉裸改**（零把关，改坏无人拦）。hopbuild2 内部的修错机械（D57 质检环修错步、D70 意见轮 fix 路由）只活在构建 run 的生命周期内，run 外无入口。

作者点破（2026-09-02，0036 轮终审后）："现在要考虑的是，应该有一个工具，来做定向修正，而不是动辄从头重构。" 命名 hopfix（与 hopbuild/hopjit 同族）。

## 定位与四层分工【决策+契约】 ^anc-meta-hopfix-position

| 工具 | 管什么 | 时机 | 成本 |
|------|--------|------|------|
| hopbuild/hopbuild2 | 造——NL skill → HopSpec | 从零构建 | 小时级 |
| validate | 查——静态文法（51 条规则） | 每次改动后 | 秒级 |
| deep-validate | 查——运行期假设（LLM 推理） | 跑前/改后 | 分钟级 |
| **hopfix** | **修——按工单定向修正既有 spec** | 查出缺陷后 | 分钟级 |

查-修闭环：deep-validate 的 risk_report 可直接作 hopfix 的结构化工单（机器对机器，不经人转写）。服务面不限 hopbuild2 产物——手写 spec、examples、任务卡同适用。

**A 案对 B 案胜出**（B=hopbuild2 加 fix 模式入口）：通用性 + 独立工具不拖构建器重装置（修两个步骤不必过 133 研判点体量的流程）。B 案留作 hopfix 落地后的薄接线（hopbuild2 耗尽兜底 rebuild 选项旁加"转 hopfix"指引），另批做。

## 能力契约【契约】 ^anc-meta-hopfix-contract

- **Inputs**：
  - `spec_path: line`——待修 spec 的 workspace 相对路径（路径形态闸复用 D72② 三判：绝对拒/含 .. 拒/不在场拒，坏形态带拒因重问）；
  - `fix_order: text`——修正工单。**双收**（作者拍板③）：自然语言意见原话（"步骤 27 的发射卡改成 call parallel 形态"）或结构化报告全文（deep-validate risk_report / 合理关缺陷清单）——分诊步统一拆解，不区分入口。
- **Output**：`fix_report: markdown`——修了什么（逐项：节点/动作/依据）/ 拒了什么（逐项拒因与指路）/ 三层把关各自结论 / 快照路径。
- **修正范围边界**：只修**产物文本可定向编辑**的局部缺陷（补步骤/换执行形态/改措辞/加输入声明/修变量链）。**结构性拆法与头部契约超范围**——分诊判出即如实拒并指路（该走 hopbuild2 重构或人工），**拒是正确交付不是失败**（复用 D70 四档判据的分诊哲学：拿不准局部还是结构时倾向试修——修不动经把关失败路径如实上浮，选错"拒"则把可修的推去重烧小时级）。

## 关键逻辑（HopSop）【契约】 ^anc-meta-hopfix-sop

1. **收件与体检**：路径闸（D72② 形态）→ 读原件全文 + validate 基线（error/warning 计数与族分布——修后对照）。**基线含 error 时响亮提示不拒收**（2026-09-02 首实战复盘,作者拍 A 案——基线 error 进 baseline_note 明细留痕,供层一对照与人读;不拒收的理由:hopfix 的工单本身可能就是"修掉这个 validate error",拒收恰把正当场景拒之门外）；
2. **分诊**：工单拆解为节点级修正项清单，逐项判档（局部可修 / 结构性拒 / 契约面拒），拒项带拒因与指路；全拒则直接出报告终止（零改动零快照）；
3. **定向编辑——LLM 只产编辑清单，全文拼装归 body**（deep-validate 自检风险 2 后改定，2026-09-02：初版让 LLM 产出修正草稿全文，与"禁全文重写"约束当面冲突——被修 spec 数万字级时全文经 LLM 输出变量吐出必撞单次回复输出上限，#55/D72 同族病）：
   - LLM 步产出 `edits: [{node_path, fragment}]` 编辑清单（replace_node 的 replacements 原生形态——每项只写受影响节点的完整新片段），全文拼装由下一步 body 一次批量调用 `replace_node(spec_text, replacements: edits)` 引擎直执完成，**LLM 永不吐全文**；
   - 四档动作统一归一 replace 形态（body 禁循环、insert_node 是单点调用，逐项套用做不了——归一后一次批量调用零循环）：edit_text/edit_body=该节点新片段；add_step=落位处兄弟节点替换成"原节点+新步骤"片段；remove_step=父容器节点替换成去掉该子步的片段；
   - **编辑清单的 YAML 交付纪律**（自检风险 1：清单含自由文本值位 order_quote/reject_reason，工单原话天然含 ASCII 定界符，flow 形态裸值必炸解析）：自由文本字段一律块标量（`字段: |`）交付，禁 flow 行内映射，引号是语法必需件照抄保留——分诊步与编辑步说明明文教；
   - **fragment 步号自洽约定同须明文教**（2026-09-02 首实战复盘补——replace_node 要求片段内步号从 "1." 起自洽编号,不写原文真实点分步号;实撞:LLM 反复用真实步号〔"18.1.1."/"12.1."〕撞 "references non-existent parent" 解析拒,约半数重试轮烧在此,撞墙自悟后重试轮上下文重置又复犯——约定不进说明,每轮都要重新撞一遍）；
4. **三层把关**（作者拍板②，递进关系——机械保范围、语义保正确、深检保运行期）：
   - **层一·改动外零变化机械闸**（body 引擎直执）：范围保护经"编辑清单+引擎拼装"架构**由构造保证**（首测后改定 2026-09-02——初版设计"节点切片 diff 比对白名单"，实现时发现 read_spec_tree 无枚举全节点的模式；而架构本身已封死威胁面：LLM 只产 edits 清单、全文由 replace_node 纯函数拼装，只有目标节点会变，"顺手优化工单外"物理不可达）。闸的机械动作收敛为两件,外加一条报文契约：
     - ①复核拼装确定性——用同一 edits 对原文重放 replace_node，产物与步 3 拼装产物（draft_text）逐字节一致（拼装无飘）；
     - ②validate 对照——**error 与 warning 同律,均对照基线不用绝对零**（2026-09-02 首实战复盘改定,作者拍 A 案）。新律:修后 error 集不得多于基线 error 集〔按 rule+step 定位比对,新增即拦〕,既有 error 不背锅、工单恰是治 error 时修掉了算改善;warning 族不多于基线（新增族=改出新病;族比对由层一 body 直判——基线族串在收件步落账,层一提取修后族串比对,新增计入 gate1_note 点名）。
       - 改定出处:原形态"0 error 绝对闸"实撞结构性死锁——引擎版本错位对目标 spec 的新语法误报 1 个假 error,七处纯文字修正再正确也永不过闸,12 轮盲烧 232 万 tokens 重试耗尽;基线带病〔真病或假病〕时绝对零把修复质量与环境病绑死同判;
     - **gate1_note 必带明细不只报计数**（同批改定——原形态只报"1 error",重试 LLM 12 轮不知道 error 是什么/在哪/与己是否有关,反馈零信息量重试即盲烧;新律:新增 error/warning 的 rule+message 原文进 note,重试轮按明细定向补修）；
   - **层二·局部合理关**（LLM 判定，输入含**原件与改后件双份**——判"未破坏"须对照改前）：只审改动节点 + 变量链直接邻居——判据：改动落实了工单意图 / 未破坏邻居变量链（对照原件） / 说明与 body 仍一致；
   - **把关败路明文**：层一或层二任一不过 → 汇总判定 false 带缺口原文重跑修检事务，反馈进定向编辑步按 note 定向补修编辑清单（不推倒重来）；事务 retry 耗尽如实上浮为 run 失败——修不动不硬修；
   - **层三·deep-validate 复验指引**：hopfix 不内嵌 call deep-validate（内嵌会把分钟级工具拖到十分钟级，且 deep-validate 是独立 run 有自己的介入面）——改动涉及执行形态（步骤类型变更/body 增删/工具面变化）时，fix_report 里**必须**给出带参数的复验命令指引并标注"建议跑后再投产"；纯措辞类改动可标注"复验非必须"。判据机械可判（改动项的动作类型清单里有无形态类动作）；
5. **呈人确认**：ask require_human，呈纲要（修 N 拒 M/三层结论/修正稿与报告文件路径——完整改动按修正稿路径打开对读原件，D68③ 走文件不内联同款；初版承诺的"逐项改前改后要点内联摘要"收敛为纲要+路径对读——载荷大时 diff 摘要同样会超，恒走纲要档更稳）。**人否决（答非 yes）→ 不写回**：修正稿与报告留 work_zone 供自行取用或再来一轮，零写盘零快照；
6. **写回**（commit，作者拍板①）：先快照（work_zone 留 `<原名>.pre-fix.md`——commit 语义快照即回滚面，与 anchor-audit 快照纪律同哲学），后覆盖原路径；两拍逐判成败，失败路径写进产出值不静默。**快照失败即拒写**：快照读回与原件不一致时以计算异常令本步响亮失败——覆盖拍不执行，原件未被碰。

## 工单分诊类型【契约】 ^anc-meta-hopfix-triage

分诊产物每项字段逐条：

- `node_id: line`——受影响节点步号（定位不到时本项判拒，拒因"工单指涉的位置在 spec 里找不到"）；
- `action: enum(edit_text, edit_body, add_step, remove_step, restructure, out_of_scope)`——前四档可修；restructure=结构性拒；out_of_scope=契约面拒；
- `order_quote: text`——工单原话切片（本项的依据，呈人与报告都引它）；
- `reject_reason: text`——拒项必填（可修项空串）。

## 作者拍板与否决案【决策】

三拍板（2026-09-02）：①写回=原地覆盖+快照备份（否 B 案"输出 .fixed.md 新文件不动原件"——修完还要人手动换文件半途而废）；②把关=波及面复核+改动外零变化机械闸+deep-validate 复验三层（否"整文合理关"——133 研判点体量复审把'动辄从头'的时间病带回来）；③工单=自然语言与结构化双收（deep-validate 报告直接喂，查-修管道机器对机器）。

## 与 hopbuild2 内建修错回路的关系【说明】

同一修错哲学（D57"错在产物就地修，不整树重建"）的两个载体：hopbuild2 的 5.1.3.1.x 质检环服务构建 run 内的草稿，hopfix 服务 run 外的成品。判据可复用（D70 四档分诊/合法关形态），载体独立重织——hopfix 无构建循环语境，不背台账/终审/档位机制。
