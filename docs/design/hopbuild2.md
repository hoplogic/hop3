## 核心思路：类 LLVM pass 的递归等价分拆【决策：作者定 2026-08-21】 ^anc-build-pass-model

**节点两型（2026-08-21 作者定'本质上初始节点是 NL node,要一直拆到能用 hop node 表达'）**：

- **NL node**：一段自然语言任务描述——语义在散文里,引擎无法结构化强制。初始树=一个覆盖原文全文的 NL node;
- **hop node**：HopSpec 步骤——类型已定（reason/act/commit/check/confirm/ask/call 或容器结构）、I/O 已声明、纪律由引擎强制。reason 的料全部经 `←`/doc-ref 喂入（**reason 无工具面**——分析判断只动脑;要取数=前置 act 步,这是 act/reason 二分的执行面本义）。

**过程 = NL node 的逐遍消解**：每一遍分拆把一个 NL node 变成"hop 结构（subtask/branch/loop 骨架）+ 更小的 NL node 子节点"或直接落定为 hop node（原子步骤/hop_python body）。类比 LLVM pass：每遍语义等价,只改表示形态,IR 从散文逐遍降到结构。

**终态两档（2026-08-21 作者定'拆解不了的最终态也有价值,可以用于复用模式运行';2026-09-16 D94 语义勘误——原文"standalone 下该步会按 reason/act 的严格面跑,料不齐则失败"是立卷时的过时口径,与概念层 free 档条款〔核心规范:116"独立模式由引擎带工具面的 LLM 循环执行"〕、step-dispatcher 实装〔^anc-exec-act-free-role executeActWithTools〕直接矛盾,却经产物文件头括注模板复制进每份 mixed 产物,成为最大声的错误教学源——作者连问三问后排查实锤全链错位点恰在本段）**：

- **全 hop 化（hop 档）**：树上无 NL node——每步要么纯推理、要么带 body 引擎直执、要么动作已收窄到声明工具面内,**不依赖执行体的裁量纵深**,双模式皆稳;
- **含未尽原子（mixed 档）**：个别节点以自然语言任务描述落定（[act free] 形态）——**合法交付档,不是缺陷**。执行语义两模式同构:standalone 由引擎带工具面的 LLM 循环执行（Anthropic tool_use 多轮——基础文件工具族恒在+Tools 段声明的外部工具）,复用模式由 caller 智能体执行。**两档的真实差异是对工具面的依赖形态**:未尽原子的动作若需要引擎注册面之外的能力（跑命令/外部服务）,**standalone 下的供给链两环**:①工具进入某步工具面的下发通道=**节点 `- 工具:` 授权行**（^anc-step-tool-grant——无授权行即不在该步工具面,声明了没授权=工具静默不可见,LLM 只能空转,不报错——split-patterns 教的"最难发现的失效形态"）;②spec 头 Tools 段=需求声明与 init 对账闸（声明了而环境没有→INIT_FAILED 早失败）。跑命令另有前置 body 步 subprocess.run 白名单通道。**构建器义务=两环齐写**（对齐门收工具面进 Tools 段+分拆器给消费步写授权行——split-node 既有条款）,产物两环齐则 standalone 即可跑;复用模式因 caller 能力面开放（宿主生态工具动态可用）对供给缺口天然宽容。产物档位标注的是**结构化程度与工具面依赖**,不是"哪个模式不支持"。分拆器不为"拆到全 hop 化"硬拆（硬拆产物比诚实的 NL 步骤更差——错误的结构化是负资产）。

**与 v1 的本质差异**：v1 是"单轮作业四拍（分解→升格→核查）+ 占位递归"——一轮内既拆结构又补 I/O 又核查，关注点混载；hopbuild2 每一遍只做**一种分拆判定**，按固定优先级依次尝试，判定不中即落到下一种——每遍简单、可读、可解释（与「渐进展开，保持可读性和可解释能力」指导思想同源，hopbuild v5.0.0 首要原则在新形态下的结构化兑现）。

## 递归分拆算法【决策：作者定形 2026-08-21】 ^anc-build-split-algorithm

（2026-09-15 D92 重定形:递归到底改有界浅拆——迭代≤2、叶子恒三件套,见 ^anc-build-shallow-split;本节的判定序〔顺序→分支→循环〕与结构分拆机制仍现行,第 4 段原子判定与"递归到烧尽才落定"的下半段已废,保留为沿革——照本节第 4/5 段实现叶子落定就是在实现已废弃的逻辑,叶子形态以 D92 为准）

对每个未落定的节点，按以下优先级**依次尝试**（命中即做、做完递归、退出本节点判定；三结构判不中走第 4 段原子判定,原子也不过走第 5 段未尽原子）：

```
递归分拆(节点):
1. 看能不能有明确的【顺序】分拆 → 可以:
   1.1 subtask 顺序分拆
       1.1.0 计划覆盖预检（D36,产计划的判定步自查——计划各条的原文范围标注并起来
             必须覆盖 node_source 全部小节/段落;有小节不在任何条目范围内 → 计划
             不合格,当场补条目或并入邻条,不许带缺口下发。错在哪层修在哪层：计划
             是冻结输入,缺口传给执行机后,骨架照计划写→忠实关必打回,重试者只能
             重写骨架、无权修计划——确定性矛盾,烧尽 retry 也过不去（dr7 实撞:
             "评审执行"节点 5 条计划漏 2 节,4 攻全灭））
       1.1.1 按原文自然顺序分拆（每个子节点=原文一段明确范围,带一句任务描述;
             含不可逆动作/达标要求的段落须守 探索-检验-提交 序——commit 不混进
             探索段、验收在提交前,其余平铺顺序照原文即可;选型判据与范式取自
             范式库,不在本步内联;见 ^anc-build-split-patterns）
       1.1.2 检查语法是否正确（分拆产物过 validate 机械核——子节点序列/容器形态合法）
       1.1.3 检查语义是否忠实、检查知识是否完备
             （子节点并集覆盖父节点原文范围无遗漏、无杜撰;各子节点所需判据/规则可得,
              缺失即记研判点台账不臆造;不忠实/不完备→本遍撤销,节点保持原样）
   1.2 递归分拆每个子节点
       （D37:子节点递归 call 失败〔子层 retry 耗尽〕→ 不上抛炸层——该子节点按
        分型降档落定为未尽原子,保住已拆好的兄弟成果,本层照常拼装交付 tier=mixed。
        分型三档:子任务含不可逆动作→探索范式三件套〔act free 探索+check final+
        commit,commit 从 NL 描述剥出单列——free 不得作提交载体,作者红线〕;含交互
        闸门→ask/confirm 步剥出保留、其余落 act free〔闸门语义蒸发是 D33 定过性
        的重病,兜底不重犯〕;其余→单步 act free〔纯推理才落 reason〕。载体=
        split-structure 3.3 call 外套 [subtask retry=0]+[on fail] 兜底块——
        retry=0 首败即入兜底零重烧〔子层自己的 retry 已烧完,层级再重试=盲赌〕。
        dr7 实撞:ae01 四子节点三个已交付 hop 档,第四个 4 攻耗尽 CalleeFailure
        炸掉整层,合格成果全作废从骨架重拆;层存活率=子节点成功率连乘,树越深越
        必然全灭——降档出口把连乘变 100%,代价只是个别节点 mixed,本就是设计
        承诺的合法交付档）
   1.3 退出
2. 看能不能有明确的【分支】分拆 → 可以:
   2.1 branch+case 分支分拆（case 就是 branch 下的 subtask）
       2.1.1 分拆时注意 条件的明确归属与穷尽,注意 case 条件用 hop_python 纯表达式表述
             （每个 case=原文一个明确条件路径;条件不穷尽时补 [case(else)] 兜底并记档;
              分支公共的前置取数上提为 branch 前的顺序步骤,不复制进各 case;
              下游要消费分支产出时 branch 头声明统一接口 + →,各 case 同名赋值）
       2.1.2 检查语法是否正确（同 1.1.2——branch 只含 case/条件表达式合法/else 居末）
       2.1.3 检查语义是否忠实、检查知识是否完备
             （各 case 对回原文各自条件路径;条件判据缺失即记档暂定,不臆造阈值）
       （计划覆盖预检同 1.1.0,失败降档同 1.2 的 D37 条——三结构同款,不逐段重复）
   2.2 递归分拆每个 case 子节点
   2.3 退出
3. 看能不能有明确的【循环】分拆 → 可以:
   3.1 循环分拆（loop for-each / loop max）
       3.1.1 分拆时注意 遍历对象与收集通道的明确表述,注意循环体=单项处理
             （"每个/逐个"且条目可枚举→for-each（遍历列表须 [T] 型,来源不明即先补
              取数步骤）;"重复直到/最多 N 次"→subtask retry+check final 优先（引擎
              自带事务语义）,真非事务性重复才 loop max;体内产出要汇总→collect 子句
              声明单项与列表两个名字;循环体只写单项份内事,跨项汇总归收齐后的串行步骤）
       3.1.2 检查语法是否正确（同 1.1.2——for-each 列表型/collect 配对/体非空合法）
       3.1.3 检查语义是否忠实、检查知识是否完备
             （循环体对回原文单项处理描述;遍历范围与原文一致——"所有/未处理的/本周的"
              等限定词落到列表来源,不落到体内自行过滤）
       （计划覆盖预检同 1.1.0,失败降档同 1.2 的 D37 条——三结构同款,不逐段重复）
   3.2 递归分拆循环体
   3.3 退出
4. 原子判定（三结构判全不中即到此——2026-08-21 作者定'合并,然后再细分':原判定四〔可降格〕
   与判定五〔原子〕判的是同一件事的两半——'是否纯机械'恰是类型认领 act vs reason 的同一判别式,
   两判必重复;合并为一判'是不是单步?类型是什么?',降格回归本义=原子落定时的表达形式选择
   〔有 body/无 body〕,非独立判定档）:
   4.1 自足可执行四条一次判:①步骤类型能明确认领（reason/act/commit/check/confirm/ask
       之一,按动词认;认不出=任务描述含糊,改写描述后重走判定序——不是继续硬拆）
       ②一步一动作（描述只一个动词主干;双动作=第 1 判漏了,退回顺序拆）
       ③I/O 可声明（← 有来源、→ 能命名——写不出 I/O 的是散文不是步骤）
       ④量级正常（任务描述一两句话装得下）
       → 全过=atomic_hit + 认领类型;有不过=unresolved（落第 5 段）
   4.2 细分:命中且类型∈{act,commit,check} 且动作纯机械（零推理零裁量——判别式:失败重做
       安全且结果确定）→ **带 body 落定**:写 hop_python body（白名单+已声明工具;
       work_zone_path() 涂鸦区）→ 语法核（validate B 组）→ 语义核（body 与原文逐行等价;
       check 降格=双槽判定逻辑与原文判据一致）;不等价/验证耗尽 → [on fail] 兜底撤销降格,
       落无 body 原子步（记档——诚实的 NL 描述好过错误的 body）

       成文单步（类型+一句任务描述+IO 声明+必要执行说明）
   4.4 退出
5. 原子判定不过 → 未尽原子落定（就地终局,零跨调用状态）:
   当场记研判点台账、原样落定为"未尽原子"（合法交付档非缺陷——执行语义两模式同构,工具面依赖账见终态两档 D94 勘误;

   retry 机制;"试 N 遍再放弃"的结构形态=[subtask retry=N]+[on fail] 失败兜底块
   〔^anc-step-on-fail〕;深度触顶同此形态:max_call_depth 引擎闸自然报）

要点（作者定向的推演展开）：

- **优先级即判定序**：顺序 > 分支 > 循环 > 原子（含类型认领与 body/无 body 细分）——每个节点先找最外层的顺序结构（最容易明确、认知负担最低），顺序拆不动才看分支，再看循环；结构全拆尽后进原子判定，纯机械的 act/commit/check 型带 hop_python body 落定（执行期零 LLM）。**"明确"是硬门槛**——判定不明确就不拆，节点保持原样留给下一遍（或最终作为带自然语言描述的原子步骤落定）；
- **三检的失败语义统一**：任一检不过 → **本遍对该节点的分拆撤销**（树回到分拆前形态），节点留给下一遍或落定为原子——分拆是等价变换，检不过=等价性存疑，宁不拆不错拆；
- **递归即遍历**：1.2/2.2/3.2 对每个子节点重新走同一判定序——树逐遍长深，每个节点独立收敛（有的一遍落定，有的多遍才拆尽）。

**D86 备料/提交分离——不可逆动作命令定不死时的降档正形（2026-09-09,todo/0082,0079 复测实证。实撞:sandbox 480KB 复测产物〔run 54d9f489〕步骤⑤"生命周期执行"未尽原子含铲除/擦盘/钉钉外发,不可逆语义只落散文嘱咐"须由 commit 步承载"——真跑 operation=teardown 走到不可逆处被引擎运行期禁 commit 拦死,无出路:运行期到步展开的计划无人预审,引擎强制禁其携带 commit,后延不可逆动作等于把这半边功能结构性锁死。作者三轮对焦定调:①"不要把递归额度用光当成不好的事情,这个恰恰是我们渐进所期待的事情"——烧尽非缺陷,mixed 是合法中间态,判据是产物满足翻译原则体系不是额度用没用光;②"这个分离就是给个教学,无非是在 work_zone 里探索好,满足了要求,再一起提交"——不动预算机制不动引擎,纯教学范式;③"比较大的产物放文件,避免变量过载"）**：

病根定位——三类内容的可后延性不对称：探索性动作（act）后延零损失（运行期到步展开本就合法）;门禁（check）后延降级（引擎强制的把关步退化成约束文字+执行者自觉）;**不可逆动作（commit）后延即死路**（运行期禁 commit）。而模板 D 既有退路条款"生成期命令序列定不死才退 [act free]+confirm 闸门承载不可逆语义"把定不死的场景整个推给了 free+散文,恰是死路的入口。本条升级该退路：**命令定不死 ≠ commit 步写不出**——裁量全部前移到备料与人批环节,commit body 里只剩零裁量的机械执行。范式四件：

1. **原子（act free）只备料**：在 work_zone 只读发现、staging、生成**精确执行清单文件**（哪台机器/什么命令/什么顺序/保留项——具体到可机械执行）+证据;交付物=清单文件路径变量（line 型）——大产物走文件不走变量（与修错步 draft_path/并行分拆 child_frag_path 同轴的既有形态）;
2. **confirm 闸呈清单人批**：前置机械 act 读清单文件入文本变量,confirm 消费该变量——confirm 停驻时引擎把它声明的输入值完整呈给人（超长自动文件卸载,^anc-exec-hitl-presentation 人通道）,这是 confirm 呈现材料的文法正道（present_inputs 属性是 ask 专属,confirm 不收——首版样板误用被独立阅卷 validate 实抓,属性总闸 parse 拒）;与运维类原文"对精确清单明确授权"的纪律天然同构,原文这类句子翻译时直接落这一步;
3. **commit body 静态定死为"按人批清单执行"**：代码生成期定死,数据来自人批过的清单文件——裁量发生在备料（LLM 探索）与人批（confirm）,commit 执行期零裁量,模板 D 的既有纪律（逐拍判码/失败入产出值/恒退 0 脚本按 stdout 判）全部适用。执行形态两种（hop_python 无循环语句,阅卷实抓的文法对齐点）：清单条目数生成期已知→逐条 subprocess.run 逐拍判码;条目数看现场→备料步把清单落成可执行脚本（set -e 逐条失败即停）,confirm 批的就是脚本内容,commit 消费批过的文本本体单调执行判整体退出码（body 内把批过的文本写回涂鸦区再执行刚写的这份——数据血缘落实,批完到执行的盘上文件改动窗口消失;独立阅卷判③建议采纳）;
4. **运行期禁 commit 红线零改动**：探索归展开（原子内 act/check 随便展开）,提交归骨架（confirm+commit 静态在场、经终审门人审）——分工天然满足红线。

**D90 可选工具不硬声明——对齐门工具面的条件能力判据（2026-09-10,todo/0083 记账后落地。实撞:七份语料的对齐门呈审里,同一类误判被人工纠正四次——sandbox 的钉钉通知（原文"仅在用户要求且 webhook 已注入时发送"）、医保的文档解析服务与数据库写入（原文"若提供…可以调用"/"仅当任务给出 schema 与权限时"）、claude-md-improver 的 bash（只为跑一条 find,引擎内置工具本就能做）、incident-response 的监控/事故管理/聊天三件（原文"If X is connected"——条件句式最显白的一例）。判据在人脑里拍了四次,构建器每次从原文冷启动学不会——本条把它落成教学常识）**：

判据一句话：**原文以条件句式引入的外部能力,不写进产物的 Tools 段**。条件句式包括"If X is connected"“若提供 X”“仅当配置了 X”“用户要求时才用 X”这类表述——它们的共同点是:原文自己就预期这个能力可能缺席,缺席时 skill 的核心功能照常工作。

为什么不能硬声明：引擎启动 spec 时对 Tools 段逐个对账,声明了环境里没注册的工具当场拒载（INIT_FAILED）。把可选能力写进 Tools 段,等于强迫所有用户配齐这些服务才能起跑——把原文的"锦上添花"翻译成了"没有就不让干活",这是翻译失真。

正确做法两步：①条件语义写进消费步骤的说明文字,"有它时怎么做、没它时怎么做"都写清（例:"运行环境连接了聊天服务时,经它把状态通报发到事故频道;未连接时,通报文档照常生成,由用户自行分发"）;②能力真身是包内脚本的,随参考性附属清单登记分发,想用的用户自己配环境。

什么工具才该硬声明：**拿掉这个工具,spec 承诺的交付物就做不出来的**——如测试驱动开发的"运行测试"能力（没有它整个 skill 无法工作）、远程部署的 SSH 执行（碰不到目标机器）。判断方法:假设环境里没有这个工具,问"Goal 还能交付吗?"——能交付=可选,不硬声明;不能=必需,声明并让缺失环境尽早失败。四案里 TDD 的 shell 与 sandbox 的 ssh_exec 被判"保留"正是走的这半边。

完整对照示例（取自 incident-response 实案——原文第 150 行写"If **~~chat** is connected: post status updates to incident channel"）：

❌ 错误形态（硬声明进 Tools 段——这就是被人工纠正的第四案原样）：

```
Tools:
- chat(channel, message) -> post_id: line  # 发送状态更新到事故频道
  - channel: line  # 目标频道标识
  - message: text  # 状态更新正文
```

后果：用户环境没注册 chat 工具时,引擎起跑对账当场拒载（INIT_FAILED）——而这位用户可能只想用这份 skill 写复盘文档,复盘功能根本不碰聊天服务。

✅ 正确形态（Tools 段不出现 chat;条件语义写进消费它的那个步骤的说明文字）：

```
5. [act free] 撰写状态通报并分发
  - ← incident_info
  + → incident_document: markdown  # 状态通报文档
  > 按四要素（发生了什么/影响谁/我们在做什么/下次更新时间）撰写状态通报。
  > 分发方式看环境：运行环境连接了聊天服务时,把通报发到事故频道并建战情室;
  > 未连接时,通报文档照常生成,由用户自行复制分发——文档本体是交付物,分发是旁路。
```

落点：spec.md 步骤 4.2 tools_available 生成条款（三类假工具判据之后,作为第四判据）;与 D73（载体语汇翻译）分工——D73 管"宿主机制名不进契约",本条管"条件能力不进工具面",都是翻译保真的边界判据。

## 分拆范式库（builder 的可用形态清单）【契约】 ^anc-build-split-patterns

分拆产物优先套用下列**范式**（named patterns）——builder 知道有哪些形态可用,产物才不会自由发挥;每个范式=一个可讲清的分拆理由（可读可解释的正向供给）。**本库是分拆步的知识供给面**（算法伪码只留判定序骨架,选型细则全在此——实现时经 doc-ref 按步注入,1.1.1 等分拆步不内联重述）。首批如下,随实跑沉淀扩充：

**范式 0：act/reason/commit 选型（步骤定型基础判据）**——分拆出的每个子节点按动词认领类型：

- 试错/计算/取数/落盘 → `act`（可逆,可安全重做）;分析/判断/决策 → `reason`（动脑,料须经 ← 喂齐——无工具面）;
- **不可逆动作**（发送/支付/写生产/删除）→ `commit` 单列,**置于检验之后**且**前序必须有针对交付物的 check**（验收将要提交的东西本身;原文没写验收就补一个并记档——三段序补全非添业务步骤;真要人拍板的用 confirm）;
- 拿不准 act 还是 reason：看失败重做是否安全且结果确定——确定性重做=act,每次可能想出不同答案=reason。

**范式 1：subtask-check-retry（探索-验收事务,2026-08-21 作者点名）**——"做一段活并保证它达标"的标准形态：

```
N. [subtask retry=K] <这段活的目标>
  + → <交付变量>: <type>  # 交付物
  N.1. [act/reason] <干活>          ← 探索段（可多步:取数/加工/分析）
    + → <交付变量>: <type>  # 产出
  N.2. [check final] <验收判据>     ← 验收门（机器可验;判据来自原文的"必须/确保/达标"句）
    - ← <交付变量>
    + → ok: bool  # 判定槽
    + → note: text  # 说明槽（不过时的缺口——引擎注入重跑轮定向修正）
```

- **识别信号**（NL node 里）："核对并确保…"、"验证…后再…"、"质量达标才…"、"不对就重做"——凡是"产出+达标要求"成对出现的段落;
- **语义**：check false → 引擎带反馈整组重跑（note 槽注入重跑上下文,非盲重试）;retry=K 耗尽 → fail 上浮（或接范式 1b）;
- **1b 变体（+失败兜底,高级扩展——普通产物不必用）**：末位加 `[on fail]` 块（记档/降级/给兜底值,耗尽后失败被消化不上浮）——见概念 ^anc-step-on-fail 高级特性分级;builder 只在原文明写"实在不行就…"类兜底语义时用;
- **反例（不套范式的错误形态）**：❌ loop max=N 包一段+branch 判"是否通过"手搭重试（丢失引擎事务语义,v1 primer 反例同款）;❌ check 塞进探索段中间（验收该钉在探索之后——C7）;❌ 交付变量只在 check 里出现（验收对象须是真产出）。

**范式 2：结构替代——遍历被下层确定性代码承载,不硬拆（v1 语料验证定形,fraud 路最重研判）**：原文"逐个处理 X 族"的遍历若由被引代码结构（registry/配置表驱动的总入口）在进程内完成,产物落**一步 act 调总入口**,不拆 loop for-each——遍历真身在下层代码里,硬拆成 loop 是杜撰不是忠实（拆出来的成员清单是快照,代码侧增删成员后 spec 即失真）。识别信号:原文点名"由 X.js/注册表统一调度""新增检测器只需注册"。台账记一句"遍历被 <入口> 结构承载"。

**范式 3：横切动作抽子 spec——各落点一行 call（v1 语料验证定形,sandbox 每阶段通知 60 行样板实撞）**：同构动作出现在多个落点（每阶段通知/逐段落盘/分级验收）时,抽成**全步带 body 的子 spec**,各落点一行 `[call 子spec(参数)]`——60 行同构样板变每处一行,改逻辑只改一处。自查判据不变:漏写某处 call 与漏抄样板同为动作蒸发（D84 逐句过账罩它）。

**范式 4：跨轮依赖——外层 loop 串行+轮内 call parallel（v1 语料验证定形,doc-review 多轮差异化派发实撞）**：原文"分多轮、后轮依赖前轮发现"的形态:外层 `[loop max=N]` 串行承载轮次（体内 reason 按前轮发现设计本轮成员,累加器变量承载跨轮依赖）+轮内 for-each `[call … parallel]` 并发派发。两条纪律:跨轮依赖合法（经变量流动）;**同轮成员必须独立**（同批并行不可能依赖彼此未产出的东西——原文写同批内依赖=原文不自洽,记台账）。降级成单批全并发=丢跨轮语义,是保真缺陷。

**范式 5：宿主命令类不可逆动作（v1 模板 D 移植,作者拍"本质上都是一堆 bash 命令"后定形）**：SSH 擦盘/kubeadm reset 这类宿主命令不可逆动作:前置 act 备好参数 → `[commit]` body `subprocess.run` 命令序列**生成期定死**,逐拍判 returncode（非零即停,不判则前拍失败后拍照跑,产出谎报成功）,失败路径写进产出值;部署前提（命令白名单）随交付清单。**生成期命令序列定不死**才退 `[act free]`+confirm 闸门+研判点台账——这是合法形态不是降档。

分拆时的接线纪律：范式实例的 `<交付变量>` 就是该 NL node 对父层承诺的输出——套范式不改变节点的对外 I/O 契约（等价变换不变量①的范式面兑现）。

**压测三缺陷补（2026-08-21 四轮压测实抓——工单/周报/doc-review 三 fixture 机械 validate 全绿而语义层三病,全靠走查产物对读引擎语义定性）**：

- **D1 check 后死分支**（周报例:`[check]` 后接 `[case(not ok)] 返工重译`——引擎 check false 当场 failStep 整组重跑,not ok 分支永不可达且与 retry 双轨）→ 范式 1 补"check false 即整组重跑,check 后不要再写返工 branch（死分支）;返工语义=retry 自带,唯一要写的是验收判据本身";

## 分拆不变量（每一遍都必须保持）【契约】 ^anc-build-invariants

1. **语义等价**：任何一遍分拆前后，树表达的业务语义不变——分拆只改表示形态（等价变换），不增删业务步骤；原文没给的判据/阈值不算缺陷（暂定+记档，同 v5.0.0 首要原则①）；
2. **探索-检验-提交分离**：分拆产物中不可逆动作（commit）不混入探索段；**凡有提交动作,其前序必须有对应的 check**（2026-08-21 作者点明——验收的是**将要提交的东西**,不是泛泛把关:发送清单前 check 的是清单本身;分拆出 commit 时若原文没写验收,补一个针对交付物的 check 并记研判点台账——这是三段序的补全不是添业务步骤,validate P8 同规则机器兜底）（唯一硬纪律面，同首要原则②）；
3. **每遍量级受控**：一遍只做一个节点的一种分拆——不许一遍内把多层结构一次拆穿（渐进生成，同首要原则③）；
4. **可读可解释**：每次分拆能讲出"命中了哪种判定、为什么明确"——判定理由即分拆的解释（同首要原则④）。
