> HopSpec V3扩展：Python 语法沙箱

## 定位

本篇解决一个 hop_python 自身解决不了的问题：**规约的交付物本身是一份真 Python 脚本时，探索态怎么安全地生成它、验证它。**

hop_python 是**编排语言**——引擎解释执行它，因此它必须宿主中立（TS/Python/Rust 引擎都能跑），这是环境无关原则（[[HopSpec V3核心规范#^anc-exec-mode-invariants]]）的硬约束，也是它不能 `import` Python 库的根本原因。

但有一类任务的交付物是**产物代码**：它不由引擎执行，而是写到盘上交付出去，由目标环境的真 CPython 运行。典型场景是「给一个仓库生成校验脚本」——脚本的消费者是那个仓库的 CI 与维护者，它必须是真 Python、必须能 `import ast`、必须能独立跑。这类产物不需要宿主中立，它需要在目标环境里正确。

**把这两类代码混为一谈，是本篇要消除的分类错误。** 编排代码归 hop_python，产物代码归本篇的 Python 语法沙箱。

**名字里的"语法"是实义词**：这道沙箱建在**解析期**——危险能力不是运行时被拦住，是**源码里压根写不出来**（不在白名单的名字不是合法程序）。它与操作系统级的运行期围栏（seatbelt / bwrap / 容器）是两类东西，可以叠加但互不替代。

**同时必须说清一条技术事实：语法层内部没有第二道防线。** 白名单即语法层的唯一边界——漏一个符号，就是从产物源码直通到宿主，语法层自己不会有第二层兜下来；宿主有系统沙箱时，系统沙箱是语法层之外的那一道（下节）。这不是本方案独有的性质（业界一切沙箱都有逃逸面），但维护白名单的人必须知道自己守的是语法层唯一那道，而不是语法层三道里的一道。

选它而不选运行期黑名单的理由，也正在这里：**两者的失效方向相反**。白名单漏一个符号 → 正当写法被拒，响亮失败、当场可见、加一条即可；运行期黑名单漏一个动作 → 危险动作静默放行，程序全绿照跑（2.1 有实测：一份看起来周全的运行期拦截器漏订阅三个事件，当场真删了一整个目录）。**朝安全侧倒的失效，是本方案的地基。**

### 与系统沙箱的关系：可叠加，不依赖 ^anc-pysb-os-independence

**语法沙箱可以运行在系统沙箱（macOS seatbelt / Linux bwrap、seccomp / 容器）里，但不依赖系统沙箱存在。** 这是一条硬性设计约束，不是权宜：

- **不依赖**——语法沙箱的安全边界完全由白名单承担。宿主有没有系统沙箱、是哪一种、版本多少，**不改变本方案的准入判据**，也不改变产物能做什么。理由是环境无关原则：系统沙箱各平台形态不同（macOS 的 `sandbox-exec` 已被 Apple 标为废弃、Linux 的 `bwrap` 默认不预装、Windows 没有等价轻量件），把安全性建在它上面，等于让同一份 spec 在不同机器上有不同的安全级别；
- **在场即必须套上**——在场时就是纵深防御多一层，白名单万一漏了一个符号，系统沙箱还能挡一道。引擎检测到可用的系统沙箱时，**必须**把产物的执行放进去，不是"可以顺带"；**但不得因此放宽白名单**（"外面有围墙所以里面可以松一点"是这类设计最典型的塌方路径）；
- **缺席时照跑，但如实标明只有单层防护**。既不硬失败（它本不是前置依赖），也不降级放宽（判据本就与它无关）。缺席时唯一变化是少了一层冗余：引擎在执行账与日志里明确记"本次执行只有语法层单层防护"，让看账的人知道这次跑的防护等级，不改变准入判据。

**业界共识与本方案的回应。** 业界对语言层沙箱的主流判断是"它不算安全边界，必须再套一层进程或操作系统隔离"：pysandbox 作者放弃该项目时的结论是"整个 Python 进程必须放进外部沙箱"，理由是"沙箱的安全性等于它最弱的那一环，一个 bug 就够逃出整个沙箱"；RestrictedPython 自述编译期限制"不足以构成沙箱"；smolagents 自述"任何本地 Python 沙箱都不可能完全安全"，推荐远程容器或虚拟机执行；PyPy 的沙箱干脆是两个进程的模型，受限进程的一切系统调用都交给外部控制进程代办。本方案不与这个共识对立，而是在三处与共识里的失败案例结构不同，这三处正是"不依赖"能够成立的理由：

- **不自写解释器**。业界翻车的语言层沙箱多半是"自己写一个 Python 解释器，在宿主进程里一个节点一个节点地执行不可信代码"——asteval 被人在"检查属性名"与"真正取属性"之间篡改语法树节点绕过（先检查后使用的时间差），`raise SystemExit` 越过宿主的 `except Exception` 直接让宿主进程退出；smolagents 的本地执行器同属此类。本方案的审查用 CPython 自己的解析器，产物由独立的 CPython 子进程执行，这一整类"解释器自己的漏洞"不存在；
- **名单是封闭的小集合**。能写进源码的名字只有白名单里的不到两百个，每个入名单前逐个验过属性图，而不是"默认全放、发现一个口子堵一个"（pysandbox 正是后一种，删功能删到只剩算 `1+(2*3)` 的能力）；
- **只读、不起子进程**。白名单里没有写模式的 `open`、没有 `subprocess`，产物能做的事本身就收窄在"读、算、打印、设退出码"之内。

**残余风险要说清**：pysandbox 作者那条"最弱一环"的论点对本方案依然成立——若 CPython 在白名单可触及的范围内有一个能让解释器崩溃或破坏内存的缺陷，语法层兜不住。这正是"在场即必须套上"的理由：环境无关原则不许把准入判据建在系统沙箱上，但不妨碍在它在场时把这道残余风险挡在外面。

## 一、问题：探索态生成产物代码，卡在"验证"上

写一份 `.py` 到盘上，今天就完全合法——`write` 一个文件而已，没有任何争议。卡住的只有一件事：**要确认它真能跑，就得执行它**，而执行由执行模型现场决定要跑什么的脚本，就把不可逆能力交给了运行期的 LLM。

不验证的代价是实证过的，不是推演。`standard-decompose-codify`（标准拆解与代码化）规约要求「生成的校验脚本必须实跑验证」，而 standalone 装配的工具面只有文件读写、没有任何执行手段，三家模型在同一步各撞一种死法（todo/0110）：

- 一家把「本该被执行的脚本」换了十三个名字写了十三遍，烧尽工具轮数上限；
- 一家幻觉出一个不存在的 `bash` 工具，连发九轮一字不差的文本，重试耗尽；
- 一家（强模型）两条校验里一条诚实降级、**另一条自述「以 shell 运行，退出码 0」而全轮零执行**——脚本本体是对的，假的是"跑过了"这句话。

第三种最要紧：**规约把「实跑留痕」定成必填字段、把「已码」这个档位定义成「跑通」，而环境不给实跑手段，模型只剩「编造」或「拒交」两条路。** 这不是模型的诚信档位问题——同一个模型在两条校验上各选了一条。**环境逼出的失格，账算在工装头上。**

所以本篇要同时满足三件事，缺一件都不成立：

1. 产物是真 Python（能 `import ast`，能独立在别人的 CI 里跑）；
2. 验证是真执行（回执是引擎手里的机器凭证，不是模型的自述）；
3. 探索态的安全边界不破（模型不能借这条路获得规约作者没授权的能力）。

## 二、解法：引擎不执行产物，只审产物 ^anc-pysb-model

**核心形态一句话：引擎按一份白名单静态审这份 Python 源码，审过才许跑、才许交付。**

引擎从不解释产物的语义，也不在自己的进程里执行它。它做的是**解析期的形态检查**：把源码解析成语法树，逐个核对源码里出现的每个名字在不在白名单里、用法合不合这个条目的许可。因此：

- **环境无关原则没破**——检查器是随引擎发布的一份固定的 Python 检查脚本，由宿主的 `python3` 运行。TS、Python、Rust 哪种宿主的引擎都调用同一份检查脚本，行为一致；产物要实跑本就需要 `python3`，检查器不引入新依赖。检查器为什么必须用 Python 自己的解析器、不能用宿主语言另写一份，见 2.2 规则一；
- **`import` 不再违宪**——那不是 body 的 import，是**产物的** import。产物运行在目标环境的真 CPython 里，本就该用目标环境的库。

### 2.1 为什么是白名单，而且要覆盖源码里的每一个名字

**白名单与黑名单的差别是本方案的地基，不是风格偏好。** 两种形态的失效方式根本不同：

- **黑名单（运行期拦截危险动作）**：安全性等于"名单列全了没有"。列漏一个，程序照跑、全绿、正常功能毫无异样，只在某个特定动作上静默放行。**实测印证**：用 Python 的审计钩子（PEP 578）写了一份看起来相当周全的拦截器，拦了起子进程、`os.system`、连网、`ctypes`、`open` 写模式，第一轮七项逃逸全部拦住；第二轮换成不走 `open` 的动作，`os.remove` / `os.rename` / `shutil.rmtree` 三项直接穿过去，**把沙箱外的一整个目录真删了**。事后确认这三个事件 Python 全都报了，是漏订阅。**把安全边界建在一份要靠人列全名单的黑名单上，等于把边界建在注意力上。**
- **白名单（解析期只许已列出的名字）**：不在名单里的东西**压根写不出来**——不是"被拦住"，是解析期就不是合法程序。列漏一个的后果是**正当写法被拒**（响亮失败、当场可见、加一条即可），不是危险动作被放行。**失效方向朝安全侧倒，这是选它的唯一理由。**

**白名单的单位是"模块.符号"，不是模块。** 实测：从候选模块出发，只用非下划线属性做三跳广度搜索——

| 模块 | 三跳内可达的危险模块 |
|---|---|
| `ast` `csv` `difflib` `collections` `math` `itertools` `hashlib` `datetime` `string` | 干净 |
| `json` | `json.codecs.builtins` → `builtins`；`json.codecs.sys` → `sys` |
| `re` | `re.enum.bltns` → `builtins`；`re.enum.sys` → `sys` |
| `pathlib` | `pathlib.ntpath.os` → `os`；`pathlib.ntpath.genericpath.os` → `os` |
| `textwrap` `tokenize` | 经 `re` 中转达 `builtins` / `sys` |

Python 模块之间互相 import，属性图一连就通到 `os`/`sys`/`builtins`。**放行 `re` 这个模块，等于顺带放行了 `re.enum.sys`。** 所以白名单的单位不是「允许用 `re`」，而是「允许 `re.match`、`re.sub`、`re.findall` 这几个函数」。

**模块对象不许成为值。** 仅仅在白名单里列出 `re.match` 还不够——只要 `re` 这个模块对象能被当成普通的值传递，静态检查就跟丢了。实测：

```python
import re
def f(m):
    return m.enum.sys      # 每一节都是字面标识符,但 m 是形参不是模块名
s = f(re)
osmod = s.modules['os']    # 实测:真的拿到了 os
print(osmod.uname().sysname)   # → Darwin
```

"属性链每一节都必须是字面标识符"这条判据在这里失守了——它检查的是**写法**，而这段代码的每一节写法都合规，失守的是**值的流向**。堵它不需要数据流分析（追踪每个变量此刻可能持有什么对象），只需要**在源头不让模块变成值**：模块名在源码里只许以 `模块.符号` 这一种形态出现——`f(re)`、`m = re`、`[re]` 都不合法；模块名也不许被重新绑定（`re = open`、`def f(re)`、`for re in …` 都不合法，否则检查器以为 `re.match` 里的 `re` 是模块，实际它已经是别的对象）。模块对象进不了任何变量、容器、实参，也就无处流动。

**同一个道理推广到一切有能力的对象：有能力的对象不许作为值出现，只许以固定形态使用。** 模块是一例，`open` 是另一例——`open` 安不安全取决于模式实参，检查器只有在调用点看得见实参时才能判，一旦它被当值传走（`f = open`、`{"w": open}`、`map(open, …)`、类属性 `class C: f = open`），调用发生时检查器已经看不到实参了。所以 `open` 只许直接调用。

**这条原则不能靠一份"危险对象名单"来执行。** 那样的名单本身就是黑名单——漏列一个，危险就被静默放行。执行它的办法是让**源码里出现的每一个名字都查白名单**，而每个白名单条目自带用法许可：这个条目能不能当值用、实参有什么约束。**没写许可的条目缺省只许直接调用**。于是"危险对象不许作为值"是白名单条目许可的自然结果，审查对象从"世界上有哪些危险"（开放集，永远列不全）换成了"白名单里这几十个条目各自安不安全"（封闭集，入名单时逐个审一次）。

白名单必须覆盖三类名字，缺一类就留一个口子：

| 名字的种类 | 例子 | 不进白名单会怎样（实测） |
|---|---|---|
| 模块属性 | `re.match` `sys.argv` | `sys.modules['os']` 拿到任意模块 |
| 内置名 | `len` `open` `print` | Python 不经 import 就在场的内置名共 150 个（不计下划线开头的），只禁一小撮等于黑名单：`breakpoint()` `help('modules')` 都能逃逸；`__builtins__` 这个名字本身就是万能钥匙，`__builtins__.eval(…)` 直接拿到 `eval` |
| 对象属性（方法与字段） | `.lineno` `.append` `.read` | `"{0.__class__.__mro__}".format(1)` 在运行期解释模板里的属性链（语法树上只是个字符串常量）；生成器对象的 `.gi_frame.f_globals` 拿到 `__builtins__` 再取 `eval`——这两条都不带下划线开头的属性名，只禁下划线开头的属性挡不住 |

对象属性这一类最容易被当成"只要禁掉下划线开头的就行"，那恰恰是黑名单形态：Python 每次升级都会给内置类型加新方法（3.9 给字符串加了 `removeprefix`），哪天加一个会解释模板或穿透属性的方法，只查形态的设计会静默放行它。属性白名单不怕这个——新方法不在名单里，写了就被拒。

这跟 hop_python 今天的安全原理是同一套：hop_python 安全不是因为它拦住了危险函数，是因为它的白名单里没有那些名字。

### 2.2 三条规则 ^anc-pysb-defenses

检查器只执行三条规则，每一条都对应一类实测过的逃逸，不是假想威胁。

**规则一：用 CPython 自己的解析器，按原始字节解析。**

检查器必须调 Python 标准库的 `ast.parse`，把盘上文件的**原始字节**交给它，不能用宿主语言另写一份 Python 解析器。理由是检查器看到的源码必须与真正运行它的 CPython 看到的一模一样，而 Python 的源码到"名字"之间有两道自己写的解析器极易漏掉的变换：

- **编码声明**：文件头写 `# -*- coding: utf-7 -*-`，CPython 就按 UTF-7 解码整个文件。实测 `+AF8AXwBpAG0AcABvAHIAdABfAF8-("os")` 这串按 UTF-8 读是一堆字母和符号，按 UTF-7 解码后是 `__import__("os")`，真的拿到了 `os`；
- **标识符归一化**：CPython 对标识符做 Unicode NFKC 归一化，全角的 `ｅval` 就是 `eval`。实测 `print(ｅval("6*7"))` 输出 42。

自己写的解析器只要在这两件事上与 CPython 有一丝不同，检查器审的就不是真正会跑的那份程序。用同一个解析器，这一整类分歧从根上不存在。按原始字节交是因为 `ast.parse` 收到字节时会照编码声明解码，与 CPython 运行时一致；若先按 UTF-8 解成文本再交，就又制造了一次分歧。

**规则二：只许 `import 模块`；模块名只以 `模块.符号` 形态出现，不许重新绑定。**

- 只许 `import 模块` 一种写法，禁 `from 模块 import 符号`、禁 `as` 改名、禁 `import os.path` 这类带点的写法。只留一种写法是为了让"模块名"这个集合在源码里一眼可辨；
- 模块名在源码里只许紧跟一个 `.符号`，且这个 `模块.符号` 组合必须在白名单里；
- 模块名不许出现在任何绑定位置：赋值目标、形参、循环变量、`except … as`、`def`/`class` 名、`global`/`nonlocal` 声明。

**首批白名单从窄起步，共 18 个模块符号**（2026-09-23 作者定"白名单先缩小，甚至按更细的颗粒度去 import"；同日改为按使用处检查，颗粒度不变，见 §六 第 1 条）：

| 模块 | 放行的符号 | 为什么要它 |
|---|---|---|
| `ast` | `parse` `walk` `FunctionDef` `AsyncFunctionDef` `ClassDef` `get_docstring` `iter_child_nodes` | 语法级代码检查——这是 hop_python 表达不了、而产物代码真正需要的能力 |
| `re` | `match` `search` `findall` `sub` `split` `escape` | 正则——hop_python 完全没有 |
| `json` | `loads` `dumps` | 结构解析 |
| `sys` | `argv` `exit` `stderr` | 产物要能独立跑：取参数、设退出码、报错输出 |

**这 18 个符号逐个实测过两件事**：① 符号本身不是模块对象（反例：`os.path` 就是 `posixpath` 这个模块，`os.path.os` 全通，放行它等于什么都没收窄）；② 它们的返回值对象（语法树节点、正则匹配结果、文件句柄、`sys.argv` 列表、`json.loads` 出来的字典……）三跳广度搜索内，非下划线属性爬不到任何模块。结果全部干净。这 18 个都属于"可以当值用"的条目（如 `sorted(xs, key=re.escape)`），因为不管传什么实参，它们能做的事都只是它们本身会做的那些。

**`sys` 最危险的那扇门在这条规则下写不出来**：`sys.modules` 是把任意模块拿到手的经典逃逸口（2.1 那段实测正是走它拿到 `os` 的），它不在白名单里，写出来就被拒；`sys` 又不能当值传给别处再取 `.modules`。

**明确不入首批的**：

- `pathlib`——经 `ntpath` 一跳到 `os`，且能力与 `open` 重叠，收益不抵风险；
- `csv` `difflib` `hashlib` `datetime` `math` `itertools` `collections` `string`——这批模块级三跳验过干净，但**先不放**。理由是收窄比放宽难：多放一个符号将来要收，是破坏性变更（已经写出来的产物脚本会一夜之间不合法）；少放一个符号将来要加，只是加一行。**等真实需求撞上来，一次加一个符号，加之前验一遍属性图。**

**规则三：源码里出现的每个名字都查白名单，条目自带用法许可。**

模块符号已由规则二管住，本条管另外两类名字：内置名与对象属性。

- **内置名白名单**。首批：`print` `len` `range` `int` `str` `float` `bool` `list` `dict` `set` `tuple` `enumerate` `sorted` `reversed` `sum` `min` `max` `any` `all` `abs` `zip` `isinstance` `map` `filter` `repr` `open`，以及常用的异常类 `Exception` `ValueError` `KeyError` `OSError` `SyntaxError`。不在名单里的内置名一律拒（`eval` `exec` `getattr` `vars` `type` `breakpoint` `help` `__import__` `__builtins__` 等全在此列）。内置名也不许被重新绑定——否则 `def g(): eval = 1` 这类写法会让检查器误以为顶层的 `eval` 是脚本自己定义的名字（实测：只看"名字是否在脚本里被赋值过"而不分作用域的检查器被这样骗过，输出 42）；
- **对象属性白名单**。两部分组成：一是语法树节点的字段名（`body` `name` `lineno` `end_lineno` `id` `value` `args`……），由检查器从运行它的那个 Python 版本的 `ast` 节点定义机械导出，不手列；二是手列的常用方法（字符串的 `strip` `split` `join` `startswith` `replace` `lower`、列表的 `append` `extend` `sort`、字典的 `get` `keys` `items`、文件句柄的 `read` `readlines`、匹配结果的 `group` `start` `end` 等，约六十个）。**明确不入名单**：`format` `format_map`（运行期解释模板里的属性链；拼字符串用 f-string，f-string 里的名字在语法树上可见，照常受白名单管）、`write` `writelines` `truncate`（产物不落盘，报错输出用 `print(…, file=sys.stderr)`）、`fileno` `buffer` `detach` `reconfigure`（通向底层文件描述符）、帧与代码对象相关的一切属性（`gi_frame` `f_globals` 等）。属性名是按名字放行的——静态检查不知道 `x.read` 里的 `x` 是什么类型——所以一个属性名入名单的前提是它在一切可能拿到的对象上都安全；实测首批约一百三十五个属性名，从白名单符号的一切返回值出发四跳内爬不到任何模块、帧、代码对象或内置函数；
- **用法许可**。首批条目里只有 `open` 需要附加约束：只许直接调用（`open(…)`，不许绑名、不许放进容器、不许当实参、不许作类属性），模式实参必须是字面量 `'r'` `'rb'` 或 `'rt'`，不许用 `*`/`**` 展开实参（否则模式藏在展开里，调用点看不见）。其余首批条目都可以当值用。CPython 自己会兜底（读模式句柄上调 `write` 报 `UnsupportedOperation`，实测确认），但解析期的拒绝是主防线；
- **下划线开头的名字与属性恒不在白名单里**。这不再是一道独立防线，是白名单的自然结果；检查器仍会对它单独报错，拒绝报文更好懂。

**为什么 `open` 要放行而不是一禁了之**：产物是「能独立在别人 CI 里跑的脚本」，它必须能自己读被检查的文件、读 `sys.argv`、设退出码。全禁的话产物就得靠引擎喂 stdin，那它就不再是一份独立脚本，交付契约不成立。**只放读不放写**是取舍点——产物能读能判能退出码，不能落盘。

**白名单为什么是密封的**：规则二让命名空间里没有模块对象，规则三让能写出来的名字（模块符号、内置名、属性名）全都来自一份封闭名单，`open` 这类要看实参的条目又不许脱离调用点——**能出现在源码里的名字就是白名单里那几个**，一眼看全，没有运行期才知道的部分。

**实测对照**（原型检查器按上面三条规则实现，约一百行）：sdc 那份守卫脚本、`sorted(key=len)`、`sorted(key=lambda …)`、`map(re.escape, …)` 等正当写法全部放行；本节与 2.1 列出的全部逃逸——`__builtins__.eval`、`breakpoint()`、`help('modules')`、UTF-7 编码声明、全角 `ｅval`、`f = open`、`{"w": open}`、`map(open, …)`、`open` 模式用变量、`open(**{"mode": "w"})`、类属性藏 `open`、`.format`、`str.format(模板, 1)`、`.format_map`、`gi_frame` 取帧、`f(re)`、`re.enum.sys`、`re = open`、`def f(re)`、作用域错位的 `eval`、`sys.modules`、`case int(__class__=c)` 的模式匹配取属性、`type(1)`——全部被拒。

### 2.3 执行：审过之后怎么跑 ^anc-pysb-exec

审过的脚本由引擎执行，回执（`returncode` / `stdout` / `stderr`）作为机器凭证入执行账。五条约束：

- **审的字节就是跑的字节**——执行前引擎把文件读进内存一次，审这份字节；审过后把同一份字节写到模型写不到的私有位置，执行的是这份私有副本，不再按原路径重新读盘。理由：写盘与执行之间有时间窗，脚本可能被另一步改过；只是"执行前重审一遍"还不够，审完到开跑之间仍有间隙，文件能在间隙里被换掉（先检查后使用的时间差，asteval 的一个逃逸正是这一类）。之前的审查结论一律不认，每次执行都从读字节开始；
- **隔离模式运行**——子进程一律以 `python3 -I` 启动。实测（Python 3.14）：模型在脚本旁边再写一个 `json.py`（里面 `import os` 加任意代码），被审过的脚本只写了一行合规的 `import json`，用 `python3 脚本` 运行时加载的是冒牌 `json.py`，`os` 真的被调用；加 `-I` 后冒牌文件被忽略。原因是 Python 默认把脚本所在目录放在模块搜索路径最前面，而三条规则只审被执行的那一个文件，管不到旁边的文件。`-I` 同时做三件事：不把脚本目录放进搜索路径、忽略一切 `PYTHON` 开头的环境变量、不加载用户级第三方包目录——白名单里的 `import json` 因此只可能指向标准库的 `json`；
- **子进程不许再生**——产物代码里 `subprocess` 不在白名单，孙进程无从产生。这一条让"审过的就是跑的"成立（沙箱路线最难处理的就是子进程逃逸，这里靠白名单直接消解）；
- **超时与输出限额**——沿用 `subprocess.run` 已有的那套（缺省 60 秒、输出捕获），不另造；
- **系统沙箱在场即套上**——见"与系统沙箱的关系"一节：在场必须把这次执行放进去，缺席照跑并在执行账里记"只有语法层单层防护"。

**审查没过怎么办：本步失败，进重试链**（2026-09-23 作者定）。不是直接终止整个执行，而是把这一步判失败、带着拒绝报文回到重试链里，让模型有机会改写脚本再来一遍。

这么定的理由是**拒绝报文自带可操作的信息**：白名单的每个条目都是一个具体的名字，被拒时引擎知道得很具体——哪一行、哪个名字、为什么不在名单里、名单里有没有能替代的。报文要按这个形态写，比如「第 3 行 `import pathlib` 被拒：`pathlib` 不在白名单内。读文件请用内置的 `open`（只读模式）」。这是模型照着就能改的信息，和"你的产出形态不符合输出声明"那种笼统打回（0110 里 Ling 连撞九轮的那种）是两回事。

重试链耗尽仍不过，按普通的步骤失败处理，不为此另设出口。规约自己的「降档为需人裁」出口照常可走——**诚实降档，不是把不合格的脚本硬塞过去**。

**这条链路上，被信任的是「白名单 + 静态审查」，不是模型、不是规约作者的自觉。** 三者的差别要说清楚：

| 谁在授权 | 形态 | 安全性来自 |
|---|---|---|
| 规约作者写死 body 里的 `subprocess.run(["python3", …])` | 生成期白纸黑字，人能 review | **人的审查**——今天已有，能力上等价，但责任在人 |
| 执行模型自由调一个执行工具 | 运行期现场决定 | **无**——这是 todo/0110 里 `run_script` 的问题所在 |
| 本方案 | 模型写、机器按人定的白名单审、审过才跑 | **机器强制的形态收窄** |

### 2.4 白名单的归属：引擎内置基础名单，宿主只能做减法 ^anc-pysb-whitelist-authority

`requires_commands`（命令白名单）的先例是「宿主配置声明供给、spec 声明依赖、INIT 时对账」。本方案**部分沿用、一处不沿用**：

- **沿用**：spec 用 `requires_modules: [ast, re]` 声明依赖，引擎在 INIT 时与宿主供给对账，缺就在进任何步骤之前拦下并指明怎么配。声明是下限不是上限——未声明的仍由运行期白名单核兜底拒（与 `requires_commands` 同款语义）。这里声明的是模块名（给人看"这份 spec 的产物要用什么"），准入判定仍按 `模块.符号` 逐个走；
- **不沿用**：宿主**不能往名单里加东西，只能在引擎内置的首批名单内做减法**。理由就是 2.1 那两组实测——命令白名单放 `git` 就是放 `git`，而模块白名单放一个没验证过的符号可能等于放 `os`（`os.path` 那种情形）。每个入名单的条目——模块符号、内置名、对象属性名都一样——都要过一遍"它不是模块 + 它的返回值爬不到模块、帧、代码对象或内置函数"并定下用法许可（能不能当值用），这件事不能交给宿主配置的人临场判断。

宿主要加新条目的正路：走引擎的发布流程，附上属性图验证结果。

### 2.5 交付形态：格式化 + 机器生成标头 ^anc-pysb-artifact-form

2026-09-23 作者定：引擎对交付的脚本做格式化，并在文件头注明机器生成与来源。这一条不影响安全性，影响的是**交付物落到别人仓库里之后，那边的维护者能不能看懂它是什么、从哪来、该不该手改**。

**标头形态**（引擎填写，非模型填写——见下）：

```python
# 本文件由 HopJIT 引擎自动生成，请勿手工修改。
# 来源规约: standard-decompose-codify
# 对应条款: C1（单个函数不得超过 40 行）
# 生成实例: <run_id>
# 校验状态: 已通过 Python 语法沙箱静态审查 + 正反样例实跑
```

三条纪律：

- **标头字段一律由引擎填，不由模型填。** 模型能自由写进标头的话，"机器生成、已通过审查"这句话就成了模型的自述——正是 0110 那个验证盲区的形态（判据要机器凭证，拿到的却是模型的作文）。条款文本这类需要从上下文取的字段，引擎从规约的结构化产出里取（`clause_id` 对应的 `quote`），不接受模型另写一份；
- **标头是注释，但仍要过审查。** 顺序是：模型写脚本 → 引擎审 → 引擎加标头与格式化 → **再审一遍** → 执行 → 交付。为什么最后要再审：2.3 已经定了"审的字节就是跑的字节"，引擎自己改过的文件也不例外——**引擎不给自己开豁免**，否则"审过的就是跑的"这条不变式就有了缺口；
- **标头不带生成时间戳。** 带了的话同一份 spec 跑两次产出的文件字节不同，交付到目标仓库里每次都是一个 diff，而那边多半有 CI 在比对。要追溯时间去查 `run_id` 对应的执行账，那里记得比标头全。

**格式化谁来做，有一个需要注意的取舍**：引擎是 TypeScript 写的，手里没有 Python 的格式化器。两条路——调宿主环境里的 `black`/`ruff`（要求宿主装了它，而且不同版本格式化结果有差异），或者引擎自己做一套最小的确定性规整（统一缩进为 4 空格、去行尾空白、文件末尾恰好一个换行、import 行按字母顺序排）。**本篇倾向后者**，理由与 2.4 的白名单归属同源：外部格式化器在场与否、版本几号，会让同一份 spec 在不同机器上产出不同的文件，这与本篇一以贯之的环境无关原则相抵。最小规整虽然不如 `black` 漂亮，但它确定、无依赖、且对"给人读"这个目的已经够用。**这一条是工程实现层的选择，落地时若有更好的判断可以推翻，但推翻要连带解决"跨机器产出一致"这个问题。**

## 三、边界：本方案不做什么

**不是通用 Python 沙箱。** 它管的是「引擎自己生成并执行的产物脚本」这一条链路。用户手工写的脚本、第三方脚本不在射程内——那些该用操作系统级隔离。

**不防资源耗尽。** 白名单挡不住 `[0] * 10**10` 或者一个死循环。对治靠执行侧的超时与输出限额，不靠静态审查。**相关缺口另记**：body 解释器今天没有任何执行预算（没有步数上限、没有时钟），这是独立于本方案的既有技术债。

**不保证产物质量。** 审过 ≠ 脚本是对的。产物对不对由规约自己的验证判据管（实跑正反样例），本方案只保证"跑它不会伤害宿主"。

**降档出口保留。** 有些检查用白名单内的能力写不出来，规约该走自己已有的「降档为需人裁」出口——**诚实降档，不是伪装通过**。

## 四、与既有概念的关系

| 概念 | 关系 |
|---|---|
| **hop_python**（[[HopSpec V3核心规范#^anc-step-act-body-lang]]） | **不是它的扩展，是它的对偶**。hop_python = 引擎执行的编排代码，宿主中立，一个库都不能 import；本篇 = 引擎审查的产物代码，目标环境相关，可以 `import` 白名单内的模块、按 `模块.符号` 逐个使用。两者共享"解析期白名单"这一安全原理，不共享能力面 |
| **`subprocess.run`**（[[HopSpec V3语法参考#^anc-step-subprocess-run]]） | 同源不同授权主体。那条是规约作者生成期写死，本篇是模型运行期生成但机器审过。命令白名单与模块白名单是同一设计思想的两次应用 |
| **验证环境**（[[HopSpec V3配套HopJIT运行时能力]]） | **不同主体，不合篇**。彼处被沙箱的是有序思考动态生成的 **HopSpec 步骤**，此处是**产物 Python 源码**。只是名字里都有"沙箱" |
| **执行沙箱**（同上） | 本篇是它在"产物代码"这一面的具体落地。既有表述「HopJIT 在运行时负责强制沙箱边界」对子进程并不成立，本方案靠"白名单内无 subprocess"把这个缺口消解掉 |
| **探索/提交分离** | 不破。产物脚本的执行是**只读的、可重做的**（白名单无写模式 `open`、无 subprocess），落在探索态的能力面内。真正的写盘交付仍归 `[commit]` |

## 五、落到 sdc 那个用例上（端到端）

1. `[act free]` 步：模型 `write` 出一份真 Python 校验脚本（`import ast`，用 `ast.parse` / `ast.walk` 遍历语法树，逐个 `ast.FunctionDef` 算 `end_lineno - lineno + 1 > 40`），再 `write` 出合规与违规两个样例；
2. 引擎按白名单审这三个文件——`ast.parse` / `ast.walk` / `ast.FunctionDef`、`sys.argv` / `sys.exit`、直接调用的读模式 `open`、属性 `.lineno` / `.end_lineno` / `.name` / `.read`，全部在名单内，通过；
3. 引擎执行校验脚本两次（对两个样例），回执入执行账：违规样例 `returncode=1` 且 stdout 指出超限函数，合规样例 `returncode=0`；
4. `[check]` 步核对这份**机器回执**——不再是核对模型自述的文本。0110 记的那个验证盲区（判据是"实跑留痕"而留痕是模型自述、没有机器凭证对账）在这里关上；
5. `[commit]` 步交付脚本文件。

**与 hop_python 转译路的对比**（那是另一条候选，此处说明为什么不够）：把校验写成 hop_python、引擎跑完再转译成真 Python——实测可行，且结果与真 `ast` 版在自造样例上逐字一致。但它**做的是按缩进扫行的启发式**，遇到 docstring 里的 `def `、装饰器、多行签名、嵌套函数会给错答案。**交付一个会误报的守卫，比不交付更糟。** 转译路覆盖"纯文本结构计算且启发式够用"的那一片，不覆盖需要语法级理解的这一类。

1. **首批白名单范围：从窄起步，按更细的颗粒度控制**（2026-09-23 作者定）。落定为 2.2 规则二：首批 18 个模块符号（`ast` 七个、`re` 六个、`json` 两个、`sys` 三个），外加规则三的内置名与对象属性白名单。`csv` / `difflib` / `hashlib` / `datetime` / `math` / `itertools` / `collections` / `string` 这批模块级三跳干净的模块**不入首批**，按真实需求一次加一个符号。**同日修订语法形态**（作者定"禁止 lib 被当值用，import 可以简化，在使用时检查白名单即可"）：原定只许 `from 模块 import 符号`、禁 `import 模块`；改为只许 `import 模块`，模块名只以 `模块.符号` 形态出现且不许重新绑定，白名单在使用处检查。颗粒度不变（条目仍是 `re.match` 这一级），变的只是检查的位置从 import 行挪到了使用处。改的原因：`from` 形态靠"模块名在命名空间里不存在"防止模块对象被当值传递，`import` 形态靠"模块名只许以一种形态出现"防止同一件事，两者效果相同；后者与"有能力的对象不许作为值出现"这条统一原则同构，而且 `re.match` 这种带模块名的写法是 Python 惯用写法，交付物落到别人仓库里更易读；
2. **五道防线收为三条规则**（2026-09-23 作者定）。落定为 2.2。起因：按原来的五道防线写原型检查器实测，撞出四个洞——`__builtins__` 这个名字直接拿到 `eval` 和 `open`；内置名用的是黑名单，`breakpoint()`、`help('modules')` 能逃逸；原文"检查器可以用任何宿主语言写"不成立，UTF-7 编码声明与全角标识符会让自己写的解析器与 CPython 看到不同的源码；可调用对象当值传递（`f = open`、`map(open, …)`、先绑 `.format` 再调）绕过按调用点做的检查。修法：用 CPython 自己的 `ast.parse` 按原始字节解析；源码里每个名字（模块符号、内置名、对象属性）都查白名单，条目自带用法许可，缺省只许直接调用。过程中作者两次纠正方向：一是"调用位上的值只是白名单函数并不危险"——所以不是一刀禁掉一切当值用法，只管有能力的对象；二是"这种是不是又成为了打地鼠"——所以不能靠一份危险对象名单来管，对象属性也必须进白名单；
3. **静态审查没过时：本步失败，走重试链**（2026-09-23 作者定）。落定在 2.3 末段，含拒绝报文的形态要求（点名哪一行、哪个符号、为什么、有没有替代写法）与"重试耗尽按普通步骤失败处理、不另设出口"；
4. **交付形态：格式化 + 文件头注明机器生成与来源规约**（2026-09-23 作者定）。落定为 2.5，含标头形态与三条纪律（字段由引擎填不由模型填 / 加完标头再审一遍不给引擎开豁免 / 不带时间戳以免每次交付都是一个 diff）；
5. **与系统沙箱的关系：判据不依赖，在场即必须套上**（2026-09-23 作者定，选"保留不依赖并正面回应业界共识"与"在场强制套上、缺席标单层防护"两案合并）。起因：对照业界做法（pysandbox 作者放弃说明、RestrictedPython 与 smolagents 自述、PyPy 双进程沙箱、Crawl4AI 与 asteval 的沙箱逃逸通告），主流共识是语言层沙箱不算安全边界、必须叠加操作系统隔离，原文"可叠加、不依赖"在措辞上与共识相反且没有回应。落定为"与系统沙箱的关系"一节：准入判据仍不依赖系统沙箱（环境无关原则），在场由"应当顺带"升为"必须套上"，缺席在执行账记单层防护；补写与共识中失败案例的三处结构差别及残余风险（CPython 自身缺陷）。未选"必须有系统沙箱、缺席拒绝执行"，理由是 macOS 的 `sandbox-exec` 已废弃、Linux 的 bwrap 不预装、Windows 无等价轻量件，选它等于一半平台关掉此功能。同批次由业界案例推出两条收紧写入 2.3：审的字节就是跑的字节（关先检查后使用的时间差）、子进程以 `python3 -I` 启动（实测同目录冒牌标准库模块的逃逸）。

**留给实现层的取舍只有一个**：格式化由谁做——调宿主的 `black` / `ruff`（有环境依赖，不同版本结果有差异）还是引擎自己做最小确定性规整（缩进、行尾、import 排序）。2.5 写明了倾向后者及其理由；落地时可以推翻，但推翻要连带解决"跨机器产出一致"这个问题。
