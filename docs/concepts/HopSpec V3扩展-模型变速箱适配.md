> HopSpec V3 扩展——模型变速箱适配

## 定位

HopSpec 有两个核心作用：**控制器**（spec 声明流程与把关，引擎强制执行）与**变速箱**（同一套控制逻辑，适配不同能力的基座模型与执行载体）。本篇是变速箱的概念规范：怎么度量一个模型、怎么把度量结果换算成适配动作、有哪些已验证的适配方法。

变速箱的存在意义：HOP 的目标是让轻量小模型也能正确转起来。强模型跑什么形态都行；弱模型不是不能用，是**要换挡**——把任务切小、把把关封闭化、把供给收窄。挡位换对了，"弱模型执行 + 强模型把关"的组合能以强模型几分之一的成本跑完同样的活。

## 一、度量的两条原则

**原则一：度量对象是 model service（模型 × 服务端点），不是模型。**

同一个模型名经不同端点，能力可以差到判若两物——中间层会注入系统提示、做量化、改采样参数，这些对协议探针全部不可见。每份能力画像必须绑定它实测的那个端点；换端点等于换被测对象，全部维度重测，不存在"同模型免测"。

**原则二：从模型的基础能力维度展开，不从引擎故障现象展开。**

引擎的失败计数（schema 打回几次、工具循环撞墙几次）是症状不是能力——一个症状背后常混着多个能力，且计数随引擎版本变，无法横向比。正确做法：先立能力维度，每个维度定探针与判据，引擎现象只作为可观测指标映射回维度。

## 二、能力维度（两组制）

**通识组 G1-G6**（业界共识能力面，探针对准 HopSpec 步骤类型的生存前提）：

| 维度 | 测什么 | 谁消费 |
|---|---|---|
| G1 推理复杂度 | 推理难度升到哪档开始出错（直接推理）或断链（迭代推理） | 判定步、重推理步的路由 |
| G2 任务复杂度 | 多大的活能一次做对（首轮通过率的坍塌点） | 构建器切步尺寸 |
| G3 分解与规划 | 大活拆得开、排得顺吗 | 到步展开（subtask free）的资格 |
| G4 工具使用 | 单步内多轮工具循环收得住吗 | 带工具步骤的路由 |
| G5 结构化交付 | 按声明的字段形态交付吗（嵌套复杂度 + 容错后能力双指标） | 一切多输出步骤 |
| G6 代码生成 | Python/SQL/HopSpec 各能写到多复杂（一次写对率 + 自愈率双指标） | body 生成、构建产物质量 |
| G7 领域知识充分度 | 目标业务领域的事实、术语、常识在模型里存量够不够 | 知识供给策略（缺多少喂多少） |
| G8 渐进知识获取 | 发现自己缺知识时，会不会去搜、搜得到、用得上——检索与使用的闭环 | 检索型步骤的路由；知识缺口的自补资格 |

**实践组 P1-P3**（真机实撞总结的维度，通用评测测不出，直接决定适配开关）：

| 维度 | 测什么 | 为什么通用评测测不出 |
|---|---|---|
| P1 核验能力 | 把关步能给它什么形态的考卷（开放式 → 按清单 → 单点的三档阶梯） | 评测判定题都是单发单题；"跨轮框架一致"与"多题自洽"只在重试循环里当判官才暴露 |
| P2 inline 工具耐受 | 工具在场但用不上时忍得住吗 | 要把满配工具塞给纯推理任务才看得见——闲置工具面是行为吸引子 |
| P3 修订落实 | 打回意见能落实到产出上吗（指令散文序列理解） | 真实工程形态是"全量供给+尾部修正"的一篇长文，评测的指令遵从与多轮修正都不是这个语境 |

维度详解、探针方法与统计纪律见接入教程（D12）；机读档案与度量仪器见 model-gearbox/。

## 三、适配方法（已验证的换挡动作）

每个方法解决一个能力维度偏弱时的问题。共同思路：**不改模型，改供给面与产物形态**——把模型干不了的协调工作拿走，只留它干得了的原子工作。

### 方法 1：把关步按核验能力选考卷形态（P1 偏弱）

把关步按执行模型的核验能力档位选形态，三档阶梯：

- **开放式判官**（P1 开放式可用）：一步 check，判据写散文，模型自建核对框架。弱模型跑它的死相是**自反**——每轮现建一个框架，同一对象两轮给出相反指令，重试变成"每轮换考官"，预算必然烧尽；
- **清单判官**（P1 按清单可用）：spec 替模型建好框架（封闭问题清单 + 机械汇总规则），模型只逐题作答；
- **微判定三件套**（P1 仅单点可用）：把关拆三段——**机械归组**（hop_python body 把判定对象分组成作业单，零 LLM）→ **逐题小题**（loop 每轮只问一个封闭问题，可包 subtask parallel）→ **机械汇总**（body 收集 yes/no 出判定与说明双槽）。

微判定的核心思想：**判定确定性归引擎，LLM 只出原子事实**。建框架归程序、遍历完整性归循环结构、汇总与门槛归 body——判官摇摆在结构上无处发生。零新引擎机制，纯既有原语（act body / loop / check body）的组合写法。已验证的收敛形态：失败不再是摇摆烧尽，而是每次收敛到一个具体可修的判据缺口。

小题粒度从紧：**一次一个原子问题**。"一行一题"在一行多断言并列时仍会失焦（实测：断言逐字在场仍被判缺）——细到一断言一题，或小题内强制显式核销（先拆断言清单、逐条写"断言 → 覆盖它的条目或无"，再给结论）。

### 方法 2：每步任务量不超过模型的可靠处理上限（G2 偏弱）

度量已经测出这个模型"一次能做对多大的活"（比如一次提取不超过 4 个要点）。写产物时就把每一步的任务量压在这条线以内——超过的活拆成循环分多轮做，太重的推理步拆成几个轻步骤。构建器按目标执行档出产物时机械执行这条规则，不靠临场判断。

### 方法 3：不让规划能力弱的模型现场拆任务（G3 偏弱）

到步展开（subtask free）的意思是：spec 里留一个粗步骤，执行到这里时让模型现场拆出子步骤。规划能力弱的模型会把这个机制当成逃生舱——看起来拆了，实际把一大段流程收缩成一个空壳步骤，内容全丢。对治：给这类模型出的产物里不用 subtask free，所有子步骤在构建期就由强模型写死，不把拆任务的活留到运行期。

### 方法 4：修订轮换一份短提示词（P3 偏弱）

先说问题。产出被把关步打回后，引擎会让模型重做一轮。标准做法是把原来的完整提示词原样再发一遍，在末尾追加打回意见——于是这份提示词里同时存在两种互相矛盾的指令：中间是原任务命令（"通读文档，提取全部要点"，教它从头做题），末尾是修订指令（"在上一版基础上把这几条意见改掉"）。强模型知道该听末尾的；弱模型的实测行为是**跟着篇幅大的那段走**——意见它读到了也读懂了（让它复述都能复述对），动手却还是从头重做全题，改动一条都不落实。把"重试轮要听修订指令"的裁决规则写进提示词也没用：那句规则自己也淹没在长文里。

解决的做法：**打回重做的那一轮，不再发完整提示词，改发一份专门的短提示词**——把原任务命令整个撤掉，换成明确的修订指令（"在上一版基础上把下面的意见逐条落实，不是重做任务"），从头做题的那些教学内容全部撤掉，只留四样东西：上一版产出（修改的基准）、打回意见、落实规则（意见没提到的地方原样保留）、交付格式。这样提示词里只剩一种指令，模型不用再做选择。引擎配置开关是 `revision_prompt: short`。

实测效果：同一个弱模型，标准提示词下修订九轮零落实；换短提示词后六发六中。缺的不是执行力，是从一篇长文里分辨"此刻该听哪段指令"的能力——短提示词等于引擎替它做了这个分辨。

### 方法 5：用不上的工具就别给（P2 偏弱）

实测发现：给模型挂一堆它用不上的工具，工具本身会引它分心——每件挂着的工具都是一个"随时可以点的按钮"，按钮多到一定程度，模型点按钮的总概率就压过了认真答题（写五种强度的"不要用工具"都拦不住，把工具拿掉立刻正常）。对治：工具按步骤声明下发——步骤声明了哪几件才给哪几件，纯推理步一件不给。物理上没有按钮，就没有分心。

### 方法 6：缺领域知识就随步喂知识（G7 偏弱的对治）

轻量模型的参数量小，装的领域知识（行业事实、专业术语、业务常识）天然比大模型少——这不是推理能力问题：推理档够用的小模型，遇到它不认识的领域照样判错（比如核查芯片行业新闻时不知道行业基本盘，可信度打标全靠猜）。

解决的做法：**知识缺口用供给补，不用换模型**。HopSpec 现成两条通道——spec 级知识声明（全程恒定供给的判据基准）与步骤级 doc-ref 注入（哪步需要哪份领域材料就在哪步引用，引擎组装提示词时自动带上）。写产物时按目标模型的知识档位决定供给量：知识充分的模型给任务就行；知识不足的模型把领域判据、术语表、参照数据作为输入材料显式喂进相关步骤。判断"要不要喂"的机械信号：该模型在这个领域的产出里编造率、术语误用率明显高于通用领域。

知识轴还有另一半：**G8 渐进知识获取**——存量不够时，模型会不会自己把缺口补上。这是一个闭环能力，四个环节缺一不可：**察觉**（意识到"这个我不知道"，而不是编一个）→ **检索**（把缺口翻译成有效的搜索查询）→ **筛选**（从检索结果里挑出真正相关的）→ **使用**（把新知识用进当前判断，而不是搜完照旧）。弱模型常见的断环形态：不察觉（直接编造）、检索空转（查询词无效反复搜）、搜到不用（结果在上下文里、结论还是按旧认知下）。

G7 与 G8 的适配组合决定知识供给策略：G8 强的模型给检索工具就能自补（供给面可以轻）；G8 弱而 G7 也弱的模型必须**预制供给**——构建期把领域材料准备好随步喂，运行期不指望它自己补课。

### 方法 7：按目标模型定制构建产物（前面各方法的构建期打包）

构建器接受一个"产物给哪个模型跑"的参数，按那个模型的能力档案出产物——方法 1/2/3/6 的适配动作全部在构建期机械落地，运行期零临场适配。注意"谁来构建"和"产物给谁跑"是两件独立的事：推荐组合是强模型构建、弱模型执行——产物质量由强者保证，日常运行成本按弱者计费。这与"弱模型执行+强模型把关"的路由组合是同一个思路的两面。

### 方法 8：思考型模型跑机械步骤时关掉思考（输出预算病的对治）

思考型模型（推理过程作为思考文字输出的模型）有一个容易误诊的故障形态：**思考文字与正式回答共用同一个输出预算池**，而思考量随任务规模自动增长。跑一个 40 要点的提取任务，实测思考部分能写出 2-4.5 万字符——如果调用方给的输出预算小（比如 8K），思考先把池子烧光，正式回答零字节。从外面看是"这个模型做这个任务得 0 分"，看起来像能力坍塌；把同一个任务在大预算下重跑就满分——**这是预算病，不是能力病**。

对治分两半：

- **诊断半边（度量时）**：给思考型模型做探针，必须先做思考开销探测——同一任务跑三个配置对照：①档案预算+思考开、②小预算+思考开、③小预算+思考关。②烧穿而①③满分，就确认思考开销主导，并顺手量出该任务档位的思考开销（①与③的输出 token 差）。不做这个对照，就会把预算病记进能力档案，整个档位的数据都是假的；
- **适配半边（写产物时）**：**机械性步骤（提取、格式转换、照单填表这类不需要推理的活）显式关掉思考**。实测同一提取任务：思考开着要 1.7-2 万输出 token，关掉只要 2 千出头、得分持平——费用差 8-9 倍。开关体系是一条五级优先链（2026-09-20 落地，高到低）：思考烧穿记名册（止血恒最高）→ 步骤级 `@thinking on|off` 标注（本方法的落点——机械提取步逐步标 off；语法见语法参考）→ 运行配置 routing_rules 按步骤类型整类开关 → provider 级思考缺省（逐模型矫正——各端点缺省互相相反且不可见，配置层显式化）→ 引擎内建步骤类型缺省（act/commit 关，act free/reason/check/replan 开——需要推理的形态天然拿到推理通道）。五级全兜底后思考行为恒显式恒可审计，端点私有缺省不再左右行为。

关思考的适用面比直觉宽：**关思考不等于不推理——推理会迁移到正式回答的正文里**（模型把演算过程写进回答），而思考通道的文字远比正文演算啰嗦（同一任务思考通道写 1.5-1.8 万 token，正文演算 2-3 千就够）。实测连纯推理任务都扛得住：12 位×12 位手算乘法（该模型思考开着测出的最高档）关思考连发 4 次全对，每发只花 2-3 千 token；13 位有效数字的迭代长除法关思考 3 发全对。等于把推理换到了一个便宜得多的载体上。

真正的边界只有一条实锤加两个未验证面：**工具编排步骤不关**（实测反例：没有预定义脚本的工具步关思考后，工具调用循环打转二十轮烧尽——多轮工具编排的"下一步调什么"决策确实依赖思考通道）；未验证面是判官/核验类步骤（判定质量是否依赖思考通道没对照过）与"交付格式禁止分析文字"的步骤（推理要迁移到正文，正文又被格式禁掉，两头堵的效果未知）。所以落地策略是**按任务族白名单扩，不做全局关**：提取、格式转换、机械推演已实证进白名单；判官类补对照后再定。另注意关思考的收益与安全面是逐模型的事实——每接入一个思考型模型都要单独探（思考开销探测法见度量教程）。

### 方法 9：概率型步骤用并发多实例加并集汇总（覆盖率方差的对治）

有一类步骤的失败不是"能力不够"而是"每次做成功概率 p<1"——同一份文档同一个模型，这次提取满分、下次漏三点，像掷硬币。对这类步骤加串行重试是慢药：每轮要等判官打回才知道漏了，判官轮本身还要花钱。

正确形态是**并发 N 个独立实例同做一份活，产出取并集再机械去重**。两笔账都合算：

- **概率账**：单次成功概率 p=1/3 时，三并发至少一个全对的概率 ≈70%；而并集比"至少一个全对"更强——各实例漏的往往是不同的点（实测三份各漏 2-3 个不同点，并起来就齐了），所以并集覆盖率恒不低于最好的单份。实测三个能力档位完全不同的模型，最优块尺寸下 3 并发并集全部收敛 100%；
- **成本账**：N 倍单发调用费，但省掉串行重试的判官轮与等待墙钟（并发实例同时跑，墙钟不涨）。密集提取类任务通常净赚。

HopSpec 原生承载：`[call … parallel]` / `[subtask parallel]` 发并发实例，汇总归机械 body（拼接+去重零 LLM）。适用判据：步骤产出是**可并集的集合**（提取点、检索结果、候选清单）——产出是单一决定（一个判定、一段改写）的步骤不适用，那是投票（方法 1 微判定的领地）不是并集。

与方法 2（切块）正交可叠加：切块治"单次任务太大做不动"，并发并集治"做得动但每次漏的不一样"——弱模型的密集提取步常两个都要（先切到能做对的块，每块再并发取并集）。

## 四、实践教训

**教学清不了零。** 文字供给（教学、禁令、示例）只能降低错误概率，清不了零——实测三案：五级强度的"不要用工具"全部无效、明文禁令在场照披代码围栏、格式教学完整在场仍照抄输入渲染语法。

**惯性不分强弱模型**——最强模型同样把上下文里的高频形态带进输出，差别只在概率。结论：凡是"模型可能复读供给形态"的病，防线必须是机械的（引擎剥壳/校验闸/物理拿走），教学只作辅助。

**弱档的正确消费是适配，不是弃用。** 每个偏弱维度都有对应的换挡方法；换挡后弱模型在它的可用形态里是完全可工作的（微判定的 n 发小调用总成本常低于强模型一发）。判档的产出物永远是路由决策与适配开关，不是"这模型不行"的结论。
