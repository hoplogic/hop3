# HopSop：Hop 标准作业流程

> **HopSop** = Hop Standard Operating Procedure（Hop 标准作业流程，2026-08-10 作者定名；曾名"HopSop（Hop 标准作业流程）/HopSop"）。与 HopSpec 一字之差成配对：**HopSop 是大致流程，HopSpec 是可执行规范**——SOP 写好，需要 HopJIT 双态融合执行时按第七章升级为 HopSpec。Hop 概念三件套之一（Hop契约 HopTrait / Hop类型 HopType / HopSop——见 [[HopType体系]] 定位节）。
>
> **定位**：HOP 概念层的**轻量结构化流程语法**——用纯 Markdown 表达"顺序/循环/分支 + 分层编号 + 自然语言流控"的流程逻辑。它是 HopSpec 的无执行态近亲：共享同一控制流骨架（子任务/循环/分支即 subtask/loop/branch+case），但**不含**变量流（`←`/`+→`）、步骤类型（reason/act/check/…）与执行语义（retry/adaptive/HITL）。适用场景是"人要看懂流程逻辑、暂不需要机器执行"的表达；需要 HopJIT 双态融合执行时按第七章升级为 HopSpec。
>
> **三条核心要求**【契约】（本标准的锁定语义，任何使用方与语言版本必须保持） ^anc-flow-core-requirements：
> ①整体控制逻辑仅用顺序、循环和分支，不使用 goto、任意回边或跨层跳转；
> ②分层表达清晰逻辑边界——节点位置、父子范围和同级顺序明确，不依赖含混的自然语言指代；
> ③表达保持简洁且可等价转换——本文只规定默认 Markdown 表面语法，逻辑等价的其他表达同样合法，转换不得改变流程语义。
>
> **已知使用方**：① [[HopKB知识工程核心架构]] §6.5 **过程型知识**的默认表达；② HopKB **复杂规则的判断流程**——构成要件、排除条件与例外的多层判断次序（借用表达不改变知识形态：规则仍是规则型）；③ 任何 HOP 系组件中"给人读的流程逻辑"（hopagent 规约的人读概览、运维手册的操作流程等）。使用方引用本标准，不复制规定。

## 二、容器与节点【契约】 ^anc-flow-containers

中文版本使用：

```text
[循环]      子节点构成循环体
[分支]      根据命中条件选择子分支
[条件(…)]   表示某个分支的命中条件，括号内写具体条件；兜底分支写 [条件(其他)]
[子任务]    组织一组具有共同边界的子节点
```

同一父节点下的普通节点按出现顺序执行，不需要额外声明顺序类型。`[循环]`划定循环体，`[分支]`的直接子节点使用`[条件(分支命中条件)]`表示互斥条件，兜底分支写`[条件(其他)]`（只能放最后）。

**`[条件(…)]`节点等同于子任务**【决策：原则性，2026-08-08 作者定】：它直接拥有并组织所命中分支路径的顺序子节点，不需要在其下再垫一层`[子任务]`。why：多步分支是常态，强制垫层徒增一级缩进且无语义增量。（与 HopSpec 的 case 语义对齐：case 就是 branch 下的 subtask。）

`[子任务]`只负责分层和边界，不增加第四种控制逻辑。默认表达中，只有`[子任务]`、`[循环]`、`[分支]`和等同于子任务的`[条件(…)]`可以拥有子节点；普通步骤和流控节点不得拥有子节点。

**节点的输入与输出（可选）** ^anc-flow-node-io：过程与规则的重要区别在于——**过程的每一步都有输入和输出，即使表达中可以省略**。需要显式表达时，在节点行下方缩进写 `输入:` / `输出:` 行（直接用大白话词，不用符号——降低读者门槛）：

```text
1 汇总销售数据：按周合并流水。
  输入: 销售流水
  输出: 周汇总表
```

- 两行都可选、可只写一行；多项用顿号或逗号分隔；值是自然语言名称——**不写类型**（类型是升级为 HopSpec 时的事）；
- 容器节点（`[子任务]`/`[循环]`/`[分支]`）也可标注（表达该段的整体进出），普通步骤最常用；
- 省略不等于没有——每步的输入输出客观存在，省略只是"此处不必说"；升级为 HopSpec 时每步的 `←`/`→` 必须补全。

## 三、分层与作用边界【契约】 ^anc-flow-numbering

在顺序、循环和分支结构确定之后，默认Markdown表达使用多层数字序号把节点位置、父子范围和同级顺序显示出来：

```text
1
1.1
1.1.1
1.2
2
```

序号需要与容器和分层共同理解，不独立决定流程语义。它用于：

- 显示节点在当前流程中的位置；
- 显示父子层级和同级顺序；
- 明确循环、分支和说明所作用的范围；
- 为流控和引用提供清晰目标。

子节点继承父节点前缀。流程说明避免使用"上一步""后面那一步"等不稳定指代，使用明确序号、节点标识或 Wikilink。

## 四、流控语句【契约】 ^anc-flow-flowctl

流控节点与容器节点同用**中括号词汇型标注**（2026-08-16 作者定改版——原裸文本形态『继续循环 1.3』与普通步骤无形态区分,机读须靠词头猜;加括号后与 [子任务]/[循环]/[分支]/[条件(…)] 同族,凡结构语义皆入 `[]`）：

```text
[继续循环 <循环节点序号>]
[退出循环 <循环节点序号>]
[完成任务]
```

例如：

```text
[继续循环 1.3]
[退出循环 1.3]
[完成任务]
```

"[继续循环 1.3]"结束当前节点之后属于循环`1.3`的本次迭代内容，进入循环`1.3`的下一次迭代。

"[退出循环 1.3]"结束循环`1.3`，然后执行循环`1.3`之后的同级节点。**退出目标仅限循环节点**（2026-08-14 作者定）——子任务与分支不设退出语句：子任务的子节点顺序结束后自然返回父层，分支命中路径走完自然汇合，为它们提供中途退出徒增跳转面（与结构化三原则的"不跳转"相悖）；确需提前结束的逻辑用条件分支表达。

退出与继续的目标必须真实存在，且是当前流控节点的**祖先循环**。流控不能指向未来节点、同级容器或无父子包含关系的节点。

"[完成任务]"表示当前流程已经得到目标结果，立即成功结束整个流程，剩余节点不再执行。子任务不需要独立完成语句，其子节点顺序结束后自然返回父层。

## 五、语言版本【契约】 ^anc-flow-lang

中文是默认表面语法。**英文对偶版本**（2026-08-16 作者定与 HopSpec 关键词对偶——同一词族,HopSop 升级 HopSpec 时词汇零换挡）：

| 中文 | 英文 | 对应 HopSpec |
|---|---|---|
| `[子任务]` | `[subtask]` | subtask |
| `[循环]` | `[loop]` | loop |
| `[分支]` | `[branch]` | branch |
| `[条件(命中条件)]` | `[case(condition)]` | case |
| `[条件(其他)]` | `[case(else)]` | case(else) |
| `[继续循环 <序号>]` | `[continue <序号>]` | continue |
| `[退出循环 <序号>]` | `[break <序号>]` | break |
| `[完成任务]` | `[exit]` | exit |
| `输入:` | `input:` | `- ←` |
| `输出:` | `output:` | `+ →` |

不同语言版本必须映射到相同流程语义；同一文档内两语可混写（与 HopSpec 方案 B 双语直通同口径）。正文不要求暴露内部英文关键字；解析器根据标注词汇直接识别，无语言声明。

## 六、最小形式【说明：示例】

以 HopKB 知识形成流程为例（使用方之一，见头部"已知使用方"）：

```text
1 [子任务] 形成知识：把材料转化为3+N+X知识。
  1.1 发现材料：在知识库或任务中发现值得处理的内容。
  1.2 [分支] 检查同名知识：比较现有知识的一句话核心表述。
    1.2.1 [条件(含义相同)] 更新已有知识：保持同一主知识及其当前限定名称。
    1.2.2 [条件(含义不同)] 创建新知识：把同名条目放入能够消歧的领域目录。
    1.2.3 [条件(其他)] 请求人确认：无法判断时暂停，交人裁决。
  1.3 [循环] 处理关键表述：对每个需要沉淀的表述循环。
    输入: 关键表述清单
    输出: 沉淀后的知识条目
    1.3.1 形成一句话：表达核心含义。
    1.3.2 [分支] 检查是否值得沉淀：判断是否具备复用价值。
      1.3.2.1 [条件(否)] 继续循环 1.3：处理下一个关键表述。
      1.3.2.2 [条件(是)] 完整展开：补充一段话。
    1.3.3 补充Attributes：按需增加结构化语境。
    1.3.4 [分支] 检查是否应终止：判断是否达到处理上限。
      1.3.4.1 [条件(是)] 退出循环 1.3：结束关键表述循环。
      1.3.4.2 [条件(否)] 保持循环：继续循环 1.3。
2 写入目标知识库：一次只写入一个知识库。
3 [分支] 检查任务目标：判断知识是否已经写入并可被重新读取。
  3.1 [条件(已完成)] 完成任务：结束当前过程。
  3.2 [条件(未完成)] 补充缺失内容：继续后续修正步骤。
```

## 七、向 HopSpec 的升级【契约】 ^anc-flow-to-hopspec

本表达是 HopSpec 的真子集投影，升级映射逐项对应：

| HopSop | HopSpec | 升级时补充 |
|---|---|---|
| `[子任务]` | `[subtask]` | retry/adaptive 属性、`+→` 导出契约 |
| `[循环]` | `[loop]` | max_iterations 或 for-each 子句 |
| `[分支]` + `[条件(…)]` | `[branch]` + `[case(条件)]`（统配 `[条件(其他)]` ↔ `[case(else)]`） | 条件表达式机器化（方括号内圆括号文法） |
| 普通步骤 | reason/act/check/confirm/ask/commit | **步骤类型判定**——升级的主要工作：这一步是推理、计算、核验还是介入点 |
| `[继续循环 <序号>]/[退出循环 <序号>]/[完成任务]` | `[continue <序号>]`/`[break <序号>]`/`[exit]` | 目标序号直通（HopSpec 侧同为可选:缺省=最近祖先循环）;exit 补交付变量 |
| `输入:`/`输出:` 行 | `- ←` / `+ →` | 补类型与 `#` 说明（HopSop 只写名称;省略的输入输出升级时必须补全——每步 I/O 客观存在,见 ^anc-flow-node-io） |
| 多层数字序号 | step ID | 直接沿用 |
| （无） | 变量流 `←`/`+→`、Goal/Constraints/Types | 升级时新增 |

升级保持控制流逻辑等价（三条核心要求的第③条）；解析实现可以使用不同节点标识和数据结构，只需逻辑等价。

**执行边界**：本表达描述流程本身，不承担运行时执行——没有状态机、重试、暂停恢复。需要 HopJIT 双态融合执行时升级为 HopSpec，由 HopJIT 负责运行、验证与审计。使用方文档（如 HopKB 过程型知识）保持本表达形态即可满足"人读得懂流程"；是否升级由该流程是否需要 HopJIT 双态融合执行决定。

## 八、流程设计方法论：循环的识别和优化【契约】 ^anc-flow-loop-method

（2026-08-08 作者定，源于 hopkb 构建hopagent 流程实撞：粗稿到定稿的每步实质改进都是循环动作。）

**流程设计的核心是循环的识别和优化**——散文糊住的循环永远不会被追问单轮原子性与跨轮状态；写成`[循环]`节点的那一刻，这些问题自动浮现。两步过：

**1. 识别（把隐式循环显式化）**：凡"逐X""每个""依次"类表述必须写成`[循环]`节点，禁止用散文带过——这不是格式要求，而是循环识别的强制机制。容器节点只放子节点，动作进循环体。

**2. 优化（对齐批处理循环的通行实践，三条基本功）**：
- **每轮原子、完成即提交，粒度尽可能小**：一轮是一个不可分的工作单元，做完即持久——断点、冲突面、崩溃损失都以"一轮"为界；条件允许时提交粒度尽可能小、渐进式（小粒度换来断点可续、冲突面小、可审查、可回退），仅当多个变更不可分割（拆开会留下中间不一致态）才合并为一轮。此处"提交"指任何形式的成果持久化，不限于 HopSpec 的 commit 步骤：写沙盒临时表、落中间文件、记工作清单同样是提交——单轮成果离开易失的会话上下文即可，不可逆的正式提交（commit）只是其中最重的一档；
- **幂等**：同一轮重复执行不产生重复副作用——这是重试与续跑可以放心做的前提（只有检查点没有幂等，重放=重复落盘）；
- **检查点续跑**：进度随轮持久化，崩溃后从最后完成轮继续，不从头重跑；不回改已完成轮次。
