# HopAnt（元蚁）：Hop 体系的群体智能单元

 HopAnt 是 Hop 体系的**群体智能单元**。"单元"是相对群体说的——它的价值在两个方向上兑现：
 + **纵向**，一个 HopAnt 专注于做一件事情，在HopSpec智能体原生语言的保障和支持下，在被反复使用中持续演进，持续打磨，不断完善，越用越可靠。多个 HopAnt 能力单元经HopAnt编排单元可以涌现出超乎想象的能力；
 + **横向**，HopAnt 易于安全审计，可以自发适配，，在人和智能体之间方便的分享。一个人的实践经验安全便捷的成为群体的智力资产。
 
 在用户手里,HopAnt 叫 **Hop 流程元件**：一个完整的、由 HopSpec 驱动的工具（像手机上的 app 一样装上就能用）,**由 /hop 安装、适配、编排、演化、封装、分享**——前四个动作是纵向（把一份用起来、让它变好）,后两个是横向（成为群体智力资产）。

 **名称分两层,按读者用**（2026-10-12 作者定）：学名 HopAnt（元蚁）;概念与设计文档定义它时说"Hop 体系的群体智能单元";面向用户的文字（README、教程、/hop 对用户说的话）统一叫"Hop 流程元件",第一次出现时括注一次 HopAnt。"app""HopSpec 工具"只作解释时的类比,不当名字用。

## 动机

HopSpec 定义的是**一个任务怎么做**——目标、步骤、核验、交付。但一件任务不是一个可以反复用、给别人用、越用越好的东西：它没有名字、没有跨次执行的状态、不知道自己依赖什么环境、改好了也没有版本。HopAnt 把"一组 spec + 知识附件 + 代码工具 + 场景适配"收成一个单元,让这组东西能被安装、编排、演化、封装、分享——HopSpec 是任务,HopAnt 是会干这类任务的智能单元。

小单元各司其职,通过 HopSpec 编排协作,可以涌现出复杂能力——这是"群体智能"和"蚁"这个名字的由来：单个 HopAnt 专注于一类任务,群体靠分享传播改进、靠编排组合能力。HopAnt 的 spec 跑起来时,引擎在四个维度上给它供能力与记忆（知识 / 工具与沙箱 / 数据 / 身份），本文描述 HopAnt 实体是什么、用户怎么用它。

## 五个关键特性 ^anc-struct-hopant-traits

HopAnt 区别于"一个 skill""一个 agent 脚本"的,是下面五条：前两条是它作为群体智能单元的能力面,第三条是它能被放心从网上装来用的安全面,后两条是它作为 hop 体系一员的组织面。

**1. 关键过程可控可靠**——由 HopSpec 的双态融合执行引擎保障：显性结构化逻辑控制,加探索-核验-提交范式强化。HopAnt 的每一件活都是一份 HopSpec 在引擎上跑：顺序由结构化步骤确保,不靠 LLM 记住;每段产出过 `check` 核验,判 false 就带反馈重做;不可逆动作只许在 `commit` 步、且前面必须有最后一道核验（`check final`）或人的确认。"可控"指智能体的任务规约可以和人高效对齐，关键控制点可以由人指定并不可被绕过；"可靠"指显性结构化逻辑由引擎执行，模糊推理逻辑有核验和重试机制支持，以支持生产级可靠性。这是 HopAnt 能被当成工具装来用、而不是当成一段提示词碰运气的根据。

**2. 自主探索与迭代演进**——`subtask free` / `adaptive` 承担探索,渐进固化承担演进。HopAnt 的 Spec 不必把每一步写死：没想清楚的段落写成 `[subtask free]`,执行到那里引擎拿着真实输入向 LLM 要计划、按计划跑、check 不过再重新规划和探索（[[HopSpec V3核心规范#^anc-step-subtask-free]] / [[HopSpec V3核心规范#^anc-exec-adaptive-fallback]]）;探索出来的成功路径按渐进固化回写进 HopAnt 自己的 Spec（生命周期「演化」）。所以 HopAnt 既能处理没见过的输入,又会把见过的变成确定路径——越用越确定、越用越快,而探索段始终被第 1 条的把关面兜着。

**3. 安全可审计**——每个 HopAnt 要什么写在入口 spec 的文件头里、装前能审、跑时不可逆动作进不了探索步、事后有账;对照之下,当前 skill 的安全体系已成灾难。现在一个 skill 就是一段自然语言指令,装进载体后它能让 agent 干的事与 agent 本身能干的事完全一样——读任意文件、跑任意命令、发任意请求——没有声明、没有边界、没有记录:用户装的时候看不出它要什么,跑的时候拦不住它做什么,出事后查不明它为什么要这么做。

**hop 的安全模型是什么。** 它不是 Claude Code / Codex 那种"每条命令弹窗、每个路径核一遍"——那种做法笨重,是因为宿主不知道这个动作在任务里处于什么位置,只能逐个问。hop 知道，所以 hop 问三个问题：
+ **这个动作可逆吗？** 可逆的（读文件、查资料、算一算、写自己的涂鸦区）在探索步（act/check）放开做。可逆不可逆怎么判——**在工具注册的时候标一次** `requires_commit`（注册面必填,不设缺省）,之后由步骤类型自动分配：标了`requires_commit`的工具,act 步调它引擎直接拒（`COMMIT_REQUIRED`）,只有 commit 步能调。子进程同理：会改世界的命令只能进 commit 步的 body;探索步里的命令走任务 spec 的《已批准命令》清单,批的是"这个任务里这类命令可以跑",不是"这台机器上永远可以跑"。
+ **不可逆动作前核验充分么？** 不可逆的（改正式文件、发请求、删东西、起会留痕的进程）只许在 `commit` 步做,而 commit 步能执行的前提是前面的最后一道核验（`check final`）或人的确认已经过了。这个核验的完备性是结合整个任务的上下文来判定的，可以由Agent和人共同确认。一条会留下后果的动作能不能跑,看它在这个任务的哪一步、前面核验结论是什么,不看它是哪条命令、要碰哪个路径——这比命令白名单领先一代,也不需要给每个工具再套一层路径笼子。
+ **这句不可逆动作安全吗？** 一份 spec 的某句 commit 第一次要执行时,引擎先做一次安全分析（2026-10-08 作者定）：新建文件、追加、移动、覆盖或删除前已把旧版本留存进回收站的写入这类可逆或低危动作,打安全标记直接放行,不问人,以后也不再问;销毁内容且找不回的删除与覆盖、运行命令、发通知、后果不明的外部调用,用不懂代码的人也读得懂的话说明后果和建议,请人批准——只批这一次、这一步以后都通过、或不批准。文件工具 write / edit_file / move / remove 缺省就把被覆盖或被删除的旧版本留存进状态目录下的回收站（每个文件保留 3 份,一次运行只留存一次）,所以最常见的写入天然落在安全档。HopAnt 的批准记录存在它自己的 `inner_store/commit_approvals.json`,跟着这台机器上的这个 HopAnt 走;回收站在用户项目的状态目录里,不写进只读的 HopAnt 目录。引擎落地见 [[../design/exec-engine#^anc-exec-commit-approval]]。

HopAnt 在三个时点各有一道检查：

- **装前可审（声明面）**：入口 spec 文件头的 `Tools` 段声明这个 HopAnt 依赖哪些工具、《已批准命令》段声明哪些命令前缀;凭证需求从 Tools 段声明的工具在注册面的 `auth_env` 推出,适配时核。安装时原文呈给用户,读入口 spec 的文件头就知道它要什么,与读一段 skill 散文猜它会干什么,是两回事。每个被声明的工具在这台机器的注册面上都带 `requires_commit` 标注——所以用户审的不只是"它用哪些工具",还有"这些工具里哪些是不可逆的"。
- **跑时可控（执行面）**：这是上面安全模型的直接后果,**两个模式下引擎都强制**——body 解释器、`hopjit tool-call` 通道、独立模式的工具下发三处都拦 `COMMIT_REQUIRED`,不是约定。探索步能做的事天然可重做,所以 HopAnt 的探索段哪怕走偏,也留不下后果;留后果的那一步前面必有核验或人。另外两条今天的实际约束力要如实说：
	- 命令：不在《已批准命令》上的,引擎直接拒绝执行;要不要加进清单是用户的决定——agent 的驱动指令要求它停下问用户、不许自己加、不许改用宿主的 Bash 绕过去,但后半句是对 agent 的要求,不是引擎能保证的;
	- 复用模式下宿主 agent 用自己的工具干活,引擎能做到的是起跑前按清单核一遍、清单外的工具不告诉它有;它要是在探索步用自己的 Bash 做一件不可逆的事,引擎看不见——"选复用模式就是信任宿主 agent"这条既有口径不变。
- **事后有账（观测面）**：每一步做了什么、调了哪个工具、跑了哪条命令（argv/cwd/返回码/耗时）、读写了哪些文件,全部进 HopLog;人的确认与 agent 的裁定分开记。出了事不是翻聊天记录猜,是对着账查。


**4. Hop 体系双引擎支持**——主 Agent 驱动与 MCP 独立驱动,按任务各取所长。一个 HopAnt 可以由宿主 agent（Claude Code / Codex / opencode）当推理引擎在会话里跑（复用模式,HopSkill 形态：上下文在场、零 API key、适合与用户正在干的活交织的任务）,也可以由 hopjit MCP server 用自己绑定的模型独立跑完（独立模式,HopAgent 形态：不占对话上下文、可换低成本模型、可无人值守、适合批量与长时任务）。两个引擎共享同一套**执行语义**：流控轨迹、人机交互、恢复闭环、沙箱边界定义、HopLog 日志审计（[[HopSpec V3配套HopJIT运行时能力#^anc-exec-mode-invariants]]）,区别只在谁出推理、上下文住哪。两个形态命名忠实：HopSkill 之所以叫 skill,因为它确实是宿主的技能;HopAgent 之所以叫 agent,因为它确实自主运行。它们是**部署形态**不是组件类别——实体只有一份,同一个 HopAnt 可以先以 HopSkill 形态在宿主会话里验证,再以 HopAgent 形态无人值守部署（渐进固化路径）。`hopjit pack` 产出的具名 skill（`/coffee-week`）是 HopSkill 形态的早期实例,已并入 HopAnt（见「与既有机制的关系」）。 ^anc-struct-hopant-deploy-forms

**双引擎差异性**：语义一致是HopJIT引擎已经保证的，但执行时的差异性来自于它的能力依赖——要求全部显性化。三道现实差距,以及 HopAnt 怎么处理它们：

- **沙箱在两个模式里的约束力不一样**（hop 安全模型本身见第 3 条,这里只说差别）。结构侧的要求一致，步骤顺序、commit 前必过核验、不交出下一步宿主就拿不到 commit——两个模式下都由引擎强制执行,宿主想跳也跳不过。工具侧的强制性不一样：
  - 独立模式：读写文件、跑命令都经引擎自己的工具,`requires_commit` 的工具在探索步根本不下发给 LLM,越界的调用执行不到——引擎拦得住;
  - 复用模式：干活的是宿主 agent（比如 Claude Code）,用的是它自己的 Read/Write/Bash,不经过 hopjit;hopjit 把规则写进指令请它遵守,它在探索步偷偷用 Bash 做一件不可逆的事,hopjit 看不见也拦不住——只能靠宿主遵守约定。
  - **HopAnt 怎么处理**：入口 spec 头的 `Tools` 段两个模式都读。独立模式按它配沙箱、照常强制;复用模式起跑时按它核一遍——声明里没有的工具不告诉宿主有,声明了但这台机器没有的当场报错,不让它跑到一半才断;跑起来之后仍是请宿主遵守。"选复用模式就是信任宿主 agent"这条既有口径不变,HopAnt 只是把"要它遵守什么"写成了一份可以核对的清单。
- **`[act free]` 步骤在两个模式里能用的工具不一样**。act free 是"这一步具体怎么做到了再说"的开放步骤
	- 独立模式下由引擎带着一组工具让 LLM 循环调用——能用的只有基础文件工具,加上 `Tools` 段声明过的工具
	- 复用模式下干活的是宿主 agent,它手上的所有工具都能用。于是一个在 Claude Code 里跑通的 HopAnt,如果某个 act free 步偷偷用了 Claude Code 自带的网页搜索而没有在 `Tools` 段声明,搬到独立模式就断在那一步。
	- HopAnt 怎么处理：封装时把 Spec 里实际用到的工具扫出来写进 `Tools` 段——没声明的用不了,声明了的两个引擎都能供给;要不要进一步给 HopAnt 分"能否无人值守"的档位、怎么分,**待作者拍**（构建器内部有 hop/mixed 的产物分级,是否沿用未定）。
- **两个模式各有一些"怎么做"的习惯动作,写进 Spec 就会把要求固定下来**。复用模式下,最后一道核验是派一个新的 subagent 来判、需要用户确认的地方是用宿主的提问工具问用户、并行是起后台 worker;独立模式下,最后一道核验由引擎自己的 LLM 判、需要用户确认的地方是暂停后回调调用方、并行在引擎内部派发。两边最后达到的效果一样,但做法完全不同。如果 HopAnt 的 Spec 正文里写了"派一个 subagent 核一遍"这样的话,在独立模式下就是一句没人能执行的废话。HopAnt 怎么处理：Spec 只写**要做成什么、要核什么**,不写"由谁、用什么工具去做"——那是驱动层按自己的模式决定的事;封装时扫到 subagent、AskUserQuestion 这类宿主专属的字眼就报出来让作者改。

选哪个引擎是部署与调用时的选择,不是 HopAnt 作者的选择——但作者要把依赖声明清晰,这个选择权才真的在用户手里。

**5. Hop 体系封装**——避免各个 agent 碎片化,简化用户体验。用户面只有一个入口 `/hop`,HopAnt 由它安装、适配、编排、演化、封装、分享;用户不需要知道一个 HopAnt 底下是几份 spec、用了哪些工具、跑在哪个引擎上。没有这层封装,每个任务型 agent 各自一套安装法、配置法、调用法、输出格式,用户面对的是一地碎片;有了它,HopAnt 之间同一套清单、同一套目录、同一套适配与分享机制,装十个 HopAnt 与装一个一样简单。封装也是"分享传的是种子"能成立的前提——接收方不需要理解发布方的机器,只需要 /hop。

## HopAnt实体形态 ^anc-struct-hopant-entity

本节回答"HopAnt 落在盘上是什么样、用户怎么碰到它"——它是用户面前的 **Hop 流程元件**：一个完整的、由 HopSpec 驱动的工具,装在 hop 自己的目录下,由 `/hop` 统一安装、适配、编排、演化、封装、分享。类比：skill 之于 Claude Code,app 之于手机——但 HopAnt 比 skill 多三样东西：

| skill（宿主技能） | HopAnt（Hop 流程元件） |
|---|---|
| 一份指令文本,宿主读了照做 | 一组 HopSpec + 知识附件,入口 spec 头声明依赖,引擎按步执行、把关、记账 |
| 无状态,每次从零 | 有 `inner_store/`（跨 run 累积的数据、本机适配、用户偏好） |
| 装上就是最终形态 | 装上后要本地适配（这台机器的工具叫什么、凭证在哪）;跑的过程中按渐进固化回写自己,版本演进 |

**与两个部署形态的关系**：实体形态是 HopAnt 在盘上的**静态存在**,HopSkill / HopAgent 是它被**拉起来跑**时的两种动态形态——同一个 HopAnt 目录,`/hop` 在宿主会话里调它就是 HopSkill 形态,hopjit MCP server 用自己的 LLM 跑它就是 HopAgent 形态。实体只有一份,不为两个形态各存一份。

### HopAnt 的目录部署约定 ^anc-struct-hopant-layout

**一个 HopAnt = hop 目录下的一个子目录**,目录名即 HopAnt 的 id。hop 目录有两级（作者定 2026-10-10"应该有项目级 hopant 位置"）：**用户级** `~/.hopjit/`——跟人走,所有项目可用,装进来的别人的 HopAnt 住这里;**项目级** `<项目>/hop_tasks/`——跟项目走,这个项目里干完的活总结出来的 HopAnt 住这里（/hop 的一切住 hop_tasks/ 一个家：活跃任务卡、archive/、ants/ 三分区）。两级同一布局,只是根不同;查找时项目级先于用户级,同 id 项目级遮住用户级。

```
<hop 目录>/ants/<ant-id>/          ← hop 目录 = ~/.hopjit/（用户级）或 <项目>/hop_tasks/（项目级）
  <ant-id>.md        ← 入口 spec（文件名即 HopAnt 的 id）——它的文件头就是 HopAnt 的清单,见下;执行的始终是这个文件
  <ant-id>.orig.md   ← 入口 spec 被改过才有：逻辑适配（装进来后为本机改）或在项目里修订（项目级 HopAnt 被 /hop 改）之前拷出的原件,之后不再碰
  *.md               ← 内部子 spec（入口 spec 经 call 调用;照常 Goal/Inputs/Outputs/Steps）
  knowledge/         ← 知识附件（术语表、样例、primer,spec 经 doc-ref 引用）
  scripts/           ← HopAnt 自带的代码工具（如 pdf 抽取、ocr 脚本,spec 经 run_script 调用）
  bootstrap.js       ← 可选。本 HopAnt 的安装脚本：核 hopjit 版本、装自己的运行时依赖（uv / playwright / 系统包……,作者写,hop 不替它管）;支持 --dry-run 只打印计划。安装时跑,适配与升级时可重跑
  SKILL.md           ← 可选薄壳（见下「与 skill 结构兼容」）
  inner_store/       ← 持久性数据：跨 run 累积的结构化数据、适配戳与适配记录、谱系。只在本机,不随分享外传
```

**跑 HopAnt 时的工作区**：/hop 起 run 时,工作区（workspace）是**用户发起 /hop 时所在的项目目录**,不是 HopAnt 自己的目录——HopAnt 是工具,用户项目是它加工的对象。文件工具的读写、commit 的落点、spec 里相对路径的解析都按用户项目算。HopAnt 目录（`<hop 目录>/ants/<ant-id>/`）是**只读资源目录**：`knowledge/` 经 doc-ref 引用（引擎先在 spec 所在目录找,再在工作区找）;数据样例经文件工具读（spec 所在目录在读权限内）;`scripts/` 里 HopAnt 自带的脚本经入口 spec《已批准命令》列出、body 里 `subprocess.run` 调用,路径用 `spec_dir("scripts/x.py")` 取——它们是随 HopAnt 分发、装前可审的代码,走任务级授权,不经 `run_script`（那是给执行模型现写的脚本用的,另一套安全面）。commit 步不能写 HopAnt 目录——可分发面不被运行弄脏;演化回写 HopAnt 自己的 spec 归生命周期④另开口子。`inner_store/` 的注入归 todo/0144。

**一个 HopAnt 一个入口**：对外只有一份入口 spec `<ant-id>.md`,其余 spec 都是它的内部子 spec;粒度 = 一件用户一句话能说清的活。同领域几件事要么各立 HopAnt 互相 `call`,要么入口 spec 里 `[ask]` + `[case]` 分支——那是 HopSpec 自己的表达能力,HopAnt 层不加"多入口"机制（多入口就要一份"哪些是入口"的声明,又回到另造清单的老路）。

**可分发面与本机面**：入口 spec + 子 spec + `knowledge/` + `scripts/` + `bootstrap.js`（+ 可选 SKILL.md）是**可分发面**——分享时装进 HopAnt 包的就是这些;`inner_store/` + `*.orig.md` 是**本机面**,永远不出这台机器。这个二分是部署约定里最重要的一条线：它让"同一个 HopAnt 装在十台机器上"各自有各自的状态与本机配置,而分享出去的那一份不带任何一台机器的私有信息（适配主要改本机配置不改 spec,见生命周期②）。

**与 skill 结构兼容**（可选）：目录里放一个 `SKILL.md`,它就同时是载体能识别的 skill。`SKILL.md` 用 `hopjit pack` 现有的生成模板（`src/cli.ts` packSpec,按载体分 CC / Codex 两版）：frontmatter（name / version / description）+ 前置（hopjit 版本 ≥ 打包版本、hopspec 驱动 skill 已装）+ 参数（从入口 spec 的 Inputs 生成）+ 执行（`/hopspec run <入口 spec>`）+ 用户注意力纪律。模板内容全部由入口 spec 推导,不手写。pack 的产物由此并入 HopAnt：带 `SKILL.md` 的 HopAnt 目录。

**HopAnt声明清单见入口HopSpec**（2026-10-04 作者抓"这在 hopspec 里不是有么？为什么要再造一个"——首版自造的 `hopant.yaml` 撤销）。HopSpec 的文件头已经是一份引擎真读、真对账的自描述清单,HopAnt 需要声明的每一项都有对应物：

| HopAnt 要声明的 | 入口 spec 头里已有的 | 引擎怎么用它 |
|---|---|---|
| 是什么、干什么 | `# Spec: 标题` + `Id:` + `Goal:` | /hop 分派时按它匹配用户意图 |
| 依赖哪些工具 | `## Tools` 段 | 起跑时 `reconcileTools` 对环境注册面对账,缺即 INIT_FAILED |
| 依赖哪些命令 | `## 已批准命令` 段 + `Config.requires_commands` | 起跑预检 + 运行时按前缀拒 |
| 需要的引擎版本 | `Config.engine_min_version` | 起跑核 |
| 知识附件 | Constraints 里的 doc-ref `[[…]]` | 校验存在性,执行时注入 |
| 数据结构 | `Types` 段 + `Outputs` | 类型校验 |
| 依赖哪些其他 HopAnt | `call <ant-id>(…)` 语句本身 | 按 Id 解析——`<ant-id>` 既是目录名也是入口 spec 的 Id,单入口之下不需要"某 HopAnt 的某 Spec"两段寻址 |

凭证不在 spec 头里单独声明：spec 声明的是工具（Tools 段）,每个工具需要什么凭证写在工具注册面（`auth_env`）,模型凭证在 providers（`api_key_env`）——适配动作顺着 Tools 段把这些凭证名收齐、核本机在场与否（作者定：凭证适配在适配步解决,不加语法）。


### HopAnt Package（HopAnt 包）：分发封包格式 ^anc-struct-hopant-package

HopAnt 包是用于封装一个或多个HopAnt用于共享的包。"HopAnt包"指封包形态,不限于 npm 包：一个目录、它的压缩包、一个 git 仓库、一个 npm 包,都是 HopAnt 包,里面装一个或多个 HopAnt 的可分发面。两者的转换就是生命周期里的两个动作：**分享** = 把若干 HopAnt 的可分发面装进一个包;**安装** = 把包拆开,里面的每个 HopAnt 各自落到 hop 目录成为活的 HopAnt。包在拆开那一刻完成使命,之后 hop 目录里只有 HopAnt,没有"包"——装自同一个包的几个 HopAnt 之间没有任何"同包"关系,各自独立适配、演化、被分派、再被装进别的包分享出去。

```
<HopAnt 包根>/
  package.json       ← name / version / files: ["ants/"];不带 scripts（作者 2026-10-09 定"删 postinstall"——与 hopjit 自身撤 postinstall 钩子同一原则：改用户机器归用户拍板,安装恒由 /hop 安装 显式触发）;三条通道（本地目录 / git / npm）同一份,npm 通道直接 pack
  ants/
    <ant-id-1>/      ← 一个 HopAnt 的可分发面（上节布局去掉本机面）
    <ant-id-2>/
```

由"两个东西"推出的几条：

- 一个包装几个 HopAnt 都行——`ants/` 下每个子目录一个;单 ant 包就是 `ants/` 下只有一个子目录,两种同形,不为单 ant 另设扁平布局。
- `<ant-id>` 全局唯一,不加包名前缀——分派、`call`、目录名三处都用它,包名在拆箱后已经不存在;两个包里的 ant 撞 id,安装提示让用户选，可以改名。
- **包和 HopAnt 各自有自己的版本**：每个 HopAnt 有自己的谱系版本（见生命周期④）,包的 `version` 只是这次打包的运输标签（npm 要求有,git 用 tag,压缩包用文件名）;分享时谱系按 ant 逐个写进 `package.json`,接收方拆箱后各 ant 各自记来源。
- 包根的 `package.json` 是包的东西,不是任何一个 HopAnt 的东西——拆箱后不进 hop 目录。**安装脚本归 HopAnt 不归包**（作者定 2026-10-06）：依赖是每个 HopAnt 自己的（pdf 那个要 uv,翻译那个什么都不要）,所以 `bootstrap.js` 住在 HopAnt 目录里、随 ant 落进 hop 目录;`/hop 安装` 拆箱时遍历 `ants/*/bootstrap.js` 逐个调（dry-run 时逐个收集计划一并呈给用户）,三条通道同一遍历。这样 ant 拆进 hop 目录后脚本还在,适配发现依赖缺、升级换了新版,都能重跑它自己的。
- `files` 用白名单不用 `.npmignore` 黑名单：漏列一个本机文件的后果是把用户状态发出去,白名单漏列的后果只是包里少一个文件装不上——出错方向安全。

**与 npm 包兼容**：

- npm 对包内容零要求,只要根目录 `package.json` 有 `name` 与 `version`——所以 HopAnt 包的目录本身就是合法 npm 包,不加任何壳。包名与 `<ant-id>` 都按 npm 包名规则起（小写、数字、连字符）,三条通道共用同一规则。
- **对 hopjit 的依赖不用 npm 依赖机制表达**。`dependencies` 会在全局装时把 hopjit 私装进 HopAnt 自己的 `node_modules/`,每个 HopAnt 一份副本、与用户已装的全局 hopjit 版本可能不一致;`peerDependencies` 在 npm 7 之后缺省自动安装,回到同一问题,且全局装的 hopjit 不在 HopAnt 的依赖树里,npm 看不见它。hopjit 是**运行时环境**（像 python、像 docker）,不是包依赖。所需的 hopjit 最低版本只在一处声明——入口 spec 头的 `Config.engine_min_version`（三条通道共用）。
- **运行时依赖由每个 HopAnt 自带的 `bootstrap.js` 装,hop 不替它管**（作者定 2026-10-06——PDF/OCR 要 uv + Python 包,playwright 要浏览器,pandoc 要系统包:生态各异,hop 给每种生态写安装逻辑是无底洞）。作者在 ant 自己的 `bootstrap.js` 里写：核 `hopjit --version` 够不够 `engine_min_version`、装自己的依赖（`uv sync` / `npx playwright install` / 检查系统包后指路）。`/hop 安装` 遍历调用,三条通道同形。一条约定：
  - **先 dry-run 后执行**：`bootstrap.js --dry-run` 只打印计划不动机器;hop 装前先跑 dry-run 把计划呈给用户（第 3 条安全特性"装前可审"的延伸——一段 JS 不像 spec 头能机器读出它要什么,dry-run 就是让它自己说出来）,用户同意后再跑真的。
- 安装侧：包拿到本机后恒经 `/hop 安装 <目录或包名>`（底下 `hopjit ant install`;npm 通道落地时由它 `npm pack` 取 tgz 解到 `ants/`）——没有 npm 自动触发的安装路径（postinstall 已删）。**项目级 `npm install`（不带 -g）不该用**：它会改写用户项目的 package.json 与 lock 文件、把 HopAnt 登记成代码依赖,对非 Node 项目还会凭空建出 node_modules。两种全局装法选哪个为主归设计层（todo/0142 决策①）。

## 生命周期：六个动作都从 /hop 走 ^anc-struct-hopant-lifecycle

> 作者定：HopAnt 由 /hop **安装、适配、编排、演化、封装、分享**。

六个动作全部经 `/hop` 分派（/hop 是用户唯一入口的口径不变）。顺序即用户的典型路径：先把别人的 HopAnt 用起来（安装→适配→编排）,用的过程中它变好（演化）,自己的活也能长成 HopAnt（封装）,再把它给别人（分享）——消费侧三步、生产侧三步,首尾相接成一个生态循环。

**① 安装（本地或远端 → hop 目录）**。装进哪一级由用户定,缺省用户级（装别人的 HopAnt 是给自己用,不是给这个项目用）;"只在这个项目里用"装项目级。封装格式就是目录本身（或它的压缩包）,不加包壳——spec 头已经是清单,目录结构已经是布局。分发通道按门槛分三层（2026-10-04 作者点出"不是所有人都有 npm 发布能力"）：**本地目录 / 压缩包**（零门槛,拷贝、发消息、放共享盘）→ **git 仓库 URL**（有 git 就能发,版本=tag 或 commit,更新=pull;内网 git / gitee 同样适用,不受 GitHub 访问限制）→ **npm**（留给要进公共生态、要版本语义与镜像分发的人）。三条通道装进来的都是同一个目录（包格式见实体形态「HopAnt Package」节）,/hop 只在"取包"一步分支;npm 通道全局装或 pack 解包两法归设计层定,项目级 `npm install` 不用。安装不改宿主的 skills 目录：宿主菜单里仍只有 `/hop`,HopAnt 由 /hop 分派。

**② 适配（装完第一次跑之前,本地化）**。先把要适配的项列实——spec 里会随机器变的位置其实很少：

| 适配项 | 在哪 | 随机器变的是什么 | 怎么办 |
|---|---|---|---|
| 工具名 | `Tools` 段、步骤 `- 工具:` 授权行 | 同一能力在本机的注册名（`web_search` vs `bailian_search`） | 改本机 hop 配置的工具映射,spec 不动 |
| 命令 | 《已批准命令》、body `subprocess.run` | 可执行文件在不在 PATH | 已批准命令本就是前缀,路径归 PATH;缺的由 ant 自己的 bootstrap 装,spec 不动 |
| 凭证变量名 | 不在 spec 里（工具注册面 `auth_env` / providers `api_key_env`） | 本机叫什么名 | 改本机 hop 配置,spec 不动 |
| 知识文件、脚本 | doc-ref、`run_script` 路径 | 不变——相对 HopAnt 目录解析 | 不需要适配 |
| 用户偏好 | `Inputs` 缺省值、`Config` 输出位置 | 这个用户想要的缺省 | 用户主动改 spec,算本机演化 |

所以适配分两档（作者定 2026-10-06）：

- **配置适配（常态）**：`/hop` 按入口 spec 头核本机——`Tools` 段的工具在 hop 配置里注册了没（调引擎已有的 `reconcileTools`,今天独立模式起跑才跑它,复用模式也要跑）、凭证变量在场没（从 Tools 段顺到注册面 `auth_env`、从模型配置顺到 `api_key_env`,收齐名单逐个核 `process.env`）、命令在不在。缺口按性质处理：工具名不同→写映射进 `~/.hopjit/config.yaml`;凭证缺→告诉用户要导出哪个名字,不替配;运行时依赖缺→重跑 HopAnt 自己的 `bootstrap.js`（先 dry-run 呈计划、用户同意再执行）。**这一档 spec 一字不改**,`<ant-id>.md` 保持原版,分享自然干净。
- **逻辑适配（例外）**：spec 在本机的运行逻辑就不成立——某个工具这台机器没有任何等价物、某步假设的环境根本不存在——配置改不过来,只能改 spec。这时 `/hop` 先把 `<ant-id>.md` 拷成 `<ant-id>.orig.md` 备份,再改写 `<ant-id>.md`;执行的始终是 `<ant-id>.md`,引擎、分派、SKILL.md 里的 `/hopspec run` 都不需要知道。**逻辑适配就是一次本机演化**,按④打本机版本、记谱系;之后一切改动只改 `<ant-id>.md`,不回头碰 `.orig.md`（作者定）。

**怎么知道该不该适配、有没有适配过**（作者 2026-10-06 问"目录拷贝来的怎么知道需要适配、怎么确定已经适配过"）：不靠安装通道判断,靠一条记录核对。适配完成时 `/hop` 在 `inner_store/` 记一行适配戳 `adapted: <归属标识> @ <入口 spec 文件头的内容哈希>`——归属标识是本机的（`<用户>-<机器>`,见④）,哈希覆盖适配核过的那些段（Tools / 已批准命令 / Config）。每次要跑一个 HopAnt 之前,/hop 核这一行：标识是本机、哈希与当前 spec 头一致 → 已适配,直接跑;记录不存在、标识不是本机（目录是从别的机器拷来的）、哈希不符（spec 被升级或改过）→ 走适配。纯本地比对,不占注意力。配套一条：安装时三条通道都**丢弃来包里带的 `inner_store/`**——它本在白名单外,但目录拷贝时发送方可能没删,接收方装时清掉,别人的累积数据与适配戳不进本机。适配结果本身（映射写了什么、装了什么、是否走了逻辑适配）也记在 `inner_store/`,供重跑时只补缺的。

**③ 编排（把 HopAnt 用起来）**。用户对 `/hop` 说活,/hop 分派——HopAnt 走的就是 /hop 既有分派里"一份现成 spec"那一路（入口 spec 本来就是一份现成 spec）,不加新路。**筛选不许浪费主对话注意力**（作者定 2026-10-06）：不是逐个读三十份 spec 头,而是读一张本机索引——安装/卸载时 /hop 把每个 HopAnt 的 `id + 标题 + Goal 首行` 收进 `<hop 目录>/ants/index.md`,一行一个（Goal 多行时只取第一行,标题取 `# Spec:` 标题行——一行一个 HopAnt 是索引能被一眼扫完的前提;2026-10-11 作者确认,与实现 rebuildIndex 对齐）;分派时主对话只读这一张表,命中即按那份入口 spec 走,没命中再走升格主路。分派出去的是一次有账、有把关、可续的 HopSpec 执行,不是一段指令文本。编排有三档：**单用**——一个 HopAnt 跑完一件活;**组合**——/hop 建的任务卡里 `call` 多个 HopAnt,HopAnt 之间不互相感知,由任务卡这一层串起来;**嵌入**——HopAnt 的 spec 内部 `call` 另一个 HopAnt（`call` 语句即依赖声明,安装时核在场）。单入口之下 `call` 的目标就是 `<ant-id>`,与 call 一份普通 spec 零区别,不需要寻址扩展。三档都走引擎的既有 call/parallel 机制,不另造协作协议——多 HopAnt 的协商/竞争/委托仍归待探索。编排是 HopAnt 价值兑现的那一步：蚁的意象"各司其职、经编排涌现复杂能力"落在这里。

**④ 演化（跑 → 回写 → 本机新版本,谱系记账）**。HopAnt 跑的过程中,adaptive/replan 产生的新子步、check 打回后修正出的更好做法、执行中发现的隐性约束——按 [[HopSpec V3扩展-有序思考与渐进固化#渐进固化（Progressive Solidification）]] 的四态（候选→验证→沉淀→降级）回写到 HopAnt **自己的** spec 与 `knowledge/`：候选态落 `inner_store/`,多次执行验证通过后由 `/hop` 提请人审,人审过了才改 spec 正文。**改变 HopAnt 今后行为的回写必过人审**（对齐 confirm 哲学：这是外向动作）。

**只有 spec 被改过的 HopAnt 才有本机版本与谱系**（作者定 2026-10-06）。常态下 `<ant-id>.md` 就是来源包里的原样,它的版本就是来源包的版本,没有第二个数。一旦走了逻辑适配（②）或人审过的演化回写——也就是 `<ant-id>.md` 与来源不再相同——这份 HopAnt 才开始记谱系。谱系节点 = **归属标识/版本**：归属标识缺省取 `<用户标识>-<机器标识>`,用户标识有 git 配置（`git config user.name`）就用它、没有用本机登录名,机器标识用主机名——自动生成,不问人;打包分享时明示这个 id 并问要不要改,人改了或确认了就存进 `~/.hopjit/config.yaml`,之后恒用存的那个,不再问;也可以加参数跳过询问直接用（作者定 2026-10-06;⑥分享条同此）;版本在每个归属标识下各自从 v1 计数,每次改 spec 递增一次。坐标写成 `来源 <来源分支>/<版本> → <本分支>/v1 → v2 …`,记在 `inner_store/`。**不用包名作标识**：目录拷贝与压缩包两条通道没有"起包名"这一步,接收方拿到的 package.json 里 name 还是上游的,靠包名分不开;归属标识在改动发生时就定下,三条通道都带得走。分享时谱系按 ant-id 逐个写进新包的 `package.json`（`hopant.lineage` 映射,一包多 ant 各记各的）成为接收方的来源,**此时 /hop 把归属标识呈给用户确认**——缺省的 `用户-机器` 可改成团队名、项目名,这是用户唯一需要碰它的时刻。十台机器各自改过就是十条分支,没改过的那些不在树上——它们就是来源本身。

**⑤ 封装（干完的活 → HopAnt）**。用户对干完的活说"总结一下 / 沉淀下来 / 下次还要干这种事",`/hop` 就把它总结成一个 HopAnt——对用户的说法是"一个可复用的 Hop 流程元件（即 HopAnt）",学名括注一次不先抛（作者 2026-10-10 定"元蚁概念还不流行,应该有个等价的说法"）——落到本项目的 `hop_tasks/ants/<id>/`（作者定 2026-10-10"总结成 hopant,而且应该有项目级 hopant 位置"——不再先落一份裸 spec 再问要不要封;以前叫"提纯件"的中间形态取消,动作名由"提纯"改"总结"）。总结做四件事：把这一次的具体值提成 Inputs（参数化）、把实跑中展开出来的稳定结构固化、把这次被把关抓过的坑写死进判据、把"这一次"的语境改写成通用使用说明;然后把 spec 与知识附件归位到目录,**核齐入口 spec 的文件头**——Tools 段、《已批准命令》、doc-ref 与 spec 正文里实际调用的工具、命令、知识文件逐一对账,少声明的补上、多声明的删掉（作者不手填,/hop 从正文扫;**标准工具例外**——`web_search` 这类由调用方 LLM 自带能力落实的工具,正文里没有调用形态,声明了就保留,2026-10-09 作者定"这个口留着"）。总结出的 HopAnt 立刻就是活的：`/hop` 下次分派能命中它、`call <id>` 能调它、能装到别的机器、能分享。判据：封装出来的 HopAnt 在**另一台干净机器**上装完、适配完能跑。

**⑥ 分享（HopAnt → 别人的机器）**。把若干 HopAnt 的可分发面装进一个 HopAnt 包（格式见实体形态「HopAnt Package」节）,打成目录压缩包、推到 git 仓库,或发布为 npm 包（通道三层见安装）。分享前 `/hop` 做四件事：核入口 spec 头与目录一致、核 spec、知识附件与脚本里没有凭证值（只许环境变量名;这道核是启发式的尽力防线,**不保证无漏——不把密钥写进 hop 文档和代码是用户自己的责任**,密钥应经环境变量或密钥管理服务取用,2026-10-09 作者定）、核本机面（`inner_store/`、`*.orig.md`）不在包里、有谱系的把谱系写进包的 `package.json` 作接收方的来源（归属标识此时明示并问要不要改,缺省 `用户-机器`,答过就存进 `~/.hopjit/config.yaml` 下次不再问;加参数可跳过询问直接用）。分享的就是当前 `<ant-id>.md`——配置适配不碰它所以天然干净;改过的那些,改动在里面且已记入谱系。包的 version 由分享者定,只是这次打包的标签;包内每个 ant 的身份在谱系字段里——改过的记它从哪个来源的哪个本机版本长出来,没改过的就是来源的再分发,接收方装的那一刻起走自己的适配与演化,成为谱系的下一层分叉——这是有意的：HopAnt 不是集中托管的服务,是各机器上各自长的生命体,分享传的是种子不是实例。接收方演化出的改进要回到上游,靠的是接收方再分享一个新版本,不靠自动同步。

**升级与卸载**（不另立动作,是安装与适配的组合;作者定 2026-10-06）：**卸载**=删 `<hop 目录>/ants/<id>/`,`inner_store/` 留不留问用户,索引同步。**升级**先看 `<ant-id>.md` 有没有被本机改过——没改过（常态）直接换成新版、重做一次配置适配,不问;**改过的才有两路要选**：**重新适配**（以新版为准重装,丢弃本机改动,谱系记新来源）或**融合**（来源版 / 本机版 / 新版三方比对——来源版就是谱系记的那个——差异呈用户决定留哪些,结果记一次本机版本）。哪种合适由用户按本机改了多少来定,/hop 不替选。

**六个动作的归属与闭环**：安装、适配、编排是**消费侧**（把别处的东西用起来）,演化、封装、分享是**生产侧**（本机长出新东西并给出去）。一个 HopAnt 的典型一生：在 A 机器上由任务封装出来,打包 v0.1.0 → 编排进几次活、演化改了三版 → 打包 v0.2.0 推到 git（谱系：v0.1.0 → 本机 v3 → v0.2.0）→ B 机器安装（来源 v0.2.0）、配置适配、编排进自己的活,一字没改——B 不在谱系树上,它就是 v0.2.0 → C 机器装了同一版但逻辑适配改了一处,C 开始记谱系。

### 与既有机制的关系 ^anc-struct-hopant-vs-existing

| 既有机制 | 它是什么 | HopAnt 与它的关系 |
|---|---|---|
| `hopjit pack` 具名 skill | 把一份 spec 打成宿主可见的 `/xxx` skill | 被 HopAnt 吸收：pack 的产物就是"带可选 SKILL.md 薄壳的 HopAnt 目录"（见实体形态「与 skill 结构兼容」）,不再是独立概念 |
| `/hop distill` 总结 | 干完的活 → 直接总结成一个 HopAnt,落项目级 `hop_tasks/ants/<id>/` | 就是封装动作本身（2026-10-10 作者定"总结成 hopant"——此前先落一份裸 spec 到 `hop_tasks/specs/` 再问要不要封,中间形态与"以后都应该是 HopAnt"矛盾,取消） |
| `install-skill --plus` 附装件 | hop-fact-check / hop-deep-research 两份随包 spec | 第一批该转成 HopAnt 的候选——它们已有工具依赖与知识附件,是依赖声明与本地适配的天然试金石 |
| 渐进固化四态 | 运行时能力：路径候选→验证→沉淀 | 演化动作的机制来源。固化的落点从"Spec 库"具体化为"HopAnt 自己的 spec 与 knowledge/" |
| 两个部署形态 | HopSkill / HopAgent | 实体形态的两种运行方式,见本节首段 |
