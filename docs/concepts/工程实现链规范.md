# 工程实现链规范

概念→设计→代码→测试这条工程实现链上各环节的职责边界、文档规范与对齐规则。这是 AgentHOP 项目所有文档和代码工作的元规范。

## 心智模型：抽象度 × 内容角色 ^anc-meta-model

工程实现链不是"概念层装决策、设计层装推演"的分类桶——决策和推演这两件事不分层，它们正交于分层。理解这条链要分两个独立的维度：

**维度一·抽象度（纵向）**：核心概念 → 架构 → 接口 → 实现，逐级下降。这是"层"的本义。
**维度二·内容角色（性质）**：每一层内部，内容都同时分两种角色——**推演产物**（由上层逻辑锁死、无需人介入）和**决策点**（上层未锁死、需人拍板选定）。

性质维度垂直穿过每一条抽象横带：**每一层都既有推演又有决策**。概念层不是"只有决策"，设计层也不是"只有推演"。把这两个维度缠在一起，是过去这套规范讲不清概念/设计边界的根因。

### 纵向的本质：可行域逐层收窄 ^anc-meta-narrowing

每个上层产出，定义的不是一个确定的点，而是一个**合法解的可行域**。下层工作 = 在这个域内继续定位：

- 被上层逻辑锁死的方向 → **推演产物**（determined）
- 仍留有自由度的方向 → **决策点**（underdetermined，需人选一个点）

决策做完 → 可行域收窄一截 → 传给下层 → 再收窄。到代码层收窄成一个可执行的点。而测试层验证这些决策是不是得到了严格的保障。

这解释了三件事：①为什么每层都有推演+决策（收窄既有自动也有手动）；②为什么设计层是多层的（收窄是连续的，可切多刀：架构 → 模块 → 接口 HopType/关键 HopType → 关键任务 HopSpec 骨干）；③为什么概念层内部就已经有推演产物（第一刀收窄时就有方向被自动锁死）。

### 决策点的三种来源 ^anc-meta-decision-sources

不是所有决策都在抽象层就能看见。决策点按浮现时机分三类，处理方式不同：

| 来源       | 浮现时机                         | 处理                       |
| -------- | ---------------------------- | ------------------------ |
| **原则性**  | 抽象层即现，是可行域边界上的方向选择，影响面大      | 慎重论证，必须记 why 与影响范围       |
| **依赖驱动** | 引入某实现依赖后才暴露的新自由度             | 标注"由哪个依赖触发"——依赖若变，决策可能失效 |
| **偏好**   | 逻辑上无差别的方向（yaml vs json、命名风格） | 一次定调、全局遵循，不必每次论证         |

**依赖驱动**这类最易被误解：它在抽象层根本看不见，是有了进一步实现依赖后才出现的决策。规范显式承认它的合法存在，避免"这决策为什么没在概念层出现"的困惑。

## 各层职责 ^anc-meta-layer-division

下面四层是抽象度维度上的台阶。每一层的描述都按"该层收到什么可行域 / 推演出什么 / 留下什么决策点"展开。

### 概念层：定义系统身份与可行域起点 ^anc-meta-layer-concept

概念层定义"我们在造什么、它必须怎样"，是整条链可行域的**初始形状**。**本层产出两半，缺一即残：结构定义 + 关键原则与规则**。它内部同样分推演与决策两类内容。

- **核心概念（推演起点）**：系统的基础结构与语义——如 HopSpec 的规约结构、14 种步骤类型。它们不是"决策"，是后续一切推演的公理。
- **关键原则与规则（推演的支点）**：安全语义、行为规则这类条文，是可行域边界的**显式写法**、下层一切推演的**直接依据**——推演链显式化写的"由概念层原则 X 推演"，X 就产自这里。一条原则不落笔，下层就少一条可依循的链源，漂移无对照。原则与结构定义**同等强制**，不是结构之外的附注。**原则可以有例外，但例外必须经决策与登记**：走 `^anc-meta-agent-duty-decide`（人拍板，Agent 不得自行破例），且落笔登记（在原则所在处或例外落点标注例外范围与 why）——未经决策登记的破例即违规，与静默跳过守卫同罪。
- **概念级决策**：可行域边界上需人拍板的方向选择。判据是**身份测试**——改了它，造出来的是一个不同的系统（行为特征/安全模型/语义规则不同），而非用不同方式造同一个系统。
  - 正例："paused 是合法稳定状态，引擎绝不替 caller 决策"——"超时自动批准"也是合法选项，需人明确排除。
  - 正例："act 必须可逆、不可逆副作用隔离到 commit"——这是 HopSpec 的安全身份，在引擎拦截、工具 `requires_commit`、沙箱边界等下层都有落点，但那些是**向下推演**而非全链强制约束（对比下文「宪法级原则」的辨析）。
- **概念内的推演产物**：从核心概念第一刀收窄就被锁死的方向，本层即可写出，无需下放。

> 宪法级原则不属此层（也不属任何单层）——见下文「宪法级原则」。

### 设计层：在可行域内推演解法架构（可多级） ^anc-meta-layer-design

设计层回答"怎么造它"，承接概念可行域，逐级收窄成技术解法。**设计层本身是多级的**，不是单层：**架构**（系统如何分层、组件如何拆分）→ **模块**（封闭可行子域的划定与边界声明，见 `^anc-meta-module-spec`）→ **接口 HopType/关键 HopType**（模块出入口的类型契约与承载核心语义的组件类型（struct）/Hop契约（HopTrait）——签名、数据结构、规则枚举）→ **关键任务 HopSpec 骨干**（关键行为用 HopSpec 步骤逻辑表述的主干，即 `^anc-meta-hoptype-spec` 要素④）。每一级都在上一级的可行域内继续定位；"关键"是注意力经济的筛选——只有关键类型与关键逻辑才占设计层篇幅，其余留给代码层直接落点。

- **架构级关键原则与规则（本级推演的支点，与概念层原则同构）**：架构级不只画分层与组件图，还必须**显式设定本级的关键原则与规则**（如分层桥接点约束、跨切面契约、依赖方向规则），供模块/接口/骨干各级推演依循——"由架构级 Y 推演"的 Y 就产自这里，不落笔则下级推演无链源。**例外同样必须经决策与登记**（同概念层原则的例外纪律，见 `^anc-meta-layer-concept`），Agent 不得自行破例。
- **推演产物**：从上层逻辑锁死的技术约定。**推演链显式化**——写明来源（"由概念层原则 X 推演：…"／"由架构级规则 Y 推演：…"）。
- **设计级决策**：判据是**用户感知测试**——Spec 作者/Caller 感知不到的内部取舍属设计层（如 PromptAssembler 6 层的 token 预算分配、SandboxConfig 切四维还是三维）。三种来源都可能出现，**依赖驱动**类尤其常见（选了文件持久化 → 才浮现 YAML 单文件 vs 多文件）。
- **模块是设计层的显式交付单元**：架构级收窄的产物必须以**模块**落笔成形——不只是"组件怎么拆"的叙述，而是每个模块一份可核查的设计存在（必备件清单见 `^anc-meta-module-spec`"设计层必备件"）。四层追溯链是**纵向**的，模块是**横向**环——纵向链每环都齐、横向不登记，链仍不完整（实撞教训：新模块代码/测试/纵向锚点全齐，但架构视图、模块盘点、出口清单未同步，三处机检红灯与视图过期并存多日才被人盘出）。
- **上升规则**：设计层遇到拿不准的选择，要分辨它是**设计级**（自行定夺，记 why）还是触碰了**身份契约**（上升概念层的是背后的关键要点/要求，不是实现细节本身）。

### 代码层：收窄为可执行的点 ^anc-meta-layer-code

代码忠实实现设计契约，不引入设计层没有的语义——它是可行域收窄的终点。

- 代码中发现设计缺陷 → 先回设计层修订，再改代码（一致性审查永远是下游对齐上游）
- 合理的工程偏差（如 v1 简化）必须在设计层标注"v1 偏差"，不能只存在于代码

### 测试层：验证落点确在可行域内 ^anc-meta-layer-test

测试验证代码行为符合设计契约——不仅验证"函数存在"，更验证"行为匹配"。三条核心测试原则，其守卫落实见 [[工程实现链-守卫规范]] §三（项目级工具与台账归设计层，本库见 chain-enforcement）：

- **合理覆盖率（行覆盖 + 分支覆盖）**：覆盖关键路径 + 边界 + 错误路径，仅 happy path 不算完整；仓库锁定行/分支覆盖率基线，机检保证只升不降（提升后人工上调，不自动放松）。覆盖率是底线不是目标——数字达标不等于关键路径被真验证
- **e2e 测真结果、核真过程**：端到端测试必须验证**真实执行的最终结果**，且必须**查实际执行日志核验过程正确**——只断言最终输出，过程走歪（中间步被跳过、顺序错、该暂停没暂停）测不出来；结果对 + 过程对，缺一不算 e2e 通过
- **正反例成对**：每个行为变更（新特性、bug 修复、判定/豁免规则）的测试必须**正例（该过的过）与反例（该拒的拒）成对**——只有正例钉不住边界：豁免会外溢、拦截会漏放、修复会误伤相邻语义，全都只有反例才测得出。反例优先钉在**修复动过的判定边界**上（改了豁免就测豁免不外溢、改了轮次判定就测相邻的 resume 语义不被误伤）。判定/守卫类代码（validator 规则、e2e 断言、机检脚本）**无反例即不完整**
- 测试发现行为与设计不符 → 修代码（或经确认后修设计），不许修测试迁就代码

## 宪法级原则 ^anc-meta-constitution

一类**最高强制**约束：违反即错、无例外、垂直穿透概念/设计/代码/测试每一层——声明一次、全链生效。它们与具体概念无关（换个项目也成立），管的是"内容怎么写、动作怎么做"，不管"系统是什么"。分两组：**内容宪法**约束产物，**行为宪法**约束 Agent 动作。

### 内容宪法（约束产物）

- **命名忠实**：名称读出来的含义必须与实际所指一致——**禁止望词生义**。这是宪法级要求，因为每个读者（人或 LLM）都按名字面理解，一个误导性名称在每次被阅读时注入一次错误假设，沿调用链指数放大。具体规则：
  - 字段存 ID 就叫 `*_id`（`callee_spec_id` 而非 `callee_spec`——后者会被误读为"Spec 对象本身"）
  - 字段存路径叫 `*_path` / `*_dir`，存名称叫 `*_name`
  - 布尔字段名直接陈述真值含义（`requires_commit` 而非 `commit_flag`）
  - 方法名动词准确表达副作用（`saveSnapshot` 落盘，`getX` 无副作用）
  - 往往一个词组也说不清概念，故每个类型/变量定义时都应配 `#` 一句话注释锚定语义
- **比喻只解释不指代**：类比可在首次解释时帮助理解，但任何称呼、引用、术语必须用**本名**，禁止用比喻词指代——比喻携带大量无关寓意，用作指代会望词生义、产生概念错乱。**一个比喻词被套到多个不同机制上尤其有害**（如"冒泡"同时指容器聚合输出、exit 退出传播、call 决策传递，读者无法从词本身区分指的是哪个）。命名忠实与比喻不指代是一对：前者管"给新事物起的名要忠实"，后者管"别用旧比喻词去指代"。
- **锚点对齐**：四层追溯链（`^anc-*` / `@a:` / `@v:`）上任一锚点不对齐都沿层级向下放大——审计必须全量、最严格（见下文「锚点追溯链」、anchor-audit skill）
- **推演链显式**：从上层推来的内容须标注来源（"由概念层 X 推演：…"）；下游对齐上游，不反向迁就

### 行为宪法（约束 Agent 动作）

- **收链前置**：Agent 动手细化或编码前，**必须先收集相关的锚点实现链**（前序框架 + 依赖引入 + 新决策三组锚点）。未收链就编码本身即违规——等于在可行域外盲走。这是 Agent 作业协议职责一的强制前置，细则见下文「Agent 作业协议」
- **设计先行**：改代码（`src/*.ts` 等实现文件）前，**对应的设计文档（`design/*.md`）必须先行改定**。代码只能实现已在设计层定下的契约——发现设计有误先回设计层修订，再改代码。**"改定"有内容底线，不是碰过就算**——涉及的这三样必须真的写出来（与 [[工程实现链-模块规范]] 核心内容元素同一套要求）：
	- **能力契约**：这个改动让模块对外提供/改变了什么能力——**用 HopSpec 契约写**（Spec without Steps：Goal/Constraints/Inputs/Outputs——输入什么、给出什么、什么约束下失败），不用散文描述代替；
	- **类型约定**：新增或变更的关键类型与字段——**用 HopType 表达**（字段逐条列出，每字段一句话说明；不直接堆 TS/Python 签名当设计）；
	- **关键逻辑步骤**：行为怎么走的主干——**用 HopSop 写**（[[HopSop标准作业流程]]），判定顺序、分支走向、多个使用点各在哪——读设计就能预判代码怎么写，才算表达到位。
	只写一句"XX 已调整"或只记版本史，不算改定。**禁止跨层直达**（从概念/想法一步跳到代码、跳过设计层）——这是 Agent 最易犯、诱惑最大的失效（"急着写"压过"先想清"），比收链前置更难自觉。判据可机检：一次改动里 `src/` 有改而对应 `design/` 无对应改动，即跳层信号。合理的工程偏差（v1 简化）允许"先实现后补设计"，但**必须当场在设计层显式标注 v1 偏差**，不得只存在于代码
- **修 bug 也一样，不豁免**：越是"一行就能修好"的 bug，越容易不看设计直接改代码——这正是最常见的跨层直达。修任何 bug 都按同一个顺序走：
	1. 先把设计文档里管这个行为的那段规定**读一遍**（光看代码旁边的注释不算）；
	2. 问自己：是代码写错了没照设计做，还是**设计本身要改**？前者直接修代码；后者**先改设计正文**、再改代码——在版本史里记一笔不等于改了设计；
	3. 改的这条规则如果在几个地方都被用到，把这几个地方**都列在设计里**——只改一处，别处照旧按老规则跑，等于没修全；
	4. 测试要一对：改完该通过的真通过，该被拦的真被拦（见测试层"正反例成对"）。

	机器检查只看"这次提交里设计文档动没动"，分不出你是先想清了才写码、还是写完码回头补两句。这是宪法级红线：**必须严格遵守，违反即错**——语义审计与评审事后必究
- **严禁"顺带"执行命令之外的事**：执行一条命令时，**严禁"顺带""顺手"做命令范围之外的任何修改**——哪怕途中发现了真实问题。顺带修改的危害是双重的：它绕过了人的授权（占用的不是注意力而是决定权），且藏在主命令的 diff 里难以审查。正确做法：若认为某事可由推理链确认该做、不需人做判断，**单独提出申请**——讲清楚事情本身、推理依据与可信度，获得授权后再执行；执行也**独立成次**（独立 commit/独立改动），不与主命令混在一个交付里。发现问题≠获得处置授权，报告发现是本分，擅自处置是越界

> **与概念要素的区别（易混淆）**：像"act 可逆 / commit 显式"这样的安全语义，虽在概念/引擎/工具多层都有落点，但它**不是**宪法级原则——它是 HopSpec 的**核心概念要素**（定义语言的安全身份），属概念层。它在下层的落点是**向下推演**（语义→引擎拦截→工具实现），而非全链强制约束。判别法：宪法级原则与造什么系统无关（换个项目也成立），概念要素一旦改变系统身份就变了。误把概念要素当宪法级原则，会让人忽视它的可行域收窄链。

## 核心理念原则：注意力经济（人与 Agent 双主体） ^anc-meta-attention

整条链的分层与标注，统摄于一条核心理念原则：**让有限的注意力只落在真正需要它的地方**。这里的"注意力"有两类主体——人和 Agent（执行实现的 LLM）——**两者都是受约束的有限主体，这套体系同时为两者服务**。

之前一个隐藏的错误假设是"推演产物丢给机器即可、机器注意力无限"。不成立：Agent 的上下文窗口是硬约束，且**只进不出**——把关键约束和大段推演混在一起塞进来，决策信号会被噪声淹没。Agent"实现失控、抓不住要点"正源于此。

### 人与 Agent 的注意力差异 ^anc-meta-attention-actors

| | 人 | Agent（实现 LLM） |
|---|---|---|
| 瓶颈 | 阅读/决策带宽有限，不愿读大段推演 | 上下文窗口有限，远端约束易被淹没/遗忘 |
| 失效表现 | 漏掉该决策的点；被噪声拖垮判断 | 三类失控，见下「Agent 作业协议」违反职责的后果 |
| 体系如何帮它 | 分级标注路由注意力到【决策】 | 锚点定位可行域 + 分级区分"该对齐 vs 该实现" |

### 两条硬要求（对人对 Agent 同时成立） ^anc-meta-attention-rules

- **a. 决策点结构可见**：章节标题/标签标明哪节是【决策】。人扫大纲即知何处需停下思考；Agent 据此判断"这里不能擅自推演，要先对齐"，不通读大段推演内容。
- **b. 决策点上下文自足**：每个决策点自带背景、约束、备选项、工程链条锚点（指向上下游影响）。人无需四处翻找即可拍板；Agent 无需把整份文档拉进窗口，顺锚点按需取用即可定位可行域。

这正是下文「内容分级」与「锚点追溯链」的设计目的——分级是注意力的**路由表**，锚点是可行域的**定位器**，两者共同把人和 Agent 的有限注意力都约束在要点上。

## Agent 作业协议 ^anc-meta-agent-protocol

上文讲"体系如何帮 Agent"，本节讲 Agent 自己**必须做什么**。Agent（执行实现的 LLM）在这条链上不是被动查阅文档的工具，而是承担两项核心职责。这是 Agent 的作业协议，不是建议。

### 职责一·推演到实现测试：先收链，后细化 ^anc-meta-agent-duty-implement

Agent 负责把任务从当前层推演到下一层，直至代码与测试。**动手细化或编码前，必须先收集相关的锚点实现链**——这是「宪法级原则·行为宪法·收链前置」（见上文），违反即在可行域外盲走。此处给出收什么、怎么收。

实现链由三组锚点拼成，缺一不可：

1. **前序框架**：前层概念与设计给出的可行域边界（上层 `^anc-*` 原则与契约）——定义"我不能越过什么"
2. **依赖引入的锚点**：设计层因引入某依赖而新增的约定（依赖驱动决策对应的锚点）——定义"这条实现路径额外锁死了什么"
3. **新决策引入的锚点**：本次推演中新拍板的决策点所产出的锚点——定义"我这一刀收窄了哪个自由度"

收齐这三组 → 可行域边界完整进入上下文 → 才动手。这直接对治「可行域漂移」：漂移的根因就是动手前没把链拉进上下文。收链顺着锚点的反向链接与追溯卡片（TRACEABILITY）进行，按需取用，不必把整份文档拉进窗口。

### 职责二·决策建议：发现、定位、建议，不替人拍板 ^anc-meta-agent-duty-decide

Agent 不只是执行者，还是**决策点的发现者与定位者**。推演过程中遇到上层未锁死的自由度时：

1. **发现（第一关，最易错）**：⚠️**默认动手，问是例外**。先判"这是不是决策点"——问："能否从已锁死的上层原则**一步推演**出答案？"能→是推演产物，**直接做、别问**；不能（真有多个合法选项、上层没锁）→才进第 2 步定位。**问一个可推演的项 = 角色混淆、失职，不是谨慎**。反例：已定"执行链归 subagent"后还问"run 该不该也交 subagent"——run 属执行链是纯推演，不是新决策；把它当决策点上报，浪费拍板人注意力，与"擅自替人决策"是同一失职的两面（都源于没分清推演 vs 决策）。
2. **定位**：判定它该在哪一层决策——用身份测试（改了系统身份变没变？变→概念层）与用户感知测试（Spec 作者/Caller 感知得到吗？感知不到→设计层），并标注来源（原则性／依赖驱动／偏好）
3. **建议**：给出备选项与倾向，一并呈给人。**上报必须上下文自足——不许没头没脑地甩问题**：拍板的人没跟着走过你的推演，上报自带①问题与来龙去脉②现状事实③各备选的后果代价④你的倾向与理由，用对方读得懂的话写；**完整靠选材不靠堆量**——过度繁琐同样浪费拍板人注意力。**判据：对方不追问任何背景、也不用在废话里刨重点，读完即可拍板＝合格**

**拍板权归人**：Agent 做发现、定位、建议，**不替人决策**。把决策点当推演产物擅自发挥、越过本该由人定的边界，是最危险的失职（见下「角色混淆」）。偏好类决策若已全局定调，Agent 遵循即可、不必每次上报；原则性与依赖驱动类必须显式提请人确认。

**推演权归 Agent（与拍板权对偶）**：判定为可推演的项，Agent 就地办结，两个义务同时成立、缺一即失职的另一半：

- **对链：记录推理过程、明确推理结果**。推演不是"做了就完"——过程与结论要按「推演链显式化」落笔（"由 X 推演：…"），让结果可审计、可回溯，而非只存在于会话现场。没落笔的推演，下次改动时等于没推过。
- **对人：不打扰**。可推演的项不上报、不请示、也不把推演过程摊开给人过目"求放心"——这与问一个可推演的项是同一种浪费，都在消耗拍板人的注意力（`^anc-meta-attention`）。当时呈给人的只有决策点；落笔的推演结果不是拍板时的呈件，而是留在链上供**后继人/Agent review** 的——审计与后续改动顺链核验时才读它（这正是"对链落笔"义务的服务对象）。

### 违反职责的后果：Agent 特有失效模式 ^anc-meta-agent-failures

不履行上述职责时，Agent 实现反复出现三类失控，这套体系正是对治它们的纪律：

1. **可行域漂移**（违反职责一收链前置）：上层锁定的边界若不在就近上下文，Agent 推演中会逐渐违反它，自己还觉得合理。→ 对治：**收链前置 + 锚点定位器**——实现前反查"我被哪些 `^anc-*` 锁住"，把边界拉进上下文。
2. **跨层直达**（违反职责一逐级推演）：Agent 倾向从概念一步生成代码（因为"能"一步到位），跳过设计层逐级收窄，落点常在可行域外。→ 对治：**收窄模型是工作纪律**——意识到自己在哪一层，不跳级；缺设计层时先补设计再写代码。
3. **角色混淆**（违反职责二的边界）：把推演产物当决策点（在已锁死方向上过度设计、反复纠结），或更危险地把决策点当推演产物（擅自发挥、越过本该由人定的边界）。→ 对治：**分级标注是注意力路由**——【决策】= 先停下对齐、不自作主张；【契约】= 已锁定、忠实实现别重新发明；【说明】= 参考不照搬。

> **对治不会自动生效——由守卫体系兜底**（见下「守卫体系」`^anc-meta-guard-system`）：上述三条对治都是**行为纪律**类守卫（`^anc-meta-guard-three-kinds`——约束动作而非产物，多数不可机检），单靠 Agent 自觉必然衰减。因此每类失效还须有产物侧的守卫接住漏网：跨层直达有机检信号（src 改而 design 未改，设计先行判据）；可行域漂移靠语义审计（anchor-audit 查代码与上层锚点对齐）事后暴露；角色混淆靠评审（【决策】章节改动需作者确认）拦截。行为纪律管"别犯"，产物守卫管"犯了会红"——两层都在，失效才算被守住；哪类失效缺产物侧守卫，按「空白台账」纪律（`^anc-meta-guard-gap-discipline`）显式登记，不许默认裸奔。

## 设计文档规范 ^anc-meta-design-doc

### 内容分级：决策 / 契约 / 说明 ^anc-meta-content-grading

内容分级把「注意力经济」落地为可操作的标注——它对应的正是上文「内容角色」维度：【决策】= 决策点（人要停下拍板、Agent 要先对齐不可擅自推演），【契约】+【说明】= 推演产物（已锁定，Agent 忠实实现/参考，不在此重新发明也不反复纠结）。设计文档的每个章节必须标明分级，让人和 Agent 都能扫大纲即知何处需要介入：

| 分级 | 内容角色 | 含义 | 审计要求 |
|------|---------|------|---------|
| **【决策】** | 决策点 | 人拍板的关键选择 | 改动需作者确认；建议注明决策来源（原则性／依赖驱动／偏好）与 why |
| **【契约】** | 推演产物 | 带 `^anc-*` 锚点的技术约定 | 代码/测试必须对齐，anchor-audit 全量审查 |
| **【说明】** | 推演产物 | 示例、格式演示、辅助理解 | 与契约一致即可，无独立锚点 |

操作要求：

- 章节标题内嵌标签：`## 日志级别【契约】 ^anc-obs-log-levels`、`## 主文件结构【说明：示例】`。锚点保持行尾（Obsidian block ref 有效性）
- **决策章节宜标来源**：`## 超时策略【决策：原则性】`、`## 持久化格式【决策：依赖驱动】`——来源标注让读者快速判断该决策的稳定性（偏好类几乎不变，依赖驱动类随依赖变化）
- 文档开头设"文档结构与内容分级"一节：分级定义表 + 全部章节的分级归类表（含锚点清单）。该归类表即本文档的**决策点路由表**——人据此直接跳到需决策的章节
- 文档标题必须与内容范围一致；范围更大的能力（如"可观测性"⊋ HopLog）需在开头说明关系并指向相邻文档

### HopType 描述规范 ^anc-meta-hoptype-spec

> **权威=[[HopType体系#^anc-hoptype-desc-spec]]**。每个组件类型（struct）的设计描述必须覆盖**四要素**：

1. **自身定位**——是什么、解决什么问题（本体语言，不依赖比喻）
2. **与其他 HopType 的关系**——被谁用、用谁、与相邻组件的职责边界
3. **Hop契约（HopTrait）与主要成员**——逐条完整介绍；成员超 5 个必须按职责分组
4. **核心行为实现（impl）的 HopSop 逻辑**——**关键契约与关键流程一起展示**：流程必须与它兑现的契约（HopTrait）同节在场，只展示流程缺漏契约=三件套描述不清（流程表述用 HopSop）

## 模块规范：注意力自足的封闭子域 ^anc-meta-module-spec

> **权威=[[工程实现链-模块规范]]（六条要求 [[工程实现链-模块规范#^anc-module-requirements]]）**。模块=架构级收窄切出的封闭可行子域，唯一动机是注意力经济（Agent 在有限窗口内安全理解/修改/验证单个模块）。六条本质要求：

1. **封闭子域**——边界显式声明，每项"不碰"标注去向（→承载模块 或 →项目外）
2. **注意力自足**——设计契约+接口+测试构成独立可理解单元
3. **接口面最小**——说不出消费方的出口不准出口
4. **测试边界对齐**——每模块有专属红灯，不靠上层间接兜底
5. **依赖方向单向**——只依赖同层与更低层，越向须先经桥接决策
6. **版本随契约**——出口契约不变则版本不动，互为核查锚

内容次序（核心内容前置：trait 契约→struct 类型→关键逻辑流程；守卫件后置）、生命周期、拆分信号见新规范。

**设计层必备件** ^anc-meta-module-design-artifacts：核心内容件四件（定位边界/能力契约/关键类型/关键逻辑流程·可选）+ 守卫链件五件（出口表/版本/继承声明/锚点成对/架构视图），全表见 [[工程实现链-模块规范#^anc-module-artifacts]]。

## 锚点追溯链 ^anc-meta-traceability

四层通过锚点连接成可审计的追溯链：

| 层 | 锚点语法 | 审计维度 |
|---|---------|---------|
| 概念层 | `^anc-*`（Obsidian block ref） | S→D：设计是否忠实传达概念 |
| 设计层 | `^anc-*` | D→C：代码是否忠实实现设计 |
| 代码层 | `// @a: anc-*` | C→T：测试是否充分覆盖代码 |
| 测试层 | `// @v: anc-*` | — |

Markdown 文档中的锚点一律用 `^anc-*` 语法（出现在代码围栏内也一样）。

任何一个锚点的不对齐都会沿层级向下累积放大——审计必须全量、最严格（见 anchor-audit skill 宪法级原则）。

> **权威=[[工程实现链-模块规范#^anc-module-trace]]**。`@module:`/`@module-deps:` 把每个文件显式绑定到模块，横向环的代码侧落点；审计三维度（无遗漏/指向真实/声明=实际依赖）。

## 守卫体系：链的防腐机制 ^anc-meta-guard-system

> **权威=[[工程实现链-守卫规范#^anc-guard-principles]]**。链会腐坏且腐坏默认无声，守卫体系是元规范自身完整性的承诺——三原则（2026-08-08 作者审定：原五条重构，1/3 合并、5 删除降为推论、2 重写为两维正交）：

1. **显式覆盖：每一环显式回答"由谁守、何时执行"；"不守"必须入台账、处置三选一——空白可以存在，模糊不允许存在** ^anc-meta-guard-mapping ^anc-meta-guard-gap-discipline
2. **手段×对象两维正交：手段只有机检与语义审计两种（评审=语义审计人工形态）；行为不可直接守，只能守其产物投影——每条行为纪律必须声明产物侧信号** ^anc-meta-guard-three-kinds
3. **守卫自证：负向验证/判据回归/禁静默跳过/零假警报** ^anc-meta-guard-self-trust

推论（无宽限期）：未入映射、未自证的守卫**视同不存在**。 ^anc-meta-guard-admission-principle

> 三者关系：分层/锚点/模块定义**链是什么**，宪法/协议定义**怎么作业**，守卫体系定义**凭什么相信前两者被持续遵守**。

## 协作规则

1. **修改方向默认向下**：内容变更先改上游层，再同步下游层。上游可行域一变，下游所有落点都要重新核验是否仍在新域内。下游反向修正必须先和作者确认
2. **每层对上一层负责**：设计对概念、代码对设计、测试对代码。跨层跳跃（概念直接改代码）会撕裂追溯链
3. **审查沿链进行**：一致性审查永远是下游对齐上游，而非反过来
4. **依赖驱动决策随依赖复审**：标注了"依赖驱动"来源的决策，当其触发依赖变更时（如持久化方案、第三方库更换），必须复审该决策是否仍成立——它不像原则性决策那样稳定
