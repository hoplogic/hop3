# 有序思考与渐进固化

> HopJIT 运行时能力扩展（TODO：概念探索阶段）

## 定位

有序思考与渐进固化不是 HopSpec 语言层的步骤类型，而是 **HopJIT 在 Spec 级别的运行时能力**。核心规范定义了 Spec 的两种形态——有 Steps（具体实现）和无 Steps（**HopTrait，Hop契约**——定名见 [[HopType体系#^anc-hoptype-hoptrait]]）。HopTrait 只提供 WHAT——Goal、Constraints、Inputs、Outputs，HopJIT 负责 HOW——生成 Steps、试跑、验证、渐进固化。一句话：**有序思考 = 给 HopTrait 配出可执行实现**。

这是 HopSpec"锁定目标，放开路径"理念的极致体现：连 Steps 都可以不写，由 HopJIT 从零探索。

**循环的归属分界**：spec 里的循环只有一种——**数据遍历**（对每个元素做一件事，`loop for-each`/`max=N`），它是业务逻辑的一部分，归作者。**收敛迭代**（试→验→不达标带反馈再试，直到达标或放弃）不归作者手写——作者交付的是目标与可验证的停止条件（HopTrait 的 Goal/Constraints/Outputs），迭代策略归运行时：局部失败走引擎升级阶梯（带反馈重跑→备用链路→adaptive 重规划），从零探索即本文的有序思考——同一闭环的两个入口。业界"loop engineering"实践（设计 agent 的迭代循环：目标+停止条件+验证器，循环自己收敛）与此同构：其手工形态是作者自搓收敛循环，Hop 的形态是把循环纪律编译进运行时。

## 探索验证闭环

HopJIT 收到 HopTrait 时的执行流程：

```
评估复杂度与置信度
       ↓ 置信度不足
搜索（外部信源 / 知识库 / Spec 库，按约定）
       ↓
有序思考（生成 Steps）
       ↓
在验证环境中试跑
       ↓
验证
       ↓ fail → 带失败上下文重新思考
       ↓ pass
交付结果 + 候选 spec 入库
```

- 生成的 Steps 禁止包含 `commit`（沙盒内试跑，无不可逆副作用）
- `Constraints` 约束思考方向和执行边界
- 验证标准：
	- Outputs 类型结构满足
	- Constraints 全部通过
	- 生成的 check 步骤全部通过
	- 在沙盒中构造多组样例输入验证鲁棒性

### 思维方式是策略，不进闭环契约

闭环的**不变量只有机制面**：契约锁死、生成物过 validate、试跑验证、停止规则、路径记录。至于一轮之内**怎么想**——按什么章法分解、何时反思、何时修正——是**思维策略**：可插拔、按任务类型选型、且本身就是渐进固化的沉淀对象（哪类问题用哪种想法有效，和哪条路径有效一样是经验资产）。adaptive 三段流水线中间那段"策略"与此同一概念：选策略是闭环的一个环节，不是闭环的骨架。

**缺省参考策略：六阶段**——

1. **Decompose（分解）**：复杂问题拆为子问题
2. **Plan（规划）**：为每个子问题设计执行步骤
3. **Execute + Monitor（执行+监控）**：逐步执行，边跑边检中间结果
4. **Reflect（反思）**：收敛判定——当前结果是否满足验证标准
5. **Revise（修正）**：不满足则带失败上下文调整方案，回到 Execute
6. **Synthesize（综合）**：满足则汇总交付

Monitor 与 Reflect 是两道不同的检查：Monitor 管单步产出对不对（边跑边拦），Reflect 管整体收敛没有（一轮一判）。

策略可换，但**停止规则与验证标准不随策略走**——任何策略都在同一套机制面内运行（进展指纹的输出契约即策略必须满足的对接面：无论怎么想，每轮都要交出可比较的收敛状态）。

**策略的语言面挂点 = [subtask free]（作者确认 2026-08-29）**："策略本身就是 HopSpec"（2026-08-26 裁定）的语法载体——策略即**带洞的 spec 骨架**：洞放在哪、每次展开摊多开，就是"怎么想"本身（一次全摊平=先想全再干；每次只写看得清的一段、更远处再留洞=渐进细化；先分解出子问题清单、每个子问题一个洞=六阶段参考策略——它也只是一种放洞的形状）。机制面（契约锁死/展开强制 check/禁 commit/总数熔断/expansion_context 递真值）引擎焊死不随策略变；策略面写在 spec 文本里，可存、可提纯、可复用。**策略族是开放的多元集合（作者定 2026-08-29"策略机制本身可以有多种，loop engineering 也只是其中一种"）**：loop engineering（收敛迭代——试→验→带反馈再试直到达标）只是族内一员，与渐进细化放洞、六阶段分解、递归等价分拆（hopbuild2 判定序）并列——谁也不是骨架，骨架只有机制面五箍。新策略不需要引擎开口子：写成带洞骨架（或成品 spec）即入族，与既有成员同库同态。边界：此为策略的**表达**；策略的**选型**（哪类任务用哪种策略）仍待类别标与动态 callee（见待探索）。

### 停止规则：达标之外的三个出口

没有显式终止逻辑的探索循环是最贵的失控形态。除验证通过（唯一成功出口）外，闭环必须有：

- **预算耗尽**：迭代上限即 `max=N` 既有语义（收敛迭代=条件循环，探索容器头同词复用）。**token/成本预算独立一路**——迭代数不是成本的可靠代理（一轮探索可能很便宜也可能很贵），由运行时资源护栏按累计 token 拦（既有 BUDGET_EXCEEDED 机制，探索实例照常受管），两路任一触发即停
- **无进展中断**：连续多轮 Reflect 结果无实质变化即停，不等预算烧完
- **升级给人**：上述任一出口触发后抛外部交互信号——交互模式向 caller 请求补充信息或指引方向（复用 ask 冒泡语义）；批量模式交付 **UNCERTAIN**（＝顶层验证 check 判 uncertain 的上浮，见原语盘点 check 三值化："在给定预算内未能收敛"，产出部分结果+探索记录，标记待人工审阅）。宁可承认收敛不了，不高效地做错事

### 与 adaptive 的关系：同一闭环，作用单元是"带契约的容器"

**spec 与 subtask 本质上没有区别**：spec 就是根容器，头部 Goal/Constraints/Outputs 与 subtask 的 summary/check final/`+ →` 交付契约是**同一契约面在两个语法位置**。有序思考作用于"带契约的容器"——契约锁死、内部生成，与这个容器挂在树根（HopTrait）还是树里（adaptive subtask）无关：

| 维度 | 树里（adaptive subtask） | 树根（HopTrait） |
|------|----------|---------|
| 触发 | children 执行失败，重规划 | 一开始就没有 children（无 Steps） |
| 不可变面 | `+ →` 契约与 check final | Outputs / Constraints |
| 起点 | 有一版失败的 children 作反例 | 从零 |

差异只剩触发时机与起点素材，闭环本体（机制面+可插拔思维策略、停止规则、路径记录、固化）完全同一套。推论：**subtask 也可以一开始就没有 children**——那就是挂在树里的局部 HopTrait，与根级 HopTrait 走同一条探索线（是否放开此写法归待探索）。

## 渐进固化（Progressive Solidification）

成功执行的路径不应该是一次性的：

1. **动态 → 候选**：首次成功后，生成的 Steps 连同执行中补充的约束、修正，自动存入 Spec 库
2. **候选 → 验证**：经过多次执行、不同输入验证后，鲁棒性得到确认
3. **验证 → 沉淀**：人工审查确认后，正式成为可复用的最佳实践
4. **沉淀 → 降级**：已沉淀的 Spec 在新场景下连续失败超过阈值时，降级为候选重新进入验证流程

固化的不只是步骤，还包括：
- 执行中发现的隐性约束 → 补充到 Constraints
- 失败路径的经验 → 体现为 check 步骤和 `>` 执行说明
- 领域知识 → 编码为 Types 和数据结构
- **哪类问题用哪种思维策略有效** → 策略选型经验（与路径同为经验资产，见「思维方式是策略」节）

已沉淀的 Spec 可以被后续有序思考查询复用，也可以直接通过 `call` 调用——系统越用越聪明。

**四态是库里资产的状态；运行时对应三种执行模式**：

| 执行模式 | 行为 | 可靠性走向 |
|---|---|---|
| 探索 | 无可用固化路径，走完整探索验证闭环 | 最低、最贵 |
| 加载固化 | 命中候选/验证态路径，**优先直接执行它；失败才回退探索**（回退即降级信号，计入该路径的降级判据） | 中 |
| 确定 | 沉淀态经人审转为有 Steps 的普通 spec，照常执行，不再探索 | 最高、最快 |

"固化路径失败自动回退探索"是运行时那半边的降级链，与库状态的"沉淀→降级"一体两面：前者管这一次执行怎么继续，后者管这条路径今后还信不信。**候选/验证 → 沉淀必须过人审**（对齐 confirm 哲学：改变系统今后行为的固化是外向动作，人拍板）。

## 支撑原语盘点

把闭环逐环节反推所需语义支撑，按三档列出——先复用、再扩展、最后才发明：

**先立一条总原则：探索的中间表示 = HopSpec 自身**。思维策略 Plan 出的产物是 Steps、试跑的对象是 spec、固化的资产还是 spec——全程一种表示，不为探索发明第二种中间语言。路径记录、候选、沉淀只是同一份 spec 文本在不同状态下的身份，这是"渐进固化"能成立的语言学前提。

### 第一档：语言面已有，直接复用（零新语法）

| 原语 | 在闭环中承担 |
|---|---|
| HopTrait（无 Steps spec） | 探索的入口与契约——Goal/Constraints/Outputs 即"目标+停止条件+验收面" |
| `max=N`（loop 安全上限语义） | 探索预算——收敛迭代本质是条件循环，其迭代上限就是 max 的既有词汇，复用到探索容器头（不发明"探索预算"新概念） |
| Constraints → check final 化身 | 验证器——验证标准四条里的前三条由既有校验与 check 机制承载 |
| ask（冒泡语义） | 交互模式的"向 caller 请求指引方向"——升级给人出口复用它，不设新介入点类型 |
| confirm | 固化晋升人审闸——候选/验证 → 沉淀的确认动作 |
| call | 调用方无感消费：HopTrait 与具体实现经同一 call 语法调用，探索对 caller 透明 |
| FailRecord（fail_kind）+ check text 槽 | "带失败上下文重想"的反馈载体——Revise 读的就是它们，与升级阶梯第 1 档同源 |

### 第二档：运行时已有，需扩展

| 现有件                                           | 缺口                                                                                                              |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| check 固定双槽签名（bool 判定 + text 说明） | **判定槽零动;说明槽升格双档 text\|yaml + `escalatable` 属性**（2026-08-26 作者定,已改判入核心规范 ^anc-step-check-escalatable）——升层不进判定值域,进**失败说明的结构**:escalatable 的 check 说明槽为结构化 yaml（缺口清单=进展指纹载体,`escalate/need` 保留字段）,fail 且 `escalate: true` → 不入 retry 走升层问路（ask 冒泡链,应答注入下一轮,不扣预算）。**三值化议过撤了**（裁定记录见修订史——防重新发明）：①初判"升层已有 ask/max/case 一等表达"→②被"check fail 恒入 retry、后继 case 不可达"推翻→③终判"失败自己声明处置"（与 OUTPUT_TRUNCATED 前缀/fail_kind=deterministic 同模式第三成员）。原"进展指纹"新原语随之消解为 gap 结构化的轮间比较;"uncertain 上浮/终态第三态"撤——顶层没收敛的诚实交付用既有终态+探索记录表达 |
| adaptive 三段流水线（失败分析→策略→生成）                    | 就是探索闭环的流水线——作用单元同为"带契约的容器"（见上节），树根 HopTrait 与树里 subtask 走同一条，只差触发时机与起点素材，不发明第二条                                 |
| replan_audit 四元组 + 候选文件落盘                     | 现只采集失败重规划路径；需扩为**探索路径记录**——成功路径同样入账（生成的 Steps + 各步 verdict + 修订历史），固化的原料一半在成功侧                                  |
| SpecProvider（现仅 resolve 单动作）                  | 需扩 Spec 库三动作：**query**（按 HopTrait 契约匹配已有实现——签名/Constraints 相容性判定）、**store**（候选入库）、**status**（四态迁移记录）。**v1=driver 层目录形态先跑（2026-08-29 作者定"先跑起来"）**：/hop distill 落 hop_tasks/specs/（store+人审）+开活查现货扫标题与 Goal（query 的 LLM 语义版）——引擎三动作推迟至目录版撑不住（提纯件规模化/standalone 按契约检索需求出现）再建,避免两套复用体系并存            |
| validate（生成物静态校验） | 探索生成的 Steps 过既有 validate 即可，**无需 dry-run 执行期新闸**——生成物禁 commit 静态可查，act 的身份就是可安全重跑，两者合起来试跑天然无不可逆副作用（作者定 2026-08-13） |

### 第三档：真新原语（概念层待定义）

1. **进展指纹**：无进展中断的前提是"一轮的收敛状态可比较"——Reflect 的产出必须结构化（收敛评估 + 剩余缺口清单，非散文），连续 N 轮指纹不变即触发中断。这同时是思维策略的对接面契约（策略可换，每轮必须交出可比较的收敛状态）。**载体半边已随 escalatable 落地**（yaml 缺口清单）;轮间比较半边挂账 hoplogic3 todo/0032（2026-08-29 作者定——hopbuild2 doc review 修错环已实撞人肉简化版:retry=10+耗尽落盘含"每轮变少变轻=在收敛"人工评估,正式版待根级长探索场景出现同批装）；
2. **uncertain 上浮语义**（第二档 check 三值化的配套）：交付物结构 = 部分 Outputs + 探索记录引用 + 未收敛原因；上浮规则（哪层容器可接住处置、哪层透传）待定义。

（原第三样"探索预算声明"已消解归第一档：收敛迭代本质是条件循环，其安全上限就是 `loop max=N` 的既有语义——探索预算 = max 词汇复用到探索容器头，作者定 2026-08-13。剩余仅挂点书写形式的小决策，见待探索。）

三档合看：真要发明的只有两样，其中一样（2）还是第二档扩展的语义面。闭环的骨架几乎全部由既有原语组装——这印证"有序思考是运行时能力而非语言新特性"的定位。
