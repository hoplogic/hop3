# 工程实现链 · 模块规范

> **定位**：工程实现链的**模块级概念权威**——回答"什么是模块、模块必须满足什么、模块怎么生老病死"。[[工程实现链规范]] 定义链的纵向四层（概念→设计→代码→测试），本规范定义链的**横向环**：模块是把纵向链切成可管理片段的封装单元。
>
> **分工**：本文档管**概念级要求**（为什么、是什么、必须什么）；[[../design/module-principles|module-principles]] 管**本库操作化**（机检判据、分层表、拆分信号、盘点）；[[../design/chain-enforcement|chain-enforcement]] §1c-2 管**建模块的动作协议**（八件单；件数与切分以其现值为准——它按动作序列切、本文 §五按内容分组切，两种视角）。下游文档引用本规范，不复制规定。
>
> **锚点保留策略**：原 `^anc-meta-module-spec` / `^anc-meta-module-design-artifacts` / `^anc-meta-module-evolution` / `^anc-meta-module-trace` 锚点在 [[工程实现链规范]] 原位保留（跨文档引用不断链），**语义权威自本文档生效**——源文档对应节已收为摘要+指针。

## 一、模块的定义 ^anc-module-definition

**模块 = 设计层「架构级收窄」切出的一块封闭可行子域**：一组内聚的能力，对外只经声明的接口交互，对内拥有独立的设计契约、代码归属和测试红灯。

三个"不是"划清边界：
- **模块 ≠ 文件**：一个模块可含多个 src 文件，判据是关注点内聚而非文件数；
- **模块 ≠ 目录**：物理形态按信号逐档演进（平铺+标注 → lint → 子目录 → 分包），逻辑边界先于物理边界存在；
- **模块 ≠ 组件类型**：HopType（struct/trait）描述单个类型，模块是更粗的封装粒度——一个模块通常承载若干 HopType 及其协作。

## 二、为什么要模块（唯一动机） ^anc-module-why

模块化在工程实现链中**不是为"人的代码整洁"**，而是为**注意力经济**（[[工程实现链规范#^anc-meta-attention]]）在封装粒度的落地：

> **Agent 必须能在有限上下文窗口内，安全地理解、修改、验证单个模块——不把依赖模块全文拉进窗口。**

这一条动机推演出下面全部要求。任何模块决策（拆、合、边界调整）的最终判据都回到它：这样切之后，Agent 收链是变轻了还是变重了？

## 三、六条本质要求 ^anc-module-requirements

每个模块必须同时满足（一至四自元规范 `^anc-meta-module-spec` 承接；五自 module-principles §2 依赖方向规则**上提**至概念层；六自元规范演进节 `^anc-meta-module-evolution` 收拢）：

1. **封闭子域**：边界显式声明——"负责什么 / **不**碰什么"（形态见 §四元素 0）。缺边界声明则职责必然蔓延。**"不碰"必须写明去向**（2026-08-08 作者定）：每项不碰的职责标注由哪个模块承载，或完全不在本项目范围内——只说"不碰"不说谁碰，边界间会留无主缝隙（两个模块都以为对方管，或都确信自己不管），且收链 Agent 找不到该去哪个模块。
2. **注意力自足**：设计契约 + 对外接口 + 专属测试构成**独立可理解单元**。操作判据：三者之和一个上下文窗口装得下且有富余。
3. **接口面最小**：对外只暴露必要公开契约，**说不出消费方的出口不准出口**；为测试暴露私有逻辑是拆分信号，不是出口理由。
4. **测试边界对齐**：每个模块有专属红灯，改坏了由自己的测试拦，不靠上层 e2e 间接兜底。
5. **依赖方向单向**：模块处于分层秩序中，只依赖同层与更低层；越向依赖必须先经桥接决策登记，禁止先斩后奏。
6. **版本随契约**：每个模块自带语义化版本，由**该模块对外接口的兼容性变化**驱动——出口契约不变则版本不动，版本不动则契约不许破坏性地变（互为核查锚）。

## 四、模块设计的内容次序：核心内容前置，守卫件后置 ^anc-module-content-order

（本节次序为原则性决策，2026-08-08 作者定；"模块依赖"元素为同日 hopkb 九模块实撞后作者补定。）

**文档开头几屏是人（与收链 Agent）注意力的黄金位**——必须放模块的核心内容，不放机读守卫材料，而且**必须说人话**：先用平白语言讲清"这是什么、干什么用、对谁有什么承诺"；术语和出处只作补充说明，放在括号里，不进正句。判据：不了解内部实现的读者读完前几屏，能说出这个模块对自己有什么用——做不到就是写给自己看的，不是写给读者的。锚点约束、版本行、继承声明是**机读守卫链**的定位符：它们保证链可审计，但不承载理解——放在最前面浪费人的注意力（注意力经济在文档结构上的直接推演）。

**核心内容五元素**（文档前部，按此序；各元素的形态要求就地写全——2026-08-08 作者定"规定随元素走，不设集中细则桶"）： ^anc-module-expression-rules

**0. 定位与边界 = 模块是什么、管什么**（紧贴文档开头）：

- **定位句用户视角先行**：第一段回答"用户来这里能得到什么"——用该模块的直接用户（人/调用组件/Agent）的语言讲功能与承诺；实现手段（算法、流水线、内部结构）退居次段"实现路径"。反例：定位第一句就是"多路召回+RRF融合+折叠分流"——全是手段，读者不知道对自己有什么用；
- **边界声明说人话、列表展开**："负责"与"不碰"各自独立小节、逐条列表项，禁止分号串行聚成一坨。具体要求：
  - 每条先用平白语言讲"这是件什么事"，需要术语或出处时放在括号里补充；
  - 每项"不碰"标注去向：由哪个模块承载，或者完全不在本项目范围内。

**1. 依赖 = 模块在秩序中的位置**：依赖谁（下行，到接口粒度）、被谁依赖（上行消费方，含经工具面的间接消费）、禁止哪些边（各带依据）——收链 Agent 打开单份文档即知自己在依赖秩序中的位置，不必回架构翻全局图（六条本质要求第 5 条的文档落点）。

**2. 功能 = 能力契约（trait 形式）**：模块对外提供什么能力——模块存在的理由，第一屏就要看到。写法：

- 节首一句总注"本节各 Spec 均为能力契约（Spec without Steps），由 X 组件实现（impl）"；
- `# Spec: <中文名>` 行保持干净——trait 身份由章节标题承担，禁止行尾贴 `# trait: xxx` 类标签；
- **Id 行带函数原型签名**：`Id: <id> (参数: 类型, …) -> 返回类型`——传统函数原型一眼可见；Inputs/Outputs 仍为权威展开（签名是索引不是替代）；
- `Goal:` 后接 `>` 展开行说明语境与调用方；
- **Inputs/Outputs 每参数必带 `#` 一句话说明**（命名忠实"每成员一句话"在参数上的直接应用）。

**3. 类型 = 契约的承载体**：承载这些能力契约的关键类型——契约靠类型成形。写法：**字段列表逐条展开**，每字段独立列表项 `- 字段名: 类型  # 一句话`——禁止顿号串行；嵌套结构逐层缩进展开。

**4. 关键逻辑 = HopSop**（有则必到位，无则不硬造）：关键任务的逻辑流程（[[HopSop标准作业流程]]）——能力如何达成的关键支撑。纯类型/常量模块、薄适配层可以没有关键任务逻辑，不为凑件硬写。写法：**契约-实现 Id 配对**——流程块带**完整 Spec 头**且与其能力契约**同 Id**（无 Steps=契约、带 Steps=实现骨干），头内 `>` 注"契约与约束见上节同 Id 能力契约；此处只展开控制流"；光秃编号流程（无 Goal/Inputs/Outputs 语境）禁止。

（元素 0-4 的写法要求均为 2026-08-08 作者在 hopkb 九模块实撞中逐条锤定。）

**五元素的表达语言 = HopType**（2026-08-08 作者定）：契约与类型都用 [[HopType体系]] 表达——能力契约用 **trait**（Spec without Steps：Goal/Constraints/Inputs/Outputs），组件类型用 **struct**（身份、状态字段、能力边界），行为绑定用 **impl**。不另造描述格式，也不直接堆宿主语言（TS/Python）签名当设计——宿主语言类型是代码层落点，设计层用 HopType 保持环境无关（单个组件类型的描述细则见 [[工程实现链规范#^anc-meta-hoptype-spec]] 四要素）。

**守卫件后置**：出口符号表、版本行、根锚点继承声明、架构视图登记等移到文档**后部专节**；`^anc-*` 锚点随其所标注的章节就近存在（锚点本身不挪，挪的是以锚点为主体的成块守卫材料）。存量设计文档**不强迁**，新建与大改时按本次序执行。

## 五、设计层必备件（模块环完整性清单） ^anc-module-artifacts

模块不只是代码组织——**在设计层必须有显式存在**，缺任一件即模块环不完整。按内容次序（§四）分两组：

**A. 核心内容件（文档前部）**：

| # | 必备件 | 内容 | 时机 |
|---|---|---|---|
| 1 | 定位与边界 | 见 §四元素 0（用户视角定位+人话边界清单+"不碰"标去向）（`^anc-struct-<模块名>` 定位锚点随节就近） | 创建时先行 |
| 2 | 模块依赖 | 见 §四元素 1（下行/上行/禁止三段；全局依赖图管整体无环，本件管单份自足） | 创建时先行 |
| 3 | 能力契约 | 见 §四元素 2（HopType trait；Spec文法/Id签名/参数注释） | 创建时先行 |
| 4 | 关键类型 | 见 §四元素 3（HopType struct 按四要素；字段逐条展开） | 创建时先行 |
| 5 | 关键任务逻辑流程（**可选**） | 见 §四元素 4（HopSop缺省档/HopSpec精确档；契约-实现同Id配对；无则不硬造） | 有则创建时先行，演进同步 |

**B. 守卫链件（文档后部专节，机读为主）**：

| # | 必备件 | 内容 | 时机 |
|---|---|---|---|
| 6 | 对外接口清单【封闭】 | 出口符号表（符号/种类/出口文件/消费方/稳定性），表外即内部 | 创建时先行 |
| 7 | 版本行 | 模块语义化版本一行（当前版本+一句稳定性口径；演进流水不进文档，git log 为权威——2026-08-10 作者定） | 创建时先行，演进同步 |
| 8 | 根锚点继承声明 | 本模块因哪些概念锚点存在、受哪些元规范义务约束 | 创建时先行 |
| 9 | 契约锚点成对 | 每个设计锚点（`^anc-<类别>-<名>`）在代码侧有 `@a:` 落点、关键行为在测试侧有 `@v:` 落点——不悬空 | 创建与演进同步 |
| 10 | 架构视图在场 | 模块名在全库三视图（Doctree 模块索引 / ARCHITECTURE / 模块盘点）可见，与模块本体同一次改动更新 | 创建与演进同步 |

**根锚点继承声明的 why**：继承不声明，漂移无对照——模块与根的关系只存在于脑中时，根变了没人知道该核对谁。

**模块依赖件的 why**：第 5 条本质要求此前只有全局落点（架构依赖图），没有模块级落点——hopkb 九模块实撞中九份全漏，证明"要求不配必备件=必然漏"（守卫规范"显式覆盖"原则在必备件清单上的应用）。

## 六、生命周期三段 ^anc-module-lifecycle

**创建**：设计先行——核心内容件先于 `src` 存在；全部件与代码/测试**一次改动交齐**（动作协议=chain-enforcement 八件单），不许散落多 commit 事后补。

**演进**：接口变更驱动版本，规则见 §七（模块演进——本规范收拢自元规范同名节，2026-08-08 作者指出拆分遗漏后补齐）。

**拆分/合并**：设计级决策——Agent 依信号（收链装不下/测试跨关注点/新特性无处安放/接口被迫扩大/分发需要）**发现并提案**，人拍板；无信号不提案，杜绝"为整洁而拆"。

## 七、模块演进：接口稳定性分级与破坏性变更 ^anc-module-evolution

本规范其余各节讲**静态一致性**（某一时刻各层对齐）。但模块有生命周期：接口会变、依赖会变、序列化格式会变——**演进必须受控，破坏性变更不能静默发生**。（原文与 `^anc-meta-module-evolution` 锚点在 [[工程实现链规范]] 原位保留；本节为语义权威。）

**1. 版本号是每个封装单元的通用属性，分层但同规则**【契约】：版本号不是"包独有"——每个封装单元各自带一个版本号，由**该单元自身边界的接口兼容性变化**驱动，遵循同一套语义化版本规则。区别只在边界，不在规则：

- **包级版本**：封装单元=系统对外边界，驱动它的是对外契约（命令与参数、响应结构、持久化格式——外部使用者依赖的面）；
- **模块级版本**：封装单元=单个模块边界，驱动它的是该模块对外暴露的接口（被其它模块依赖的签名/类型/语义）；
- **无特殊联动**：模块版本不"冒泡"到包版本——只有改动触及对外边界自身的契约时，包版本按其自身规则升。两个边界各自独立判定，不是联动机制；
- 版本号必须与接口兼容性真实挂钩、不得空转——挂钩的核查机制即第 2 条的版本-契约互锁。

**2. 语义化版本规则（MAJOR.MINOR.PATCH，所有封装单元通用）**【契约】：

- **MAJOR**：破坏本单元接口契约（删/改签名、改语义、格式不兼容）。**0.x 阶段**视为未承诺稳定，破坏性变更可走 MINOR，但仍须经决策；1.0 起 MAJOR 才真正锁死兼容承诺；
- **MINOR**：向后兼容地新增能力，旧调用方不受影响；
- **PATCH**：不改契约的修复；
- **物理记载**：模块级版本记在模块设计文档（守卫链件第 6 件，与该模块契约同处）；包级版本记在包的对应位置；
- **版本-契约互锁**：改版本号的提交必须同时改出口契约，出口契约不变则版本不动——两者互为核查锚（可机检）。

**3. 破坏性变更 = 原则性决策**【契约】：改稳定接口影响面大、改了系统对外行为——必须**人拍板** + 兼容策略显式三选一：并行支持旧接口一段（写明移除条件）／提供迁移／直接断并升版本。**禁止 Agent 顺手加散落的"兼容旧写法"补丁**而不经决策点——临时兼容会无声累积成技术债，且无人知其何时可移除。

**4. 持久化/序列化格式带独立版本轴**【契约】：`format_version` 是与代码语义版本**正交**的格式版本轴（整数，格式破坏式变更才 +1）。带格式版本的数据必须显式选定策略——"破坏式不兼容"（读旧版明确拒绝+提示重建）或"提供迁移"（升级读函数）；选哪个是依赖驱动决策，随分发/用户数据存活需求复审。

**5. 偏差标注是前向演进信息**【说明】：`v1 偏差` 不只标"现在没做"——补全该偏差若会改动接口，应同时标注"补全后接口如何变、哪些下游受影响"，让偏差同时是演进路标。

## 八、模块归属标注：横向环的代码侧落点 ^anc-module-trace

纵向追溯链沿抽象度（概念→设计→代码→测试），模块归属是**横向**的：把每个代码/测试文件**显式绑定到所属模块**，让"模块"从脑中的概念变成代码里**可机检的事实**。复用 `@a:`/`@v:` 同一套代码注释锚点风格。（原文与 `^anc-meta-module-trace` 锚点在 [[工程实现链规范]] 原位保留；本节为语义权威。）

| 标注 | 用在哪 | 语法 | 含义 |
|---|---|---|---|
| `@module:` | 每个 src 文件、单测文件 | `// @module: <模块名> ^anc-struct-<锚点>` | 声明本文件归属哪个模块（指向该模块的设计定位锚点） |
| `@module-deps:` | 集成测试（跨多模块） | `// @module-deps: <模块a>, <模块b>, …` | 声明本集成测试依赖/验证哪些模块 |

规则四条：

1. **每个 src 文件恰好属于一个模块**（模块按关注点划分可含多文件，不强制 1:1），文件头一行 `@module:`；
2. **单测文件**与其被测 src 同模块；
3. **集成测试**不属单一模块，改用 `@module-deps:` 列真实依赖（从 import 推导，不漏不冗）；
4. 标注置于文件头部，与既有头部注释并列。

**横向审计三维度**（补充纵向追溯链）：①每个 src/单测文件都有归属，无遗漏；②每个标注指向的模块真实存在（有对应 `^anc-struct-*`）；③集成测试声明的依赖与实际 import 一致。三条均可机检。

## 九、与工程链其它部分的关系 ^anc-module-chain-relation

- 纵向链（概念→设计→代码→测试）管**忠实传达**；模块环管**封装完整**——纵向每环都齐、横向不登记，链仍不完整；
- 模块是收链的**天然单元**：行为宪法"收链前置"在改模块时的具体形态就是"拉这个模块的定位章节+接口清单+专属测试"；
- 守卫体系对模块环的机检覆盖：边界违规/出口注释/锚点悬空/三视图在场/版本-出口互锁——机检覆盖不了的（边界声明质量、流程表达是否达意）靠评审。
