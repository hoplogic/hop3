# HopSpec 错误处理机制

## 设计哲学：授权与上报

对普通人，**异常的语义**贴近直觉——它就是人类组织处理失败的方式：干活的人失败了不必自己兜住一切，失败自动上报，由有权限、有更大上下文的一层决定怎么办。但**异常的语法**（try/catch 块、异常类型层级）是纯程序员概念。显式错误处理（每步之后写"如果坏了怎么办"）更糟：三行正事七行防错，主流程被淹没。

HopSpec 取异常的语义、弃异常的语法——**失败处理不写在流程里，而是挂在结构上**：

- `[subtask retry=3]` 读出来就是"这摊事，这个组负责，给三次机会"——事务边界即职责范围，retry 预算即授权额度；
- 预算耗尽即"报给上一级"——容器 fail 后继续沿结构向上找下一个事务边界；
- 调用链顶端的人是终极决策者。

spec 读起来像一张职责表而不是一段程序。在此之上的第二原则：**修复优先于回滚，修复优先于放弃**——执行者是 LLM agent，具备理解失败原因并换策略的能力，因此每一层拿到的失败不是"重试或放弃"二选一，而是四档由高到低可信的修复阶梯（见下）。修复自由度严格限定在策略层——改 HOW 不改 WHAT，`Constraints`/`[check final]`/`Outputs` 是不可绕过的完整性约束。

## 两条线：错误走状态机，值空间只有值

HopSpec 语言层没有 try/catch、没有异常值、没有 Result 类型——**错误的原子单位是步骤，不是表达式**。

**错误线**：唯一载体是步骤状态机的 `fail(reason)`。入口四类：

1. **执行体报告失败**——执行者明确报告干不成（失败上报是每种 runtime 载体驱动协议的固定通道，通道形态属设计层）；
2. **check 判 false**——验证算子裁定产出不达标（主动质检入口）；
3. **计算异常**——步骤 body（act/commit 内嵌的 hop_python 执行体，见 [[HopSpec V3核心规范]] hop_python 节）或 case 条件里的类型错误、非法下标：程序错了就是这一步失败（body 算错 → 本步 fail；条件算错 → branch fail）。不折 None 继续跑——那是教义外的第三通道；
4. **引擎守卫**——超时、产出反复不符声明结构、预算耗尽等资源/协议护栏。

宿主运行时的异常只在引擎内部承载，出口统一折为步骤 fail，**绝不穿出语言面**。静态可查的（语法、变量存在性、枚举成员、类型路径）全部装载期拦截，能漏到运行时的基本只剩值内容问题——那正该让修复阶梯拿着失败原因去修。

**值线**：`None` 是普通的合法值，同 Python。来源只有两种：显式重置（`= Null`）、声明未产出（分支未走）。它不携带错误语义，**没有"消费 None 自动 fail"的闸**。下游拿到 None 是业务情形：条件探测（`x == None`）走降级、执行 LLM 看着 None 输入自行斟酌、或 check 拦住不合格产出。

**fail 是函数级的，与异常同构**：一次 fail 只有两个去向——被某层事务边界接住修复（重试阶梯），或者穿透全部边界、**终止整个 spec 实例**（未捕获异常终止函数）。不存在"失败了还继续往下跑"的第三态。因此"失败影响下游"的问题在语义上不存在：下游步骤永远不会在一个未被修复的失败之后运行——要么失败被修好、下游看到的是修复后的正常产出，要么执行已经终止、下游根本不运行。唯一的显式例外是 parallel 的部分失败语义（见「升级链」节末）——那是作者选用 parallel 结构时显式选择的集合语义，不是引擎的失败容忍缺省。

## 失败记录（FailRecord）：fail 信息的承载体

fail 不是一个布尔位，它携带信息；信息的唯一承载体是**失败记录（FailRecord）**——错误模型里最重要的数据结构，异常机制里 exception 对象的对应物。四个字段：

| 字段 | 含义 | 谁用它 |
|------|------|--------|
| **失败步骤** | 谁败了 | 升级链定位事务边界的起点；人定位问题 |
| **reason** | 真因，人可读、供 LLM 理解失败 | 修复阶梯的核心输入——"理解并修复"理解的就是它 |
| **fail_kind** | 分类：`error` / `lack_of_info` | 路由修复路径（第一个分叉，见五要素·分类） |
| **轮次** | 同一事务边界内第几次失败 | 带反馈重跑知道"这是第几次、每次错在哪" |

三条性质：

- **逐轮累积，不覆盖**——每轮失败各自留记录，形成失败历史；修复阶梯第 1 档注入重跑上下文的正是这份历史；
- **随实例状态留存**——不是瞬时事件，实例存续期内随时可取（升级链、修复阶梯、caller 事后读账都靠它）；
- **跨界加壳，内核原封**——跨 call 边界传递时不重造：子实例的失败记录原封作内核，外加跨界壳（callee spec 标识、子实例引用）。"内核字段必须原封"是机械判据，杜绝驱动方自由文本转述（见「call 边界」节）。

与 HopLog 的分界：失败记录是**执行态数据**（参与修复决策）；HopLog 是**只读观测流**（给人与审计看）。同一次失败在两边各留痕，但去向与职责不同（见五要素·观测）。

## 步骤 fail 的五要素

`fail` 不是布尔标记，是五要素的复合语义：

1. **判定**——四类入口（上节）；
2. **状态**——两件事：步骤 `running → failed`（终态）；**失败记录**落档（承载体定义见上节）。**不碰值空间**：fail 不清理、不回滚——失败步骤与同轮前序步骤已写下的变量、做到一半的工作，引擎都不动（只擦失败节点自己是半吊子清理，比不保证更糟），残留的处置归 spec 作者（初值 `= Null` 重置、重跑覆盖、rollback 扩展）；
3. **分类（fail_kind）**——`error`（干砸了）走修复阶梯；`lack_of_info`（缺知识）走补充检索后重试。**分类决定修复路径**，这是"理解并修复"对"机械重试"的第一个分叉；
4. **升级**——沿事务边界逐级上报（下节）；
5. **观测**——失败事件（reason/fail_kind）实时入 HopLog，给人与审计看的只读轨迹：哪步败了、第几轮、每轮败因，事后可完整复盘。它不参与执行——修复用的失败反馈走的是第 2 要素的失败记录（升级链与修复阶梯从那里取，见下节第 1 档"失败原因注入重跑上下文"），两条通道各司其职。

## fail 之后：升级链与修复阶梯

步骤 fail 后引擎走固定四步：

1. **就近找事务边界**：沿祖先找最近的 `subtask`/`case`（唯一携带 retry 的容器；**subtask 总是内置事务边界**，retry 缺省 3）。找不到 = 未捕获失败，实例终止（见「未捕获失败」节）；
2. **查预算**：`retry=N` 是该容器的**总失败预算**——容器内任何 child 的任何一次 fail 扣同一预算。耗尽 → **先看兜底**：容器声明了 `[on fail]` 失败兜底块（[[HopSpec V3核心规范#^anc-step-on-fail]],2026-08-21 作者立）→ 执行兜底 children,正常走完=失败被消化、容器按 done 收场、主线继续（兜底块自身失败不再兜,照下条上浮）;无兜底（或兜底也败）→ 容器自身 fail，**容器作为"一个步骤"递归走第 1 步**找它的外层事务边界——这就是逐层上报的机制本体（嵌套 try/catch 语义：外层接手重跑时，内层事务边界的预算计数复位——外层给子树全新一轮机会）。递归到顶仍无边界 → 未捕获失败，实例终止（见「未捕获失败」节）；
3. **预算未尽，按可信度降级修复**（四档阶梯）：
   - **第 1 档·带反馈重跑**（首次失败）：结构不变从头再走，失败原因注入重跑上下文——执行者知道"上次错在哪"，非机械盲跑。便宜、最可信（结构是作者写定测过的）；
   - **第 2 档·选预声明备用链路**（adaptive、有匹配时）：按 `(spec_id, step_id, 错误模式)` 查预声明备用链路库，选预先写好测过的备用 children——是选择不是生成，高可信；
   - **第 3 档·基于备用链路重规划**：有脚手架地改，中可信；
   - **第 4 档·从零重规划**：LLM 分析失败自由重排 children——低可信兜底，产物必须经 HopLog 提报沉淀（渐进固化：下次同错命中第 2 档）。
   无 adaptive 只有第 1 档反复用。无论哪档，交付契约（`+ →`）与 `[check final]` 不可改——改策略不改目标；
4. **重跑是全新一轮**：容器子树从头再走（具体状态复位机制属设计层）。新一轮看得见的历史是**失败与重试本身**——上次错在哪、这是第几次，经反馈注入重跑上下文；而不是上一轮对世界的触达结果——工具调用等对外交互重新发生，不复用旧结果（旧结果可能正是失败的成因）。**变量自然保留**——上一轮残留是下一轮修复素材（`last_err` 反馈模式的基础）；需要干净起点的变量，作者以初值声明（`= Null`）每轮重置。

与 Erlang supervisor 对比：supervisor 只能重启相同进程；这里每一层拿着失败原因换策略修——不是重启，是修复。

**parallel 的部分失败是显式集合语义**（唯一例外）：parallel 容器内一个 child fail 不打断已在跑的兄弟（各 worker 独立），失败 child 不贡献收集元素（列表乱序、槽位无归属——部分失败 = 列表变短），失败记录照常记账；部分结果可否接受由 join 后的消费步骤裁量。这是作者选用 parallel 结构时显式选择的语义（集合操作天然是尽力而为），不改变"fail 是函数级"的总则。

## 未捕获失败：实例终止（函数级 fail）

一次 fail 沿事务边界上报，当再也找不到边界接手时——**实例立即终止、判 failed、上报 caller**。与未捕获异常终止函数完全同构：后续步骤不再执行，不存在"失败了还继续往下跑"的形态。两条到达路径，同一结局：

- **一开始就没边界**——失败步骤的祖先里没有任何 subtask/case（失败点挂在 spec 顶层，或只被 loop/branch 这类非事务容器包着）。典型如"1. 取数 2. 分析 3. 出报告"式的平铺 spec：作者没把步骤组进 subtask，等于没为它们声明失败处理职责，升级链第 1 步就找不到边界；
- **耗尽到顶**——有边界，但最外层事务边界的预算也烧完，容器自身 fail 后再无外层可报。

终止时值空间不清理（fail 不碰值空间）：失败点之前已产出的变量都在。交付给 caller 的因此是"failed + 失败记录 + 部分产出"——失败点之后承诺的 Outputs 缺席（未产出），caller 读失败记录与部分结果自行裁量（跨 call 边界的结构化传递见下节）。

要点反转提示：失败中断执行是**缺省**（异常语义的本义），不需要作者做任何事；作者要显式表达的是相反方向——**要容忍失败**才需要动结构：包事务边界（给修复机会）、用 parallel（集合的部分失败语义）、或用 branch/条件把"可能失败的探测"降为业务分支。

## call 边界：异常的跨函数传播

`call` 是函数调用，也是失败的跨实例边界。语义对称于成功路径：

- **成功**：子实例 completed → 引擎按 output_mapping 从子实例回填父变量（机器通道）；
- **失败**：子实例 failed → call 步骤 fail，**子实例的失败记录加壳随界传递**——原封的失败记录（失败步骤/reason/fail_kind/轮次）加上跨界壳（callee spec 标识、子实例引用）。不是驱动方的自由文本转述（那相当于 catch 到异常却丢了 stack trace，只剩一句人工总结）；
- **fail_kind 跨界继承**：子实例因 lack_of_info 失败 → 父层先用自己的 KnowledgeProvider 补（逐层自治上升），不当普通 error 烧重试预算；
- call 步骤 fail 后走 caller 侧标准升级链——**重跑 call = 重新调用整个子 spec**；
- **confirm 不在此列**：授权暂停不逐层上传，直达有权决策者（"有权"是全局属性非栈属性）。

监督链全貌：subtask 局部修复 → 耗尽上报 caller → 每层 caller（有推理能力的 agent）在更广上下文修复 → 顶端人类终极决策（重试/跳过/终止）。这是 catch-reason-repair-or-escalate，不是 catch-and-rethrow。

## 事务与补偿（扩展，未实装）

> ⚠️ 本节为规划中的扩展设计（[[HopSpec V3扩展-事务与补偿]]），`* rollback:` 文法与 `tx` 属性**当前 parser/engine 均未实现**——读者勿当现行能力。

核心错误处理覆盖 act（可安全重做）与 reason/check（纯推理）。commit（不可逆副作用）的失败处理由两种扩展模式承接：

- **rollback 尽力补偿**：commit 节点声明补偿动作，下游失败时已完成的 commit 逆序触发补偿（best-effort，已被外部消费的副作用可能无法撤销）；
- **tx 事务原子化**：subtask 声明 tx，内部 commit 要求原子性——数据库 commit 走原生事务，非数据库走补偿兜底。

| 场景 | 机制 | 策略 |
|------|------|------|
| act/reason 失败 | 四档修复阶梯 | 换策略重做 |
| commit 失败需撤销已完成操作 | rollback 补偿（扩展） | 逆序撤回 |
| 多 commit 需原子性 | tx 事务（扩展） | 原生事务+补偿兜底 |
