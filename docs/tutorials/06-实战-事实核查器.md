# 教程 6 · 实战：一个事实核查器的完整解剖

**目标**：逐段读懂 `examples/hop-fact-check.md`——一个真实可用的文档事实核查器，看 03/04/05 三篇讲的零件（把关闸门、确定性计算、并行遍历）怎么组装成一台完整的机器。
**前提**：完成 [[03-探索与提交]]、[[D10-hop_python计算体]]、[[05-并行与遍历]]（本文假设你认识这些零件）。

## 它干什么、为什么值得抄

给它一份文档，它把每个**事实断言**（可查证的）和**推演结论**（从事实推出来的）逐条挖出来，给你一份速览清单，然后**并行**逐条核查——事实点搜外部依据并给来源打可信度标，推演点做前提溯源 + 推理谬误审查——最后汇聚成一张二维判定报告。

**热身（30 秒，装过 `--demo` 就能跑）**：先用演示版找体感——它只核一级事实（可直接查证的断言），流程短：

Claude Code 命令：

```
/demo-fact-check 核查 ~/.claude/skills/demo-fact-check/fact-check-sample.md
```

Codex 命令（skill 装在项目内）：

```
$demo-fact-check 核查 .agents/skills/demo-fact-check/fact-check-sample.md
```

**本篇解剖的是完整版** `examples/hop-fact-check.md`（在项目仓库，未随 npm 包）——因为本篇要讲的四个进阶件（自查回路、推演分流、机械点名、二维判定）恰恰是演示版为了简短删掉的那些。示范输入 `fact-check-sample.md` 是一篇咖啡与健康的短文，**故意埋了可核实的事实点和一个有跳跃的推演**——最后一段从"咖啡不致癌"跳到"孕妇和心脏病患者大可放心"。演示版核不出这个跳跃（它不管推理）；完整版抓它：

Claude Code 命令：

```
/hopspec run examples/hop-fact-check.md --params '{"doc_path": "examples/fact-check-sample.md"}'
```

Codex 命令：

```
$hopspec run examples/hop-fact-check.md --params '{"doc_path": "examples/fact-check-sample.md"}'
```

这个 spec 值得当模板抄，因为它把"LLM 干活不可靠"的三大坑全部用结构堵死了——而且**每一处堵法你都刚学过**。下面按执行顺序解剖。

## 解剖 1：提取环节——"自查回路"怎么写（步骤 1-2）

天真写法是一步 `[reason]` "提取所有核查点"——LLM 漏了你不知道。它的写法是一个**带反馈通道的重试回路**：

```
1  [act]              初始化 extract_gap = ""        ← 反馈通道，先置空
2  [subtask retry=2]  提取并验收
   2.1  [act]         读文档、生成带行号分析物
   2.2  [check]       文档长度闸（超 30000 字拦在提取前）
   2.3  [reason]      提取（← doc_content, extract_gap）
   2.4  [check final] 验收完备性（→ extract_ok, extract_gap）
```

机制拆开看：
- `2.2 [check]` 是带 body 的机械判定：超长文档在昂贵的 LLM 提取步**之前**就被拦下，失败信息里带分拆指引——闸门放在贵步骤前面，白跑的成本省下来；
- `2.4 [check final]` 逐段扫原文核对清单是否穷尽——**不完备就 `extract_ok=false` 并把漏项写进 `extract_gap`**；
- check 失败触发 subtask retry → 2.3 重跑，而这次它 `← extract_gap` **读到了上轮漏了什么**，定向补齐而不是从头再来；
- `retry=2` 封顶，防无限循环（首轮 + 2 次重试）。

这是 [[05-并行与遍历]] 没讲的进阶件：**check final + 反馈变量 = 自我验收回路**。LLM 第一遍漏没关系，验收的也是它，但验收有原文对照、有明确判据（"是否有可查证断言未列"），比"一次做对"可靠得多。注意反馈变量 `extract_gap` 在步骤 1 用 `[act]` 显式初始化——变量声明是 spec 里可见的一步，不是魔法。

## 解剖 2：清单速览——信息呈现而非确认停点（步骤 3）

```
3. [act] 生成核查点速览与统计
```

清单在扇出（并行核查）之前给你过目——首行统计值（总数/事实/推演各几个），后接每点一行。注意这是**信息性呈现，不是确认停点**：执行不停下来等你答复，你看到清单不对可以随时中止。这个设计经历过一次翻案：早期版本这里是 `[ask]` 确认停点（人批了清单才继续），实际使用发现清单动辄几十条，逐条人审意义不大——步骤 2 的自查回路已经把完备性把住了，人在这里只需要"看一眼有没有明显跑偏"的机会，不需要被强制拦下。**什么时候用 ask、什么时候只做呈现**，判据就是这个：人的答复会改变后续执行吗？会（要人给值、给决策）→ ask；不会（只是知情）→ 信息性步骤，别拿停点打断人。

## 解剖 3：并行核查——四层结构一次看懂（步骤 4）

这是全 spec 最厚的一段，四层嵌套，每层只干一件事：

```
4      [loop for-each point in points, collect check_item into check_result]
4.1      [subtask retry=5 parallel]          ← 并行 + 单点可重试
4.1.1      [branch]                          ← 按点类型分流
4.1.1.1      [case point.type == "fact"]     ← 事实点：搜索 → 来源打标
4.1.1.2      [case point.type == "inference"]← 推演点：前提溯源 → 谬误审查
```

- **for-each + collect**（[[05-并行与遍历]] 写法一）：引擎数数，一个点都漏不掉；结果收进 `check_result` 列表；
- **`parallel` 标在 4.1**（循环体，不是循环头）——每个点派一个 worker，边遍历边并发；
- **`retry=5` 也在 4.1**——失败单元是"这一个点"，某个点搜挂了重试它自己，不牵连别的点；
- **branch/case 分流**：事实点和推演点核查路径完全不同，用 `case` 的确定性条件（`point.type == "fact"`）分流——这是 [[D10-hop_python计算体]] 讲的"确定性条件"的容器级用法：分流不靠 LLM 判断，靠字段值；
- case 内部都是**搜索 → 评估打标**两步，四个 worker 步全是 `[act free]`（自由任务档——搜什么关键词、怎么择优收依据，留给执行 LLM 裁量），其中搜索步各带一行 `- 工具: web_search` 授权（[[08-接入MCP服务]] 讲的规矩：free 步骤要用外部工具，spec 作者逐步点名授权）——搜索失败重搜无成本，正是 [[03-探索与提交]] 讲的可安全重试的探索。

乱序归位靠结构而不靠散文：worker 的产出 `check_item` 是一个 **CheckResult 结构**（Types 节定义的八个字段：id/line_ref/claim/verdict/credibility/validity/evidence_summary/conclusion），其中 `id` 字段照抄 point.id——并行是乱序收集的，靠字段自带编号对号入座，不靠顺序。更妙的是 verdict/credibility 两个等级字段声明为 `enum`，**引擎按 schema 强制校验**：LLM 把可信度级别写错（比如自造一个 "maybe"）当场被打回重来，四级标法不再靠 LLM 散文自觉。写自己的并行 spec 时抄这一手：核心判定进结构化字段 + enum 锁词表。

## 解剖 4：汇聚环节——LLM 汇总 + 机器点名（步骤 5）

汇聚报告又是一个自查回路（5.1 汇聚 ↔ 5.4 check final + `report_gap` 反馈），但中间插了两步值得细看：

```
5.1  [reason] 汇聚报告
5.2  [act]    机械核对存在性与降级项      ← 亮点
5.3  [reason] 审查降级项的合理性
5.4  [check final] 验收
```

**5.2 是全 spec 最漂亮的一步**：LLM 汇总长列表最容易"悄悄丢两条"，它不跟这个毛病讲道理——用一个纯 `[act]` 做机械核对，而且因为 worker 产出已是结构化的 CheckResult，核对全程**字段直读**：降级项判定就是 `r['credibility'] == 'questionable'` 这样的字段等值比较（早期版本在结论散文里做子串检索，散文顺带写一句"并非 questionable"也会被误捞——结构化后这坑填了）。缺失还分成两类，语义完全不同：**missing_in_report**（有核查结论但报告漏汇了——重汇能修）和 **unchecked_ids**（这个点压根没核出结论——核查失败点，重汇变不出结论，只要求报告如实列进"未能核查"节）。分清这两类是保命的：混为一谈会让完备性闸索要不可能的东西，重试烧光后整个 run 报废在最后一步。零推理、零漏检、零成本（[[D10-hop_python计算体]] 的核心论点：数数点名这种事，让程序做）。然后 5.3 用 `[reason]` 只干机器干不了的部分——复核降级判定合不合理。

**act 检出 + reason 审查**的搭配值得记住：机器负责"全不全"，LLM 负责"对不对"。

## 全图：三大坑对三种结构

| LLM 的老毛病 | 这个 spec 的堵法 | 零件出处 |
|---|---|---|
| 提取/汇总会漏 | check final + gap 反馈变量的自查回路（×2 处）；act 机械点名 | 05 / 04 |
| 遍历长列表会丢 | for-each + collect，引擎数数 | 05 |
| 关键决定自作主张 | 扇出前速览呈现（信息性）+ 自查回路把完备性 | 01 / 03 |

外加两条工程细节：并行结论的 `id` 字段照抄 point.id（乱序免疫）、搜不到就标 `not_found` 不编造（写进 Constraints，靠评估步的输出约束兜底）。

## 拿去改成你自己的

这个骨架换个心脏就是另一台机器：把"核查点"换成"待办事项"（提取→确认→并行执行→汇总）就是任务分解器；换成"代码文件"（列文件→确认范围→并行审查→汇总报告）就是代码审查器——事实上仓库的 anchor-audit 审计工具正是同款骨架。**提取-确认-扇出-汇聚 + 两个自查回路**，是值得默写的 spec 母版。
