# 教程 11 · Hop 流程元件：装、跑、总结、分享

**给谁**：跑过演示件（教程 01）、用 /hop 干过活（教程 04），想把好用的流程攒下来反复用、装别人做好的流程、或把自己的流程交给队友的人。
**前置**：教程 01（第一次运行）、教程 04（日常活交给 hop）。

## 一句话定位

**Hop 流程元件**（hop 里的学名叫 HopAnt）是一个装好就能用的流程：一个目录，里面有一份入口 spec、它要用的知识材料和脚本。像手机上的 app——装上、点开、用完，下次还在。

它和你已经见过的两样东西不同：

| | 是什么 | 用几次 |
|---|---|---|
| 任务卡（教程 04） | 这一次的活的计划和账，参数写死了这一次的值 | 一次，干完归档 |
| skill（Claude Code 等宿主的技能） | 一段给 agent 读的指令文本，执行靠 agent 自觉 | 反复，但没有引擎把关 |
| **Hop 流程元件** | 一份带输入参数的 spec 加它的材料，由引擎按步执行 | 反复，每次换参数，把关由引擎强制 |

教程 01 里跑的 `demo-coffee-week` 就是一个流程元件。本篇讲它从哪来、怎么跑、怎么攒、怎么给别人。整个过程你只对 /hop 说话；每节末尾的"命令行对照"给想知道底下发生了什么的人看，日常用不到。

## 它在盘上长什么样

一个流程元件是一个目录，目录名就是它的 id：

```
demo-coffee-week/
├── demo-coffee-week.md      ← 入口 spec,文件名与 id 相同
├── coffee-sales.json        ← 它要用的数据
├── knowledge/               ← 可选:知识材料,spec 引用它们
├── scripts/                 ← 可选:spec 调用的脚本
├── bootstrap.js             ← 可选:它自己的安装脚本(装运行时依赖)
└── inner_store/             ← 本机数据:适配记录、跨次运行累积的东西
```

**两级位置**。流程元件住在两个地方，结构一模一样，只是根目录不同：

| 级别 | 位置 | 放什么 |
|---|---|---|
| 项目级 | `<你的项目>/hop_tasks/ants/<id>/` | 这个项目里总结出来的流程，跟着项目走 |
| 用户级 | `~/.hopjit/ants/<id>/` | 装进来的流程，所有项目都能用 |

两级都有同一个 id 时，以项目级为准——项目级那份是为这个项目改过的版本。每一级各有一张索引 `ants/index.md`，一行一个流程元件（id、标题、目标），由 hopjit 维护，不要手改。

**可分发的部分和本机的部分**。目录里大部分东西可以原样给别人：入口 spec、知识材料、脚本、数据。两样东西只属于本机：`inner_store/`（本机的适配记录和累积数据）和 `*.orig.md`（改 spec 之前留的备份）。分享时这两样被排除在包外，安装时即使来源里带着也会被丢掉——别人的累积数据和适配记录不会进你的机器。

## 跑一个现成的

setup 缺省装了三个演示件到用户级：`demo-coffee-week`（咖啡店周报）、`demo-fact-check`（事实核查简化版）、`demo-rename`（批量改名，带确认与提交）。跑它们和跑任何流程元件一样：

```
/hop 跑一下咖啡店周报
```

/hop 收到一个不是一句话能答完的活，先读两张索引（先项目级、再用户级），看有没有哪个流程元件的标题或目标就是你要的事。命中了就跑它，不建新任务卡。你问"有哪些现成的流程"，/hop 列出两级的清单，每行带级别和适配状态。

**跑之前先核适配状态**。同一个流程元件放到不同机器上，依赖的工具、凭证、命令不一定都在。每个流程元件有一个适配状态：

| 状态 | 意思 | /hop 怎么做 |
|---|---|---|
| `adapted` | 在这台机器上核过，依赖都在 | 直接跑 |
| `never` | 装上之后还没核过 | 先核一遍再跑 |
| `stale` | 核过之后入口 spec 的头部变了，或者目录是从别的机器拷来的 | 重新核一遍再跑 |

"核一遍"查四件事：spec 声明的工具在 hopjit 配置里注册了没有、要用的凭证环境变量有没有值、卡上批准的命令在不在 PATH 里、hopjit 版本够不够。全齐就记一条适配记录（本机标识 + spec 头部的哈希），之后直接跑；有缺口时 /hop 把补法逐条告诉你，例如"`web_fetch` 没有注册到 tool_servers"，补齐之前不跑。

**工作区是你的项目，流程元件的目录只读**。流程元件是工具，你发起 /hop 时所在的项目才是它加工的对象：它读你的文件、往你的项目里写产出，自己的目录不被运行弄脏。跑起来时 /hop 会说一句"这个活在 <目录> 上跑"。

命令行对照：`hopjit ant list`（清单与适配状态）、`hopjit ant adapt <id>`（核依赖、写适配记录）。

## 装别人的

别人给了你一个流程元件目录，或一个装着几个流程元件的包目录：

```
/hop 安装 ~/Downloads/weekly-report-pack
```

规则四条：

- **缺省装到用户级**——装进来的东西一般是给自己所有项目用的。说"只在这个项目里用"，装到本项目的 `hop_tasks/ants/`。
- **全装或全不装**。一个包里有几个流程元件就装几个；其中任何一个和同一级已装的撞了 id，整单拒绝、一个都不写。原因：装了一半的状态比没装更难收拾。撞了 id 由你决定：删掉旧的再装，或者改来源里的 id（文件名和 spec 里的 Id 一起改）。项目级装一个和用户级同 id 的流程元件不算撞，那是合法的遮蔽。
- **自带安装脚本的，先看计划再跑**。有的流程元件带 `bootstrap.js`，用来装它自己的运行时依赖（比如 uv、playwright）。这是流程元件作者写的脚本，安装时 hopjit 不自动跑它，/hop 先用 `--dry-run` 让它打印打算做什么，讲给你听，你同意才真跑。
- **装完核一遍适配**。新装的流程元件状态是 `never`，第一次跑之前 /hop 会核依赖；有缺口照上一节的补法补。

命令行对照：`hopjit ant install <目录> [--scope user|project] [--dry-run]`、`hopjit ant bootstrap <id> [--dry-run]`。

## 组合起来用

任务卡或另一份 spec 里可以直接调用一个已装的流程元件，写法是一个 `call` 步骤，方括号里写它的 id 和参数：

```markdown
3. [call demo-fact-check(doc_path: draft_path)] 对初稿做一轮事实核查
  - ← draft_path
  + → check_report: report
```

`demo-fact-check(doc_path: draft_path)` 把本卡的变量 `draft_path` 传给它的输入参数 `doc_path`，`+ → check_report: report` 把它的交付物 `report` 收进本卡的变量 `check_report`。引擎按 id 找它：先找调用方同目录下的同名 spec，再找项目级，再找用户级。

**起跑时引擎先核依赖**。入口 spec 的 `## Tools` 段里声明的工具（标准工具 `web_search` 除外）必须注册在 hopjit 配置（`~/.hopjit/config.yaml` 或项目 `hopjit.yaml`）的 `tool_servers` 里；`call` 的目标必须是同目录的 spec、已装的流程元件或已注册的工具。核不过时起跑直接失败，返回 `INIT_FAILED`，带着缺了哪些工具、哪些调用目标和补法。宿主自己挂的 MCP 工具（例如 Claude Code 里装的某个 MCP）没注册进 hopjit 的同样核不过——这是有意的：同一份 spec 换到独立模式也必须找得到这个工具。

## 把干完的活总结成流程元件

这是流程元件最常见的来源，教程 04 的"总结"一节讲了全过程，这里只说要点：

- 一个活用 /hop 跑通之后，说"总结一下"或"下次还要干这种事"，/hop 把那张任务卡改写成流程元件：这一次的具体值提成输入参数，这次实战里被核验打回过的缺口写进判据，没走到的分支如实标注。
- /hop 先给你一段摘要过目——叫什么、有哪几个输入参数、分几步、哪几步有把关——然后问"按此封装成 Hop 流程元件？"，你确认后才落盘。
- 总结出来的流程元件落在**项目级** `hop_tasks/ants/<id>/`，它是这个项目的产物。
- 以后改它：/hop 先把入口 spec 备份成 `<id>.orig.md` 再改，改完校验通过、你过目确认才生效，然后重新核适配。项目级流程元件所在的 `hop_tasks/` 不进 git，`.orig.md` 是唯一的一份备份。

命令行对照：`hopjit ant pack <spec> --out hop_tasks/ants`（封装：归位目录、对齐入口 spec 头部声明的工具和命令）。

## 分享给别人

```
/hop 把 weekly-report 分享给队友
```

/hop 把一个或几个流程元件装进一个**包目录**：`<输出目录>/<包名>/` 下一个 `package.json` 加 `ants/<id>/…`。本项目总结出来的流程元件不用先装到用户级，可以直接分享。

**写包之前先过四道核对**，任何一道不过就拒绝、不写包，并指出是哪个文件哪一行：

1. 入口 spec 头部的声明和目录内容一致；
2. spec、知识材料、脚本里没有凭证的字面值（只许写环境变量名）；
3. 本机的部分（`inner_store/`、`*.orig.md`）不在包里；
4. 有演化谱系的写进谱系。

**归属标识第一次会问**。包里带一个归属标识，标明是谁的哪台机器做的。这台机器第一次分享时，/hop 会问一句："分享包会带上归属标识 `<用户名-主机名>`，用这个还是改一个？"你答过之后它记进 `~/.hopjit/config.yaml`，以后分享直接用，不再问。

**凭证扫描是尽力防线，不是保证**。第 2 道核对按三层证据综合判断：像已知厂商密钥格式的、高熵随机串、凭证类键名配上像密钥的值。证据强的直接拒绝；证据弱的包照常写，但 /hop 会把每条警告念给你，请你自己过一眼。/hop 还会转述一句免责说明：这道扫描是启发式的，不保证没有遗漏；不把密钥写进 hop 文档和代码是你自己的责任，密钥应当经环境变量取用。

**交给对方**。产物是一个普通目录。要压缩自己 `tar czf`，要放 git 自己建仓推上去——目前分享只产出目录，不经 git 或 npm 发布。对方拿到后 `/hop 安装 <目录>` 就有了，装完那边会核一遍适配。

命令行对照：`hopjit ant share <id>... [--out <目录>] [--name <包名>] [--pkg-version <v>] [--owner <标识>] [--yes]`。

## 升级与卸载

**卸载**：

```
/hop 卸载 demo-rename
```

删掉那个流程元件的目录，索引同步更新。两级都有同一个 id 时，删的是项目级那份；要删用户级那份，明说"删用户级的"。`inner_store/` 里有跨次运行累积的数据时，可以要求保留——它会被挪到 `~/.hopjit/ants-store-backup/<id>/` 再删目录。

**升级**目前是卸载加重装：同一级里已有同 id 的流程元件时安装会因撞 id 被拒，所以先卸载旧版（要留数据就带保留），再装新版，装完重新核适配。如果你改过旧版的 spec，卸载前先把改动另存——重装会以新版为准。"没改过就直接换新版、改过就让你选重新适配还是三方融合"的升级流程在概念设计里，还没有实现。

命令行对照：`hopjit ant remove <id> [--keep-store] [--scope user|project]`。

## 演化（规划中）

概念设计里，流程元件还有一个"演化"动作：在反复使用中积累改进候选，候选在实际运行里验证过足够次数后，经你审过再回写进流程元件自己的 spec，并记下谱系（从哪个版本、因为什么改来的）。这个动作**还没有实现**。现在要改一个流程元件，走上面"总结"一节最后一条的修订流程：备份、修改、校验、你过目、重新核适配。

## 上手建议

1. 先跑一遍 `demo-rename`：它带确认步骤和不可逆的提交步骤，能看到一个流程元件里的把关是怎么工作的。
2. 拿手头一件每周都要干的小活，用 /hop 跑通一次，然后说"总结一下"，看它变成流程元件；下周开同类活时，/hop 会先问你要不要直接跑它。
3. 把它分享给一个队友，让对方装上跑一次——适配状态从对方的 `never` 走到 `adapted`，就是这个流程元件真正能离开你的机器了。

想看真实的流程元件长什么样：库里 `examples/ants/hop-fact-check/` 是一个完整的事实核查流程元件（入口 spec 加示例文档）。想知道底下的设计：`docs/concepts/HopAnt概念.md`。
