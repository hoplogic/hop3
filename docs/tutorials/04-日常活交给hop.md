# 教程 4 · 日常活交给 /hop：你的计划，引擎的账

**给谁**：已经会跑现成 spec（教程 01），想把**自己手头的日常活**——调研、写报告、核对清单、多步骤的杂事——也放进引擎管护的人。
**前置**：教程 02（读懂一份 spec）。写过 spec 更好，没写过也行——/hop 的重点恰恰是"你不用先学会写 spec"。

## 一句话定位

`/hop` 把你正要干的活（或对话里已经列出来的 plan）**升格**为一份 HopSpec 跑起来：你自己驱动、自己干活，引擎只管三件事——**顺序不乱、把关不跳、进展有账**。对话断了活不死，回来一句 `/hop` 接着跑。

和 `/hopspec` 的分工一句话说清：跑**成品 spec**（别人写好的、参数要确认的）用 `/hopspec`；**现场冒出来的日常活**用 `/hop`。前者是"执行一份规约"，后者是"把活变成规约再执行"。

## 为什么不直接用对话里的 todo list

对话里的 todo list 有三个天生的弱点，/hop 逐个补上：

| todo list 的弱点 | /hop 给的 |
|---|---|
| 对话一断（压缩/关窗口）计划就没了 | 任务卡在盘上、进度在引擎账上，`/hop` 一声即接续 |
| "核对一下"这步赶时间就跳过了 | check 步引擎强制——不如实判 false 就过不去 |
| 干到哪了全凭记忆，多个活一混就乱 | `/hop list` 每个活到哪步、停在哪，一眼清 |

反过来说，**不是所有事都该进 /hop**。判据是：要不要账、要不要续、要不要把关。"3+5 等于几""这段话翻译一下"——张口就答完的，自然语言直接干；要查三个来源写成报告、要跑完六步才算数的，进 /hop。

## 六个动作就是全部用法

```
/hop 查一下X的三个来源,写成报告发给我   ← 开新活
/hop                                  ← 有当前活:续跑;没有:列清单
/hop list                             ← 手头活清单(各到哪步、停在哪)
/hop 2  或  /hop 合同                  ← 切到那个活,接着干
/hop archive 2                        ← 收起一个活(不删,历史全留)
/hop distill 2                        ← 提纯:把干完的活总结成可复用的 spec
```

像一个 todo 管理器——但每个活背后是一份可控可靠的 spec：有账、可执行、可续跑、有把关。

## 一次完整体验：从一句话到一份报告

你说：

```
/hop 调研X的现状,交叉核对后写成报告
```

接下来发生的事（你不用做任何 spec 编写动作）：

**第 1 步，agent 把活升格成任务卡**，落在 `hop_tasks/调研X现状/调研X现状.md`——一个活一个目录，材料草稿证据都住在里面。卡的核心是一段 Steps：

```markdown
1. [act free] 查 X 的三个独立来源
  + → sources: yaml  # 来源与要点

2. [reason] 交叉核对,整理要点
  - ← sources
  + → digest: text  # 核对后的要点

3. [subtask] 成文并把关
  3.1. [act free] 写初稿
  3.2. [check final] 核对:来源全覆盖、结论与要点一致

4. [commit] 发出去
  > ```hop_python
  > written = write(path: "报告/调研X.md", content: report)
  > ```
```

这就是教程 02 学过的那套语法——只是这次**写它的是 agent，不是你**。你要做的只是看一眼这个计划靠不靠谱。

**第 2 步，agent 逐步执行，每完成一步给你一行**：

```
✅ 1 查来源（3 源已取）
✅ 2 交叉核对
▶️ 3.1 写初稿…
```

**第 3 步，走到把关点，规矩变了**。`3.2 [check final]` 不是 agent 自己说"我觉得写得不错"就能过——判定会交给一个**没参与干活的新 agent** 去核（后面"阅卷"一节讲为什么）。判 false 就带着缺口说明重写，判 true 才放行第 4 步。

**第 4 步，干完收工**：报告交付给你，任务目录挪进 `hop_tasks/archive/`。历史不删——哪天想看"上次那个调研怎么做的"，档案还在。

中间任何时刻对话断了？新会话敲 `/hop`——或者直接说"继续上次的活"——从断的那步继续，这是整套机制的核心承诺。斜杠不是每句话的前缀：活跑着的时候说"继续""改一下后面的计划"都行，agent 认的是意图。只有一种情况它会先问一句：你光说了"继续"俩字、又没点名要继续什么（比如新会话开口第一句），它会先确认——"你是要继续《调研X现状》吗？上次干到 3/5 步，停在写初稿"——免得把你随口的"继续"错当成续活的指令。

## 任务卡：计划和语境住在同一个文件里

打开 `hop_tasks/` 下的任务卡，spec 段（Goal/Outputs/Steps——引擎读）之外还有几个叙事章节：

```markdown
## 背景            ← 为什么干这活、对话里已拍定的口径
## 参考            ← 材料链接、相关笔记的 [[双链]]
## 处置记录        ← 关键判断逐条追加,给下一个读者看的"为什么"(惯例名单成员,天然不进 prompt)
```

**背景和参考不是摆设——写进卡的内容章节，引擎缺省全程供给执行 LLM**。对话里定过的口径、排除项、材料指针，落进卡里就等于喂给了每一步的执行者；跨会话续跑时，新会话读卡即接手，零追问。例外是留给人读的节：处置记录（惯例名单成员，天然不供给）和任何你标了 `(不供给)` 的节——那些是流水，不进 prompt。

## 计划还没想清楚？留一个"到时候再说"

日常活经常是前半截清楚、后半截"到时候看情况"。/hop 不逼你预先想全——没想清楚的段落写成一个空的 `[subtask free]`：

```markdown
2. [subtask free] 后面的活（到步展开）
  - ← 前面的产出
  + → 交付物: text
```

底下一个子步都不用写。执行真走到这里时，引擎停下来向 agent 要计划——这时候**第 1 步的实际产出已经在手上**，拿着真材料定后半截计划，而不是开工前盲猜。两条纪律引擎强制：展开出来的计划**必须含 check**（运行时出的计划没人预审过，check 是唯一把关），**禁止含 commit**（不可逆动作必须写卡时显式声明，不许运行时临时冒出来）。

## commit 步为什么长着一段代码

上面样例的第 4 步下面挂着三行 `hop_python`——这不是装饰。**不可逆动作（发送/写正式文件/发布）必须在写卡时就用代码定死**：发什么、写到哪，执行期零裁量。引擎对没有代码块的 commit 直接拒载。为什么这么严：不可逆动作交给 LLM 现场发挥，每次重跑动作可能不同，"幂等"无从谈起——出过真事故的教训。

agent 替你写卡时会自动带上这段；你只需要知道：看到 commit 步下面的代码块，读一遍它到底要做什么——那就是这个活唯一收不回的动作。

另外两条 agent 写这段代码时守的纪律，你在核对计划时也可以顺眼看一下：跑 git 这类外部命令要指定工作目录、每一步都要检查命令真成功了（有过一次四条命令全失败、产出却报"已推送"的实撞——就是因为没检查返回码）。

## 阅卷为什么要外移

/hop 自驱有一个结构性风险：写计划的、干活的、判合格的，是同一个 agent。自己出题自己答题自己阅卷——判据写得再严，总有能绕的缝。

所以 `[check final]` 的判定**恒外移**：交给一个全新的 agent，只给它三样东西——待判产出物全文、判据原文、任务卡的背景章节。**不给执行过程叙事**——阅卷人不该被"我为什么这么做"说服，只对着产出和判据判。判定回来，执行 agent 原样提交，不改判、不软化；不服就修产出重来。

对你来说这一切是透明的——你只会注意到 check final 那步偶尔判 false 打回重做。那不是故障，**那是机制在工作**。

## 边跑边改计划

干到第 2 步发现第 3 步的思路不对？直接说，agent 会改计划接着跑。三条规矩引擎强制：

- 只能改**未执行**的部分——已做的是历史；
- `[check final]` 不许改掉或跳过——改路径可以，拆把关不行；
- 交付契约（Outputs）不许改——改策略不改目标。

"随时可改计划"的自由，是靠"把关点不可动"来定价的。

## 收活：干完的、不要了的、回头再干的

活干完，确认交付后收进 archive。活**没干完**就想收，agent 会问一句："这个活还没干完——是不要了，还是先收起来、回头接着干？"

- **回头再干**：目录挪进 archive，账保留，哪天挪回来 `/hop` 照续；
- **不要了**：账面记为已放弃再归档——不记的话账上永远挂着"进行中"，等于谎报。此时若有半成品要交付，会明确标注"这活没走完最后的核对"——没把关的产出不冒充正品。

没有 delete。收起来的活历史全留，`/hop list all` 随时可看。

## 提纯：干完一次，以后直接跑

一个活跑通了，那份任务卡就是一条**被实战验证过的流程**——但它是一次性的：参数写死了这一次的值、背景写的是这一次的语境。`/hop distill 2` 把它升格为可复用的成品 spec：

- **这一次的具体值提为输入参数**——下次跑同类活，换个参数就走；
- **实战抓过的坑写死进判据**——这次 check 打回过的缺口，成为今后每次执行的强制把关。一次性任务里"下次注意"的教训，在提纯件里变成引擎强制，这是提纯最值钱的部分；
- **没走到的分支如实标注**——这次实战没验证过的路径不冒充验证过。

产出落在 `hop_tasks/specs/` 下，给你过目确认后落定——从此这份 spec 会被反复跑，这一眼值得花。原任务照常归档，出处可溯。

提纯件不用你惦记着去用——**下次开新活时 agent 会先说一声"我先看看已有的流程里有没有可复用的"再查**：有同类就问你"拿它当底稿开？"，同意就以它为底稿建这次的任务卡（同类照抄填参、差一截就改），比从头写快，而且带着上次实战验证过的把关。你也可以随时问"哪些可以复用"，agent 会列清单。**嫌它多嘴就说"直接开"**——带这三个字的活不查现货，径直从头建卡。

不用记命令——对着干完的活说"总结一下""沉淀下来""下次还要干这种事"，agent 就会主动做提纯；`/hop distill 2` 只是要指定哪个活时的显式写法。干完收活时 agent 也会顺口问一句"要不要提纯"——常干的活值得，真正一次性的活不必。**没走 /hop 的活也能总结**：对话里直接干完的事（比如刚做完的一次代码审查），说"把刚才这个流程总结成可复用的"，agent 会从对话轨迹提炼——只是这种提纯件里的核对步骤是"该有"而不是"引擎验过"，agent 会如实标明。

## 一个真实的例子：工程开发活也这么走

/hop 不只管查资料写报告这类轻活——本库自己的工程开发就在用它。两句话就够（话术的来历与要件拆解见 [[D2-用AI做工程-AIcoding与验收]]）：

```
/hop 开工，严格按照工程链规范实现，落实设计hop三件套，
     实现时同步设计代码一致性，保持设计合理性，测试时保障正反例覆盖
```

agent 会把这批实现活升格为一份计划（读现状 → 定方案 → 设计文档先落盘 → 改实现 → 全量测试+独立核验 → 提交推送），你在进展行里看着它一步步走；核验那步由一个没参与实现的独立 AI 对着产出判——不是干活的自己给自己打分。干完想 review，同一个入口：

```
/hop 严格根据锚点做工程链review，检查设计三件套完整性，
     设计合理性，设计代码一致性，和测试正反例覆盖
```

这两类活各干完一次后说声"总结一下"，就沉淀出各自的可复用流程——下次再开同类活，agent 会主动问"有现成流程，拿它当底稿开？"，上次踩过的坑（比如"结构性改动先写最小探针验证""大改后必扫旧编号残留"）已经写死在底稿的把关里。

## 中文关键词：让任务卡全中文

步骤类型和段头有中英两套关键词，引擎完全等价——`[探索 开放]` 就是 `[act free]`，`## 目标` 就是 `## Goal`（完整对照表在语法参考的"中文关键词对照"一节）。想让项目里生成的 spec 缺省都用中文关键词，在项目根的 `hopjit.yaml` 里加一行：

```yaml
language: zh
```

加了之后，hopbuild 翻译出来的 spec、引擎序列化输出的内容都是中文关键词；不加（或写 `en`）就是英文。对话里直接说也行——"以后生成的都用中文关键词"，agent 会替你改这一行。

已有的 spec 想转语言，一条命令：

```bash
hopjit lang 路径/某份spec.md --to zh    # 转中文关键词
hopjit lang 路径/某份spec.md --to en    # 转回英文
```

转换前自动备份（同目录 `.bak.时间戳` 文件），只改关键词——变量名、说明文字、代码块一个字节不动；万一转换会把文件转出毛病，它拒绝写回、原件不动。对话里说"把这份 spec 转成中文关键词"就是在用它。

## 上手建议

第一个活选个**真实但不大**的：三五步、有一处值得核对的产出、半小时体量。体验四件事——升格出来的计划你认不认、check 打回重做的手感、中断后 `/hop` 接续、收工归档。之后你自然会知道手头哪些活值得进 /hop。

想看引擎在底下做了什么：任务目录里的卡是明文，`.hopstate/` 是引擎的账（机器读的，人不用翻）；诊断执行历史的方法在 [[D6-用HopLog诊断]]。想自己写更复杂的 spec 结构，继续主线教程 05-06。
