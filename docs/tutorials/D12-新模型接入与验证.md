# D12 · 新模型接入与验证：四层测试把关

**给谁**：要给引擎接入一个新模型（新 provider，或既有 provider 换模型）的开发者。
**与 D8 的关系**：[[D8-模型与工具配置]] 教配置**怎么写**（配置地图、分档心法），本篇教接入**怎么验**——配置写对了不等于模型能用，模型能应答不等于引擎的防线在它身上有效。

## 为什么不能"配上能跑就算接好了"

引擎对模型的依赖远不止"发请求收回答"。三个真实教训：

- **端点路径有变体陷阱**：同一个服务商可能挂多条路径，只有一条是对的。真实案例：某网关 `/anthropic/v1/messages` 走登录态网关报"未登录"、`/v1/messages` 直接 404、只有 `/api/anthropic` 前缀是 API key 通道——不逐个探，配置写错后报错完全不指向真因；
- **防线依赖响应字段的标准形态**：引擎的输出截断闸、推理烧穿检测全靠 `stop_reason: max_tokens` 这个字段；工具循环靠标准 `tool_use` 块。端点不按标准形态报，防线就静默失明——引擎不报错，只是该拦的拦不住了；
- **模型自报的身份不可信**：问模型"你是什么"得到的答案与真实调用的模型经常对不上（模型经网关转发时，自己都不知道被以什么名义调用）。身份的事实边界是**响应体里的 `model` 字段**，永远以它为准。

所以接入要分层验证。四层从便宜到贵排序，**前一层红了后面的不用跑**——每层拦一类不同性质的失败。

## 第一层：协议面探针（curl 直连，分钟级，零引擎）

验"端点说的话引擎听不听得懂"。四个探针逐个跑：

**探针 1：端点与鉴权形态。** 用最小请求试出真路径与 key 头形态（`x-api-key` 还是 `Authorization: Bearer`）：

```bash
curl -s -m 30 <base_url>/v1/messages \
  -H "x-api-key: $YOUR_KEY" -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"model":"<模型名>","max_tokens":100,"messages":[{"role":"user","content":"只回答一个词: ok"}]}'
```

判据：返回标准 message 形态（`content` 块数组 + `usage` + `model` 回报真名）。返回登录跳转、404、或非标准包裹形态都算红——换路径变体再试，全部变体试尽仍红，就是该端点不支持此协议。

**探针 2：thinking 双档。** 分别带 `"thinking":{"type":"enabled","budget_tokens":1024}` 与 `"thinking":{"type":"disabled"}` 各发一次：

- enabled 判据：响应 content 里 `thinking` 块与 `text` 块**分离**（思考不混进正文）；
- disabled 判据：端点认这个参数（不报 400），返回纯 `text` 块。

这两档直接决定引擎的推理治理链（烧穿检测、降档重试、按步路由）在这个模型上是否可用。注意 budget_tokens 别低于 1024——有的端点对更小的值报参数违约。

**探针 3：tool_use 单发。** 带一个工具定义，问一个必然要用工具的问题。

判据：返回 `stop_reason: tool_use` + 标准 `tool_use` 块（name/input 结构完整）。这是工具循环类步骤的前提——不过关的模型只能干纯推理活。

**探针 4：截断形态。** 故意给很小的 max_tokens（如 50），问一个长问题。

判据：`stop_reason` 如实报 `max_tokens`。引擎的截断检测与推理烧穿检测全押在这个字段上。

## 第二层：引擎冒烟（一个两步小 spec，五分钟）

验 provider 配置 → 请求装配 → 响应解析 → 产出收割的全链。写一个最小 spec：

```markdown
# Spec: 接入冒烟
Id: onboard-smoke
Goal: 验证新模型经引擎通道可完成一次推理步与一次机械步

Inputs:
- topic: line  # 一个词的主题

Outputs:
- summary: text  # 两句话介绍
- word_count: int  # 介绍的字符数

## Steps

### 1. [reason] 用两句话介绍主题
- ← topic
+ → summary: text  # 两句话介绍（中文,不超过 80 字）

### 2. [act] 统计字符数
- ← summary
+ → word_count: int  # summary 的字符长度

纯机械零 LLM：
> ```hop_python
> word_count = len(summary)
> ```
```

配套项目级 `hopjit.yaml` 一行 `default_model: <service_id>/<模型名>`，跑起来看终态。判据三条：run completed；summary 是干净的两句话（无围栏包裹、无思考文字混入）；word_count 与 summary 真实长度吻合（证明 LLM 产出真进了变量空间、机械步真消费到了）。

冒烟还捎带一项**指令遵从检查**：给任务加一两条明确禁令（如"不要使用工具""不超过 80 字"），看守不守。指令遵从不是一个独立度量维度——守不住基本禁令的模型直接不进第三层。

另外注意：**providers 是 server 启动期快照**——改完 `~/.hopjit/config.yaml` 要重启（或重连）MCP server 才生效。新 provider 报"service 不在 providers 内"时先查这个。

## 规格资格线：窗口与输出上限要多大才够（2026-09-19 按机制值+真机峰值盘定）

接入前先对模型规格做一次纸面筛——规格不够的模型，能力再好也只能干局部岗位。三个数各有资格线：

**上下文窗口（按目标岗位查实测水位）**。引擎每步是独立 API 调用（无对话历史累积），单步请求体量的实测峰值（ctx 水位 = input + cache 合计）按任务类型分档：

| 目标岗位 | 实测单步水位 | 窗口资格线 |
|---|---|---|
| 轻执行步（小语料活） | 30K～91K | **128K 够用** |
| 判官步（deep-validate 级） | 中件 <120K；有"八份材料全文直喂"的高水位形态在案 | 128K 可用但无余量 |
| 构建步（hopbuild2 大件） | 480KB 语料件实测峰值 181K～255K（治理后可压回 103K） | **按 256K 规划**；128K 只够治理后小件 |

已知硬墙实例：262144 窗口的端点对 267330 输入直接 400 拒。另有一条**软墙**：窗口装得下不等于跑得动——某载体实测 150K+ 单轮延迟超线性恶化、170K+ 服务端超时零产出；软墙位随载体不同（另一端点 244K 正常），接入时要自己探。

**最大输出 tokens（真机撞顶案例定线）**：

| 档 | 判据（全部实测） |
|---|---|
| 4K | **不可用**——判官步在 4096 预算下六发五发 thinking 烧穿（预算全烧思考、正文全空） |
| 16K | 轻中档可用；重档不够——大提取任务 16384 下六发全烧穿；旧引擎缺省 16384 被重档步截断实撞后才抬的档 |
| 32K | 引擎现行缺省（物理防线定位） |
| 64K | 构建/判官跑批的实配值——仍有单轮 9.1 万输出撞 65535 顶的案例，但已是可工作水位 |

thinking 型模型（思考与正文共享输出池）对这条线更敏感——8K 这类小输出上限对 thinking 型基本等于"想两步就没纸了"。

**stop_reason 如实上报是资格线不是数值线**：引擎的截断防线与烧穿防线全押 `stop_reason: max_tokens` 这个字段——端点不如实报，防线静默失明，这比窗口小更危险（第一层探针 4 就是验它的）。

**引擎思考缺省已改为恒显式（2026-09-20 五级优先链落地——接入新模型前先知道这件事）**：引擎不再"不发思考参数吃端点缺省"。每个请求的思考开关按五级链定（思考烧穿记名册 > 步骤 `@thinking` 标注 > routing_rules 的 thinking > provider 级 thinking 缺省 > 引擎内建步骤类型缺省——最后一级：act/commit 关，act free/reason/check/replan 开）。对接入工作的影响两条：①"端点缺省开还是关"从行为决定因子降级为一个需要探明的事实（探明后写进 provider 级 thinking 键做逐模型矫正——antchat 类"端点缺省关"的服务若不配，reason/check/act free 步会转为开、费用上升；配 `thinking: disabled` 即压回）；②度量探针发请求时要显式带思考参数与引擎对齐，不许再依赖端点缺省（本教程此前的 Ling 假数据一课正是端点缺省不可见的代价）。

**思考开销探测（thinking 型模型必测——不测就会把预算病误判成能力病）**：思考型模型的思考文字与正式回答共用输出预算池，而**思考量随任务规模增长**——同一模型，40 要点的提取任务实测思考 2-4.5 万字符。不实测思考开销曲线，就会出现这种故障：探针给 8K 预算测它，思考先把池子烧光、正文零字节、得分 0%——看起来是"能力坍塌"，实际是预算病（同题 64K 预算下满分；关思考后 2K 预算都够且同样满分）。探测法：挑一个中等规模任务（如 40 要点提取），三配置各 n≥2 对照——①档案预算+思考开 ②小预算+思考开 ③小预算+思考关。读数：②烧穿而①③满分 = 思考开销主导，记"思考开销 ≈ ①的 output_tokens - ③的 output_tokens"；由此定两件事：该模型跑此类任务的**最小安全预算**（思考开销 × 1.5 + 正文预估），以及**该不该关思考**（③与①得分持平 → 此类任务关思考，费用差可达 8-9 倍）。

关思考的适用面探测可以再进一步：**拿该模型思考开着测出的推理最高档任务，关着思考重发几次**。实测案例（deepseek）：12 位×12 位手算乘法关思考 4 发全对、13 位有效数字迭代长除法 3 发全对，每发只花 2-3 千 token——推理没有消失，是迁移到了正文里（模型把演算写进回答），而正文演算远比思考通道省字。读数进档案的形态：该模型"关思考白名单"能扩到哪些任务族（提取/格式转换/机械推演/纯推理演算），以及一条硬边界——工具编排步骤永远不进白名单（实测关思考后工具循环打转烧尽）。

这个探测省不得的实证：本库首版切块标定表给 deepseek 记了一整列假数据（整篇 0%、各块尺寸 25%-72.5%）——探针自设 8K 预算，思考先烧光预算正文全空。按档案预算（64K）重测后全配置满分，"deepseek 需要切块"的结论整个作废。一次没做思考开销探测，代价是一张表的数据加一个错误的适配建议。

**最大思维链长度（thinking 型模型的隐性坑）**：anthropic 协议下思考与正文共享 `max_tokens` 输出池。引擎对 thinking enabled 的步骤发 `budget_tokens = 输出上限一半`（想把思考压在预算内），但**这只在端点透传该参数时有效**——不透传的端点（实测有）CoT 长度由端点自己决定，规格页标"最大思维链 256K"而你的 max_tokens 只给 64K 时，模型一想长了整个输出池被思考烧光、正文零字节（引擎的 THINKING_EXHAUSTED 检测能兜住这个形态并变招重试，但前提还是 stop_reason 如实报）。接入时加一发 **CoT 压力探针**：必然长思考的题（如 8 位长除法）+ 故意小的 max_tokens（4096），看三种形态——思考被截且 stop_reason 如实报=可烧穿但可检测，能接；正文完整返回=端点服务端管了 CoT，更好；形态混乱=防线失明，不过资格线。

**同一模型的不同接入通道，规格可以不同**：实例——同一个模型，原生 API 市场页标 1M 窗口/128K 输出，而 claude 兼容代理通道实测 262K 窗口（267330 输入被 400 拒）/65536 输出。规格以**你实际走的那条通道的实测**为准，市场页数字只作线索（这也是"度量对象是 model service"原则在规格面的体现）。

**RPM 限额**基本不构成约束：引擎单 run 以串行调用为主，并行子实例也远到不了每分钟几百发。

## 第三层：能力面度量（半小时级，最有价值的一层）

### 先立两条原则

**原则一：度量对象是 model service（模型 × 服务端点的组合），不是模型。**

同一个模型名经不同服务端点，能力可以差到判若两物——中间层会注入系统提示、做量化、改采样参数，而这些对协议探针全部不可见（探针全绿，照样可能是另一个东西）。所以不能认为模型一样、能力就一样：每份能力画像必须绑定它实测的那个端点（档案里记 provider_ref 与端点说明），**换端点等于换被测对象，全部维度重测**，不存在"同模型免测"。

实测例子：同名 Qwen3.8-27B 在两个端点上，工具循环失控计数一个 118 次、一个 0 次；判官任务一个零产出、一个交出高质量报告。这不是一个模型的两种状态，是两个 model service（详见文末实例二的勘误章）。

**原则二：从模型的基础能力维度展开，不从引擎故障现象展开。**

引擎的失败计数（schema 打回几次、工具循环撞墙几次）是**症状**，不是能力。一个症状背后常混着多个能力（工具循环撞墙，可能是工具选错、可能是不知道何时收手、也可能是一轮贪多干太多），而且计数随引擎版本变，没法横向比。正确做法：先立能力维度，每个维度定探针与判据，引擎现象只作为"可观测指标"映射回维度。

### 模型能力维度总览

维度分两组：**通识组**（G1-G8，业界评测普遍在测的能力面，我们只把探针对准 HopSpec 步骤类型的生存前提）与**实践组**（P1-P3，本项目真机撞出来的维度，通用评测测不出，但直接决定引擎的适配开关怎么设）。

| 编号 | 维度 | 一句话说明 | 谁消费这个档位 |
|---|---|---|---|
| G1 | 推理复杂度 | 推理难度升到哪档开始出错或失控 | 判定步、重推理步的路由 |
| G2 | 任务复杂度 | 多大的活能一次做对 | hopbuild2 切步尺寸 |
| G3 | 分解与规划 | 大活拆得开、排得顺吗 | subtask free 到步展开 |
| G4 | 工具使用 | 单步内的多轮工具循环跑得好吗 | 带工具步骤的路由 |
| G5 | 结构化交付 | 按声明的字段名/类型/数量交付产出吗 | 一切多输出步骤 |
| G6 | 代码生成 | 三种目标语言（Python/SQL/HopSpec）各能写到多复杂 | act body 生成、hopbuild2 产物质量、hopfix |
| G7 | 领域知识充分度 | 目标业务领域的事实、术语、常识存量够不够 | 知识供给策略（doc-ref/@knowledge 喂多少） |
| G8 | 渐进知识获取 | 缺知识时会不会搜、搜得到、用得上（察觉→检索→筛选→使用闭环） | 检索型步骤的路由；知识自补资格 |
| P1 | 核验能力 | 把关步能路由给它吗，以什么形态 | check 步的路由与写法 |
| P2 | inline 工具耐受 | 工具在场但用不上时，忍得住不乱用吗 | 工具下发上限开关 |
| P3 | 修订落实 | 打回意见能落实到产出上吗 | 修订短卷开关 |

### 通识组详解

**G1 推理复杂度。** 测推理难度升到哪一档开始塌。塌有两种形态，但它们在同一根轴上：轻推理**答错**（正确性塌）、重推理**想不完**（失控烧穿，稳定性塌）。所以档案记的不是两个分数，而是一条"复杂度-可靠性"曲线上的坍塌点。

现成的轻量阶梯两种任务形态，考同一根轴上两种不同的推理负载：

- **乘法**（N 位 × N 位）：**直接推理**——各部分积可以分头算完再加，一遍成型；
- **除法**（2N 位 ÷ N 位，商保留 2N+1 位有效数字四舍五入）：**迭代推理**——每一位商都依赖上一步的余数，错一步后面全错；2N+1 位有效数字逼到小数位，不能整数商糊弄、不能估算。

都找"正确率 ≥90% 的最大 N"，两个数分开记档。实测迭代档普遍比直接档低（同一模型乘法 3 位、除法 2 位）——长依赖链是比单遍计算更早坍塌的负载。爬梯时每档先测 5 次，**接近边界的档必须加测到 20 次再下结论**——小样本既会冤枉（真 90% 的能力有三分之一概率在 5 次里错 1 次）也会放水（5 次全对的档，20 次可能只对 16 次）。

引擎里的对应症状：判官误判、推理预算烧穿（THINKING_EXHAUSTED）、关 thinking 后答案翻转、单步耗时异常。

**G2 任务复杂度。** 测"多大的活能一次做对"。引擎的重试机制能兜住首轮失败，但兜底有成本（轮数、费用、时延），档案要记**裸能力**：首轮就做对的任务尺寸上界。这是 hopbuild2 最直接消费的维度——构建器给某个模型出产物时，每步的任务尺寸要按这个坍塌点切分（大文档拆成多轮小提取、重步拆成轻步序列）。

度量考题两族（合成阶梯量裸能力坍塌点，真实任务阶梯量全链表现）：

**考题族一：合成提取阶梯**（`probes/extract-scaling/`，答案键机械判分，一键跑批 `run-task-complexity.mjs`）。同一任务形态（从文档提取事实点/推演点）按要素数递增，六档：

| 档 | 要素数 | 文档字节 |
|---|---|---|
| XS | 2 点 | 0.13K |
| S | 4 点 | 0.29K |
| M | 9 点 | 0.74K |
| L | 18 点 | 1.5K |
| XL | 40 点 | 3.4K |
| XXL | 80 点 | 8.5K |

每档 n=6 单发裸测（无重试无引擎），对答案键机械判分，记首轮通过率跌下去的档。任务规模恒用"要素数 + 文档字节数"两个数一起描述（同字节数下要素密度不同，难度不同）。

读数三条纪律（2026-09-19 真实卷对账后补——当时数据都在，解读方法漏了前两条；第三条是概率读数的消费出口）：

- **通过率当概率读，不只当门槛用**。坍塌不是悬崖是斜坡：某档 2/6 的含义是"这个难度上它每次做的成功概率约三分之一"——这个数直接可用于预测（配 retry=K 的任务成功率 ≈ 1-(1-p)^K）和排产（该不该派、重试给几次）。实证：真实 fact-check 卷跑两次过一次，与探针同难度带 2/6 的概率完全对上——探针早就量出来了，当时只拿它画了坍塌线；
- **任务尺寸按"实际会拆出多少要素"算，不按字节数猜**。1.9K 字节的新闻在"宁细勿漏"提取规矩下拆出 50-85 个要点——难度落在探针 XL/XXL 档（40-80 点），不是字节数相近的 L 档（1.5K/18 点）。预估要素数的方法：按该任务的拆分规矩对语料抽一段手算密度再外推。高档语料由 `gen-corpus.mjs` 生成——点数与填充比两轴独立可调，答案键自动派生。已知待扩：提取只是一种任务类型，格式转换族/多约束改写族/长文摘要对账族待建；
- **概率读数的消费出口是并发并集，不只是加重试**。量出某模型在某档"每次做成功概率 p<1"之后，产出是可并集集合（提取点、检索结果）的步骤，正解是并发 N 个独立实例取并集（适配方法 9）——实测三个能力档位完全不同的模型，最优块尺寸下 3 并发并集全部收敛 100%（各实例漏的是不同的点，并起来就齐）。标定仪器 `run-chunk-calibration.mjs` 的并发臂就是量这个的：单发覆盖率定 p，并发臂定"N 路并集能收敛到多少"。

**考题族二：真实任务阶梯**（`probes/real-task-scaling/`，第四层标准工作卷的尺寸化）。真实新闻稿四档（0.5K/1.9K/5.1K/28.4K）× fact-check 与 deep-research 两卷、真实 spec 五档（2.8K～78K）× deep-validate 判官卷——量的不是裸提取而是全链（检索+交叉验证+多步协调）随尺寸的衰减。判分靠机械面（完备率/SCHEMA 计数/tokens 账）+ 强模型基线对照 + 人工抽查。

两族的分工：合成阶梯便宜、可高频复跑、判分零争议，定**裸能力坍塌点**；真实阶梯贵但真实，定**岗位资格**（这模型能不能上这个尺寸的真活）。接入新模型先跑合成族，合成过线的档位再上真实族。

**G3 分解与规划。** 先把大活拆开（分解：粒度得当、不漏块），再排执行结构（规划：层次清楚、依赖顺）。引擎里 subtask free 到步展开时，模型现场出的子步骤质量就是这个维度。弱档模型的典型病：把一大段流程收缩成一个空壳步骤——看起来拆了，内容全没了。构建产物时，对这个维度弱的模型要禁用 subtask free、把子步骤显式写死。

这个维度目前只有评测卷定性观测，专用测试方案的设计思路是**借引擎现成的两套渐进机制当考场**——它们的中间产物就是"分解规划质量"的直接物证，且引擎已有机械判分的抓手：

- **考场一：subtask free 到步展开**（有序思考线）。给模型一个带 `[subtask free]` 的任务与一段多阶段流程材料，引擎到步索计划，模型现场出子步骤。判分抓手全是机械的：展开物必须含 check（引擎强制，缺了当场拒）、子步骤对材料各阶段的覆盖率（对照材料的阶段清单数缺漏）、空壳率（子步骤字数/材料对应段字数的比值——空壳步骤这个比值塌到近零）、层次深度是否合理（一层平铺 20 步与三层各 3 步是不同的规划质量）；
- **考场二：mixed 产物渐进展开**（hopbuild2 expand 线）。给模型一份带未尽原子的 mixed 档产物做二轮展开，考的是"在既有骨架约束下做局部分解"——比空地规划更接近真实工程。判分抓手：骨架保真 diff（差异行必须全落在被展开原子的替换范围内——引擎已有机械核）、展开物 validate、展开出的结构对原子原文范围的覆盖。

两个考场各测一个半边：考场一测**空地分解**（无约束、看粒度与覆盖），考场二测**约束下分解**（骨架不可动、看局部展开不越界）。阶梯变量都是材料尺寸与阶段数（2 阶段 / 4 阶段 / 8 阶段递增），记首轮展开质量的坍塌点。方案待实装成探针，先按这个口径手工跑。

**G4 工具使用。** 本质是单步内的多轮工具循环：选对工具、参数构造对、消费返回结果、知道何时停下来交产出。与 P2 是同一个循环的两个半边：G4 管"真需要工具时用得好"，P2 管"不需要时忍得住不用"。

探针：需要 3-4 轮工具往返的定向任务。引擎里的对应症状：工具迭代超限、同一调用反复重发、活干完了不收步。

**G5 结构化交付。** 按声明的 schema 产出——字段名、类型、数量都精确。这是引擎收割产出的前提，单步的最后一关。典型病两种：把结构化数据包进字符串（内容对、形态错）、把输出裹进代码围栏。

探针设计有一个关键点：**每题的数据值在题面里全部给定**（内容零难度），这样失败必然是形态失败，G5 与 G2 互不污染。

记档用两个有体感的指标，不用探针档号：

- **嵌套复杂度**：能稳定交付的最深结构形态——平坦标量 → 混型多字段 → 对象列表 → 三层嵌套。记"最深稳定档"（如"到对象列表稳，三层嵌套半数失手"），比"T4 3/6"直白；
- **容错后能力**（弱模型必标）：探针测的是裸皮（不剥围栏、不修形态），引擎解析层有三层容忍（剥任意语言标签围栏、散文+围栏单解、值级恢复阶梯）。裸皮失分若全是引擎能吸收的病（如纯围栏包裹），容错后能力要单独标出来——路由决策消费的是容错后能力，裸皮数字只用于观察模型本性。实例：某模型两档 0/6 全是纯围栏病，裸皮"中弱"，容错后"强"（引擎下两轮真机零结构化事故）——只看裸皮会把可用模型误判成不可用。

**G6 代码生成。** 按语言 × 复杂度分格测，一个总分没有路由价值——引擎场景关心的是三种目标语言，每种的消费方不同：

- **Python**（hop_python body / 白名单脚本）：写错的 body 是确定性死（引擎直执零重试余地）；
- **SQL**（数据处理类 skill 的产物）；
- **HopSpec**（hopbuild2 的构建产物、hopfix 的修复产物——语法正确只是底线，结构语义对才算对）。

每种语言四档复杂度：**简单**（单函数/单查询，一眼可验）、**普通**（多函数协作/带连接聚合的查询/带把关的多步 spec）、**复杂**（状态机、跨表事务逻辑、带循环分支嵌套的 spec）、**大规模复杂**（多文件/多模块协作级）。判分机械化：Python 跑测试用例、SQL 对结果集、HopSpec 过 validate + 语义断言。

探针形态上有一个与其他维度不同的点：**允许自行迭代验证**——给模型跑测试/validate 的回路，记两个数：一次写对率（裸能力）与 N 轮内自愈率（带回路能力）。两个数都有路由价值：一次写对率决定"能不能当 body 生成主力"，自愈率决定"配上验证回路后能不能用"——一次写对率低但自愈率高的模型，配自动验证回路照样可用；两个都低才是真不行。

**G7 领域知识充分度。** 轻量模型的专属短板：参数量小，装的领域知识（行业事实、专业术语、业务常识）天然少。它与推理能力独立——推理档够用的小模型，在它不认识的领域照样判错，因为缺的是判断的原料不是判断力。

探针思路：同一形态的任务换几个领域跑（通用常识领域 vs 专业领域各一份材料），对比编造率与术语误用率——通用领域正常、专业领域明显劣化，就是知识缺口不是能力缺口。观测面：核查类任务的可信度打标准确率、报告里的编造条目数、术语用错的次数。

适配换算：知识缺口**用供给补，不用换模型**——HopSpec 的 spec 级知识声明与步骤级 doc-ref 注入就是为这个准备的通道：知识不足档的模型，相关步骤把领域判据、术语表、参照数据显式喂进输入材料。三模型此维度都未测（探针待建）。

**G8 渐进知识获取。** G7 的另一半：存量不够时，模型会不会自己补。四环闭环——**察觉**（知道"这个我不知道"，不编）→ **检索**（缺口翻译成有效查询）→ **筛选**（挑出真相关的结果）→ **使用**（新知识真用进判断）。弱模型的断环形态：不察觉直接编造、查询词无效反复空转、搜到了结论照旧。

探针思路：给一道**必须现查才答得对的题**（模型训练截止后发生的事实）+ 检索工具，看四环各断在哪——fact-check 真实卷天然是这个考场（时效性新闻的核查逼着每个点走完四环）。观测面：编造率（察觉环）、检索查询与缺口的相关度（检索环）、引证来源质量（筛选环）、结论与检索结果的一致性（使用环）。

适配换算：G8 强 → 给检索工具就能自补，供给面可以轻；G8 弱且 G7 也弱 → 必须预制供给（构建期备好领域材料随步喂，运行期不指望自己补课）。

### 实践组详解

实践组每个维度都要回答一个问题：为什么通用评测测不出它？

**P1 核验能力。** 把关步（check）的自我管理能力。三档阶梯，每升一档模型要多扛一种协调负担：

- **开放式核验**：spec 只给判据散文（"核对是否穷尽、是否误分类"），模型自己建核对框架、自己遍历、自己汇总，还要**跨轮保持同一框架**。弱模型的典型死相不是判错，是**自反**——每轮现建一个框架，对同一对象两轮给出相反指令（实测：第一轮命令"把 P3 从 fact 改成 inference"，执行者照办，下一轮又命令改回去）。自反的判官比误判的判官破坏力大：重试机制变成"每轮换一个考官"，执行者怎么改都过不了，预算必然烧尽；
- **按清单核验**：spec 替模型建好框架（封闭问题清单 + 机械汇总规则），模型只逐题作答。这档砍掉了"建框架"负担，裁量摇摆立刻消失——但还剩**多题自洽**负担：六题合一卷，弱模型会出现"第 3 题答 yes、终判却按第 3 题不满足来汇总"的表内矛盾；
- **单点核验**：一次调用只问一个原子问题（"这一行的断言，清单里有覆盖它的点吗？"）。协调负担全部归零，只剩判断本身。

为什么通用评测测不出：评测里的判定题都是单发单题（等价于最低档），"跨轮框架一致"与"多题自洽"这两种负担，只有在重试循环里当判官才暴露。

**P2 inline 工具耐受。** 长提示词 × 多个工具在场时，守不守得住任务焦点。发现这个维度的实验很说明问题：对一个爱乱用工具的模型，把"不要用工具"写到五种强度全部无效，把工具从供给面上**物理拿掉**立刻正常——闲置的工具面本身是行为吸引子，每件工具都是一个"随时可以点的按钮"，按钮多到一定程度，点按钮的合计概率就压过了答题。

为什么通用评测测不出：工具评测测"会不会用工具"，不测"工具在场但任务不需要时忍不忍得住"——要把满配工具塞给纯推理任务才看得见。

（注：上述实验跑在一个后来被定性为"端点走样件"的通道上——具体数字不作那个模型的能力依据，但现象与维度本身成立，它就是这个维度的发现现场。）

**P3 修订落实。** 本质是**指令散文序列理解能力**。真实工程 prompt 的指令不是并列几条，而是散布在长文各处：任务命令在中部，"首轮/重试轮"的条件说明缀在命令尾，校验反馈插在行内，修正块垫底。这个维度测模型能否从整篇散文里读出指令序列、判断此刻生效的是哪段、并执行它。

修订轮是最尖锐的观测场景：生成命令与修订指令在同一篇 prompt 里竞争。弱模型的失败形态很特别——命令内容**读到了也理解了**（让它复述，复述准确；让它分析，推理正确），行为却跟着篇幅大头走，把修订轮当成从头做题。"说到、想对、做不到"。把裁决规则写进 prompt 也救不了：那句规则本身也是散文序列里的一段，同样被篇幅淹没。

为什么通用评测测不出：评测的指令遵从测"守不守一条禁令"，多轮修正测"对话里改口"——都是单指令或有对话轮次分隔的语境。真实工程形态是"全量供给 + 尾部追加修正"的一篇长文，指令序列理解只在这种形态下暴露。

实测：某弱模型在标准修订供给下 0/9（九轮修订全部落空），把 prompt 换成只含修订指令的短卷后 6/6 全对——缺的是序列理解，不是执行力。引擎的对治开关：`revision_prompt: short`（打回重试轮把生成命令整体替换为修订命令，竞争指令物理撤场）。

### 四条度量纪律

- **症状要归因到维度再入档**："工具循环撞墙 14 次"不能入档；"工具使用弱，主因是一轮贪多不收手，参数构造正常"才能入档。归因不清就标"待拆"，不许把症状当能力写；
- **零症状也不直接等于能力强**：失败计数为零，只有在"干的活一样重"的前提下才是证据。推理烧穿是干重活才有的症状——干轻活的模型天然零烧穿，就像不跑步的人零扭伤。判据：与对照模型的 tokens 消耗差好几倍时，零失控要标"未证"，不标"强"；
- **区分"能力弱"与"防线兜住了"**：引擎重试兜着走完不等于能力合格——兜底有成本。档案记裸能力（首轮做对率），不记兜底后成功率；
- **打分粗档即可**（强/中/弱/未测；阶梯型维度 P1、P2 例外，按坍塌到哪一档记）。档案的消费者是路由决策，粗粒度够用。

这一层的产出是**按维度组织的能力画像**——它直接变成下一层的路由建议：哪个维度弱，就避开吃那个维度的步骤类型。

### P1 档位怎么换算成把关步写法

| P1 档 | 把关步的适配写法 |
|---|---|
| 开放式可用 | check 步照常路由，判据正常写 |
| 仅按清单可用 | 判据写成封闭问题清单 + 机械汇总；病灶定位不可信——打回意见只报"哪题 no"，不报展开分析 |
| 仅单点可用 | check 拆三段：机械归组（hop_python 零 LLM）→ 逐题单点判定（loop 每轮一小题）→ 机械汇总（body 出判定）。强模型一步的判官，弱模型拆成 n 发原子判定 |
| 单点也不稳 | 把关步禁路由本模型，check 一律升强模型 |

两个提醒：**"仅单点可用"不是残废档**——它是完全可工作的形态，n 发小调用的总费用常常低于强模型一发；**P1 与 G1 分开测，不许互相推断**——推理好的模型，核验框架管理照样可能塌，那是另一种能力。

**判官岗不论路由到哪一档，都要配意见返回纪律**（变速箱适配方法 10）：判 false 一次列全全部缺口不挤牙膏；每条缺口标实质/非实质（实质=不修则执行行为就是错的；非实质=措辞格式类裁量）；实质清零即放行、非实质标"放行残留"记录在案——不为文本瑕疵烧重试轮。弱判官模型三条都要写死进判据文本（它不会自发分级，还容易在小修复轮里引入新真缺陷）；强判官模型至少写死第一条（控循环成本上界）。跨轮记忆走销项台账文件（重试回滚清变量，台账不清），判官动笔前先读——禁自称首轮、已修条目"已落实"带过、未修标"复现"。

### P2 档位怎么换算成工具供给策略

| P2 档 | 判据 | 适配策略 |
|---|---|---|
| 满配耐受 | 全格点零走偏 | 无限制，现行缺省供给照用 |
| 长文敏感 | 短文正常，长文 × 多工具走偏 | 收窄工具面：纯推理步零下发，需要工具的步只下发声明的几件 |
| 工具敏感 | 只要工具在场就走偏 | 零工具路由：该模型只吃纯推理与格式转换步，一切取数动作前置为机械步或交别的模型 |
| 不适配 | 零工具的纯推理都不稳 | 不接入 |

## 第四层：能力定位（按需，非门槛）

跑标准工作负载，对比在册模型的费用、修检轮数、产物质量。回答"这个模型适合当什么"：构建主力？轻执行步？判官步？便宜大量的探索步？

标准工作卷目前三件（跑仓库原件，不跑工作面副本）：

| 卷 | 考什么 | 说明 |
|---|---|---|
| hop-fact-check（完整版） | 综合卷 | 检索链考工具使用；事实点/推演点二分类、推演点的前提溯源与推理有效性四级审查（sound/mostly/leap/invalid）考推理可信——它不只核对事实，还审"从事实推出结论"这一步跳没跳；逐点并行考结构化交付。弱模型跑 27b 微判定变体（同功能面，只换把关形态） |
| hop-deep-research | 工具重卷 | 多子问题 fan-out 检索 + 独立第二来源对抗验证 + 引用报告——比 fact-check 重一档，G4/P2 的主考场 |
| hopbuild2 构建语料（incident 8KB 等） | 构建卷 | 考 G2/G3/G6——大活切步、结构成文、修检收敛 |

产出是**路由建议三行**，写进接入记录：哪类步骤可用它、thinking 怎么配、什么场景别用它。卷上的表现按维度归因进档案（不记总分——总分没有路由价值）。

## 接入记录：探针结论要留档

四层跑完，把结论落成一段接入记录，至少含：真实端点路径与鉴权形态、规格（上下文窗口 / max_tokens 上限）、thinking 双档结论、tool_use 结论、能力画像、路由建议。探针结论只留在对话里就会蒸发——下一个人（或下个月的你）接同一家的新模型时，这份记录能省掉整个第一层。

能力画像的正式户口是 `model-gearbox/profiles/<模型名>.yaml`——按维度记档位、依据、适配开关。

## 实例二：Qwen3.8-27B 的接入记录（2026-09-17）

- **端点**：与 Ling 同网关；模型名须精确 `Qwen3.8-27B`（变体拼法报空响应）。配置教训一条：service_id 里不能带横线（标识符规则），带了 server 启动就拒载，MCP 报错却不指向真因——手工起一次 server 看启动日志最快；

### 实例二勘误：端点混因翻案（2026-09-18）

上面整段记录测的**不是 Qwen3.8-27B 的真实能力，而是那个端点上的一个走样件**。换到百炼公共端点（dashscope claude-code-proxy，鉴权 bearer）同卷重测后，画像大面积翻案。两端点的差异有两条实锤：

1. **旧端点注入了文本协议的工具调用模板**——直接问模型"你的系统提示里有没有工具调用相关指令"，旧端点的模型复述出一段"If you choose to call a function ONLY reply in the following format…"，复述途中还失控发出了真调用；百炼端点同问答"没有"。这个注入给模型开了一条"随时可以写调用文本"的先验出口，与工具打环形态直接相关；
2. **行为断崖**——同卷五件，工具循环失控计数 118 次 对 0 次；执行小卷一边空转撞墙、一边干净过卷；判官卷一边零产出、一边交出六条零编造的合格报告。

百炼端点的真实画像（与旧端点判若两物）：小件执行可用、判官可用（但形态有讲究，见度量表 P1）、构建能走完但产物带伤、**真短板是修订落实**（P3——分析对、数据不动）。现行档案 = `model-gearbox/profiles/qwen3.8-27b.yaml`（百炼实测版）。

**方法论教训（已进第一层探针清单）**：同一模型名 ≠ 同一模型，端点是能力画像的一等变量。接新端点加两问：① 自查探针——问模型系统提示里有没有工具调用指令（探注入）；② 同一模型有多个端点可用时，先跑最小同卷对照再下能力结论。

|---|---|---|

| 弱 | 一次调用只能可靠处理几个要素，大活能走完但产物空心 | qwen：实测 2~4 要素 |

|---|---|---|

| 档 | 直观说法 | 本表实例 |
|---|---|---|

| 弱 | 循环失控是常态——单件超限上百次 | Ling：137 次 |

| 档 | 直观说法 | 本表实例 |
|---|---|---|

| 到对象列表稳 | 对象列表以内稳，三层嵌套半数失手——且是真形态错（把对象交成列表），引擎容错救不了 | Ling |

**P1 核验能力**——把关步能给它什么形态的考卷：

| 档 | 直观说法 | 适配动作 |
|---|---|---|
| 开放式可用 | 给判据散文它自己建框架核，跨轮不变卦——check 步照常写 | deepseek（真实判官卷 dv S/M/L 三件全过） |
| 按清单可用 | 要替它把框架建好（封闭问题清单），它逐题答得稳 | Ling：判据写成清单形态 |
| 仅单点可用 | 一次只能问一个原子问题——把关拆成"机械归组→逐题小问→机械汇总"三段 | qwen：单点 12/12 全对 |

真实判官岗补充（2026-09-19 真实卷跑批）：**探针档位与真实岗位表现有落差**——Ling 探针按清单全满，真实判官岗却两案失稳（三轮换标准、自检两头占）；qwen 封闭判官 S/M 档可工作（还抓出高危真阳性），20K 大件失稳（幻觉核对象）。所以判官岗的最终资格按真实卷定，且按件复杂度分层路由（小件可自审，大件升强模型）。

**P2 工具耐受**——工具在场但用不上时忍得住吗：满配耐受=十件工具挂着也不乱摸（deepseek）；未测=还没按格点矩阵测过（Ling/qwen——qwen 的间接信号全正向，旧的"3 件上限"是作废端点的旧账）。

**P3 修订落实**——打回意见能改到产出上吗：强=工单逐轮销项（deepseek）；短卷开关下强=标准供给下 0/9 改不动，但引擎把修订轮换成短卷后 6/6 全绿——配置 `revision_prompt: short` 即可用（qwen）；弱（待重测）=旧账发生在旧版供给上，新版下还没再触发过修订轮（Ling）。

**G6 代码生成（Python 与 SQL，2026-09-23 实测）**——两种语言各三档，每格 6 发，判分用模型从没见过的隐藏测试。

- **Python 题**是"把一条规范条款写成 Python 校验脚本"，脚本在引擎 run_script 的真实环境里跑（先过 Python 语法沙箱，白名单在题面里全列给模型），看在隐藏测试文件上的退出码全对没有。三档：每行不超过 100 字符（简单）、函数不超过 40 行（普通）、公开函数必须有文档字符串且提到每个参数（复杂——五类参数、豁免规则、嵌套作用域都要照题面处理）；
- **SQL 题**是"按取数需求写一条 SQLite 查询"，每份测试数据单独建临时库，结果集逐行逐列全等才算对。三档：单表筛选排序（简单）、左连接加分组聚合（普通）、每个用户的最长连续登录段（复杂——去重、按日历判相邻、同长取最早）。

- **deepseek**：Python 与 SQL 都是强档。Python 复杂档一次写对只有 3/6，但失手的 3 发全是输出截断（撞到 32768 的输出上限、正文为空），不是写错——凡交出了脚本的，隐藏测试全对；40 轮提交零沙箱拒绝。复杂脚本步要给足输出预算；
- **qwen27**：SQL 三档全对，是强档；Python 中档——普通和复杂档一次写对只有一半多，但配上验证回路自愈能救回大半（普通 6/6、复杂 5/6）。复杂档有 1 发"公开样例过了、隐藏测试挂了"（漏查仅位置参数）；
- **Ling**：SQL 强中——简单档全对，普通和复杂各失手 1 发，而且两发都是"公开样例过了、隐藏测试挂了"（普通档把金额为 NULL 的已支付订单漏数，复杂档没按"每人取最长一段"收成一行）；Python 弱——50 轮提交 15 轮被沙箱拒（白名单外的 f-string 冒号格式、re.compile 等），逻辑也有错：普通档 2 发漏查类方法、复杂档 2 发把函数体内的嵌套函数也查了，这 4 发都是公开过隐藏挂；
- **"公开过隐藏挂"是最该盯的失败**：模型自己看得见的样例全过、真实数据上错了——规约内的自验把关只看得见样例，拦不住它，只能靠隐藏测试或人工复核；
- **两种语言要分开看**：同一个模型 SQL 和 Python 可以差两档（Ling、qwen27 都是 SQL 明显好于 Python），只看一种语言会误判另一种；
- 用法：SQL 取数三家都可派，Ling 的产物要有测试数据核；Python body 与 sdc 的"条款写成校验脚本"步骤，普通档以上首选 deepseek，qwen27 配验证回路可用，Ling 限简单档。

用法提醒三条：

- **每格绑定的是 model service 不是模型名**——换端点全部重测；
- **强弱档不是终身制**——Ling 的 G5 改判就是例子。维度探针的"内容零难度"设计，就是为了把"模型不会"与"供给教错"拆开；
- **弱档的正确消费是适配，不是弃用**——qwen 的 P3 弱档配短卷开关后全绿；"弱模型执行 + 强模型把关"的路由组合全链完赛。适配开关的家 = 档案的 adapt 节。
