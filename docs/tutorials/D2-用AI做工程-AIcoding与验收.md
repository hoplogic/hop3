# D2 · 用 AI 做工程（下）：AI coding 与验收

**给谁**：读完 [[D1-用AI做工程-从概念到设计]]、设计已改定、要让 AI 动代码的人。
**主线**：AI 写码不可怕，可怕的是**不受约束的 AI 写码**。本篇讲三样：给 AI 立的规矩（行为宪法）、一次改动的完整节奏、人怎么验收。

## 给 AI 立的规矩：行为宪法四条

这四条写在本库 `CLAUDE.md`（AI 每次会话自动加载），是 AI 动手的硬边界——你需要知道它们，因为**验收时你查的就是这四条有没有被守住**：

1. **收链前置**：动手前必须先收锚点实现链（前序契约/依赖/波及面）。AI 未收链就写 = 在可行域外盲走；
2. **设计先行，禁止跨层直达**：改 `src/` 前对应 `design/` 必须先改定——AI 最易犯的失效就是从想法直接跳到代码。机检判据：一次改动 src 动了 design 没动 = 跳层；
3. **修 bug 不豁免**：越是"一行就能修好"的 bug 越诱导跳层。顺序：先读设计里管这个行为的条款 → 判"代码没照设计做"还是"设计要改" → 测试正反例成对；
4. **严禁顺带**：AI 执行任务时发现别的问题，报告是本分，擅自处置是越界。

外加一条人机分工的发动机（D1 讲过）：**推演 AI 直接做，决策必须回到人**——AI 问你一个可从已定原则推演的问题是失职，AI 擅自拍一个真决策也是失职。

## 一次改动的完整节奏（你给 AI 的任务形态）

以真实小事为例——"validate 的某类报错缺步骤号，补上"：

```
① 你派活：  "修 validator 的 XX 报错缺步骤号问题，遵从工程链规范，
            三件套与正反例测试"        ← 一句话把纪律钩上
② AI 收链：  找到报错点所属锚点 → 开 TRACEABILITY 卡 → 报告波及面
③ AI 判断：  消息格式设计没锁死 → 推演，直接做
            （若涉及错误分级这类契约语义 → 停下来向你提请拍板）
④ AI 设计先行：把"消息含步骤号"写进设计条款（先于代码）
⑤ AI 改码：  改动行带 @a: 锚点标记
⑥ AI 补测试：正反例成对——正例=新消息含步骤号；反例=不该带的场景不误带
⑦ 机检：     npm run check（类型/锚点/层向/测试/审计基线/版本互锁）
⑧ 真机 e2e： 改动触及载体协议/执行链时必做（见下方"测试的两条腿"）
⑨ 你验收：   见下节
```

**派活话术的要点**：把"遵从工程链规范""三件套""正反例"这些词说出口——它们不是客套，是把 AI 钩到纪律上的锚。本库的历史经验：不说，AI 会抄近路；说了，AI 的产出自带可验收的结构。

**两句可直接复用的标准话术**（推动与 review 各一句，本库实战原文）：

> **推动实现**：
> "推动，严格按照工程链规范实现，落实设计 HOP 三件套，实现时同步设计代码一致性，保持设计合理性，测试时保障正反例覆盖。"

> **工程链 review**：
> "根据锚点做工程链 review，检查设计三件套完整性，设计合理性，设计代码一致性，和测试正反例覆盖。"

前一句用在派活/续推时——五个要件（工程链规范/三件套/设计代码一致/设计合理性/正反例）一次钩全；后一句用在阶段验收时——review 的四个检查维度即验收清单本身，AI 会沿锚点逐条核并把发现按维度归档。两句合用即"推动一段 → review 一段"的节奏，是驾驭 AI 长程工程最稳的循环。

## 用 /hop 承载这两句：话术不变，过程升格为引擎管护

上面两句话术直接说给 AI 也能干，但过程只活在对话里——对话断了进度就断，把关跳没跳全靠 AI 自觉。**更稳的形态是把话术交给 `/hop`**（用法详见 [[04-日常活交给hop]]）：

```
/hop 开工，严格按照工程链规范实现，落实设计hop三件套，
     实现时同步设计代码一致性，保持设计合理性，测试时保障正反例覆盖

/hop 严格根据锚点做工程链review，检查设计三件套完整性，
     设计合理性，设计代码一致性，和测试正反例覆盖
```

同一句话术，经 /hop 走多得到四样（这正是引擎存在的意义在工程活上的兑现）：

1. **过程有账、中断可续**——AI 把活升格为一份带步骤的计划（收链 → 定方案 → 设计先行落盘 → 实现 → 全检+核验 → 提交），每步的产出记在引擎账上。对话断了、第二天接着干，`/hop` 一声回到断点，不靠人脑记"上次干到哪"；
2. **把关跳不掉**——设计先行、机检全绿这些纪律从"话术钩住的君子协定"变成计划里的显式关卡：设计没落盘，引擎不放行实现步；核验没过，提交步走不到；
3. **验收换了个人判**——工程链核验（设计代码一致/正反例覆盖那四条）由一个**没参与实现的独立 AI** 对着产出物判，不是干活的 AI 自己说"我核过了"（出题、答题、阅卷三权分拆——自己阅自己的卷，判据再严也有能绕的缝）；
4. **跑通一次就能沉淀**——干完说一句"总结一下"，这次实战验证过的流程（含中途撞过的坑,如"结构性改动先写最小探针验证再正式动手""大面积重编号后必扫散文里的旧编号"）被提纯成可复用的成品流程,下次同类活开工时 /hop 会主动问"有现成流程,拿它当底稿开？"——踩过的坑变成下次的先手把关,不再靠"下次注意"。

实现批与 review 各会沉淀出自己的流程件。**review 件值得单独一提**：它把"机械核对外包给独立 AI（五层链逐环比对+变异核证——把代码故意改坏看测试拦不拦）、判断与修复决策留在主对话"这套注意力分工也固化了进去，这是裸话术不会自带的纵深。

## 测试的两条腿：正反例覆盖 + 端到端真机

AI 补的测试要同时站住两条腿，缺一条都是假保障：

**腿一：正反例的合理覆盖**。不是"有测试"，是**动过的每条边界都从两侧钉死**——正例证明新行为成立，反例证明旧行为没被误伤、例外路径没被放行。AI 补测试最常见的水分是只写正例（改啥测啥，皆大欢喜）；验收时专挑反例看：这次改动引入/移动的边界，反例钉的是不是它。覆盖率数字只是参考，**边界覆盖才是判据**。

**腿二：端到端真机测试，不可省**。单元测试全绿证明的是"部件各自正确"，证明不了"装在真载体里能跑"——本库血泪史：mock 全绿而真机三轮红（codex 的 MCP 注册通道、干净环境、审批层，每一层都是只有真机才暴露的）。

真机 e2e 的记忆点：发版前一条命令（例行快验用 `test:live:smoke`）：

```bash
npm run test:live:core
```

它在**真实的 CC/Codex 载体**里跑完整链路（不是 mock）：双载体的执行交接、弱模型长程驱动、demo 具名 skill、独立模式（MCP server）、并行派发——每场景有确定性断言，通过凭证落盘 `.e2e-evidence/`，发版闸据此核"双绿且新鲜"。批量入口**任务池并发 5**（总时长≈瓶颈场景,约 8 分钟;撞限速 `HOPSPEC_E2E_CONCURRENCY=3` 降档）。同族还有几个专项批量，按改动面选跑：

| 命令                           | 测什么                                        | 什么时候跑                |
| ---------------------------- | ------------------------------------------ | -------------------- |
| `npm run test:live:smoke`    | 例行档四 smoke（工具三通道/mcp 绑定/多 run 隔离/大输入内联,零/单 LLM ~2min） | 改引擎后随手跑            |
| `npm run test:live:core`     | 发版档 15 场景（9 快乐+6 失败路径,两波并发约 13min）        | 改载体协议、执行链、失败语义后;发版前必跑 |
| `npm run test:live:deep`     | 触发档 LLM 质量面（audit 深核/primer 盲测/flash 弱模型长程,可选跑单件） | 改 prompt 组装/primer/能力门后按触发条款 |
| `npm run test:e2e:<载体>:<场景>` | 上述任一场景单跑（如 `test:e2e:codex:standalone`）    | 定位问题、修复复验            |

这些都是**脚本化的一键验证**（场景断言 + 凭证落盘），区别只在**谁按回车**：AI 的沙箱环境跑得了的，AI 自己跑；跑不了的（起不了 codex app-server、连不了 LLM endpoint），**同一个脚本**交人在终端跑一条命令、贴回输出——不许因为"我这环境跑不了"就跳过。**AI 的职责是把脚本写到"一条命令 + 明确判据"的程度**，谁跑都得到同样可判的结果，而不是把测试责任推给人。

给 AI 派活时把这条也说出口（推动话术里"测试时保障正反例覆盖"之外，涉载体协议的加一句"**真机 e2e 验证，跑不了的给我写验收脚本**"）。

## 人的验收：查链，不逐行读代码

AI 交付后，你的验收动作按性价比排序：

1. **机检绿不绿**：`npm run check` 全绿是底线——类型、锚点格式、层向依赖、全部测试、审计基线、版本互锁，机器已替你查完第一轮；涉载体协议的改动还要看真机 e2e 凭证（`.e2e-evidence/`）新不新鲜；
2. **链对不对齐**：设计条款说的 = 代码做的 = 测试钉的？沿锚点抽查（`grep '@a: <锚点>' src/`、`grep '@v: <锚点>' tests/`）——重点看**测试的反例**钉的是不是这次动过的边界（AI 补测试最常见的水分是只写正例）；
3. **决策有没有被越权**：AI 的汇报里有没有"顺手"改了任务之外的东西、有没有该问你的没问；
4. **语义审计（里程碑级）**：机检查不了"设计是否忠实传达概念意图"——发版/里程碑前跑 anchor-audit（语义审计 skill，人/LLM 沿锚点全量核）。

**逐行读代码不在清单里**——不是不能读，是它性价比最低：三件套锁死了自由度、机检守住了确定性形态、链的对齐核住了忠实性之后，逐行阅读的边际收益已经很小。你的注意力应该花在决策点和边界（反例）上。

## 三类失效与对治（验收时的病理学）

| 失效 | 症状 | 对治 |
|---|---|---|
| 可行域漂移 | AI 的实现"看着对"但违反了某条上层原则——因为边界不在它上下文里 | 收链前置（派活时要求先收链） |
| 跨层直达 | design 没动 src 动了——AI 从想法直跳代码 | 机检硬拦 + 派活话术钩纪律 |
| 角色混淆 | AI 替你拍了决策，或反过来把可推演的事拿来问你 | 验收第 3 查 + 好的派活把已定决策讲清 |

## 常备工具速查

| 要什么 | 命令/去处 |
|---|---|
| 全量机检 | `npm run check`（快速版 `check:fast`） |
| 查某契约全链落点 | `grep -n "<锚点>" TRACEABILITY.md` |
| 本机试改动效果 | `npm run dev:install`（重建 dist+刷新 skill，仓库根目录跑） |
| 语义审计 | `/hopspec run scripts/audit/anchor-audit.md`（支持按模块跑） |
| 跑前体检 | `scripts/deep-validate/deep-validate.md`（spec 形态手工跑,validate 深化档——LLM 查"说明教的动作×执行模式能力面"的运行期错配,分钟级） |
| 定向修正 | `scripts/hopfix/hopfix.md`（spec 形态手工跑,或 /hopfix 一句话触发——按工单节点级定向修既有 spec:只改点名处/呈人确认/快照可回滚;结构性变更如实拒,分钟级） |
| 例行提交/发版清单 | `RELEASING.md`（手册层，每次照走） |
| 新建模块 | 八件单一次交齐（`chain-enforcement.md` §1c-2） |

## 这套方法的本质

概念-架构-模块-设计四层收窄 + 三件套表达 + 锚点链 + 机检守卫，合起来解决的是一个问题：**让 AI 的产能可用而不失控**。人的注意力从"写代码、读代码"解放出来，集中到真正只有人能做的两件事——**定方向（决策）和守边界（验收）**。这也正是 HopSpec 语言自己的哲学（锁定目标、守住边界、放开路径）在工程过程上的同构应用：对 AI 开发者放开路径，用结构而不是用盯梢来保证正确。
