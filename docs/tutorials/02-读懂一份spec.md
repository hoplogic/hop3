# 教程 2 · 读懂一份 spec：五分钟建立全景

**目标**：拿到任何一份 HopSpec 文件，知道从哪读起、每行在说什么、谁干活谁把关。这是后面所有教程的地基。
**前提**：完成教程 1（[[01-第一次运行-ClaudeCode]] 或 [[01-第一次运行-Codex]]）——至少跑过一次，见过 spec 长什么样。

对照着读效果最好——用你在教程 1 见过的：

```bash
cat examples/coffee-week.md
```

## 第一眼：头部是契约，Steps 是路径

一份 spec 分两半。**头部**回答"这是个什么任务"：

```markdown
# Spec: 咖啡店的一周            ← 标题
Goal: 汇总营业数据，产出周报     ← 一句话目标（必选）
Constraints:                    ← 不可违反的约束
- 统计数字必须来自确定性计算，不得估算
Inputs:                         ← 运行时要给的参数
- daily_sales: yaml  # 7 天营业额
Outputs:                        ← 承诺交付的东西
- weekly_report: markdown  # 周报
```

**先读头部再读 Steps**——Goal/Constraints/Outputs 是这份 spec 对你的承诺（改不了、绕不开，引擎会验收），Steps 只是兑现承诺的路径。评估一份别人写的 spec 值不值得用，读完头部就该有答案。

**`## Steps`** 之下是编号步骤树。每步一行摘要：

```markdown
2. [act] 统计一周数字
```

`2.` 是步骤号（子步骤 `2.1.`、`2.1.1.`，编号即层级），`[act]` 是**步骤类型**——读 spec 的关键就是认识这些类型。

## 先建大逻辑：spec 就是一份升级了的 SOP

如果你给新员工写过操作手册（SOP，标准作业流程），你已经离读懂 spec 不远了——但先说清一个区别。日常见到的 SOP 大多是**顺序平铺**的：步骤一路往下编号，遇到重复就写"回到第 2 步"，遇到分情况就写"如果是生鲜，跳到第 7 步"——**靠"跳转"表达循环和分支**。流程短时这没问题；但跳转会随流程长大而**复杂性爆炸**——跳转彼此交叉，改动一处会牵动看不见的远处，最要命的是**关键控制点失控**：你没法指着某一行说"要到这里，必经那道检查"，因为总可能有一条跳转路径绕过它。

这个问题软件工程界六十年代就撞过，解法就是**结构化理论**：只用**顺序、循环、分支**三种结构就能描述所有逻辑（已被证明），代价是放弃跳转——换来的正是**控制点不失控**：结构块有唯一入口和出口，卡在必经之路上的检查，任何路径都绕不开。这对今天的智能体恰是最关键的痛点解法——LLM 靠自觉"记得"过检查点是不可靠的，结构上绕不开才可靠。

HOP 把这套原则用回到给人写的流程上，叫 **HopSop**（Hop 标准作业流程）：**不许跳转**，循环和分支各自成块、用缩进层级把边界画出来。同一份拣货流程，HopSop 写法：

```text
1. 接到订单，核对商品和数量
2. [循环] 逐件拣货
   2.1. 按货位取货，扫码登记
3. [分支] 按订单类型走不同包装
   3.1. [条件(生鲜)] 加冰袋，泡沫箱
   3.2. [条件(其他)] 普通纸箱
4. 称重，打印面单，交揽收
```

对比平铺版："逐件拣货"不再是"拣完一件回到第 2 步"，而是一个 `[循环]` 块，循环体就是它的子步骤 2.1——**哪里开始重复、重复什么、重复完去哪，看缩进就知道，不用追跳转**。分支同理：两个 `[条件()]` 互斥并列，一眼看清各走各的。整份流程只有三种结构——顺序、循环、分支——加上分层编号，这就是 HopSop 的全部语法。

> 写过程序的人会觉得眼熟：`[循环]` 就是 for，`[分支]`+`[条件()]` 就是 if/else——正是当年淘汰 goto 的那套结构化编程。

HopSop 已经能把流程逻辑给人讲清楚，但交给机器执行还缺两样：**每一步谁来干**（人？LLM？程序？），以及**数据从哪来到哪去**。把这两样补上，HopSop 就升级成了 HopSpec：

| | SOP / HopSop（给人） | HopSpec（给机器） |
|---|---|---|
| 控制流 | 顺序/循环/分支 + 分层编号（**结构化，无跳转**） | 同一套（subtask/loop/branch+case） |
| 每步谁干 | 默认都是"你"——不用写 | **步骤类型**：`[reason]` LLM 动脑 / `[act]` 程序照算 / `[confirm]` 人拍板… |
| 数据 | 靠上下文意会 | **显式数据流**：`← 读入`、`+ → 产出` |

所以读 spec 的心法就一句：**骨架当 SOP 读（这个你本来就会），再看两样新东西——方括号里"谁干活"，箭头上"数据怎么流"。**下面把这两样讲清楚。

## 步骤类型全景：一张分工表

15 种类型说的全是一件事——**这一步谁干**。按干活的主体分四组记（常用的就前三组九个）：

| 组        | 类型              | 谁执行     | 一句话                             |
| -------- | --------------- | ------- | ------------------------------- |
| **动脑的**  | `reason`        | LLM     | 推理、分析、生成——需要判断的事                |
| **不动脑的** | `act`           | 引擎/工具   | 确定性计算与可逆操作，可安全重试                |
|          | `commit`        | 引擎/工具   | **不可逆**副作用（发送/支付/写正式文件），前面必有把关  |
| **把关的**  | `check`         | LLM 或引擎 | 验收已有产出：过/不过 + 失败原因，不过触发重试       |
|          | `confirm`       | **人**   | 审批闸门：approve/reject，reject 全局中止 |
|          | `ask`           | **人**   | 要数据：让人给个值（确认参数、选方案）             |
| **编排的**  | `subtask`       | —       | 把几步打包成一个可整体重试的单元（`retry=N`）；标 `free` 时子步骤可空——执行到这一步引擎会带着运行时数据要计划（到步展开）     |
|          | `loop for-each` | 引擎      | 对列表逐项执行，引擎数数                    |
|          | `branch`/`case` | 引擎      | 按确定性条件走不同路径                     |
|          | `call`          | 引擎      | 调用另一份 spec（像函数调用）               |

（剩下的：`loop` 通用循环、`break`/`continue`/`exit` 控制流、`on fail` 失败兜底块——见到再查语法参考即可。）

**读 spec 时的速判**：看到 `[reason]` 想"这里 LLM 要判断什么"；看到 `[act]` 想"这是确定性的，错了会重试"；看到 `[confirm]`/`[ask]` 想"这里会停下来找我"；看到 `[commit]` 往**前**找它的把关闸在哪——找不到就该起疑心。

> 顺带：步骤类型词和段头有中英两套写法完全等价——`[探索]`≡`[act]`、`## 目标`≡`## Goal`，读别人的 spec 撞见哪套都一样；项目可在 `hopjit.yaml` 用 `language: zh` 把生成缺省定为中文，存量转换用 `hopjit lang <spec> --to zh|en`（详见教程 04 与语法参考 §12）。

## 数据流：两个箭头看懂变量

每步下面的缩进行声明数据进出：

```markdown
2. [act] 统计一周数字
  - ← daily_sales                 ← 读入：用前面产出的（或 Inputs 里的）
  + → total: int  # 周营业额   ← 产出：变量名: 类型 # 说明
  + → best_day: int  # 最好一天
```

规则就两条：**`← x` 的 x 必须在前面出现过**（某步的 `+ →` 或头部 Inputs）；**`+ → y` 产出的 y 后面任何步骤都能用**。顺着箭头就能画出整份 spec 的数据管道——哪步的产出喂给哪步，一目了然。类型除了基础的 `int`/`float`/`text`/`bool`/`yaml`（数字类型与 Python 一致，就整数和浮点两种），还有列表 `[T]` 和头部 `Types:` 自定义的结构。

## 容器与介入点：树形结构怎么读

**容器**（subtask/loop/branch）自己不干活，管辖子步骤：

```markdown
4. [subtask retry=2] 产出并核验周报      ← 容器：整体最多重试 2 次
  4.1. [act] 组装周报                    ← 干活
  4.2. [check final] 周报核验            ← 把关：不过 → 整个 4 重跑
```

这是最常见的容器模式：**干活 + check 收尾 = 一个可自我验收的重试单元**。check 不过时重跑的是整个容器（4.1 也重来），`retry=2` 封顶。`final` 修饰符表示这道验收**任何成功路径都绕不过**——它是头部 Constraints 的可执行化身。

**介入点**（confirm/ask）是执行会真正停下来的地方。读 spec 时把它们圈出来，你就知道这个任务"哪里全自动、哪里要找我"——这是 spec 作者显式设计的，不是运行时的随机行为。教程 1 里 coffee-week 跑到"确认周目标"停下问你，就是第 1 步的 `[ask]` 在起作用。

## 实练：三分钟读完 coffee-week

用上面的方法通读 `examples/coffee-week.md`（30 行）：

1. **头部**：Goal=产周报；Constraints=数字必须确定性计算（所以统计是 act 不是 reason——约束落到了类型选择上）；Inputs 两个、Outputs 一个；
2. **骨架**：`1[ask] 确认目标 → 2[act] 统计 → 3[reason] 判断经营状态 → 4[subtask retry=2]{ 4.1[act] 组装 → 4.2[check final] 核验 }`；
3. **分工一眼清**：人出场一次（确认目标），LLM 动脑两次（判断、组装），引擎算数一次（统计），机器把关一次（核验）；
4. **数据管道**：`daily_sales → total/best_day/… → verdict/advice → weekly_report`。

读到这个程度，就够进入后面所有教程了。

> 顺带你也理解了 HOP 的一个设计：**流程先用 SOP 的写法给人写清楚，需要机器接管时再升格为 spec**——补上"谁干活"和数据流即可，控制流骨架一字不动。写给人的 HopSop 语法详见 `docs/concepts/HopSop标准作业流程.md`。

## spec 文件里的"其他章节"也是给引擎的

除了 Goal/Inputs/Steps 这些结构段，spec 文件里还可以有**内容章节**——任何非关键字的 `##` 节（比如 `## 背景`、`## 参考`）。**写进文件的就是要供给的**：这些章节全文会在执行时自动喂给执行 LLM（全程可见），不需要任何标记或引用。例外两个：节名带 `(不供给)` 标注的留给人读（比如流水账式的处置记录）；节里含步骤行的是排版分区不算内容章节。顺带：`Types:` 字段和输出声明后面的 `# 说明` 注释也会进执行 LLM 的提示——**注释不是给人看的装饰，是供给面**，写清楚值语义执行质量直接受益。
