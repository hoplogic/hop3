# 09 · 有序思考与 subtask free：还没想清楚的活，也能交给引擎

**给谁**：手头的活前半截清楚、后半截"到时候看情况"，又不想放弃引擎管护的 spec 作者。
**前置**：教程 02（读懂一份 spec）、03（探索与提交）。

## 一句话定位

写 spec 最常见的卡点不是语法，是**你还没想清楚**——探索型任务的后半截计划依赖前半截的产出，开工前根本定不下来。HopSpec 对此的回答是 `[subtask free]`（到步展开）：**写卡时只声明契约，执行到这一步时引擎停下来向你要计划**——那时前面的真产出已经在手上，拿着实际材料定计划，而不是开工前盲猜。

## 为什么有的活写不出完整步骤

看一个真实形态的任务："核对这批数据，异常项按情况处置"。

前半截能写：读数据、跑核对规则、列出异常项——步骤清清楚楚。后半截写不了：异常项长什么样还没见到，处置方式（改数据？报上游？挂账？）取决于核对出什么。硬要预先写全，只有两条路，都不好：

- **写死一种处置**——真跑出别的形态就得改 spec 重跑；
- **穷举所有分支**——case 树越写越深，多数分支永远走不到，白写。

这不是你水平不够，是**信息还没产生**。计划依赖运行时才出现的信息，就该推迟到运行时再定——这正是"有序思考"的核心：把"想清楚"这件事放到证据齐了的时刻做。

## 怎么写：一行契约，零子步骤

```markdown
1. [act] 跑核对规则
  - ← 数据
  + → 异常项清单: yaml  # 每项:位置+现象

2. [subtask free] 按分析结果处置异常项（到步展开——处置方式取决于步骤 1 的结论）
  - ← 异常项清单
  + → 处置报告: markdown  # 逐项:怎么处置的+依据
```

`[subtask free]` 底下**一个子步都不用写**。你写的是这一步的**契约**：吃什么（`- ←`）、交付什么（`+ →`）、这步是干什么的（描述）。中文写法 `[子任务 开放]` 等价。

这行能过 `validate`——children 为空是 subtask free 的合法形态，不是没写完。

## 执行到这一步时发生什么

引擎走到 subtask free，不会硬跑也不会报错，而是停下来发一个**要计划**的请求（`adaptive_needed`，标识 `reason: "initial_plan"`）。三件事值得知道：

1. **这不是失败**。`initial_plan` 的意思是"该出首个计划了"——别做失败归因，没有东西坏掉；
2. **请求里带着真材料**。`expansion_context` 装着 `- ←` 输入的**运行时实际值**——步骤 1 真跑出来的异常项清单就在里面。拿真产出定计划，这是到步展开对"预先盲猜"的本质优势；输入值为 null 的项列在 `missing_inputs` 里，计划里要么安排取数、要么按缺失处理；
3. **出计划的是执行方（agent），不是引擎**。引擎只管停下、供料、验收——想出子步骤的是驱动执行的 LLM。你（人）通常不用出手，但计划提交前后进展可见，看到跑偏随时可以叫停。

提交的计划就是普通的子步骤 markdown，引擎验过后接续执行，后面的路和写死的 subtask 一模一样——重试、check 打回、进展账，全套照旧。

## 两条展开纪律（引擎强制，不是建议）

运行时出的计划有个天生弱点：**没人预审过**。写卡时的计划至少被你看过一眼，到步展开的计划从生成到执行可能没有任何人过目。所以引擎焊死两条：

- **展开物必须含 check**——运行时计划的唯一把关就是它自己带的核验步。没有 check 的展开计划引擎直接拒收；
- **展开物禁止 commit**——不可逆动作（发送/删除/发布）必须在写卡时显式声明，让人看见。要 commit？写在 subtask free **外面**，消费它的交付物：

````markdown
2. [subtask free] 起草处置方案（到步展开）
  + → 方案: markdown

3. [confirm] 方案过目
  - ← 方案

4. [commit] 按方案执行处置
  - ← 方案
  > ```hop_python
  > written = write(path: "处置记录/异常项处置.md", content: 方案)
  > ```
````

探索归探索（可逆、引擎管），动真格归动真格（写卡时可见、人把关）——这是教程 03 那套 act/commit 分界在计划层面的延伸。

## 展开有预算，烧完要问人

到步展开可以嵌套（展开出的计划里还能有 subtask free），但次数有上限——防"越展开越发散"的失控。超限时引擎拒收并给出续批协议：**把情况呈给用户问"继续还是收手"，用户批了才能追加**。预算是人给的，追加也须人批——探索自由的定价方式和 replan 熔断同一哲学。

## 和"重规划"是什么关系

引擎向你要计划的场合一共两种，别混：

| | 到步展开（subtask free） | 重规划（adaptive replan） |
|---|---|---|
| 触发 | 走到一个没写子步骤的容器 | 计划**失败**且带反馈重跑也没救 |
| 性质 | 计划形态——"本来就打算到时候再想" | 失败修复——"原计划被现实否决了" |
| 标识 | `reason: "initial_plan"` | 带失败记录 |
| 授权 | 写 `free` 即授权 | 写 `adaptive` 即授权 |

重规划的完整故事（触发三条件、四道验证闸、候选文件沉淀、写法心法）值得单独一读——它是修复阶梯里最重的一档：失败记录里藏着世界的新样子（比如上游把 `amount` 从数字升级成嵌套对象），引擎让 LLM 把它读出来、把计划对齐上去，而交付契约与 `[check final]` 一动不动。想自己跑一遍：`examples/e2e-failure/e2e-adaptive.md`，两轮失败后现场看它换计划。失败处理全景见 [[D5-错误与异常处理]]。

两者共享同一套底线：**交付契约不许改，check final 不许拆**——无论计划是首次展开还是失败后换的，"什么算做完做对"焊死在卡上。

## 与 /hop 的衔接

如果你用 [[04-日常活交给hop|/hop]] 把日常活升格为 spec，到步展开就是它的标配形态——升格样例里"后面还没想清楚的段落"写的正是 `[subtask free]`。日常活恰恰是"前半截清楚后半截看情况"的重灾区，这个组合是为它生的。

## 上手建议

拿一个你真实的探索型活试：前半截写 2-3 个明确步骤，后半截整段收进一个 `[subtask free]`。跑到展开点时看两样东西——`expansion_context` 里带的真材料，和 agent 拿着材料出的计划。对比一下"如果开工前让我预先写这段计划"你会写成什么样，体感立刻就有了：**证据在手时定的计划，就是比盲猜的准**。
