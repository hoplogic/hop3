# D5 · 错误与异常处理：失败挂在结构上

**给谁**：写 spec 会碰到失败、或要调试一次失败执行的开发者。用户系列教程 03 讲过"探索可重试、提交有把关"——本篇讲全套：失败发生后引擎**按什么规则**处置、你在 spec 里**怎么声明**失败该谁管、调试时**去哪找**失败信息。
**权威**：`docs/concepts/HopSpec V3错误模型.md`（本篇是它的教学讲述版，细节以它为准）。

## 设计哲学：像组织处理失败，不像程序写 try/catch

传统两条路都不好：显式错误处理（每步后写"如果坏了怎么办"）三行正事七行防错；异常语法（try/catch 块）是纯程序员概念。HopSpec 取**异常的语义、弃异常的语法**——失败处理不写在流程里，而是**挂在结构上**：

```markdown
2. [subtask retry=3] 产出并核验周报     ← 读出来就是：这摊事，这个组负责，给三次机会
```

- 事务边界（subtask/case）= 职责范围；`retry=N` = 授权额度；
- 预算耗尽 = 报给上一级——沿结构向上找下一个事务边界；
- 调用链顶端的人是终极决策者。

spec 读起来像一张**职责表**，不像一段程序。第二原则：**修复优先于重试，重试优先于放弃**——执行者是能理解失败原因的 LLM，每层拿到的不是"重试或放弃"二选一，而是四档修复阶梯（见下）。

## 先立两条线：错误走状态机，值空间只有值

这是理解一切失败行为的地基，两句话：

1. **错误线**：语言层没有 try/catch、没有异常值、没有 Result 类型——**错误的原子单位是步骤**。失败的唯一载体是步骤状态机的 `fail(reason)`，入口四类：执行体报告干不成 / check 判 false / 计算异常（body 或 case 条件算错）/ 引擎守卫（超时、schema 反复不符、预算耗尽）。宿主异常绝不穿出语言面，出口统一折为步骤 fail；
2. **值线**：`None` 是普通合法值（同 Python），**不携带错误语义**——没有"消费 None 自动 fail"的闸。下游拿到 None 是业务情形（条件探测走降级、check 拦不合格产出），不是错误传播。

**fail 是函数级的**：一次 fail 只有两个去向——被某层事务边界接住修复，或穿透全部边界**终止整个实例**。不存在"失败了还继续往下跑"的第三态，所以"失败影响下游"这个问题在语义上不存在。唯一显式例外是 parallel 的部分失败（见下）。

## FailRecord：失败的"exception 对象"

失败不是布尔位，它携带信息，承载体是**失败记录**四字段：

| 字段 | 是什么 | 谁用 |
|---|---|---|
| 失败步骤 | 谁败了 | 升级链定位起点；人定位问题 |
| reason | 真因（人可读，LLM 拿它理解失败） | 修复阶梯的核心输入 |
| fail_kind | `error`（干砸了）/ `lack_of_info`（缺知识）/ `deterministic`（重跑必然同因，不烧重试预算，直达兜底）/ `tool_failure`（工具坏了，重试即愈的瞬时故障走这，见下节） | 路由修复路径的第一个分叉 |
| 轮次 | 同一边界内第几次失败 | 带反馈重跑知道"这是第几次、每次错在哪" |

三条性质：**逐轮累积不覆盖**（失败历史完整）、**随实例状态留存**（随时可查账）、**跨 call 边界加壳内核原封**（子实例失败记录原样作内核，外加 callee 标识壳——机械判据，杜绝驱动方自由文本转述）。

**调试时去哪找**：执行态的失败记录在 `.hopstate/<实例>/state.json`（`step_fail_reasons`）；给人看的轨迹在 `.hoplog/<run>/main.yaml`（每轮失败的 reason/fail_kind 实时入轨）。两边各留痕：前者参与修复决策，后者只读复盘。

## tool_failure：工具坏了，结构化自报而不是硬凑

`reason` 和无 body 的 `act` 步骤内置一个**工具故障退出口**：执行 LLM 的工具调用实际失败（报错/超时）、且没有这件工具就无法完成本步时，它不硬凑产出，而是输出单键 `tool_failure: 哪件工具怎么失败、试过什么自救`——引擎收到即按工具故障处置（`fail_kind='tool_failure'`）。

为什么要有这个出口：检索类工具坏了和"检索成功但确实搜不到"，在产出面**长得一模一样**——没有退路时，故障会伪装成"无结果"静默污染下游。给一个显式的自报通道，故障就是故障，不冒充业务结果。

两条使用纪律：

- **先自救，自救不成才报**：换参数重试、换清单里语义等价的工具、走别的路径拿到等效结果，都合法——确认换不动了才走 `tool_failure` 出口，不是工具一打嗝就报；
- **与 `lack_of_info` 分界**：材料本来就没有（缺知识）→ `lack_of_info`，走知识补充路径；取材料的**手段坏了** → `tool_failure`，走重试路径。两键语义不同不互替。

承接侧很简单：`tool_failure` 走容器缺省重试——瞬时故障（限流、网络抖动）重试即愈，不需要你在 spec 里写任何东西。有 body 的步骤不设此出口（body 的工具失败由引擎确定性承载）；`check` 也不设（判不了的正形＝如实判 false 并说明）。

## 报文面两条：空响应与实例号打错

调试时可能撞见的两个结构化报文，知道它们在说什么就不会被误导：

- **`EMPTY_OUTPUT`**——LLM 正常收尾但响应全空（不是截断，`stop_reason` 正常）。引擎不把空响应当有效值收下（否则空串灌进下游拼出残缺产物才发现），而是响亮失败触发重试，报文带 `output_tokens` 实数供核对。注意边界：模型显式产出 `键: ""` 的空值是合法业务值照常收——拦的是整个响应为空；
- **`INSTANCE_NOT_FOUND`**——显式传的实例号在 state_dir 下不存在（最常见成因：手抄实例号丢了一个字符）。报文会**列出该目录下真实存在的实例号**指路，抄错号的一眼能对出正确的号。早期这个场景误报"状态文件损坏"（`CORRUPT_STATE_FILE`），把排障方向带偏——现在两者语义分清：目录不存在归 INSTANCE_NOT_FOUND，目录在而状态文件缺/坏才是 CORRUPT_STATE_FILE。

## fail 之后：升级链 + 四档修复阶梯

步骤 fail 后引擎走固定流程：

```
步骤 fail
  → 就近找事务边界（沿祖先找最近的 subtask/case；subtask 总是内置边界，retry 缺省 3）
      ├ 找不到 → 未捕获失败，实例终止
      └ 找到 → 查预算（retry=N 是该容器的总失败预算，任何 child 的 fail 扣同一预算）
          ├ 耗尽 → 先看容器有没有 [on fail] 失败兜底块（见下节）
          │    ├ 有 → 执行兜底，正常走完=失败被消化，容器按 done 收场
          │    └ 无（或兜底也败）→ 容器自身 fail，作为"一个步骤"递归向外找边界（= 逐层上报；
          │        外层接手重跑时内层预算复位——外层给子树全新一轮机会）
          └ 未尽 → 按可信度降级修复：
              第 1 档 带反馈重跑    失败原因注入重跑上下文,结构不变（最可信,无 adaptive 时反复用它）
              第 2 档 选预声明备用链路（adaptive,有匹配时）——是选择不是生成
              第 3 档 基于备用链路重规划——有脚手架地改
              第 4 档 从零重规划——低可信兜底,产物经 HopLog 沉淀（下次同错命中第 2 档）
```

无论哪档，**交付契约（`+ →`）与 `[check final]` 不可改**——改策略不改目标。

**commit 退火先于一切档位**：事务边界内（含任意深度后代，跨 call 同界）已有 commit 成功执行的，该边界的 retry/adaptive **全部档位不再可用**——失败触发到它时立刻 fail 上报，防止 commit 随整组重跑再次执行。标记随 commit 执行即打上、沿祖先链全程有效不清零（重跑撤销不了已发生的不可逆动作，不存在"新轮次重新可试"）。所以写 spec 不必为"commit 后失败会不会重放 commit"设防——引擎不制造重放；幂等（教程 03 规矩二）防的是另一半：崩溃恢复重放。

**重跑是全新一轮**：容器子树从头再走，工具调用重新发生（不复用旧结果——旧结果可能正是败因）；但**变量自然保留**——上一轮残留是修复素材（`last_err` 反馈模式的基础），要干净起点的变量用 `= Null` 初值声明每轮重置。用户教程 06 解剖的 hop-fact-check 自查回路（check final 写 gap → retry 时定向补漏）就是这套机制的教科书用法。

## `[on fail]` 失败兜底：放弃之后先做什么

**定位先说清**：这是高级特性，缺省语义（耗尽上浮、逐层升级）覆盖绝大多数场景——**普通 spec 不需要它**。要用它的典型是构建器/元编程场景（hopbuild2 的"试 N 遍再放弃"是首个消费方）。但读失败日志时你会撞见它，得认识。

**它是什么**：subtask/case 的失败兜底块——升级链的 except 位。此前 retry 耗尽只能被动上浮，作者无法声明"放弃之后先做什么"（记档、降级、给兜底值）：

```markdown
2. [subtask retry=2] 抓取外部数据
  2.1. [act] 调接口抓取
    + → data: yaml
  2.2. [on fail] 兜底：给空数据并记档
    2.2.1. [act] 置兜底值
      + → data: yaml  # 空列表兜底,主线可继续
```

**五条规则**（读日志/写兜底都靠它们）：

1. **耗尽才进，不是每次失败都进**——每次失败归 retry 重跑，预算耗尽才轮到兜底；
2. **接住语义**：兜底块正常走完 = 失败被消化，容器按 **done** 收场、主线继续；块内 `+ →` 给容器输出赋兜底值（补上失败路径输出悬空的坑）；
3. **兜底自身失败不再兜**——容器 fail 照旧上浮（没有嵌套 catch，正如 except 里再抛）；
4. **位置**：必须是容器的**最后一个子节点**（`check final` 之后），一容器至多一个；正常路径整块 skipped，零成本；
5. **与 commit 退火正交**：退火拦的是"重跑重放"（retry 失效防不可逆重放），兜底是"善后"不重放任何东西——退火后失败**跳过 retry 阶梯直达兜底**。确定性失败（`fail_kind='deterministic'`）同理：跳过重试档位直接进兜底——只掐重跑，不掐善后。

**翻译识别信号**（把自然语言转 spec 时）："实在不行就……"、"失败的话就记下来跳过"、"不行就用默认值"——这类句子翻成 `[on fail]` 块。

## 未捕获失败：实例终止

再也找不到边界接手时，**实例立即终止、判 failed、上报 caller**——与未捕获异常终止函数完全同构。两条到达路径：一开始就没边界（平铺 spec，步骤没组进 subtask）；或耗尽到顶。终止时值空间不清理，caller 拿到的是"failed + 失败记录 + 部分产出"。

**要点反转**：失败中断执行是**缺省**，不需要作者做任何事；要**容忍**失败才需要动结构——包事务边界（给修复机会）、声明 `[on fail]` 兜底（给放弃后的善后路径）、用 parallel（集合的部分失败语义）、或用 branch 把"可能失败的探测"降为业务分支。写 spec 时问自己的不是"哪里要加错误处理"，而是"哪摊事我愿意给它重试机会、给几次"。

## parallel 的部分失败：唯一的显式例外

parallel 容器内一个 child fail **不打断**在跑的兄弟；失败 child 不贡献收集元素（**列表变短**），失败记录照常记账；部分结果可否接受由 join 后的消费步骤裁量（想核数量就 check 一下 `len`）。这是作者选用 parallel 结构时显式选择的集合语义——集合操作天然尽力而为——不是引擎的失败容忍缺省。

## parallel 的批量等人：HITL 队列

部分失败讲的是"child 败了怎么办"，这节讲"child **要问人**怎么办"——并行活里有 confirm/ask 时的语义（曾经的能力缺口：早期版本子实例一暂停就判 failed，"批量任务里单点要问人 = 整批报废"；2026-08-25 已实装为排队机制）。

**机制一句话**：并行 child 跑到 confirm/ask 就地暂停、**问题卡入队**，其余 child 照跑不受影响；人**逐张应答**，答一张续跑一个。

四条你会实际感知到的行为：

1. **等人不占并发名额**——暂停的 child 把名额让出来，其余派发照跑；但**收齐门照等**：等人的活没答完，容器不会提前闭合（等人≠完成）；
2. **队列全量可见**——standalone 下轮询 `run_status`，响应带 `paused_queue` 数组：全部待答卡一次看清（每张携问题、上下文、`child_instance` 寻址标识）。run 整体状态如实分档：主线还有活干 = `running` 带队列；主线只剩等人 = `paused` 带队列；
3. **应答按卡路由**——`resume_run` 带上那张卡的 `child_instance` 就是答它；答完该 child 续跑（重新排队占名额），其余卡继续等。不带 `child_instance` 则走顶层路由（单实例场景零变化）；
4. **主线死了连坐**——主线失败或 `stop_run` 时，等人中的 child 同批终止（答案已无处安放），卡随之清除，不留死卡。

**驱动侧纪律**（写 driver/skill 的人注意）：队列里的卡**逐张问真人、不合并、不替答**——每张卡都是 spec 作者显式声明的介入点，批量场景不改变"人拍板"的语义，只改变"排队等你"的形态。

**范围注记**：v1 覆盖独立模式的两种并行形态（subtask parallel / call parallel）；复用模式的驱动协议扩展在路线图上（现走对账兜底不受损）。契约权威 `docs/design/parallel-execution.md` ^anc-exec-parallel-hitl-queue（六件套全文）。

## call 边界：失败的跨函数传播

`call` 是函数调用，失败传播语义对称于成功回填：

- 子实例 failed → call 步骤 fail，子实例失败记录**加壳传递**（内核原封 + callee 标识壳）——等价于异常带完整 stack trace 跨函数，而不是 catch 后只剩一句人工总结；
- `fail_kind` 跨界继承：子因 `lack_of_info` 败，父层先补知识再试，不当普通 error 烧预算；
- 重跑 call = 重新调用整个子 spec；
- **confirm 不在此列**：授权暂停不逐层上传，直达有权决策者——"有权"是全局属性不是栈属性。

监督链全貌：**subtask 局部修复 → 耗尽上报 caller → 每层 caller 在更广上下文修复 → 顶端人类终极决策**。这是 catch-reason-repair-or-escalate，不是 catch-and-rethrow。

## 动手验证：三个现成的失败场景

失败路径有整批真机 e2e（六场景,已并入发版档 `npm run test:live:core`），其中三个正好对应本篇三块机制，spec 都在 `examples/e2e-failure/`：

| 场景 | 验证的机制 | 对应本篇 |
|---|---|---|
| `cc:repair` | check 失败 → last_err 反馈 → 重跑轮修好 → completed | 修复阶梯第 1 档 + 变量自然保留 |
| `cc:uncaught` | 计算异常 + 无边界 → 实例终止，后续步骤 skipped，前序产出仍在 | 未捕获失败 |
| `cc:call-fail` | 子 spec 败 → CalleeFailure 内核原封跨界 → 父 failed | call 边界加壳传递 |

读这三份 spec + 跑一遍看 hoplog，本篇每个概念都有实物对应。
