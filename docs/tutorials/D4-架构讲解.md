# D4 · 架构讲解：引擎为什么长这样

**给谁**：读完 [[D1-用AI做工程-从概念到设计]] / [[D2-用AI做工程-AIcoding与验收]]、要给 AI 派**架构级**活（跨模块改动、新增适配层、动 Provider 边界）的人。
**与权威文档的关系**：`ARCHITECTURE.md` 是架构事实的权威（人与 AI 的共同根）；本篇是它的**教学讲述版**——按"为什么"的顺序重排，帮你建立能拍架构决策的全景。细节以权威文档为准。

## 一句话架构

**一个模式无关的执行引擎核，外面套两种"谁出推理"的适配壳。**

```
                    ┌──────────────────────────────┐
                    │        引擎核心（纯逻辑）       │
                    │  SpecParser    解析+验证      │
                    │  ExecutionEngine  状态机      │
                    │  PromptAssembler  上下文组装   │
                    │  BodyInterpreter  hop_python │
                    └──────┬───────────────┬───────┘
                 Provider 接口          Provider 接口
                    ┌──────┴──────┐  ┌────┴───────────┐
                    │ 复用模式适配  │  │ 独立模式适配     │
                    │ HopCLI      │  │ StepDispatcher │
                    │ File持久化   │  │ MCP server     │
                    └──────┬──────┘  └────┬───────────┘
                    ┌──────┴──────┐  ┌────┴───────────┐
                    │ 载体（driver）│ │ LLM API        │
                    │ CC / Codex  │  │ (deepseek 等)  │
                    └─────────────┘  └────────────────┘
```

## 为什么这样分：三个决定性的"因为"

**① 因为推理可以在两个地方发生。** 用户教程讲过两种模式的取舍（复用=对话 LLM 当推理引擎，零配置；独立=引擎直调 API，省成本不占对话）。架构上这意味着：**引擎核绝不能假设"推理在哪"**——它只产出"下一步该干什么 + 完整上下文"（NextResponse），谁来推理是适配层的事。这就是"模式无关"原则，引擎核三组件在两种模式下行为完全一致。

**② 因为载体会不断增加。** CC、Codex、将来的 OpenCode——每个载体的原语都不同（CC 有 Agent 工具和 AskUserQuestion，Codex 有自己的 subagent 与对话问答）。若引擎迁就任一载体，每加一个载体就得改引擎。所以**引擎与 CLI 载体中立**（纯 JSON in/out，不假设工具执行能力），每个载体只需一套等价的**驱动指令**（`driver/` 下并列）——加载体零引擎改动。纪律是"同语义、分载体实现"：调用原语可以不同，步骤语义不许漂移（机检 `check-driver-carriers` 守着）。

**③ 因为外部世界必须可替换。** 文件系统、网络、LLM API、知识库——引擎核**一概不直接碰**，全走四个 Provider 接口：

| 接口 | 管什么 | 两种模式各给什么实现 |
|---|---|---|
| PersistenceProvider | 状态快照存取 | 复用=FilePersistence（跨进程落 `.hopstate/`）；独立=MemoryPersistence（进程内） |
| ToolProvider | act 步骤的工具执行 | 独立=DefaultToolProvider（Read/Write+沙箱）；复用=载体的工具面 |
| KnowledgeProvider | L2 知识注入 | 宿主注入（RAG/向量库） |
| IdentityProvider | 凭证 | 宿主注入或默认实现 |

唯一有意的例外：HopLog 执行日志直接落盘不走 Provider——轨迹可还原是两种模式的共同原则，日志是本质职责不是环境适配。

## 一次执行的生命线（复用模式）

把用户教程里"跑一个 spec"的体验翻到架构视角：

```
/hopspec run spec.md
  → 载体 driver 起 subagent 跑 hopjit CLI
  → SpecParser 解析验证 → Engine 初始化（FilePersistence 落盘）
  → 循环：Engine.next_step 产出 NextResponse（6 层上下文）
      ├ reason/check → 载体 LLM 推理，结果 submit 回引擎
      ├ act（有 body）→ BodyInterpreter 确定性执行，零 LLM
      ├ confirm/ask  → paused，停给真人
      └ parallel     → dispatch_ready 派发信号，worker 各领子实例
  → completed，outputs 交付
```

独立模式同一条生命线，只是"载体 LLM 推理"换成"StepDispatcher 直调 LLM API"、持久化换 MemoryPersistence、对外协议壳换 MCP server（start_run/run_status/resume_run/list_runs/stop_run 五工具）。**每步谁推理、状态落在哪，是读懂任何执行问题的两个坐标。**

## 双态分布：哪里是代码，哪里是智能

HOP 的双态融合（HopType 体系）落到本库：**确定性的一律是 TypeScript**（Parser/Engine/Assembler/BodyInterpreter/CLI/Dispatcher 调度壳——都是纯代码，测试可全覆盖）；**推理智能只在两个口**——复用模式在载体侧（CC/Codex 的 LLM），独立模式在 StepDispatcher 的 LLM 调用里。给 AI 派活时这条分布就是边界感：改 TS 组件=改确定性行为（正反例可钉死）；改 driver 指令/prompt 组装=改智能侧行为（要真机 e2e 才见真章——D2 讲的两条腿在这里合流）。

## 给 AI 派架构级活的三个注意

1. **动 Provider 边界 = 动契约面**：四接口是引擎核与外部世界的全部通道，加方法/改签名波及两种模式的全部实现——派活时明确要求 AI 先列两侧实现的波及清单；
2. **加载体不改引擎**：新载体的正确路径是新增 `driver/<载体>/` 一套驱动指令 + 对齐既有设计锚点——AI 若提出"顺便改一下引擎配合新载体"，警惕，那多半在破坏载体中立；
3. **分层依赖单向**：shared < core < adapter，低层不得引高层（机检 `check-layer-imports` 守着）——AI 的实现若需要"引擎核 import 适配层的东西"，说明抽象放错了层，退回设计。
