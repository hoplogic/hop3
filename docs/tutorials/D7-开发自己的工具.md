# D7 · 开发自己的工具：给引擎添能力

**给谁**：要给 HopJIT 添一个 spec 可调用的工具的开发者——领域计算、私有系统对接、任何内置工具（read/write 等）覆盖不到的能力。**动手前先看「已就绪工具面」一节**——PDF/OCR/检索/浏览器四件常用输入面已落地,可能零开发。要**维护 spec 文本本身**（读骨架/插步换步/验证）的不用开发——引擎内置的 spec 内容工具族见 [[D11-维护spec的内置工具]]。
**前置**：用户教程 [[08-接入MCP服务]]（注册与调用面在那篇——本篇讲注册的东西**怎么造**）。
**权威**：注册文法（用户写什么）在 `docs/reference/配置参考.md`；绑定实现契约在 `docs/design/tool-interface.md`。

## 先看现成的：已就绪工具面

动手开发前先查这张表——四件常用输入面工具已经落地（2026-08-26 批,hopissues 0038-0042），注册样例全部可抄、全部真机验证过。你的场景若只缺"取材料"，大概率零开发：

| 工具 | 干什么 | 来源 | 注册样例 |
|---|---|---|---|
| `pdf_extract` / `pdf_page_to_image` | PDF → 分页文本+元信息；指定页转 PNG（OCR 前置）。扫描页在 `no_text_pages` 如实标注并指路 OCR——不静默返回空 | **hopdoc-tools** 独立库（Python MCP server,pymupdf） | hopdoc-tools 库 README（含全键 output_schema 与 unwrap 必配项） |
| `ocr_image` | 图片/扫描件文字识别（RapidOCR 本地引擎,零外网,中文强）。低置信行点名、过滤不静默 | 同上,`[ocr]` 可选件（约 +100MB,纯 PDF 用户不背） | 同上 |
| `web_search` | 查询词 → 结果页清单（标题/URL/摘要） | 云端 MCP 检索服务——**provider 中立**：`tool_id: web_search` 解耦 wire 名,换后端只改配置 spec 零改（百炼形态已真机验证,任何 MCP 检索服务按模板同构接入） | `examples/hoptools-websearch.yaml` |
| `browser_navigate` / `browser_snapshot` 等 | 浏览器自动化：打开 URL（含动态渲染页）取内容、截图、点击填表 | 微软官方 `@playwright/mcp`（npx 免装直跑,零自建） | `examples/hoptools-playwright.yaml` |

四件的分工一句话：**不知道 URL 用 `web_search` 搜；已知 URL 用 browser 系取渲染后内容；本地 PDF 用 `pdf_extract`；扫描件走"转图 → `ocr_image`"闭环**。这是文章核查/调研/评审类 hopskill 的完整信源获取面。

配套的端到端最小 spec（每件工具怎么在 spec 里声明和调用,照抄改参即可）：

- `examples/websearch-brief.md`——检索 + 成文简报（逐要点附来源 URL,未命中如实说）;
- `examples/webpage-extract.md`——打开网页 + 按关注点提取;
- hopdoc-tools 库 `examples/hopjit/`——PDF 三工具连跑探针（提取→判无文本层→转图→OCR）。

四条实撞经验，接任何工具前先读（每条都真烧过时间）：

1. **接值类型声明如实**——playwright 返回散文文本,接值声明 `text`;声明 `yaml` 当场 SCHEMA_MISMATCH。工具返回什么形态就声明什么,不按"内容像结构"想当然;
2. **`output_schema` 按声明键裁剪**——消费的键都要声明,漏声明的键会被裁掉（下游取不到还查不出为什么）;
3. **`unwrap: json-in-text`**——server 返回 JSON-in-text（多数 Python/云端 server 如此）必须声明解包,否则整串当文本;
4. **stdio server 的 command 写装好的命令**——不要写 `uvx`/`npx -y` 现场解释形态当常驻用（每次启动做依赖同步,冷缓存下百 MB、并发争锁,拖过 MCP 60s 连接时限）;首次接入先手动预热一遍。

交互类工具（点击/填表/提交）注册时标 `requires_commit: true`——act 步误用会被 `COMMIT_REQUIRED` 当场拦（真机验证过的闸,不是纸面声明）。这是把"试错阶段不做不可逆操作"纪律推到工具面的形态。

## 先选路：两档绑定

| | **in-process 扩展模块** | **MCP server** |
|---|---|---|
| 形态 | 一个 JS 模块，装载进引擎进程 | 独立进程/服务，MCP 协议通信 |
| 性能 | 函数调用，零序列化 | 每次调用过一层协议 |
| 隔离 | **无**——它崩 = 引擎崩 | 进程隔离，崩了只是该次调用失败 |
| 状态 | 无生命周期（纯函数最佳） | 可持有状态（连接池、缓存、会话） |
| 语言 | JS/TS | 任意（MCP SDK 覆盖主流语言） |
| 适合 | 轻量确定性计算、无外部依赖的领域逻辑 | 有状态服务、重依赖、非 JS 实现、要给多方复用 |

**选型一句话**：纯函数式的轻计算走 in-process（快、简单）；有状态、要隔离、或本来就是个服务的走 MCP。拿不准就 MCP——隔离总是更安全的缺省。

## 路线一：in-process 模块（五分钟上手）

**接口契约就两个导出**（`^anc-exec-inprocess-binding`）：`execute(name, args)` 必须，`close()` 可选。参考例 `examples/ext-tools/word-stats.mjs` 全文即模板：

```js
// 你自己仓库里的一个文件——不进引擎库（引擎保持领域无关）
export function execute(name, args) {
  if (name === 'word_stats') {
    const text = String(args.text ?? '');
    const words = text.split(/\s+/).filter(Boolean);
    return {
      result: { words: words.length, chars: text.length },
      success: true,
      content_type: 'json',
    };
  }
  return { result: `unknown tool: ${name}`, success: false, content_type: 'text' };
}

export function close() { /* 有资源要还才需要实现 */ }
```

返回值三字段：`result`（字符串或结构化对象）、`success`、`content_type`（text/json）。**模块内抛异常不会炸引擎**——引擎 catch 住报 `EXT_TOOL_ERROR`，该次调用失败走升级链；但这是兜底不是许可，你的本分是在模块内处理好可预见的错。

**注册**（配置文件 `tool_servers:` 节的第三形态——通常写在项目级 `hopjit.yaml`）：

```yaml
tool_servers:
  - name: word_stats_lib
    binding:
      kind: in-process
      module: ./ext-tools/word-stats.mjs   # 相对声明所在配置文件的目录
    tools:
      - name: word_stats
        requires_commit: false
        input_schema:            # in-process 无发现源——声明即唯一发端校验源
          type: object
          properties:
            text:
              type: string
          required: [text]
        output_schema:
          words: int
          chars: int
```

**把参数语义写进注册（params/notes——两条路线通用）**：注册条目除了 `input_schema`（机器校验面），还应写 `params`（人与 LLM 的语义面）——每个参数一条 `- 名: 类型  # 说明`，说明写到**杜绝望词生义**：值语义（装的是 ID 还是名称）、取值来源、错用后果；跨参数的复杂语义（幂等性/上限/调用纪律）放 `notes:` 多行块。执行 LLM 组装调用时吃的就是这份语义——工具好不好用，一半取决于这里写没写清。样例与文法见 `docs/design/tool-interface.md` ^anc-tool-params-notes。

**in-process 的责任书**（装载 = 你对下面三条的断言）：

1. **审计状态**：它跑在引擎进程里，引擎机检不了你的库——**声明装载 = 操作者对该模块审计状态的断言，责任随声明走**。你的工具库住自己的仓库、走自己仓库的工程链（一行不进引擎库）；
2. **不可逆操作如实标 `requires_commit: true`**——这是 act 拦截的唯一依据，标错等于绕过整个探索提交分离（教程 03）；
3. **schema 如实**：in-process 没有 tools/list 发现，你声明的 `input_schema` 就是发端校验的全部——不声明 = 发端放行（校验责任滑到你模块内部）。

## 路线二：MCP server

用任意语言的 MCP SDK 写一个 server（stdio 或 Streamable HTTP），实现 `initialize` + `tools/list` + `tools/call` 就够——**引擎只消费这个最小子集**，会话性能力（订阅/回调/sampling）写了也没人听：执行主权单向是硬性质。

给 HopJIT 用时的注意点（其余同教程 08 的注册面）：

- **`tools/list` 认真写**：注册侧没声明 `input_schema` 的工具会从你的 tools/list 补全——你的 schema 就是发端校验源；
- **annotations 不被信任**：`requires_commit` 权威在用户的声明侧——你标什么不重要，用户声明什么算什么。所以文档里把哪些工具有副作用**写清楚**，让用户能正确声明；
- **错误报文写人话**：调用失败时的响应原文会进 FailRecord、供 replan 消费——一句"internal error"帮不了任何人，带上下文的错误信息是你的工具对修复阶梯的贡献；
- **单调用 60 秒硬闸**（用户可按 server 覆盖）：长操作要么内部分页、要么文档里让用户调 `call_timeout_ms`；
- **stdio server 不用管生命周期**：引擎 spawn、run 终态三段礼貌关停（EOF→SIGTERM→SIGKILL）——你只要正确响应 EOF 退出即可。

本库自己的 `hopjit-mcp`（standalone server，见 [[D4-架构讲解]]）就是这条路线的完整实例——五工具、注解齐全、错误结构化。

## 测试你的工具

- **in-process**：模块是纯 JS——直接单测（参考 `word-stats` 的用法：正常输入 / 未知工具名返回 `success: false` / 抛异常时引擎报 EXT_TOOL_ERROR 进程存活——最后这条是引擎的正反例，你测前两条）；
- **MCP server**：先脱离引擎用 MCP Inspector 或手工 JSON-RPC 验 initialize/tools/list/tools/call 三件；再接引擎跑一份调用它的 spec 看 HopLog（每次调用的进出在案，[[D6-用HopLog诊断]]）；
- **端到端**（D2 的两条腿在工具上的形态）：写一份最小 spec 真调你的工具跑到 completed——工具的"装在真引擎里能跑"只有这一步能证明。
