# D8 · 模型与工具配置：省钱与添能力

**给谁**：用独立模式（standalone）跑任务、想**按步骤类型分档用模型省成本**、或要**给引擎接工具**的开发者。
**权威**：`docs/reference/配置参考.md`（全字段表与完整样例——本篇是它的心法版，字段细节以它为准）。

## 两个命令：`/hopspec` 与 `/hopspec-mcp`——名字即模式

跑 spec 的入口有两个命令，**名字直接编码执行模式**，没有探测、没有自动切换（Codex 载体同构：`$hopspec` / `$hopspec-mcp`）：

| | `/hopspec`（缺省入口） | `/hopspec-mcp` |
|---|---|---|
| 执行模式 | **复用模式**——你的对话 LLM 亲自当推理引擎，hopjit CLI 只管流控 | **独立模式（standalone）**——执行在 hopjit MCP server 进程内，server 自己调 LLM API |
| 前置 | 零配置（装好 skill 即用，不需要 API key） | 本篇的配置（providers + 载体注册 MCP server）+ `hopjit install-skill --mcp` 装壳 |
| 什么时候用 | 入门、调试、需要载体完整工具面的 spec | 跑得久、跑得频、想换轻量模型省成本的任务 |

**为什么是两个命令而不是一个命令自动判**：早期版本曾让 skill 在运行时探测环境选模式——两次真机实红证明，把"查工具面、读配置"这类判定放进自然语言 skill，任何一侧信号不全就静默滑向另一条路径，错得合规、难以觉察。现在**模式由你敲的命令名决定**：`/hopspec` 恒复用、`/hopspec-mcp` 恒 MCP，敲错了会收到明确报错指路正确命令（引擎有双执行硬闸——同一个执行实例被两条通道各推一遍是最高危事故，跨通道操作直接被拒）。

裸说"跑一下这个 spec"时缺省就是 `/hopspec`（复用模式）；只有你明说走 MCP/standalone 时才用 `/hopspec-mcp`。**同一份 spec 两个命令都能跑，一个字不用改**——本篇往下的全部配置都只服务 `/hopspec-mcp` 这一半。

## 配置地图：什么住哪（先记这张图）

```
~/.hopjit/config.yaml      ← 系统级：跟着人走（providers 凭证引用、环境的模型档位表）
<项目根>/hopjit.yaml        ← 项目级：跟着项目走（可进仓库；工具面通常在此）
    同一 schema，逐节合并，项目级赢

spec 文件内:
  Config: 段                ← spec 级：本 spec 在意的模型差异
  步骤 > @model 标注         ← 步骤级：单点覆盖
```

**分工心法**：系统级装"你是谁、用什么后端"（换项目不变）；项目级装"这个项目要什么工具"（随项目进仓库——队友 clone 下来工具面就齐了）；spec 只写它**在意的差异**。层层可缺省——独立模式最小配置=一条 provider,其余全可省（复用模式才是真零配置），**分档是优化不是义务**。

**改了配置什么时候生效**（server 常驻时）：`tool_servers`/`env`/`routing_rules`/`default_model` 这些**数据面节每次 `start_run` 重读**——改完下一个 run 即见；`providers`（后端与凭证）例外，改它须重启 server。写错不会静默用旧配置，当次 run 直接拒。

## 模型配置：三层协作的一个主题

### 为什么分档：不同步骤类型配不同强度的模型

步骤类型天然对应算力需求——这正是"谁干活"分类（教程 02）在成本上的兑现：

| step_type | 干什么 | 建议档位 |
|---|---|---|
| `act`（含 commit） | 确定性执行，几乎不动脑 | 轻量档（flash 级） |
| `reason` | 推理分析 | 中强档 |
| `check` | 核验产出 | **宜换一家**——交叉验证防同源盲区 |
| `replan` | 重规划 = 元编程，须会写 HopSpec | 最强档 |

系统级档位表（`config.yaml` 的 `routing_rules`）：

```yaml
routing_rules:
  - step_type: act
    model: deepseek/deepseek-v4-flash
  - step_type: reason
    model: deepseek/deepseek-v4-pro
  - step_type: check
    model: bailian/qwen3.7-plus     # 换一家核验
  - step_type: replan
    model: zhipu/glm-5.2
```

（`confirm`/`ask` 是介入点、无 LLM，不可路由；`commit` 无专条时吃 `act` 条。）

### spec 层与步骤层：只写差异，不整块重配

```markdown
Config:
- models:
  - reason: deepseek/deepseek-v4-pro   # 本 spec 只对推理档有意见
- model: deepseek/deepseek-v4-flash    # 其余类别的单默认（可省）
```

```markdown
2. [reason] 分析舆情风险
  > @model deepseek/deepseek-v4-pro    # 单步覆盖，最高优先级
```

**逐键继承**是这套配置的统一心智：`Config.models` 没写的类别落 `model` 单默认、再落系统档位表——不是整块覆盖。解析优先级一条链（specific → general）：**步骤 @model → spec models[类别] → spec model → 系统 routing_rules → 系统 default_model → 兜底**，第一个命中即生效。

### 偏好语义：spec 引用的模型环境里没有，不炸

spec 面写的模型引用是**偏好**：环境里有这个 service 就用；没有则 warn 一条、沿优先级链继续向下，**链尾恒有缺省，必有归宿**。所以写了 `zhipu/glm-5.2` 的 spec 在没有智谱的环境照常跑——spec 天然可移植。**系统层没有偏好语义**：config.yaml 自己引用了 providers 里没有的 service 是笔误，启动即拒。

### 凭证纪律（一切模型配置的地基）

`providers` 条目的 `api_key_env` 只写**环境变量名**——配置文件绝不保存 key，写明文启动即拒。这条与教程 08 的工具凭证（`auth_env`）同一纪律。

## 工具面配置：要点速记

字段全表在教程 [[08-接入MCP服务]] 与配置参考——这里只记开发者最常用的判断：

- **住哪**：通常项目级 `hopjit.yaml` 的 `tool_servers:` 节——工具面跟项目走，进仓库共享；
- **三种绑定**：云端 MCP（`transport: http` + `auth_env`）/ 本地 MCP 子进程（`stdio` + `env_passthrough` 白名单）/ in-process 模块（`module:` 相对**声明所在配置文件**的目录——项目级声明就相对项目根）；
- **两条铁律**：白名单语义（声明即启用，server 实况不整包背书）；调用名全局唯一（`tool_id`/`name` 跨系统级+项目级+内置工具判重，冲突起 run 即拒——结构化错误报两个来源）；
- **`requires_commit` 必填**且权威在声明侧——act 拦 / commit 放的唯一依据；
- **`params` 推荐写**：逐参数语义声明（`- 名: 类型  # 说明`，notes 装跨参数纪律）——执行 LLM 的语义供给面，也是 spec `Tools:` 段 init 对账的对照物；
- **快捷方式**：`hopjit install-skill --plus` 会把检索（百炼 web_search）与浏览器（Playwright）两组工具配置自动并入系统级 `~/.hopjit/config.yaml`（已有同名 server 不覆盖），同时装上消费它们的两个研究 skill——手抄 `examples/hoptools-*.yaml` 之前先看这条路够不够；
- 想自己造工具 → [[D7-开发自己的工具]]。

## spec 环境参数（env: 节）：路径不硬编码

spec 里要引用材料库/知识库这类**环境路径**时，不硬编码、不猜 cwd——统一 `hop_env_` 前缀参数，配置文件 `env:` 节填值：

```yaml
env:
  hop_env_kb_root: ~/vaults/判据库
```

spec 里 `[[{hop_env_kb_root}/入库判据#完备性]]` 直接引用。三条硬规则：**只读**（spec 不能产出 hop_env_* 变量）、**凭证禁入**（会落盘入日志——key 只走 api_key_env）、**未定义即响亮报错**（不静默拼空路径找错文件）。

## 转 standalone 前的跑前体检：deep-validate

一份在复用模式（CC 亲自执行）跑得好好的 spec，转到 standalone（引擎直调 LLM API）不一定能活——两种模式的执行者能力面差别很大：复用模式的执行者自带文件工具、命令执行、整个 shell；standalone 的执行者是裸 API LLM，只有十一件文件工具、白名单命令和写域闸。步骤说明里一句"用 test -s 判断文件存在"，复用模式顺手就做了，standalone 的判官根本没有 shell——这类错配 `validate` 查不出来（它管的是静态文法），要理解说明的语义、对照执行模式的能力面才能发现。

**deep-validate 就是干这个的**：validate 的深化档，用 LLM 对你的 spec 做跑前体检——五个判据面（执行模式能力面矛盾／确定性步骤形态／体量模式／环境依赖／写域与路径），产出一份建议性风险报告（不阻断执行，采不采纳归你）。分钟级快检，不是 anchor-audit 那种几十分钟的全量审计。

**手工调用**（没有自动挂载），它本身就是一份 spec：

```
/hopspec-mcp run scripts/deep-validate/deep-validate.md   --params '{"spec_path": "你的spec.md", "exec_mode": "standalone"}'
```

**什么时候跑**：写好的 spec 第一次要在 standalone 跑之前；或者复用模式写的老 spec 要转 standalone 时。一个真实战果作参考：它首跑就命中了 anchor-audit 旧版 spec 的 6 个真坑——那 6 个坑此前是靠真机跑一趟死一趟才逐个撞出来的。

## 三个常见配方

**配方一：全 deepseek 最省心**（一条 provider + 两条分档）：

```yaml
providers:
  - service_id: deepseek
    protocol: anthropic
    base_url: https://api.deepseek.com/anthropic
    model: deepseek-v4-flash
    api_key_env: DEEPSEEK_API_KEY
routing_rules:
  - step_type: reason
    model: deepseek/deepseek-v4-pro
  - step_type: replan
    model: deepseek/deepseek-v4-pro
# act/check 落 provider 缺省的 flash——执行类用轻档,推理与重规划用强档
```

**配方二：项目级只加工具**（providers 从系统级继承）：

```yaml
# <项目根>/hopjit.yaml——整个文件就这一节,进仓库
tool_servers:
  - name: hopkb
    binding:
      kind: mcp
      transport: stdio
      command: hopkb-mcp
    tools:
      - name: kb_search
        requires_commit: false
```

**配方三：关键 spec 钉住核验档**（防环境档位表变化影响核验质量）：

```markdown
Config:
- models:
  - check: bailian/qwen3.7-plus   # 核验换家钉死;环境没有 bailian 时按偏好语义落系统档
```
