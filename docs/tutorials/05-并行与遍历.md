# 教程 5 · 并行与遍历：让引擎替你数数

**目标**：学会在 spec 里写"对每个 X 做 Y"和"这几件事同时干"，并理解为什么这比让 LLM 自己记要可靠。
**前提**：完成 [[02-读懂一份spec]]（步骤类型与 `← / + →` 数据流）。

## 为什么这件事值得单独一篇

"对每个文件做检查"——自然语言 skill 里最常见的指令，也是最常翻车的：做到第 7 个忘了还有 3 个（上下文一长必现）。HopSpec 的答案是**把遍历交给引擎**：引擎按列表长度驱动游标，做完一个收一个，全部收齐才放行。LLM 只负责"做一个"，**数数的活它一个都碰不到**。

并行是同一机制的加速形态：标注了 `parallel` 的活被派出去同时跑，主线不等它，容器结束前收齐。

## 第 1 步：先跑一个现成的

Claude Code 命令：

```
/hopspec run examples/syntax/parallel-aggregate.md
```

Codex 命令：

```
$hopspec run examples/syntax/parallel-aggregate.md
```

这个 spec 把"三个维度（统计/趋势/异常）的分析"整体标成一个 `parallel` 活：主线走到这里把它派出去，自己继续往下，聚合步骤要用到它的产出时**等它完成**才走。这就是并行的执行语义："派出去跑、收齐才走"。

> 一个诚实的注记：`parallel` 声明的是"**可以**并行"（活自包含、无共享写），**实际并发度归执行模式管**——独立模式（standalone）真并发；对话驱动的复用模式在当前版本按顺序执行这些活（结果完全一致，只是不抢时间；并发恢复在路线图上）。spec 写法两边一个字不差——这正是声明与执行分离的好处：你只管声明性质，调度策略引擎说了算。

## 第 2 步：读懂两种写法

### 写法一：遍历（for-each + collect）

"对每个 X 做 Y，结果收成列表"：

```markdown
2. [loop for-each file in file_list, collect issue into issues] 逐文件审查
  + → issues: [yaml]        # 收集列表（容器头声明）
  2.1. [subtask parallel] 审查单个文件    # 标 parallel = 每轮派一个、边遍历边并发
    + → issue: yaml         # 单项端：每轮产一个
    2.1.1. [reason] 审查
      - ← file              # file = 本轮元素，for-each 子句自动绑定
      + → issue
```

三个要点：
- **`collect issue into issues`**：每轮的单项 `issue` 由引擎收进列表 `issues`——单项和列表是两个变量，你只写"产单项"，收集是引擎的事；
- **`file` 不用声明**：for-each 子句本身就是它的定义点，循环体内直接 `← file`；
- **想并发就在循环体（child）上标 `parallel`**；不标就是老老实实一个个来（也完全合法，慢但省并发额度）。

### 写法二：兄弟并发（几件独立的事同时干）

```markdown
2. [subtask] 采集各渠道数据              # 容器边界 = 收齐点
  + → social_data: yaml
  + → news_data: yaml
  2.1. [subtask parallel] 采集社交媒体    # 派出去
    + → social_data
    ...
  2.2. [subtask parallel] 采集新闻        # 和 2.1 同时在跑
    + → news_data
    ...
```

两个渠道互不依赖，各自标 `parallel`，父容器结束前全部收齐。可跑样例：`examples/syntax/sibling-parallel.md`。

## 第 3 步：知道边界在哪（免得写出非法 spec）

`parallel` 是一个**承诺**：这个活自包含、不跟兄弟共享写。引擎的 validate 会替你核（依赖分析）——违反直接报错，常见三条：

| 想写的       | 错法                   | 对法                                                  |
| --------- | -------------------- | --------------------------------------------------- |
| 循环并发      | 在**循环头**标 `parallel` | 标在循环体的 child 上（并发是活的性质，不是循环的形态）                     |
| 并行结果给下一步用 | 兄弟步骤直接 `←` 并行步骤的输出   | 并行步骤的输出只能经**容器边界**导出（容器头 `+ →` 或 collect 列表），容器外再消费 |

| 单个失败要重试   | 给 loop 加 `retry`     | loop 没有 retry——在循环体内套 `[subtask retry=N]`，失败单元是单次迭代 |

> **并行的活里有 confirm/ask 怎么办？** 不慌——那个活会就地暂停排队等你，**其余活照跑**；你逐个回答，答一个续跑一个（不会"一个要问人、整批卡死"）。开发者细节见 [[D5-错误与异常处理]] 的 HITL 队列一节。

另外两条实用语义：
- **并发路数不进 spec**——spec 只声明"可并行"，跑多宽（乃至要不要真并发）是运行环境的事（见上面的诚实注记）；
- **部分失败不炸整批**：某个 worker 失败，它的单项不进 collect 列表，其余照收（列表可能短于输入——下游步骤想核数量就 `check` 一下 `len`）。

## 第 4 步：看一个真实的

```bash
hopjit validate examples/fact-check-demo.md
```

读 `examples/fact-check-demo.md`（随 npm 包，`--demo` 装的 `/demo-fact-check` 就是它）的第 4 步：`[loop for-each point in confirmed_points, collect check_item into check_result]`，循环体是 `[subtask retry=3 parallel]`——逐条断言并行核查、每条最多重试 3 次、结果收成列表。**遍历不漏 + 单条可重试 + 整体并发**，三件事一行结构写清（[[07-升级你的自然语言skill]] 里翻译器的 focus① 标注指的就是这个结构）。
