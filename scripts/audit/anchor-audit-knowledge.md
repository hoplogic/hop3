# 锚点审计知识文档

本文档是 `examples/anchor-audit.md`（HopSpec 范本）的**外部知识家**——spec 通过 `[[anchor-audit-knowledge#章节]]` doc-ref 精确引用各章节，引擎运行期切片注入到对应步骤的 agent 上下文。

**为什么分离**：审计判据（锚点语法、12 项结构比对、S→D/D→C/C→T 语义判据、报告模板）是**大段描述性知识**，若内联进 spec 会淹没编排逻辑。按 doc-ref 原则——spec 留编排骨架，知识沉于此，引用精度即约束强度。

> **章节标题是 doc-ref 锚点，勿随意改名**：spec 的 `[[...#章节名]]` 按标题匹配（精确→归一化序号→子串），改标题会断引用。新增判据优先在既有章节内补，不轻易增删/重命名一级章节。

## 宪法级原则

**每一个锚点都必须以最严格的标准审计，不允许采样、跳过或降级。** 锚点追溯链是概念→设计→代码→测试的唯一可验证纽带。任何一个锚点的不对齐——无论看起来多小——都会以静默方式累积：概念层的一个语义偏差传播到设计层变成接口错误，再传播到代码层变成行为 bug，最终在执行时产生不可预测的灾难。这种累积效应不是线性的，而是指数级的——因为下游的每个决策都建立在上游的假设之上。

因此：
- **全量审计，不采样**：无论锚点数量多少，每一个都必须被检查
- **语义审计必须读源文件**：不能仅凭锚点 ID 和行号推断一致性，必须读取实际内容做判断
- **⚠️ 不是"可以接受"**：每一个 ⚠️ 都必须被记录、解释原因、明确是已知偏差还是待修复项
- **不允许"看起来差不多"**：设计写 error 代码用 warn、设计写 4 个字段代码只有 3 个——这些不是"差不多"，是不对齐

## 各层锚点语法

- **概念/设计 (Markdown)**：行尾 ` ^anc-{category}-{concept}`（Obsidian block reference）。锚点**必须**出现在行尾，前面有一个空格分隔符。独立行锚点不合规——锚点总是附加在内容文本之后。正则：` \^(anc-[a-z][a-z0-9-]*)$`
  - **围栏内锚点同样有效**：设计文档常在代码围栏（如 TS 接口示例）内逐行标注锚点，扫描必须覆盖围栏内外。行尾格式本身已极大降低假阳性——这不是主要风险，禁止以过滤假阳性为由跳过围栏
  - **规则/教学文档的示例禁用真实锚点 ID**：演示锚点语法时用模板占位形式 `^anc-{category}-{concept}`（含花括号，天然不匹配扫描正则），禁止用真实 ID——否则示例会被扫描为真锚点、与权威定义形成跨文件同 ID 冲突
- **代码 (TypeScript/Python)**：定义行行尾 `// @a: anc-{category}-{concept}` 或 `# @a: ...`（可逗号分隔多个）
- **测试 (TypeScript/Python)**：`it`/`describe` 上方 `// @v: anc-{category}-{concept}` 或 `# @v: ...`（可逗号分隔多个）

## 模块归属标注语法

`@module` 与 `@a:`/`@v:`（锚点级，纵向追溯）不同——它是**文件级横向标注**，把每个代码/测试文件绑定到其所属模块（见 [[工程实现链规范#^anc-meta-module-trace]]）。语法：

- **`// @module: <模块名> ^anc-struct-<锚点>`**：每个 `src/*.ts`、单测 `tests/*.test.ts` 文件头一行，声明归属模块 + 指向该模块的设计定位锚点（可以是 `^anc-struct-*` / `^anc-provider-*` / `^anc-obs-*` 等任一模块定位锚点）。
- **`// @module-deps: <模块a>, <模块b>, ...`**：集成测试（跨多模块，如 e2e）文件头，声明依赖的模块（替代 `@module`——集成测试不属单一模块）。

> **文件→模块反查表来自标注自身**：脚本先扫全部 `@module:` 建立 `file→module` 映射（不硬编码），再用它把集成测试 import 的 src 文件映射成模块集做 deps 一致性比对。映射权威 = 标注本身，自洽。

## 结构比对判据

由 `cross_compare.py` 完成集合运算（LLM 不做计数/集合差/字符串匹配），LLM 只解读结果、判定严重度、撰写报告。14 项比对：

0. **概念→设计**：概念锚点 ∖ 设计锚点 = 设计未覆盖概念（S→D 的结构侧；概念层为空则此项 skip，不报假阳性）。语义侧"设计是否忠实传达概念语义"由语义审计 S→D 维度判，此处只查结构覆盖。
1. **设计→代码**：非组标题设计锚点 ∖ 代码锚点 = 缺失（设计声明了但代码未实现）
2. **代码→测试**：代码锚点 ∖ 测试锚点 = 未覆盖（实现了但无测试锚点）
3. **测试→代码**：测试锚点 ∖ 代码锚点 = 悬空 `@v:`（测试引用了不存在的代码锚点）
4. **追溯完整性**：代码锚点 ∖ 追溯卡片 = 缺失卡片（TRACEABILITY.md 漏登记）
5. **状态正确性**：卡片标 ✅ 但链路断裂（无代码/测试/设计锚点）= "状态错误"；标 ⚠️ 但链路完整 = "可升级为 ✅"
6. **无效引用**：`invalid_refs` 列表（TRACEABILITY 卡片引用的文件不存在＝死引用，或该文件内无标注**该引用行归属锚点**的 `@a:`/`@v:`＝追溯断链）。两条判据要点：

6b. **反向核（2026-08-30,todo/0034 清账——原引用有效性只做"卡→文件"单向,代码 @a: 落点没入卡时机检恒绿,链账悄悄漏）**：`card_missing_code_refs` 列表——对每个代码锚点 (id, file)，全部卡片的 code_refs 里应存在至少一条 (owner=id, file=同文件) 的结构化行；缺席即报（该落点在卡上不可反查）。**豁免面：文件级覆盖即可**——同锚在同文件多个代码块落点，卡只需一行该文件引用，不逐块；同锚跨多文件则每文件都要有行。测试锚 @v: 同规则（`card_missing_test_refs`）。计数进 summary 与基线比对面（新守卫从当前差集作基线起步,增量不许变差）。
   - **不比对行号**——行号是必然随代码增删腐坏的快照，定位靠锚点 id grep
   - **按行归属、非按卡片**——每条 `invalid_refs` 带 `owner` 字段（该引用行 `— @a:`/`— @v:` 声明的锚点）。卡片是嵌套树，一张卡片下常列相关锚点的落点，拿卡片 id 去那些文件里找必然假报缺失（见 design/concept-anchor-rules.md `^anc-meta-card-ref-owner`）
7. **命名规范**：`naming_violations` 列表（不符 `anc-{category}-{concept}` 格式或类别非法）
8. **代码→设计**：代码锚点 ∖ 设计锚点 = 孤儿 `@a:`（代码标了但设计无对应 `^` 定义）
9. **设计→追溯**：非组标题设计锚点 ∖ 追溯卡片 = 设计无追溯
10. **模块归属完整性**：无 `@module:`/`@module-deps:` 的 src/test 文件 = 漏标（`module_anchors.yaml` 的 unassigned）
11. **模块锚点真实性**：`@module` 指向的定位锚点 ∖ 设计锚点 = 悬空（指向不存在的模块定位）
12. **集成依赖一致性**：集成测试 `@module-deps` 声明集 △ import 推导模块集 = 不一致（声明多/少/错）
13. **模块边界接口**（见下 [[anchor-audit-knowledge#模块边界接口校验]]）：跨模块 import 违反目标模块 ⑤ 对外接口清单 = 违规。两子项：① 深入非出口文件；② import 清单外符号。仅对已声明清单的模块生效（增量式）。
14. **出口注释完整性**（见下 [[anchor-audit-knowledge#出口注释完整性校验]]）：出口文件里的 `export` 符号紧邻上方无注释 = 违规（`export_missing_comment`）。仅对已声明 ⑤ 清单的模块生效（增量式）。

## 模块边界接口校验

**判据**：模块的对外接口 = 设计文档 `^anc-<module>-exports` 节里**封闭的接口清单**（公开符号表 + 出口文件集）。跨模块调用只能 import 清单内符号、且只能从出口文件 import。此表是"边界 = 模块可被外部调用的接口集合"的机器可判形式（区别于 `@module` 归属注记——后者只答"文件属谁"，不答"谁能调我的什么"）。

**两类违规**（`cross_compare.py` 第 13 项，读 `module_boundaries.yaml`）：
1. **深入非出口文件**（`non_exit_file`）：跨模块 import 的目标文件 stem ∉ 目标模块出口文件集 → 绕过模块出口、掏内部文件。
2. **import 表外符号**（`symbol_not_public`）：import 的目标是出口文件，但具名符号 ∉ 该模块公开清单 → 依赖了未申报为对外的内部符号。

**权威与增量**：清单以**设计 ⑤ 表为唯一权威**（设计权威、代码对齐）——代码 export 超出表=未申报泄漏，表列了代码没 export=悬空申报。**增量式**：只对已声明 ⑤ 清单的模块生效，未声明的模块跳过（模块可"一个一个"补声明，机检随之逐个生效）。

**豁免**：只检 `src/` 内跨模块 import；tests 白盒直 import 内部文件（子模块独立覆盖是既定策略）跳过；同模块内文件互 import 跳过。

**清单表格式**（设计文档 `^anc-<module>-exports` 节，一符号一行供机检解析）：

| 符号 | 种类 | 出口文件 | 用途（谁依赖） | 稳定性 |
|---|---|---|---|---|
| `Xxx` | 函数/类/类型 | `foo.ts` | 一句话 + 依赖方 | stable / provisional |

范本见 [[exec-engine#^anc-struct-exec-engine-exports]]（首个声明对外接口清单的模块）。

## 出口注释完整性校验

**判据**：模块出口文件（`^anc-<module>-exports` 节声明的出口文件集）里每一个 `export` 声明，紧邻上方**必须有注释**——出口是模块对外契约面，无注释的 export 让调用方（人与 Agent）读代码时无法就地理解职责、也无指针跳回设计权威。这是良好编码工程规范的最低要求，机器可判。

**检查对象**：出口文件中的顶层 `export`（`function` / `class` / `const` / `interface` / `type` / `enum`，含 `abstract`）。

**"紧邻上方有注释"规则**：export 行向上跳过空行后的第一非空行，若以 `//`、`/*`、`*`、或以 `*/` 结尾（块注释收尾）判为有注释。行尾 `// @a: anc-*` 追溯锚点**不单独算职责注释**（它是给追溯的，非给人读职责）——判据要求的是**说明性注释**，故 export 行自带的 `// @a:` 尾注不计入，必须另有上方说明行。

**违规**（`cross_compare.py` 第 14 项，读 `module_boundaries.yaml` 的 `export_comments`）：
- **`export_missing_comment`**：出口文件的 export 符号上方无说明注释。报 `{file, symbol, line}`。

**注释形式**（推荐 JSDoc，与既有 `// @a:` 锚点并存）：
- 说明性注释用 `/** 一句话职责 + 指回 design ^anc-* 锚点 */`（JSDoc，IDE hover 可见、tsdoc 工具可消费）或 `//` 行注释均可。
- 追溯锚点 `// @a: anc-*` 仍写在 export 行尾（两者分工：JSDoc 给人读职责，`@a:` 给机器追溯）。
- 纯类型 shape（如 `interface ToolResult`）的职责语义权威在设计 `^anc-*-exports` 清单及接口正文，JSDoc 一句话概括 + 指回锚点即可，不必在代码里复述全部字段。

**权威与增量**：**增量式**——只对已声明 ⑤ 清单的模块的出口文件生效，未声明的模块跳过。**豁免**：纯 re-export 转发行（`export { X } from './y.js'`，无新增声明）不计（转发无需重复注释，语义在源头）。

## 语义审计维度判据

验证代码是否忠实实现设计契约、测试是否充分覆盖代码行为。与结构审计是不同维度——结构审计回答"锚点存在吗"，语义审计回答"实现正确吗"。**全量审计**：所有代码锚点逐一审计，不采样、不跳过。

三个维度，每个判 ✅/⚠️/❌/skip：

1. **S→D（Source→Design）**：设计是否忠实传达权威源（概念层文档）语义
   - 权威源 = 概念层 Markdown（如 HopSpec V3核心规范、CyAnt概念模型）；如果项目无独立概念层则设计层自身即权威，该维度 skip
   - ✅ 完全一致 | ⚠️ 有意简化/细化（必须注明原因）| ❌ 语义偏离

2. **D→C（Design→Code）**：代码是否忠实实现设计契约
   - ✅ 完全一致 | ⚠️ 可接受偏差（必须注明原因和影响）| ❌ 语义不一致

3. **C→T（Code→Test）**：测试是否充分覆盖代码行为
   - ✅ 充分覆盖 | ⚠️ 部分覆盖（必须列出未覆盖的关键路径）| ❌ 覆盖不足

### 判断标准（严格执行）

- 设计写 error，代码用 warn = ❌（不是 ⚠️）
- 设计定义 4 个字段，代码只有 3 个 = ❌（不是"差不多"）
- 设计定义接口方法，代码多了/少了方法 = ❌
- 测试只覆盖 happy path，缺少错误路径和边界 = ⚠️（必须列出缺失项）
- 设计标注"v2+"的功能未实现 = skip（但必须注明）
- 权威源无法定位 = skip（S→D 维度）

### 设计节表达形态核查（D 层自身形态，随 D→C 一并判）

审计一个契约锚点时，除判"代码是否忠实"外，还判**设计节自身是否按模块规范三件套展开**（工程实现链-模块规范核心内容元素，与行为宪法"设计先行"的内容底线同一套要求）：

- **能力契约用 HopSpec 契约**（Spec without Steps：Goal/Inputs/Outputs/Constraints）——散文描述能力面 = ⚠️（标"形态:散文契约"）
- **类型约定用 HopType**（字段逐条列出每字段一句话；不直接堆 TS/Python 签名当设计）——新类型只出现在代码里、设计无 HopType 描述 = ⚠️
- **关键逻辑用 HopSop**（判定顺序、分支走向、多个使用点各在哪——读设计能预判代码怎么写）——多步行为只有散文叙述 = ⚠️

**豁免判据（不硬套）**：纯语义约定节（无新能力面、无新类型、无多步流程——如"XX 不落盘、恢复时重算"这类条款型契约）条款形态即合规，不要求三件套。判据：该节若翻译成代码只是几个 if/字段注释，就是条款；若对应一个可独立描述输入输出的行为单元，就必须有契约件。

实撞案例（2026-08-10）：exec-engine 的 call-auto-map/call-depth-check 两节、mcp-server 的 run-restore 节初版均为散文/内嵌列表，作者点名核查后补齐三件——散文契约让"读设计预判代码"失效，audit 时也难逐要素对照。

### ⚠️ 判定必须附带

- 偏差的具体内容（什么不一样）
- 是否为已知/有意简化
- 不修复的风险

## 按模块分批协议

语义审计**按模块聚合分批**，不是机械按 N 个锚点切——同一模块的锚点共享设计上下文（同一设计章节、同一接口契约），一并审计才能判"模块内实现是否自洽"。分批规则：

1. 读 `module_anchors.yaml` 的 `file_modules`（文件→模块）与 `module_scale`（每模块规模），读 `code_anchors.yaml`（全部代码锚点 + 文件位置）。
2. 用"文件→模块"反查表把每个代码锚点归到其模块（按锚点所在文件的 `@module` 归属）。
3. **一模块一批**；超大模块（超 100 锚点）由 make_batches.py 按 50 锚点一段拆为多段（段名 `{module}__partN`），但**不跨模块混批**。
4. 每批头部带上该模块的规模（`code_lines / test_cases / design_chars / src_files / test_files`）——审计员据此预估工作量、判断"测试案例数 vs 代码行数"是否失衡（如 1950 行代码仅 178 测试案例 → C→T 维度重点查覆盖缺口）。
5. 断点续传：检查已存在的 `batch_*_results.yaml`，跳过已完成批次。
6. 模块过滤（按模块跑）：`modules` 输入非空时只保留列出模块的批——名字须与 `module_anchors.yaml` 模块名精确匹配，命不中任何锚点的名字**报错**（防拼错静默空跑）；产物 scope 字段如实记范围，按模块跑的产物**不能充当发版闸凭证**（闸要求 scope=full）。

## 单批语义审计执行协议

每批 = 一个模块（或大模块的一个子区），批头带模块规模。对批内的每个锚点（含文件位置）：

1. 读取设计文件（给定行号 ±15 行，不够则扩大范围直到理解完整语义）
2. 读取代码文件（给定行号 ±15 行，同上）
3. 如有测试文件，读取（给定行号 ±15 行，同上）
4. 按 [[anchor-audit-knowledge#语义审计维度判据]] 判定 S→D / D→C / C→T
5. 结合模块规模做整体判断：测试案例数显著低于代码规模 → C→T 维度重点列覆盖缺口；设计字数远小于代码行数 → D→C 维度查"代码是否引入了设计未提的行为"

结果写入 `{project_root}/.anchor-audit/batch_{module}_results.yaml`（按模块名标识，非位置序号——resume 跳过已完成模块时序号会错位），格式（批头记模块与规模，便于汇总按模块归并）：

```yaml
module: exec-engine
scale: { code_lines: 1950, test_cases: 178, design_chars: 5417 }
results:
  - anchor_id: anc-xxx
    s2d: { verdict: "✅", note: "具体说明" }
    d2c: { verdict: "⚠️", note: "具体说明" }
    c2t: { verdict: "❌", note: "具体说明" }
```

**note 值必须带双引号**（2026-09-01 实撞立规——flow 形态 `{...}` 里裸值含 `[`、`,`、`:` 任何一个都会炸 YAML 语法：某批 note 裸写 `engine.test.ts [on fail] 组 8 例…` 整文件解析失败。样例里的双引号是语法必需件不是修饰——照抄时引号必须保留；note 内容本身含双引号时改用块风格：
```yaml
    c2t:
      verdict: "⚠️"
      note: |
        多行或含特殊符号的说明写这里,块内零转义
```

**note 产出控量（2026-08-11 作者定"一次产出的内容必须控制量"——超时的直接根源是单步超大输出）**：✅ 的 note 一短句封顶（如"设计条款X逐项对齐"，禁复述条款内容/代码片段）；skip 的 note 只写跳过原因归类词；⚠️/❌ 的 note 才展开（偏差是什么、在哪个文件哪行、为何判此级——这是人工修复要用的，值得占输出）。判定深度不因 note 短而打折——控的是写出来的量，不是读和判的量。

**断点保护**：每批结果独立写盘。一批完成立即落 `batch_{module}_results.yaml`——即使后续批次失败，已写盘批次不丢，重跑（resume）时按模块名跳过已存在批次。

**大批分段落盘（不要一口吃个胖子——超过 ~30 锚点的批必须分段）**：单批锚点多时，一口气攒全量结果 yaml 意味着单次超大输出——实撞（2026-08-10）：97 锚点批两次死在产出阶段（一次 402 一次超时），已判定内容全部丢失。分段协议：

1. 把批内锚点按清单顺序切段（每段 ~25 个）；
2. **逐段判定、每段判完立即落盘**到子实例 work_zone 的 `segments.yaml`（首段创建，后续段读回追加），段落盘后才开始下一段——段间不在上下文里攒结果；
3. 全部段落盘后，从盘上读回组装完整批结果写入批结果文件（batch_{module}_results.yaml）——**提交引擎的是摘要行**（模块名+盘上路径+计数，见 spec 5.2.1 batch_digest），不是全文：全文过变量通道会在下游汇总步再次形成超大输出，2026-08-11 实撞（119k 输出 token 顶超时）；
4. 中断恢复：`segments.yaml` 已存在时读回沿用已判定锚点，从缺口继续——**不重做**；
5. 宪法级原则不因分段打折：分段只是输出节奏，不是范围裁剪——每个锚点仍实读源判定。

## 自动修复安全流程

用户选择自动修复后，按以下安全流程（任一步出错即停，绝不静默继续）：

1. **修复前快照**：在 git 仓库中执行 `git add -A && git commit -m "pre-anchor-audit snapshot"`，建立可回滚锚点
2. **修复顺序**：从文件末尾向前逐项修复，避免前序插入行导致后续目标位置偏移
3. **逐项执行**：用 Edit 工具逐项修复（加缺失 `@a:`/`@v:` 锚点、修正死引用的文件名），每项修复后标记完成
4. **修复后复核**：执行 `git diff` 并向用户展示变更摘要，等待用户确认
5. **回滚能力**：如用户不满意，提示可用 `git checkout -- .` 回滚全部修改

**可修复 vs 需人工**：结构缺失（加 `@a:`/`@v:` 锚点、修正死引用文件名）可自动修复；语义 ❌ 项需人工修复（涉及代码逻辑），⚠️ 项逐一与用户确认。
