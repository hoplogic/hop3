# model-gearbox — 模型变速箱

HopSpec 有两个核心作用：**控制器**（spec 声明流程与把关，引擎强制执行）与**变速箱**（同一套控制逻辑，适配不同能力的基座模型与不同的执行载体）。变速有两根轴：

- **模型轴**（本目录）：不同能力档位的基座模型——强模型吃得下满配工具面与重供给步骤，弱模型需要收窄的供给，步骤也要切小——度量会测出它一次调用能可靠处理几个要点，每步的任务量不超过这个数；
- **载体轴**（`driver/`）：不同的宿主 agent（Claude Code / Codex / 将来的 opencode 等）——通道与技能形态各异，流程语义同一。

本目录装模型轴的全套：**档案柜（profiles/）+ 度量仪器（probes/）**。数据流单向：

```
probes/ 跑探针产数据 → profiles/ 存档案 → 引擎与 hopbuild2 消费档案换挡
```

## 与配置三层的分工

| 层 | 位置 | 回答什么 | 性质 |
|---|---|---|---|
| providers | `~/.hopjit/config.yaml` | 怎么连（端点/凭证） | 用户私有，不入库 |
| **profiles** | 本目录 `profiles/*.yaml` | **这个 model service 是什么**（模型×服务端点组合的实测能力+适配开关——度量对象是 model service 不是 model:同名模型经不同端点能力可判若两物,每份档案绑定实测端点,换端点=换被测对象全维重测） | 公共资产零凭证——同一个 model service 对所有用户是同一份档案 |
| routing | 项目 `hopjit.yaml` | 这个项目哪步用谁 | 项目决策 |

## profiles/ 档案契约

每模型一份 yaml，三段结构：

- **`dims:`**——能力面粗档（D12 层三通识组 G1-G6：G1 推理复杂度〔正确性与稳定性是同一复杂度轴的两种坍塌形态,记坍塌点〕/G2 任务复杂度〔一次做正确的能力,记首轮通过率坍塌点,hopbuild2 按此切每步任务尺寸——数值曲线在 `extract_scaling:` 段〕/G3 分解与规划〔subtask free 到步展开的直接消费维度〕/G4 工具使用〔本质=inline 工具使用 loop,与 P2 同一循环的正用/抗噪两半边〕/G5 结构化交付/G6 代码生成〔键名 `code_generation`,按语言分档记——现有 Python 与 SQL 两档（`{python: X, sql: Y}`）:各三档复杂度的一次写对率与自愈后通过率,仪器=probes/code-generation/;HopSpec 写作归 hopbuild2 构建卷〕；指令遵从=层二冒烟项不占 dims 位;旧第七维反馈修正已收窄为实践维度 P3 修订落实），值域 `strong | mid | weak | unproven`。人读与路由参考。另有阶梯型维度**不用四档值域、按坍塌点记档**：`check_judge`（D12 实践维度 P1 核验能力，值域 `open-ok | checklist-only | closed-questions-only | unusable`——把关步能以什么形态路由给它：开放式核验/按清单核验/单点核验(微判定展开)/禁路由。三档阶梯每升一档多扛一种协调负担〔建框架跨轮一致→多题自洽→仅原子判断〕，坍塌点在协调负担不在判断本身——"仅单点核验可用"是完全可工作的形态不是残废档；与推理正确性两维分开测不许互推）；
- **`act_free:`**——act free 步工具面稳定性**数值曲线**（不是定性枚举）：`reliability_curve` 按 {供给长度 × 工具数 × 任务是否真需要工具} 网格记完成率，`rating` 从曲线机械读出。`subtask_free:` 独立记档（规划自由与执行自由是两种能力，不合并）；
- **`adapt:`**——引擎与构建器直接消费的适配开关：`max_inline_tools`（dispatcher 下发上限）/ `thinking`（档位建议）/ `build_target_profile`（hopbuild2 给该模型出产物时的缺省档）。

**三条档案纪律**：

1. **档案是测出来的，不是拍出来的，且测的是 model service**——每份档案带 `measured:` 日期与实测端点（provider_ref/endpoint_note），数据来源恒是 probes/ 探针实测；模型身份恒取响应体 `model` 字段，禁 LLM 自报；同名模型换端点不得沿用档案数据（判据方法论=D12 层三原则一）；
2. **实测与推断严格分标**——没测过的格标 `untested`/`unproven`（可附倾向注记），不许写成定论。零失败只在做功量对齐时才是能力证据（做功差数倍标 unproven 不标 strong）；
3. **每格样本量 n≥6**——单批 n=3 实测过批间反转（Qwen 2 工具档首批 2/3 偏、复测批 0/3），不足 n 的格不定档。

## probes/ 度量仪器契约

探针族对应 D12 四层测试的机械化（族数随维度仪器化递增,权威=probes/README 族表,下表列早期四族示意）：

| 族 | 层级 | 形态 | 测什么 |
|---|---|---|---|
| `protocol/` | 层一 | curl 脚本（零引擎） | 端点真路径/鉴权头/thinking 双档块分离/tool_use 标准形态/截断 stop_reason 如实报 |
| `smoke/` | 层二 | 最小 spec（真引擎） | provider 配置→请求装配→响应解析→产出收割全链 |
| `act-free-stability/` | 层三核心 | 格点任务 spec（真引擎） | act free 稳定性阶梯：{供给 短~1K/中~4K/长~8K} × {工具 0/1/3/5/10} × {真需要工具/不需要}，每格判完成率+工具轮效率+失败形态 |
| `capability/` | 层三 | 混合 | 通识组 G1-G5 定性探针（schema 阶梯/分解与规划/thinking 双档裁量对比…） |

跑批入口 `run-probes.mjs`（待实装，挂 todo/0095 批）：`--model <service/model> [--probe <族>]` → 汇总出可直接贴进 profiles/ 档案的曲线 yaml。

## 消费面（接线挂 todo/0095 批，本目录先立户口）

- dispatcher：按 `adapt.max_inline_tools` 收窄工具下发（与 reason 步按声明下发取交集——声明制管"步骤要什么"，档案管"模型受得了什么"）；
- hopbuild2：`build_target_profile` 作构建目标档缺省；
- 人：写 routing 时对着 `dims` 选步骤类型。

## 适配变体的命名约定（甲案，2026-09-18 作者拍）

母本 spec 按目标模型降档生成的变体，**与母本同目录平级平铺，文件名=母本名加模型段**：

```
<spec 目录>/
├── spec.md                    # 母本——业务语义的单一权威
├── spec.qwen3.8-27b.md        # 变体——按模型命名（模型段与 profiles/ 档案文件名同一套）
└── spec.ling-3.0-flash.md
```

- **按模型命名，不按档位命名**——档位是档案的投影会漂移（两个模型今天同档明天分家），模型名才是稳定户口；
- **不建 variants/ 子目录**——平铺零嵌套，`ls` 即母本-变体全景，母本删除时变体孤儿一眼可见；
- **变体恒生成、不手编**——文件头须标注源母本、生成时间与目标 profile；母本改动后变体必须重新生成（手编分叉=语义漂移之源）；
- **落盘是可选的**——变体的消费时点在运行期选文件，降档若足够快可现场生成不落库；本约定只管"谁要落盘就按这个名落"。

**母本修复与模型变体的分界判据（2026-09-18 作者抓"变体命名被吞了"后补立——约定首版只定了命名没定分界，改动归属靠执行者心证即失职）**：判一个 spec 改动落母本还是落变体，问一个问题——**"这个改动对所有模型都正确且必要吗？"** 是=母本修复（直接改母本，如：给实际吃大文件的步骤补 `- 工具: read` 声明——强弱模型都需要，缺声明是母本缺陷）；只对某档模型必要、对强模型是无谓降级=变体（按模型名落盘，如：把一个判官步拆成三个小步——强模型一步能干，拆开对它是浪费）。拿不准的按变体走（母本是单一权威，污染母本的代价大于多一份变体）。**归属判断必须记录**：改母本的在 commit message 写明"为什么这是母本修复不是变体"，出变体的在变体文件头写明目标 profile 与降档动作。

## 界外（有意不做的）

- **spec 降档编译器**（按档案把母本 spec 自动拆步/平坦化/消 free 档）——第四层杠杆，等执行层（0095）跑出"哪些 spec 光靠收窄供给救不回"的真机账再立项，不预建；上方命名约定先行，编译器落地时直接遵约定；
- 载体轴的一切归 `driver/`，本目录不涉。
